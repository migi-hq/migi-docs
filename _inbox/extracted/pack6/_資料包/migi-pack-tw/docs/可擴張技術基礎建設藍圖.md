# MIGI 麻將連鎖 — 可擴張技術基礎建設藍圖 v1.0

> 核心心法:**設定先行,功能後上。** 重工的痛苦 99% 來自「資料結構沒留好」,不是「功能沒做完」。
> 從第一行程式碼就為「日後變成連鎖加盟平台」鋪路,而不是只做一家店。
> 上位依據:《戰略備忘》——平台化(B2B 授權 + 加盟)是第四道護城河,速度決定一切。

---

## 0. 一句話架構

```
程式碼 → GitHub (private repo)
              ↓ 自動部署
前端 LIFF → Cloudflare Pages (靜態 SPA · Vite+React)
              ↓ API
後端/資料 → Supabase (Postgres + Edge Functions + RLS)
DNS/網域/CDN → Cloudflare (migi.com.tw)
企業信箱 → Google Workspace
入口 → LINE 官方帳號(一個品牌帳號,LIFF 切換店鋪)
```

## 1. 最容易重工的地雷:多租戶資料架構(Day 1 必做對)

**問題**:若第一家店的資料庫設計成「就是這家店」,開第二家或加盟主加入時,所有資料表都要打掉重來。

**鐵則:每一張資料表都帶兩個欄位**
- `tenant_id` — 誰擁有(直營全是你 / 加盟主 A / 加盟主 B)
- `store_id` — 哪家分店(同一個 tenant 可開多家)

| 概念 | 意義 | 範例 |
|---|---|---|
| tenant_id | 經營主體 | 你(直營)、加盟主 A、加盟主 B |
| store_id | 實體分店 | 高雄旗艦店、台中店、加盟主 A 的台南店 |

會員、牌局、交易、員工、庫存、菜單——**全部都要能回答「這是哪家店、哪個租戶的」**。
一開始多花兩天設計,省下日後三個月打掉重練。

---

## 2. 會員跨店策略(現在就要決定,影響資料怎麼存)

**決策:會員屬於「品牌」,跨店通用(非單店獨立)。**

- 一個會員在高雄總店打牌、去台中分店也能用同一個 App、同樣段位、同樣牌咖網絡。
- **跨店通用的會員網絡 = 加盟主想加入的理由**(一開店就接上全台會員池)。
- 這是 MIGI 的護城河:競品抄一家店容易,抄不走跨店的會員關係網。

→ 技術上:`members` 表掛 `tenant_id`(品牌層),不綁單一 `store_id`;消費/牌局記錄才掛 store_id。

---

## 3. 加盟金流拆帳(日後最痛的重工,現在預留欄位)

**問題**:會員在加盟店 A 儲值 5000 點,跑去加盟店 B 消費。錢 A 收、服務 B 提供 → 這筆帳怎麼拆?

**現在要預留(不必做完整系統,但結構要留好)**:
- 每筆交易記錄「**收款店 collected_store_id**」和「**服務店 served_store_id**」(可能不同)
- 點數系統能跨店流通 + 後台能算店跟店之間的應收應付
- 加盟權利金、抽成計算欄位先留著(就算現在不收)

→ 否則日後補欄位 = 改全部歷史資料。

## 4. 系統模組 roadmap(大型連鎖標準架構,先留位置)

| 模組 | 擴張為何需要 | 現在做到哪 |
|---|---|---|
| 總部後台 HQ Dashboard | 看全店數據、跨店比較、總營收 | 資料結構支援聚合查詢即可 |
| 權限分級 RBAC | 店員/店長/加盟主/總部看到的不同 | **Day 1 就要有角色欄位** |
| 中央菜單/價格管理 | 總部改價全店同步 or 加盟可自訂 | 菜單表帶 store_id +「是否繼承總部」 |
| 集中採購/庫存 | 連鎖進貨成本優勢 | 先留庫存表結構 |
| 加盟主後台 | 加盟主只能看自己的店 | 接 tenant_id 權限即可 |
| 品牌素材庫 DAM | 加盟店用統一 CIS/行銷物 | 開店後再做 |

## 5. 技術選型的擴張注意事項

### ① Supabase RLS(Row Level Security)= 多租戶安全核心
多租戶最怕「加盟主 A 看到加盟主 B 的資料」。
RLS 在資料庫層級設定「每個人只能看到自己 tenant_id 的資料」。
→ **Day 1 就要把 RLS 開好**,不是日後補。

### ② LINE:一個品牌官方帳號(非每店一個)
會員跟著品牌走,用 Rich Menu / LIFF 切換店鋪。
每店一個 LINE 帳號會把會員打散,違反「跨店通用」策略。

### ③ 環境分離:正式 / 測試 兩套(至少)
大型團隊一定有開發/測試/正式三套。
你至少要有「正式」+「測試」兩套 Supabase,改東西先在測試試,**不要直接動正式資料庫**(尤其碰錢的部分)。

## 6. 前端部署決策:GitHub vs Cloudflare Pages vs Vercel

**先澄清:GitHub 是必選(放程式碼),另外兩個才二選一(部署)。**

| 平台 | 角色 | 決定 |
|---|---|---|
| **GitHub** | 程式碼倉庫(版本控管) | ✅ 必用 |
| GitHub Pages | GitHub 附帶的簡單靜態託管 | ❌ 不用 |
| **Cloudflare Pages** | 專業前端部署平台 | ✅ 用這個 |
| Vercel | 專業部署(SSR 強) | 備案,用不到 SSR |

**為何不用 GitHub Pages**:不支援環境變數(連 Supabase 的 key 只能寫死在程式碼)、難做多環境、無 CI/CD、商業條款偏個人/開源 → 撐不起要連資料庫、要分環境的商業 App。

**為何選 Cloudflare Pages(扣著「擴張+不重工」)**:
1. MIGI 前端是純靜態 SPA(不需 SSR),Vercel 的 SSR 優勢用不到。
2. 網域 DNS、CDN、(信箱轉寄)都在 Cloudflare → 整個基礎建設同一後台管理。
3. 免費額度頻寬無上限 → 擴張成本可預測(Vercel 流量大費用會跳)。
4. Cloudflare 生態(Workers 邊緣運算、R2 存牌譜影像、WAF 防火牆)未來都接得上,不用換平台。

**唯一例外**:日後要做有 SEO 的對外官網(需 SSR/Next.js),那部分可另用 Vercel,與 LIFF App 部署分開,不衝突。

---

## 7. 渲染方式:純靜態 SPA(已確認不需 SSR)

理由:① LIFF 不需 SEO(在 LINE 內開,Google 爬不到)② 所有頁面都需登入(無法預渲染)③ 動態責任在 Supabase(client 呼叫 API + Realtime WebSocket)。
→ 用 **Vite + React** 打包成靜態檔案,丟 Cloudflare Pages。
唯一例外:分享牌局的 OG 預覽圖,用獨立 Edge Function 處理,不必整站 SSR。

---

## 8. 核心心法(總結)

**設定先行,功能後上** — 與留存系統「資料表 Day 1 全建、功能分波上線」同一道理:

- **資料結構**(tenant_id / store_id / 角色 / 跨店金流欄位 / RLS)= **Day 1 全做對**,改它要動全部資料。
- **功能**(總部後台、拆帳、加盟主介面)= **之後分波做**,加功能不傷舊資料。

重工來自結構沒留好,不是功能沒做完。功能慢慢加不痛,結構打掉重練才痛。
