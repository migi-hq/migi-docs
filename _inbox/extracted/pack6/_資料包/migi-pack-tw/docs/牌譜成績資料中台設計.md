# MIGI 麻將連鎖 — 牌譜 / 成績資料中台技術設計 v0.2

> 範圍:逐筆牌譜事件庫、成績聚合、排名、回放與分層儲存。
> 技術棧:PostgreSQL / Supabase。
> 與《配桌引擎技術設計》的接縫:本文的聚合結果回寫 `member_rating`(配桌即時讀取的實力快照)。

---

## 1. 設計概念

- **事件溯源(Event Sourcing):** 每個動作 = 一筆**不可變、只追加**的事件。事件庫是唯一真相來源;任何指標都能從事件重算。
- **來源 + 信心分層:** 每筆事件標 `source`(桌台/AI/記錄員)與 `confidence`(0~1)。官方成績只採信高信心;低信心 CV 資料存而不污染。
- **衍生聚合:** 不每次掃原始事件;維護增量更新的聚合表,供秒開儀表板與配桌讀取。
- **一份事件流、兩種用途:** 同一份 `paipu_events` 同時餵「成績統計」與「逐巡回放」。

層次:`對局(games) → 局(hands) → 逐筆事件(paipu_events)`。

## 2. 資料表(Postgres DDL)

```sql
-- 一場對局(= 一桌一個 session,通常一將/一場)
create type game_status as enum ('live','finished','void');

create table games (
  id          bigint generated always as identity primary key,
  store_id    bigint not null,
  table_id    bigint not null,
  game_type   text   not null,                 -- 4P_16 / 4P_13 / 3P_16 ...
  ruleset     text   not null default 'tw16',  -- tw16(台灣16張,現行) / jp13(保留未來擴充,暫不使用)
  is_official boolean not null default false,   -- 賽事級(高精度、可公開)
  is_ranked   boolean not null default true,    -- 是否計入評等
  status      game_status not null default 'live',
  started_at  timestamptz not null default now(),
  ended_at    timestamptz
);

-- 對局四座位是誰、最終結果
create table game_players (
  game_id     bigint   not null references games(id) on delete cascade,
  seat        smallint not null,                -- 1..4
  member_id   bigint   references members(id),
  final_rank  smallint,                         -- 1..4 名次
  final_score integer,                          -- 點數/台數結算
  primary key (game_id, seat)
);

-- 局(東1局、南2局...)
create type hand_result as enum ('tsumo','ron','draw','abort'); -- 自摸/胡牌(放槍)/流局(臭莊)/中止

create table hands (
  id           bigint generated always as identity primary key,
  game_id      bigint   not null references games(id) on delete cascade,
  round_wind   text     not null,               -- E/S/W/N(東南西北場)
  hand_no      smallint not null,               -- 第幾局
  honba        smallint not null default 0,     -- 本場/連莊
  dealer_seat  smallint not null,               -- 莊家座位
  result       hand_result,
  winner_seat  smallint,                         -- 胡牌者(流局 null)
  deal_in_seat smallint,                         -- 放槍者(自摸/流局 null)
  score_delta  jsonb,                            -- {"1":48,"2":-16,...} 各座位增減
  started_at   timestamptz not null default now(),
  ended_at     timestamptz,
  unique (game_id, round_wind, hand_no, honba)
);

-- 逐筆牌譜事件(核心,append-only,按月分區)
create type event_source as enum ('table_feed','cv','operator','online');
create type event_action as enum (
  'deal','draw','discard','chi','pon','kan_open','kan_closed','kan_added',
  'riichi','flower','replace_flower','tsumo','ron','ryuukyoku','dora_reveal'
);

create table paipu_events (
  id           bigint generated always as identity,
  game_id      bigint   not null references games(id),
  hand_id      bigint   not null references hands(id),
  seat         smallint not null,
  turn_no      smallint,                         -- 第幾巡
  action       event_action not null,
  tile         text,                             -- 牌面編碼,見 §3
  meta         jsonb,                            -- 吃碰槓對象、所用牌組等
  event_ts     timestamptz not null,
  source       event_source not null,
  confidence   numeric  not null default 1.0,    -- 0~1;AI 辨識帶信心
  is_corrected boolean  not null default false,  -- 經人工校正覆寫
  primary key (id, event_ts)
) partition by range (event_ts);

-- 月分區範例(每月建一張)
create table paipu_events_2026_06 partition of paipu_events
  for values from ('2026-06-01') to ('2026-07-01');

create index on paipu_events (game_id, hand_id, seat, turn_no);
create index on paipu_events (game_id, action);

-- 成績聚合(增量更新;member_rating 的上游)
create table member_stats_agg (
  member_id      bigint not null references members(id) on delete cascade,
  game_type      text   not null,
  period         text   not null,               -- 'lifetime' / '2026-06' ...
  games          int    not null default 0,
  hands          int    not null default 0,
  win_count      int    not null default 0,     -- 胡牌數
  deal_in_count  int    not null default 0,     -- 放槍數
  riichi_count   int    not null default 0,     -- 保留欄位:現行台麻不適用
  call_count     int    not null default 0,     -- 吃碰槓數
  rank_sum       int    not null default 0,     -- 名次總和 → 平均順位
  win_points_sum bigint not null default 0,
  updated_at     timestamptz not null default now(),
  primary key (member_id, game_type, period)
);
-- 衍生指標(查詢時計算或物化):
--   胡牌率   = win_count / nullif(hands,0)
--   放槍率   = deal_in_count / nullif(hands,0)
--   平均順位 = rank_sum / nullif(games,0)
--   吃碰槓率   = call_count / nullif(hands,0)
```

## 3. 牌 / 動作編碼

**牌面(`tile`,文字碼):**

- 數牌:`1m`–`9m`(萬)、`1p`–`9p`(筒)、`1s`–`9s`(索);紅五:`0m` `0p` `0s`
- 風牌:`E` 東、`S` 南、`W` 西、`N` 北
- 三元牌:`B` 白、`F` 發、`C` 中
- 花牌(台16):`fl1`–`fl8`(春夏秋冬 + 梅蘭竹菊)

**動作(`action`):** 以台16為現行規則:`flower`/`replace_flower`(補花)為台麻動作;`riichi`、`dora_reveal` 等動作值僅保留供未來擴充,現行不使用。「聽牌」可由事件序列推導,不必另存。

`meta` 範例(吃):`{"called_from":2,"meld":["3m","4m","5m"]}`

## 4. 來源與信心:資料品質與調和

| 層級 | 來源 | 信心 | 用途 |
|---|---|---|---|
| 局結果(誰胡/放槍/名次/點數) | `table_feed` 全自動桌數位資料、`operator` 記錄員 | 高 | **核心成績**:胡牌率、放槍率、平均順位 |
| 逐張細節(打哪張/吃碰槓/巡目) | `cv` 俯視鏡頭 AI | 中(帶 confidence) | **進階分析 + 回放**:台數效率、聽牌判斷、牌效 |

**調和規則:** 同一事件有多來源時,可信度 `operator > table_feed > cv > online`;保留全部,以最高可信來源為準(`is_corrected` 標記人工覆寫)。

**聚合門檻:** 核心成績只採計「局結果」可靠的局;CV-only 的進階指標需 `confidence >= 門檻`(例如 0.9)才計入官方數字,否則僅作參考或標「推測」。

## 5. 聚合邏輯(虛擬碼)

```text
function onGameFinalized(game):       # game.status -> 'finished' 且通過驗證
  if not game.is_ranked: return
  for p in game_players(game):
    for period in ['lifetime', monthOf(game.ended_at)]:
      upsert member_stats_agg (p.member_id, game.game_type, period):
        games          += 1
        hands          += handsCountIn(game)
        rank_sum       += p.final_rank
        win_count      += handsWonBy(p.seat, game)            # 來自 hands(可靠)
        deal_in_count  += handsDealtInBy(p.seat, game)        # 來自 hands(可靠)
        win_points_sum += pointsWonBy(p.seat, game)
        # 進階(需信心門檻):
        # riichi_count:保留欄位,現行台麻不適用
        call_count     += confidentEvents(game, p.seat, in ['chi','pon','kan_*'])
  recomputeRating(game)               # 見下

function recomputeRating(game):       # 以名次調整評等(類雀魂/天鳳)
  for p in game_players(game):

```

## 7. 賽事回放

回放不需另存資料:取某 `game_id` 的 `paipu_events`,`order by hand_id, turn_no, event_ts`,即可逐巡重播。賽事級(`is_official=true`)因經記錄員校正,回放最完整;一般場以 CV 資料回放,缺漏處以信心值標示。

---

## 8. 分層儲存與效能

- **熱層:** 近 N 個月的 `paipu_events` 月分區留在 Postgres。
- **冷層 / 資料湖:** 舊分區匯出為 Parquet 進物件儲存,接 ClickHouse / BigQuery 跑跨店分析與 AI 訓練。
- **讀取原則:** 會員儀表板、配桌一律讀 `member_stats_agg` / `member_rating`,**不掃原始事件**。
- 量未起來前(單店),只用 Postgres 分區 + 聚合表即可,先別上資料湖。Schema 先設到位,DB 之後再分層。

---

## 9. 隱私與權限

- 牌譜與成績綁定身分屬個人資料。**分析資料湖一律以假名 `member_key` 取代真實身分**,身分對照表獨立存放、嚴格權限。
- Supabase RLS:會員僅能讀自己的 `member_stats_agg` / `member_rating` / 個人牌譜;聚合運算以 service role 後端執行。
- 會員條款須載明蒐集範圍、用途、保存期限與刪除權。

## 10. 與配桌引擎的接縫

```text

## 10. 牌譜完整度分級(v0.2 新增:目標 = 圍棋棋譜等級,每一手皆記錄)

> `paipu_events` 的 schema 本就支援逐手記錄;本節定義「資料怎麼來」的三個等級。
> 人工無法記錄每一手(四家輪轉、秒級牌速),L1 以上一律設備驅動。

| 級 | 內容 | 來源 | 部署 |
|---|---|---|---|
| **L0** | 局結果(誰胡/放槍/台數)+ 將結算 | 店員快速輸入 | 第一階段全桌 |
| **L1** | 牌河逐打 + 吃碰槓 + 攤牌手牌(= 棋譜主譜) | 俯視鏡頭 CV | 第二階段一般營業桌 |
| **L2** | **完整每一手**(含每家摸進的暗牌) | 三選一:智慧牌山 / RFID 牌 / 攤牌反推 | 旗艦店、賽事桌 |

### L2 三條技術路線
1. **牌山序(首選)**:全自動桌砌牌時辨識並記錄整座牌山順序 → 配合起莊與摸牌規則,**每家摸進牌可數學推導**,不需「看」暗牌。牌山序 + L1 牌河 + 攤牌 = 完整閉環。**選桌關鍵規格:洗牌機構是否具牌張辨識、可否輸出牌山資料/API。**
2. **RFID 牌 + 感應桌面**:逐張即時識別,最精確、成本最高;賽事/直播桌適用。
3. **攤牌反推(零硬體)**:L1 牌河 + 攤牌手牌反推各家摸進序列;多數可唯一確定,推不出者標低 confidence。

### Schema 補充
```sql
-- 牌山序(每局一筆;來源:智慧桌輸出或 RFID)
create table wall_orders (
  hand_id    bigint primary key references hands(id) on delete cascade,
  tiles      jsonb  not null,        -- 144 張依砌牌順序之牌面陣列
  source     event_source not null,  -- table_feed / operator
  confidence numeric not null default 1.0
);
-- 推導出的摸牌事件寫入 paipu_events(action='draw'),
-- source 標 'table_feed'(牌山推導)或 'cv'(攤牌反推),confidence 隨之。
```

### 與分析/IP 的關係
- L1 已可支撐:逐巡回放、台數效率、吃碰槓傾向、AI 教練初版。
- L2 才能支撐:完整「上帝視角」回放(同圍棋復盤)、進攻/防守期望值分析、職業賽事轉播疊圖、頂級 AI 訓練資料 —— 此即旗艦店電視牆與牌譜資產的最終形態。

### 10.1 起手牌記錄(v0.2.1 補充)

- 起手牌事件已在 schema(`paipu_events.action='deal'`,每家一筆、tiles 於 meta);本節補「資料怎麼來」。
- **推導鏈:牌山序 + 開門位置(骰子點數)+ 固定發牌程序 → 每家起手牌 100% 可推算。**
- 缺口補上:`hands` 需記錄骰子/開門點——

```sql
alter table hands add column dice_roll smallint;   -- 骰子點數(決定開門位置)
-- 來源:智慧桌感應 / 俯視 CV 辨識桌面骰子(高可辨)/ 店員或平板點選(降級)
```

- L1-only 環境的降級:攤牌手牌 + 打出的牌 + 吃碰槓可反推起手牌(部分情況有歧義,標低 confidence)。

**解鎖的分析能力:**
1. **運氣/實力分離**:起手牌即算先天牌力(距聽牌張數、潛力值),評等改為「相對於起手牌的表現」——起手牌差守住名次加更多分;運氣評等化的解藥,段位公信力大幅提升。
2. **AI 教練質變**:可給出「起手牌不利但選擇正確」等真回饋。
3. **公正性稽核**:長期起手牌分布統計 → 驗證洗牌隨機性、偵測做牌;公正場認證的數據基礎。

### 10.2 範圍決策(v0.2.2)
- **現階段鎖定 L0 → L1**:店員局結果輸入 + 俯視鏡頭 CV(逐打牌序、吃碰槓、攤牌)。
- 骰子感應、RFID、牌山序等 L2 硬體**暫不考慮**;相關 schema(deal 事件、wall_orders、dice_roll)保留,屬「掛起」非「刪除」,未來旗艦/賽事桌可隨時啟用,系統無需改動。
- 起手牌、未胡牌者暗牌、運氣/實力分離評等 → 隨 L2 一併掛起。
- 賽事桌備選(不靠感應):選手同意下之每席手牌鏡頭(M-League 模式),僅限賽事/直播情境。

### 10.3 L1 的物理現實:中央混堆 → 即時事件擷取(v0.2.3 修正)
- **鐵律:台麻打出的牌混丟中央,不排列。** 牌堆「事後」不可讀,故 L1 不採快照讀取,改採**即時事件擷取**:
  - 牌落地瞬間 = 最後一次完整可見 → 當下完成「哪家(軌跡方位)+ 哪張(牌面分類)+ 第幾巡(時序)」記錄。
  - 動作偵測當閘門(有牌飛出才啟動辨識),平時低功耗待機。
  - 吃碰槓 = 取走「最新打出那張」(堆頂、剛記錄過),再記一筆取牌事件。
- **精度策略:** 每事件帶 confidence;胡牌攤牌時以手牌+吃碰槓記錄**反向對帳**,矛盾處降信心/標人工抽查。官方核心成績仍只採局結果(店員/桌台),CV 事件流供回放與進階分析。
- **硬體影響:** 邊緣運算盒需支援連續影像推論(規格上調),列入鏡頭選型核心項。
- 賽事直播桌未來可另議賽規(轉播可讀性需求);一般營業桌一律以混堆為唯一假設,不依賴客人行為改變。

### 10.4 規則集:南部台(無花)/ 北部台(有花)(v0.2.4)
- **鐵律:北部台有花(144 張)、南部台無花(136 張)。** 主場(高雄)= 南部台 / 無花。
- `games.ruleset` 細分:
  - `tw16_noflower`(南部台)= 136 張;**停用** `flower`/`replace_flower` 補花事件;無花牌計分。
  - `tw16_flower`(北部台)= 144 張(8 花);啟用補花事件;正花/花槓/八仙等花牌計台。
- 連動三處:**牌組大小(牌山/牌面字典)、補花事件是否記錄、花牌台數是否計分**。
- 規則參數化(底/台/各牌型台數/花牌)存於 ruleset 設定檔,不寫死 → 南店無花、北店有花、加盟可自訂,換規則集即切換。
