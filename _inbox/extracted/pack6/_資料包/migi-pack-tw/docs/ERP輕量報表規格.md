# MIGI 麻將連鎖 — ERP 輕量報表規格 v1.0

> 設計原則:**好 dashboard 是 10-15 個 KPI,讓店主 3 分鐘內回答「生意今天健康嗎?」**(業界鐵則,超過 20 個是雜訊)。
> 每個 KPI 都連到一個決定,不放好看但沒用的數字。
> 對準 MIGI 命脈:損益模型已證明命脈是「上座率/成桌率」,報表繞著它轉。
> 技術:Supabase 物化視圖(materialized view)即時算,dashboard 直接讀。

---

## 一、報表結構:四區 12 KPI

### ① 今天健康嗎 · 成桌(最重要)
| KPI | 算法 | 連到的決定 |
|---|---|---|
| **上座率/成桌率** ⭐ | 實際桌時 ÷ (桌數×營業時數) | 命脈。對照損益兩平線(目前 24.8%),低於就虧 |
| 今日營收 | 桌費 + 餐飲(當日 wallet_txns 加總) | 當日表現 |
| 今日開桌/成桌數 | count(table_sessions 當日) | 量能 |
| **白跑率** ⭐ | 想打但沒湊成桌就走 ÷ 來客 | 成桌率反指標(冷啟動關鍵);高=配桌能力不足 |
| 目前在場/容量 | 在場人數 ÷ (桌數×4) | 即時調度 |

### ② 賺錢嗎 · 獲利
| KPI | 算法 |
|---|---|
| 餐飲毛利率 | (餐飲營收 − 原料成本) ÷ 餐飲營收 |
| 客單價 | 總消費 ÷ 來客數 |
| 本月累計營收 / 預估月底 | 月累加 + 線性外推 |

### ③ 客人健康嗎 · 留存
| KPI | 算法 |
|---|---|
| 今日新客 | count(members 當日首次消費) |
| 7日回流率 | 7天內再來的會員 ÷ 上週來客 |
| 活躍會員(30日) | count(30天內有消費的會員) |
| **流失預警人數** ⭐ | lifecycle='at_risk' 的會員數 → 自動分派各主責店員去關心 |

### ④ 庫存與人效 · 營運
| KPI | 算法 |
|---|---|
| 庫存警示 | inventory.qty < 安全量 的品項 |
| 店員業績 | 各店員 配桌數 / 綁定客人來店 / 今日獎金(對 promoted_by_staff_id + primary_staff_id + bonus_rules 算) |

## 二、庫存:開店初期用「粗版進銷存」

**決策:開店初期用粗版,不做配方(recipes)。**

- **粗版(現階段)**:只管「成品/商品」進銷存。賣一杯奶茶 = 扣一個「奶茶」單位。原料(鮮奶、珍珠)用人工定期盤點 + 安全量警示。簡單、夠用、適合單店初期。
- **細版(規模化再上)**:做 `recipes` 配方表(一杯奶茶 = X 茶 + Y 奶 + Z 珍珠),賣出自動扣原料。精準但複雜,等多店、要控成本時再上。

粗版資料流:賣出 → `inventory_moves` 寫負數 → `inventory.qty` 更新 → 低於安全量 → dashboard 警示。

## 三、技術:物化視圖

報表 = 對 `wallet_txns / table_sessions / session_players / orders / inventory_moves / members` 的視圖。

- **即時 KPI**(今日營收、在場數):一般 view 或即時 query
- **重運算 KPI**(上座率、回流率、月累計):materialized view,定期 refresh(例如每 15 分鐘 / 每小時)
- 全部帶 org_id / store_id → 單店看自己、總部可聚合跨店比較

範例視圖:
- `mv_daily_revenue`(日營收:桌費+餐飲,by store)
- `mv_occupancy`(上座率:實際桌時÷可用桌時)
- `mv_member_retention`(回流率、活躍數、流失預警)
- `mv_staff_performance`(店員配桌數、綁定客人來店、獎金)

## 三之二、時間維度分析(時段熱度,可切換)

**設計原則:時段不是「預先定死的分組」,是「報表查詢時自由選的維度」。**

原始資料只存精確時間(table_sessions.started_at),報表上讓使用者自己選怎麼切 → 同一份資料想怎麼切就怎麼切,不預先定義、不需設定表。

**呼應基石②**:原始時間是事實,「怎麼分組」是觀點 → 觀點放報表層(查詢時 group by),不固化進資料。

### 報表提供的時間維度切換
| 檢視方式 | 用途 |
|---|---|
| **每小時**(10,11,12…23) | 看一天內哪個鐘點最熱/最冷 |
| **每天** | 看日營收/開桌趨勢 |
| **星期幾**(一~日) | 看週幾最旺(排班、檔期) |
| **自訂區間**(早/午/晚/深夜) | 婦女場、不同店自訂時段 |

```
[ 時段熱度 ]  檢視: ⏷ 每小時 / 每天 / 星期幾 / 自訂
每小時:  10  11  12 ... 22  23
開桌數:  ▂   ▃   ▅  ... ▇   ▃
```

### 兩種時段統計(都靠 started_at,與營業日切點無關)
- **某客人通常哪個時段開打**(按人):撈該會員開桌時間 → 統計時段分布 → 即 `member_availability` 的「行為推估」來源(系統自動算,比客人自填準)
- **全店哪個時段最多開桌**(按時段):對 table_sessions 按時段 group → 餵排班、婦女場時段、離峰活動決策

### 不做什麼
- ❌ 不建「時段設定表」(過度設計、不夠彈性)
- ✅ 報表層提供「每小時/每天/星期幾/自訂」分組選項,底層對 started_at group by

技術:物化視圖按需 group by(date_trunc 'hour'/'day' / extract dow / 自訂區間),BI 天然擅長同資料多種切法。

## 四、回填損益模型(報表的最大價值)

dashboard 的「上座率」直接回填《單店損益試算模型》:
- 損益模型假設「平均上座率 45%」是預估
- 報表跑出**真實上座率** → 回填損益模型 → 得到真實獲利
- 對照「損益兩平上座率 24.8%」這條線,一眼知道現在賺還是虧

**這是報表與損益模型的閉環**:模型預測 → 開店 → 報表量測真實值 → 修正模型 → 更準的決策。
