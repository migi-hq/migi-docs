## 配桌（MA1-C）

- **成桌時間錨點 = `play_at`（開房者指定的預定開打時間）**，不是「開房後 N 小時過期」。
  - waiting 狀態到 `play_at` 仍未滿員 → `expired`
  - **已成桌永不自動解散**；沒到的人由店員手動標 `no_show`
  - 理由：每個會員到店路程不同，用固定倒數對住遠的人不公平；「兩點半開打」是所有人共同的錨。
- **房主退房 → 轉移給次早加入者**，不解散（對其他等待者公平）。房內剩 0 人才 cancelled。
- **併發控制**：`join_match_queue_tx` 用 `SELECT ... FOR UPDATE` 鎖房，處理「兩人搶最後一位」。
- **即時更新過渡方案**：先用 5 秒輪詢；等 LINE 真登入（authenticated）後再換 Supabase Realtime。
  理由：Realtime 走 RLS，而現階段 anon 被全擋。
- **配桌等待層與 M0 計費桌分離**：App 的 `match_queues`（還沒入座）vs POS 的 `table_sessions`（已入座計費），用 `matched_session_id` 銜接。

## 牌咖

- **邀請制**：單向發起 → 對方確認才成立（不是「互相加碰巧配對」）。
- **拒絕無痕**：拒絕方跳 toast，發起方**完全收不到任何通知**。
- **接受後**寫 `mahjong_buddies` 兩筆互指，並回通知給邀請方。
- **不加防騷擾冷卻期**（被拒後可再邀）— 已拍板不做。
- **解除牌咖**：靜默雙向軟刪，對方不通知（`remove_buddy_tx`）。

## 黑名單

- **單向紀錄、雙向生效**：A 黑 B → 兩人互相看不到對方的房、互相進不去。
  只擋單向會讓 B 照樣加入 A 的房，形同虛設。
- **訊息模糊化**：被擋一律顯示「此桌已無法加入」「無法邀請此牌咖」，與桌滿/解散同語氣，**永不洩漏黑名單存在**。
  理由：MIGI 是實體店，客人見得到面，資訊洩漏會在店裡引爆衝突。
- **黑掉牌咖 → 自動解除牌咖關係**＋作廢未回覆邀請＋清理相關通知。

## 人機協作模型

**App 管撮合意圖，店員管現場執行。** 不追求線上全自動完美對齊，因為最後一哩有店員兜底：
- 店員可對未滿房**強制成桌 + 代打補位**讓桌準時開
- 店員/房主可改 `play_at`（喬時間）並通知全員
- 代打局的店員成績 M4 結算時排除；被人工介入的桌，M3 分析「自然成桌速度」時要排除
