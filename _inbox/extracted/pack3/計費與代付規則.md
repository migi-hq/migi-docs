# 計費與代付業務規則（已拍板）

> 這是什麼：MIGI 檯費計價、代付機制、儲值贈點的商業規則決策紀錄。
> 什麼時候讀：實作任何與收費相關的功能前，或對「這筆錢該算誰的」有疑問時。

---

## 一、檯費計價

### 配桌（按人頭）

| 情境 | 金額 |
|---|---|
| 3 將 | 每人 $150 |
| 2 將 | 每人 $100 |
| 中途加入 | $100 |

**「中途加入」的判斷依據是「桌子有沒有帶桌開打」（`activated_at`／`tableStarted`），不是「有沒有人先入座」。**
四個人一起報到都收開桌價；只有帶桌之後才來的（換手、補位）才算中途加入。

### 包桌（整桌計價、按實到人數分攤）

| 時段 | 整桌價 |
|---|---|
| 2 小時內 | $400 |
| 2–5 小時 | $600 |
| 5 小時以上 | $800 |

每人應付 = `Math.ceil(整桌價 / 實際入座人數)`。
人數變動時所有人重算，因此加滿人前不宜結帳。

### 當日暢打 $300

`has_daypass_tx` 判斷（台北時區自然日，過午夜失效）。
**只免配桌費，包桌不受影響。**

## 二、代付機制

### 核心原則：誰出錢，帳就是誰的

| | 付款人 | 被代付者 |
|---|---|---|
| `orders` | ✅ 一張，含多份檯費 | ❌ 無 |
| `session_players` | ✅ `charged_points` = 全額 | ✅ `charged_points` = 0、`paid_by` = 付款人 |
| 消費累積（影響會員等級） | 全額 | 0 |
| 發票 | 開給付款人 | 無 |

**被代付者仍要建 `session_players`** —— 他們確實入座了。少了這筆會導致收桌算不出實際人數、M4 段位漏掉他們的牌局、CRM 看不出他們來過店裡。

### 適用範圍

- **不分配桌包桌都可代付** —— 代付是收款層的功能，跟計價方式無關
- **只有檯費可代付**，商品與儲值不可
- 檯費份數 = 自己 1 份 + 代付人數，**份數永遠鎖定不可手動增減**（避免「改成 3 份卻沒指定幫誰付」的不一致狀態）

### 防呆

- 不能代付自己
- 不能代付已被他人代付的人（勾選列表中變灰）
- 已結帳者不出現在代付列表（不能事後改動已收的錢）
- 自己正在被別人代付時，看不到代付按鈕
- 移除某人時，相關代付關係自動清除
- 座位總數（自己 + 代付人數 + 已入座）不可超過 4

### 結帳連動

付款人結帳後，被代付者的座位卡**同步變成「已結帳」** —— 他們的費用已含在那張單裡，店員不該再向他們收錢。

## 三、儲值

- **僅選金額，不問付款方式**
- 贈點級距（快捷與自訂共用）：`1000 → +50`、`2000 → +150`、`3000 以上一律 +300`
- **不參與折扣、不可用點數購買、不可代付**
- 併入本次消費明細，但列在點數折抵下方 —— 位置本身說明它不受上面的折扣影響
- **小計不含儲值金額**（用 `discountable()` 而非 `goodsTotal()`）

## 四、身分驗證的已知風險（暫不處理）

現況是客人報手機號碼、店員查會員，**系統不驗證是否本人**。存在兩種風險：

1. **刷等級** —— 一群人固定讓某位買單，他升到高等級後全桌都享折扣
2. **冒用** —— 知道別人手機號碼即可扣其點數

**決策：不做金額門檻驗證。** 現場氣氛的摩擦成本高於防到的損失（熟客每天來，突然要出示條碼會覺得被質疑）。

**中期解法**：LINE Login 上線後改用 LIFF 掃碼。條碼從登入狀態產生、可做成動態，偽造需先登入對方 LINE 帳號。
**但掃碼功能本身仍需開發**（App 端 LIFF 條碼 + POS 端掃描器），且沒有 LINE 的長輩熟客仍只能報手機，靠店員認人。
