## 0.5 ★地基遵循（M2 所有新表/RPC 必守 M0 的 22 項資料架構）

> M0/M1 已 LIVE，22 項資料架構是地基。**M2 新增的每一張表、每一個 RPC，都必須沿用**，不可破壞一致性。下方各表的結構是**示意（只列業務欄位）**，實作時務必補齊以下共通欄位/規則：

**每張新表都要有**：
- `id uuid PK`（UUID 主鍵）
- `org_id uuid`（多租戶，RLS Day1；org_id 不可竄改）
- `created_at / updated_at timestamptz`（審計欄）
- `deleted_at timestamptz NULL`（軟刪除，不真的 DELETE）
- 唯一約束要**含 deleted_at**（避免軟刪後衝突）

**碰錢的表/RPC 額外要**（退檯費、扣費、儲值等）：
- 雙邊錢流 + 金額方向 ±、交易狀態、`external_ref`（冪等防重複）
- 退款反向沖正（不改原紀錄，新增沖正筆）
- 碰錢外鍵 restrict、改錢只 service_role
- wallet_txns 類 APPEND-ONLY（不可改不可刪）

**RLS**：SELECT org-scoped；writes service_role；前端一律走 SECURITY DEFINER RPC。

**其他**：點數 bigint、enum 用 check、FOR UPDATE 防併發、PITR、Migration 版控、個資加密遮罩。

> 下方表結構若未逐一列出這些欄位，**不代表可省略**——一律以本節為準補齊。

## 1. 桌台系統（①）

### 1.1 目標
讓「開桌 → 打牌 → 收桌」在真實資料上正式運轉。後端 `settle_session_tx`、`charge_matched_tx`、`charge_private_tx` 已寫好，這塊主要是**狀態機補完 + 店員操作接口**。

### 1.2 桌次狀態機（table_sessions.status）

```
open（開桌，已扣檯費）
  → playing（進行中，可選，或直接用 open）
  → settling（結算中，鎖定）
  → closed（已收桌; 檯費開桌已扣; 收桌核心=逐將座位輸入; 觸發消費累積/店員業績/互加牌咖; 段位等M4）
  → voided（作廢，退費用，異常處理）
```

建議 enum：`open / playing / settling / closed / voided`

### 1.3 現有表確認（M0 已建）
- `table_sessions`：桌次主檔（store_id, table_id, status, stake_level_id, rule_type, opened_at, closed_at, opened_by_staff_id...）
- `session_players`：座位（session_id, member_id, seat, joined_at, left_at, is_matched 配桌 vs 包桌）
- `tables`：實體桌台（store_id, table_no, status 空閒/使用中/整理中）

### 1.4 需要補的
| 項目 | 說明 |
|---|---|
| `tables.status` 狀態機 | idle（空閒）/ occupied（使用中）/ cleaning（整理中）/ disabled（停用）。開桌→occupied，收桌→cleaning→idle |
| 開桌 RPC `open_session_tx` **⚠️待開發（全新）** | **2026-07-13 查證：此函式不存在，須全新開發（非修改）**。建 table_session（status=open）+ 綁 session_players + **收費走 tender 模型（點數／現金／混合）** + 更新 tables.status。冪等（external_ref）。★可複用已存在的 `checkout_tx` / `charge_matched_tx` / `charge_private_tx`，不必重寫收費邏輯 |
| 作廢 RPC `void_session_tx` | 異常開錯桌：反向沖正退費（reverse_txn_tx）+ session voided + table 回 idle |
| 中途加入 | session_players 補一人 + charge 100 點（記憶：中途加入 100/人）|

### 1.5 收桌（已有 settle_session_tx）串接點
> **★M2 金流澄清（v1.8 更新，取代舊「全程點數」）**：檯費**開桌時就收**（開桌即收，不等收桌）。收桌**無金流結算**。
> **★付款方式（2026-07-13 新政策）**：售價以**元**計，付款可**純點數／純現金／點數+現金混合**。檯費＝場地使用費，可直接收現金。舊敘述「客人先付現儲值→開桌扣點數、桌面不見現金」**已作廢**。詳見《MIGI_開桌結帳流程規格_v2.0》。
> **★收桌核心工作 = 逐將輸入座位（東南西北）**：風位每將轉，每將重輸；M4 AI 辨識不了「誰坐哪」，只能店員人工套。座位是 M4 牌譜的人-座位對應基礎。
> **★填座位有彈性（Jim 定）**：店員可 **①逐將即時填**（每打完一將當下填 → 桌台看板即時顯示第幾將）**或 ②收桌時一次填**（打的時候不填，收桌一次補所有將）。**填入位置**：櫃檯電腦（POS 主機）或桌邊平板都可。
> **★「第幾將」資料來源 = 店員填的將數**：有逐將填 → 看板顯示目前第幾將；沒逐將填 → 看板該桌不顯示將數（或顯示「進行中」），收桌填完才有完整將數。（打牌中系統本身不知道第幾將，全靠店員填。）

**新增表：session_rounds（每將座位記錄）**
```
session_rounds
  id          uuid PK
  session_id  uuid FK table_sessions
  round_no    int              -- 第幾將（1,2,3）
  seat_east   uuid FK members  -- 東家是誰
  seat_south  uuid FK members  -- 南家
  seat_west   uuid FK members  -- 西家
  seat_north  uuid FK members  -- 北家
  created_at  timestamptz
  updated_at  timestamptz
  deleted_at  timestamptz NULL   -- 軟刪除
  org_id      uuid               -- 多租戶, 不可竄改
  UNIQUE(session_id, round_no, deleted_at)   -- 唯一約束含 deleted_at
```

**新增 RPC：record_rounds_tx（寫每將座位，可逐將或批次）**
```
輸入：session_id, rounds[]（一將或多將的東南西北 member_id）, source（'pos'櫃檯/'tablet'桌邊）
動作：
  - 驗證每將四座位都有人、四人是這桌的 session_players
  - upsert session_rounds（逐將即時填=一次一將；收桌填=一次多將）
  - 更新該桌目前將數（= 已填的最大 round_no，供桌台看板顯示）
  - 全部將都填 + 收桌時 → 標記 rounds_complete=true
輸出：ok, current_round（目前第幾將）
```

**收桌 settle_session_tx（M2 模式）觸發**：
1. ❌ 無檯費結算（開桌已扣）
2. ✅ 消費累積（會員 tier，若非開桌時記）
3. ✅ 店員業績（配桌獎金）— **★條件：session rounds 座位全套入才發**
4. ✅ **★收桌觸發「互加牌咖」**（詳見 §2.6）
5. ✅ **★成績輸入 App（M2=基本場次/麻將足跡）**：3 將座位都對齊（rounds_complete）→ 才把「打了這場」的紀錄推到客人 App（場次/門市/交手人數=麻將足跡）。**M2 只輸入基本場次，名次/輸贏/段位等 M4 影像辨識好了再補**（對應記憶「麻將足跡 vs 成績」：足跡 M2 就有，成績 M4 才完整）。
6. ❌ 段位/名次 → M2 關閉（等 M4 名次辨識）

**★強制規則（座位對齊是多件事的前置）**：座位沒逐將對齊完（rounds_complete=false）→ ①不能收桌 ②不能清潔開新桌 ③**成績不輸入 App**（人-座位對應不完整=不知成績算誰的）④配桌獎金不發。3 將座位全對齊 → 才解鎖這些。

**桌台狀態流轉**：playing → （座位輸入完）→ settling → closed → tables: occupied → cleaning → idle（可開新桌）

## 2. 配桌引擎（②）— 護城河核心

### 2.1 第一階段範圍（刻意簡單）
- ✅ 佇列（誰在等配桌）
- ✅ 湊桌（同積分級距 + 同規則 + 同門市，湊四人）
- ✅ **黑名單硬過濾**（拉黑的人絕不配同桌）
- ❌ 合拍度精算（先不做，但**默默記錄數據**）
- ❌ 安心分/信用過濾（先不做）
- ❌ 配桌優先序加權（先不做）

> **關鍵原則**：成桌率是命脈。完美篩選會湊不成桌，第一版求「配得成」。

### 2.2 新增表：match_queue（配桌佇列）

```
match_queue
  id            uuid PK
  member_id     uuid FK members
  store_id      uuid FK stores        -- 想在哪個門市打
  stake_level_id uuid FK stake_levels -- 想打的積分級距
  rule_type     text                  -- 台麻無花/台麻有花/美麻
  status        text                  -- waiting / matched / cancelled / expired
  matched_session_id uuid FK table_sessions NULL -- 配到的桌
  is_staff_matched boolean DEFAULT false -- 是否店員撮合（發獎金用）
  created_at    timestamptz
  matched_at    timestamptz NULL
  cancelled_at  timestamptz NULL
  updated_at    timestamptz
  deleted_at    timestamptz NULL      -- 軟刪除
  org_id        uuid                  -- 多租戶 Day1, 不可竄改
  -- 未來合拍度用（先存不開）：
  prefer_pace   text NULL             -- 出牌速度偏好（默默記錄）
  prefer_chat   text NULL             -- 聊天偏好
```

**★允許一人多筆 waiting（多桌等待，機制 A）**：同一 member_id 可同時有多筆 status=waiting（不同積分/門市）。任一筆 matched → 其餘同 member 的 waiting 自動 cancelled。

**RLS**：SELECT org-scoped；write 走 SECURITY DEFINER RPC。

### 2.3 黑名單資料來源
記憶：黑名單用 `member_interactions`（或獨立表）。確認欄位：
```
member_interactions（黑名單）
  member_id       uuid  -- 拉黑的人
  target_member_id uuid -- 被拉黑的人
  interaction_type text -- 'blacklist'
  reason          text[] -- 拉黑原因（可複選，私密，被拉黑者看不到）
  created_at
```
> 拉黑原因分兩型（記憶）：不合拍型（太慢/太愛聊/太計較/年齡差）+ 行為問題型（牌品差/騷擾/賒跑帳/作弊）。launch 只記錄+統計，仍只擋本人。

### 2.4 配桌 RPC 設計

**① 加入佇列 `join_match_queue_tx`**
```
輸入：member_id, store_id, stake_level_id, rule_type
動作：
  - 檢查會員沒有進行中的配桌/桌次
  - 建 match_queue（status=waiting）
  - 呼叫湊桌檢查 try_match（見下）
輸出：queue_id, 目前狀態（waiting / matched）
```

**② 湊桌演算法 `try_match`（核心）**
```
觸發時機：每次有人 join_match_queue，或店員手動觸發
邏輯（第一階段）：
  1. 撈出同 store_id + 同 stake_level_id + 同 rule_type 的 waiting 佇列
  2. 黑名單硬過濾：候選四人中，任兩人互為黑名單 → 不可同桌
  3. 湊滿四人 → 建 table_session（status=open）
       - session_players 綁四人（is_matched=true）
       - charge_matched_tx 扣每人檯費
       - 四人 match_queue.status=matched, matched_session_id 回填
       - tables 找一張 idle 的桌，status=occupied
  4. 湊不滿 → 維持 waiting，等下一個人進來再試
輸出：matched（成桌）或 waiting（繼續等）
```

> **黑名單過濾的組合問題**：四人中任兩人不可互黑。實作用「逐一加入候選、檢查與已在桌者是否互黑」的貪婪法即可（第一版不追求最優，追求配得成）。

**③ 取消配桌 `cancel_match_queue_tx`**
```
輸入：queue_id / member_id
動作：match_queue.status=cancelled
注意：已 matched（成桌）不能取消（要走桌次作廢流程）
記錄取消原因 → 後台統計（M3 用來決定何時放寬）
★成桌時自動取消：某筆 matched 後，同 member 其餘 waiting 全部 cancelled（多桌等待收尾）
```

**④ 店員撮合 `staff_match_tx`（護城河最深，機制 B）**
```
輸入：staff_id, member_ids[]（店員手動勾選的 2~4 人）, table_id
動作：
  - 黑名單硬過濾（勾選的人互為黑名單 → 擋下並提示店員）
  - 建 table_session（status=open, opened_by_staff_id=staff_id, is_staff_matched=true）
  - session_players 綁人 + charge_matched_tx 扣費
  - 這些人的 match_queue.status=matched, is_staff_matched=true
  - 同 member 其餘 waiting cancelled
  - tables.status=occupied
  - 記店員配桌業績（發獎金 50/桌，收桌時結算）
輸出：session_id
```

**⑤ 中途加入 `join_session_tx`（三缺一補人，★M2 第一版做，兩管道）**
> **三缺一的唯一成因**：開桌一定滿 4 人才開，所以打牌後變 3 人 = **有人中途離開**（店員在 POS 標記某人離開 → 桌變 3 人 → 顯示三缺一 → 提醒補人）。

**補人兩管道（M2 都做）：**

**管道 1 — 店員找人（手動）**
```
店員當場找到人（現場問到/名單挑）→ POS 查會員資料（搜暱稱/手機）
  → 手動 join_session_tx 加進這桌 → 扣 100 點 → 三缺一消失、恢復 4 人
特點：人已在現場，店員手動加，立即補上
```

**管道 2 — 系統配（全自動）**
```
店員按「開放中途加入」→ 這桌進配桌池
  → App 有人配到這桌 → 系統自動 join_session_tx 填上（★不管人到沒，配到就填）
  → 三缺一自動消失、自動扣 100、恢復 4 人
  → 店員完全不用手動
放鳥處理：配到的人若沒來 → 店員把他移除 → 回到三缺一 → 重走補人流程
（不設時限/不進安心分，就是移除重來）
```

**join_session_tx 共用邏輯**：
```
輸入：member_id, session_id, via（'staff'手動 / 'auto'系統配）
動作：
  - 檢查該桌 status=open/playing 且 未滿 4 人
  - 黑名單過濾（與桌上的人互黑 → 擋）
  - session_players 補一人（is_matched=true, joined_at=now）
  - charge 100 點（中途加入 100/人）
  - 滿 4 人 → 三缺一狀態消失
  - 移除待到場的人：remove_player_tx（回退，桌回三缺一）
輸出：ok
```

### 2.5 成桌率保命機制：多桌等待 + 店員主動撮合（★Jim 定案，取代「系統自動放寬」）

> **核心觀念修正**：放寬不是系統偷偷做，是**客人自主 + 店員主動撮合**。實體店有店員在現場，看得到誰在等，比演算法更靈活。

**機制 A：客人可同時等多桌（增加成桌機會）**
```
客人選 50/20 加入配桌 → 這桌一直沒湊滿
  → 客人可以「再加入其他積分/門市的桌」一起等
  → match_queue 允許同一 member 有多筆 waiting
  → 哪一桌先湊滿 4 人 → 那桌成桌，其餘 waiting 自動 cancelled
會員端顯示：「你正在等這幾桌…」（列出多筆等待）
```

**機制 B：店員主動撮合（護城河最深，發配桌獎金）**
```
店員後台桌台看板看到所有等待中的人（按門市/積分分組）：
  「50/20 有 2 人在等、30/10 有 1 人、100/20 有 1 人」（零散落單）
  → 店員判斷可湊 → 手動勾選這幾人 → 兜成一桌
  → 這桌標記為「店員配桌」（is_staff_matched=true）→ 發配桌獎金 50 元/桌
店員撮合可跨積分（店員判斷合適即可），系統自動湊只配同條件
```

**兩層配桌並存**：
| 層次 | 誰做 | 條件 | 獎金 |
|---|---|---|---|
| 系統自動湊 | 演算法 | 同積分/規則/門市 | 進全店池 |
| 店員撮合 | 店員手動 | 可跨積分（店員判斷）| 配桌獎金 50/桌 |

> **不做**：系統自動放寬積分級距（原設計），改由客人多桌等待 + 店員人工撮合處理成桌率。

### 2.6 收桌觸發「互加牌咖」（護城河飛輪）
記憶（護城河戰略）：配桌陌生人互加 = 最強護城河。收桌時：
```
settle_session_tx 收桌後：
  - 若這桌是配桌成桌（is_matched）
  - 對同桌四人，前端跳「要不要把今天的牌咖加起來？」
  - 雙向無痕加（A加B、B加A，兩邊都加才成立）
  - 成立 → 各得 1 張摸牌券（gacha 券）
  - 不出現「合拍度」字眼，只友善問
```
後端：`add_buddy_tx`（雙向無痕，兩筆記錄都 true 才 mahjong_buddies 成立）。

## 3. 即時推播（③）

### 3.1 兩個管道
| 管道 | 用途 | 計費 |
|---|---|---|
| **Supabase Realtime** | 配桌進度會動（waiting→matched 即時更新前端）| 免費（含在 Supabase）|
| **LINE Messaging API** | 成桌通知推到 LINE 聊天室（會員沒開 App 也收到）| Push 計費（約 0.2 元/則，免費 500 則/月）|

### 3.2 Supabase Realtime 設計
```
前端訂閱 match_queue 自己那筆的變化：
  supabase.channel('match:' + queue_id)
    .on('postgres_changes',
        { event: 'UPDATE', schema: 'public', table: 'match_queue',
          filter: 'id=eq.' + queue_id },
        (payload) => { 更新配桌頁 phase })
    .subscribe()
狀態變化：waiting → matched → 顯示成桌 + 桌號 + 同桌的人
```
> 需在 Supabase Dashboard 開啟 match_queue 的 Realtime（Database → Replication）。

### 3.3 LINE 推播設計（成桌通知）
```
try_match 成桌後：
  - 呼叫 Edge Function send_line_push
  - 對四人各發一則 LINE Flex Message：
    「🀄 你的桌湊齊了！MIGI 高雄自由店 3 號桌，請入座」
    + 按鈕（點了開 LIFF 對應頁）
分級（記憶）：
  - 配桌成功 = 重要 → 兩地都送（App 內 + LINE）
  - 一般（成就/點數）= 只 App 內（免費）
  - 行銷（活動優惠）= 主 LINE 群發，要分眾省錢
需檢查會員的通知偏好（migi_noti_table 開關）再決定送不送 LINE
```

### 3.4 Edge Function：send_line_push
```
輸入：member_ids[], message（Flex）
動作：
  - 查每個 member 的 line_user_id（註冊時 LINE Login 存的）
  - 查通知偏好（關了就跳過）
  - 呼叫 LINE Messaging API Push
  - 記錄推播 log（統計用量/成本）
部署：Supabase Dashboard → Edge Functions（不用 CLI）
密鑰：LINE Channel Access Token 存 Supabase Secrets
```
