# 決策紀錄

> **這是什麼**：定案的決策與其理由。重點是「為什麼」——理由比結論更難重建。
> **什麼時候讀**：想改動既有設計、或不確定某個做法當初為何這樣定時。
> 只記最終版；被推翻的舊決策以「已作廢」標示，因為知道「什麼被否決過」能避免走回頭路。

## 一、商業模式：元計價 + 混合付款（2026-07-12）

### 決策
1. 所有商品售價單位改為**元**（新台幣），顯示 `$100`
2. 付款方式：**純點數 / 純現金 / 點數+現金混合**
3. 1 點 = 1 元，點數從「計價單位」變成「**付款方式（tender）之一**」
4. **檯費 = 場地使用費，可以用現金收**

### 為什麼
牌桌上不見的是**賭資現金**（輸贏籌碼），而場地使用費是正常的服務收費，收現金天經地義。這釐清了紅線的真正邊界：紅線是「牌桌賭資不見現金 + 點數不可兌現」，不是「店裡所有收費都不能碰現金」。

### 作廢的舊規則
- ❌「桌面不見現金，一律走點數」（cash→points first）
- ❌「所有付款先轉點數，無一例外」
- ❌「現金不足 → 提示先儲值」

### 新金流鐵則（取代舊的「一律轉點數」）
1. **一律會員，無例外** — 純現金客也要建會員。舊鐵則真正想守的其實就是這件事（消費累積進 CRM、牌咖關係、店員業績歸因、段位掛人），現在直接守它，不繞點數這條路
2. **一律入帳，現金也不例外** — 每筆收款都要記 order_payments，沒有私下收現金的路徑
3. **賭資不上桌** — MIGI 只收場地費與商品費，不經手、不記錄、不抽成牌桌輸贏

### 對系統的影響
checkout_tx 本來就是 tender 模型（應付金額 → 點數折抵 → 現金補足），**天生支援新模式**，後端幾乎不用改。主要工作在 POS UI（付款方式選擇、實收找零）與開桌流程。

## 二、貨號採三段式（2026-08-07）

### 決策
`類別-子類-品項`，例如 `SVC-TBL-M3`、`FNB-MEAL-DUMP`、`FNB-DRK-MILKTEA`

### 為什麼
三段式真正的價值是**子類那一層**——同類別內需要分開看的維度（飲料 vs 餐點的毛利結構完全不同）。有了它，`sku LIKE 'FNB-DRK-%'` 就能算飲料營收，不必另建分類對照表。

### 演變過程（避免走回頭路）
1. 最早：貨號隨手取（`FEE-100`、純數字 `123`），與 category 對不上
2. 一度定：兩段式 `SER-001` 流水號 → **對檯費是錯的選擇**，流水號會把「配桌/包桌 × 將數/時段」的結構丟掉，`SER-002` 看不出是什麼
3. 定案：三段式，且檯費用語意化第三段（M2/M3/MID/P02...），餐飲零售也用語意縮寫

### 附帶修正
- 頂層分類**不需要**用 LIKE 查詢——`order_items.kind` 結帳時就存了 fee/fnb/goods，直接用更快
- 已知代價：字串比對會靜靜漏資料（打成 `FNB-DRINK-` 就從報表消失不報錯）；改貨號會改變歷史報表（order_items 不存 sku）
- 日後若子類報表變關鍵，加 `products.subcategory` 欄位，貨號純當標籤

### `SVC-TBL-MID` 為什麼獨立，不共用 `SVC-TBL-M2`
兩者同價 100，但性質不同（預定 2 將 vs 半路入場的低消）。共用會有兩個後果：日後 2 將調價，中途加入被迫跟著改；報表分不出「多少人是中途加入」——而這是評估配桌成桌品質的關鍵指標。

## 三、`unit_points` → `unit_price`（2026-07-12）

### 決策
把 products 與 order_items 的欄位更名／清理，統一為 `unit_price`（元）。

### 為什麼
改元計價後，欄位叫 points 名不符實，會長期誤導。趁測試階段、無真實訂單資料時一次改對，代價可控。

### 執行結果
- products.unit_points → unit_price（含 check 約束改名）
- order_items 原有 unit_points（not null 主欄）與 unit_price（相容欄）**雙欄重複存同一個值**，已淘汰 unit_points、unit_price 轉正為 not null
- checkout_tx 同步改為只寫 unit_price

## 四、總部後台（HQ）

| 決策 | 內容 |
|---|---|
| 系統邊界 | HQ（hq.migi.tw）與 POS（pos.migi.tw）是**兩個獨立前端，共用同一個 Supabase**。HQ 管跨全體建檔與策略（全集團視角），POS 管單店當下營運 |
| 「店長 vs 店員權限」 | 那是 POS 內部的角色差異，與 HQ 無關 |
| 登入 | Supabase Auth Email + 密碼，第一個管理員帳號在 Dashboard 手動建 |
| 權限 | 第一版只做「總部管理員」單一角色（role='hq'） |
| 商品定價 | 現階段全集團同價，但表結構已預留 store_id，未來要分店價不必改結構 |
| repo 命名 | `migi-admin`（不是 migi-hq——那會與 GitHub org 名重複變成 migi-hq/migi-hq） |
| 模組優先序 | 第一波（解鎖 POS）：商品管理、券管理 ／ 第二波：會員、報表 ／ 第三波：門市、加盟、權限 |
| UI 風格 | 白底灰框為主體，CIS 粉色用於選中態（**粉底黑字**，非桃紅字）。後台每天看資料，清晰優先 |

## 五、開桌流程設計（2026-08-07）

| 決策 | 理由 |
|---|---|
| **收費一律委派 checkout_tx** | 券折抵、等級折扣、混合付款、冪等、五表寫入都已實作完整。自己重寫等於兩套邏輯並存，一旦不一致帳就出問題（且草稿版重寫時完全漏掉「券」） |
| **兩步制**：開桌不收費，每來一人才收 | 對應櫃台實務——麻將要等人到齊，客人是陸續報到的 |
| **場次不設 'playing' 狀態** | 用 `activated_at` 是否有值區分「收費報到中／已開打」。不必擴充 status 約束，而 activated_at 本來就要記（日後接電控用） |
| **org_id 由桌位反查，不接受呼叫端傳入** | 函式是 SECURITY DEFINER（繞過 RLS），若信任呼叫端傳來的 org_id，任何登入者都能操作別的租戶 |
| **冪等鍵用正式欄位 + 唯一索引** | 草稿版借用 note 欄位（無約束、無索引），並發下兩個請求可能同時查不到而開出兩張桌 |
| **冪等鍵帶入座序號** | 同一人退出後再加入是新的收費事件，不能被當成重複請求 |
| **互黑檢查只警示不阻擋** | 系統處理標準，人處理例外——店員保有最終裁量權 |
| **不用 `exception when others`** | 會連程式 bug 一起吞掉，除錯極痛苦 |
| 收費時機 | **開桌即收**，不等收桌 |

## 六、待拍板

| 項目 | 現況 |
|---|---|
| **當日暢打（SVC-TBL-DAY 300）怎麼收** | 商品已建但無程式路徑（open_session_tx 只接受 matched/private）。選項：加第三種模式 daypass ／ 當一般商品在 POS 賣（傾向這個——「今天不限次數」與「這桌收多少」是不同維度）／ 暫不處理 |
| **檯費價格正式確認** | 配桌 2將100／3將150、中途加入100、暢打300、包桌400/600/800——這些數字取自測試資料與舊規劃文件，尚未正式拍板 |
| **打 1 將怎麼算** | 目前 open_session_tx 只接受 2 或 3 將，實務上打 1 將者以 2 將場次開桌 |
| **配桌 vs 包桌的判斷準則** | 客人自己揪四人卻用系統配桌功能，算哪種？影響收費（配桌 per-head 4人=600 vs 包桌 2小時=400），店員每天會遇到，需要明確準則 |
| **進貨成本怎麼算** | 每次進貨成本不同時，業界標準是「移動加權平均」（每次進貨重算平均成本存回 unit_cost）。需要做一個「進貨」功能才能落地。現階段可先不追成本 |

## 七、上線前必做

1. **移除 migi-web wallet 的測試券 fallback** — 現在沒券的會員會看到 3 張假券，上線會客訴
2. **清測試資料** — **含軟刪除的一起硬刪**（軟刪除是營運中機制，清庫是一次性徹底清空）。依外鍵順序：order_items → orders → ... → products。再砍測試 org（11111111-...），走正式建店流程生正式 org
3. **公司登記**（統編、營業登記）是正式上線的前置關卡——正式 org 要等公司成立才有意義
4. **products.js 的貨號自動生成要改** — 現行產兩段式流水號，與三段式不相容
