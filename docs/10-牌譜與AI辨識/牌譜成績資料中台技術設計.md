# MIGI 麻將連鎖 — 牌譜 / 成績資料中台技術設計 v0.4

> **這是什麼／何時讀**:牌譜與成績資料庫的完整技術設計(資料表結構、事件編碼、聚合邏輯、座位綁定、L0/L1/L2 分級)。要接資料庫、寫後端、或想知道「牌怎麼存」時讀這份。

> 範圍:逐筆牌譜事件庫、成績聚合、排名、回放與分層儲存。
> 技術棧:PostgreSQL / Supabase。
> 與《配桌引擎技術設計》的接縫:本文的聚合結果回寫 `member_rating`(配桌即時讀取的實力快照)。
> 用語鐵則:台麻用語(輪/吃碰槓/連莊/台/圈風);日麻項目(立直/寶牌/番符)一律「保留 schema、標記停用」,引進日麻規則集時才啟用(見 §11)。
>
> **v0.4 變更摘要**:新增「側面鏡頭直拍手牌」為 L2 主路線(§10、§10.3 象限 B);起手牌改由側面鏡頭直接取得、不再依賴牌山序(§10.1);§10.3 拆為海底(俯視即時擷取)/ 手牌(側面快照輪詢)兩象限,並將舊版兩方反推升級為三方對帳;範圍決策新增「L1+側面」中間層,把起手牌/逐輪摸打/運氣實力分離從「等重硬體」救回(§10.2);§3 補摸切/手切 meta 旗標;**新增 §10.5 座位↔會員綁定流程**;**§3 牌面編碼改為統一兩碼制(條改用 `t`、字牌補 `0`、花牌用 `H1`–`H8`),並移除台麻不存在的紅5**。schema(games/hands/paipu_events/game_players)本身不變,仍向後相容;`tile` 欄位值需依新編碼重新產出(尚無正式資料,無遷移成本)。

## 1. 設計概念

- **事件溯源(Event Sourcing):** 每個動作 = 一筆**不可變、只追加**的事件。事件庫是唯一真相來源;任何指標都能從事件重算。
- **來源 + 信心分層:** 每筆事件標 `source`(桌台/AI/記錄員)與 `confidence`(0~1)。官方成績只採信高信心;低信心 CV 資料存而不污染。
- **衍生聚合:** 不每次掃原始事件;維護增量更新的聚合表,供秒開儀表板與配桌讀取。
- **一份事件流、兩種用途:** 同一份 `paipu_events` 同時餵「成績統計」與「逐輪回放」。

層次:`對局(games) → 局(hands) → 逐筆事件(paipu_events)`。

## 2. 資料表(Postgres DDL)

```sql
-- 一場對局(= 一桌一個 session,通常一將/一場)
create type game_status as enum ('live','finished','void');

create table games (
  id          bigint generated always as identity primary key,
  store_id    bigint not null,
  table_id    bigint not null,
  game_type   text   not null,                 -- 4P_16 / 4P_13 / 3P_16 ...
  ruleset     text   not null default 'tw16',  -- tw16(台灣16張,現行) / jp13(保留未來擴充,暫不使用)
  is_official boolean not null default false,   -- 賽事級(高精度、可公開)
  is_ranked   boolean not null default true,    -- 是否計入評等
  status      game_status not null default 'live',
  started_at  timestamptz not null default now(),
  ended_at    timestamptz
);

-- 對局四座位是誰、最終結果
create table game_players (
  game_id     bigint   not null references games(id) on delete cascade,
  seat        smallint not null,                -- 1..4
  member_id   bigint   references members(id),
  final_rank  smallint,                         -- 1..4 名次
  final_score integer,                          -- 點數/台數結算
  primary key (game_id, seat)
);

-- 局(東1局、南2局...)
create type hand_result as enum ('tsumo','ron','draw','abort'); -- 自摸/胡牌(放槍)/流局(臭莊)/中止

create table hands (
  id           bigint generated always as identity primary key,
  game_id      bigint   not null references games(id) on delete cascade,
  round_wind   text     not null,               -- E/S/W/N(東南西北場)
  hand_no      smallint not null,               -- 第幾局
  renzhuang    smallint not null default 0,     -- 連莊數(連N拉N;台麻莊家連莊計數)
  dealer_seat  smallint not null,               -- 莊家座位
  result       hand_result,
  winner_seat  smallint,                         -- 胡牌者(流局 null)
  deal_in_seat smallint,                         -- 放槍者(自摸/流局 null)
  score_delta  jsonb,                            -- {"1":48,"2":-16,...} 各座位增減
  started_at   timestamptz not null default now(),
  ended_at     timestamptz,
  unique (game_id, round_wind, hand_no, renzhuang)
);

-- 逐筆牌譜事件(核心,append-only,按月分區)
create type event_source as enum ('table_feed','cv','operator','online');
create type event_action as enum (
  'deal','draw','discard','chi','pon','kan_open','kan_closed','kan_added',
  'flower','replace_flower','tsumo','ron','ryuukyoku',
  'riichi','dora_reveal'   -- ⚠ 日麻專用:引進日麻規則集(ruleset='jp13')時才啟用;台麻不使用
);

create table paipu_events (
  id           bigint generated always as identity,
  game_id      bigint   not null references games(id),
  hand_id      bigint   not null references hands(id),
  seat         smallint not null,
  turn_no      smallint,                         -- 第幾輪
  action       event_action not null,
  tile         text,                             -- 牌面編碼,見 §3
  meta         jsonb,                            -- 吃碰槓對象、所用牌組等
  event_ts     timestamptz not null,
  source       event_source not null,
  confidence   numeric  not null default 1.0,    -- 0~1;AI 辨識帶信心
  is_corrected boolean  not null default false,  -- 經人工校正覆寫
  primary key (id, event_ts)
) partition by range (event_ts);

-- 月分區範例(每月建一張)
create table paipu_events_2026_06 partition of paipu_events
  for values from ('2026-06-01') to ('2026-07-01');

create index on paipu_events (game_id, hand_id, seat, turn_no);
create index on paipu_events (game_id, action);

-- 成績聚合(增量更新;member_rating 的上游)
create table member_stats_agg (
  member_id      bigint not null references members(id) on delete cascade,
  game_type      text   not null,
  period         text   not null,               -- 'lifetime' / '2026-06' ...
  games          int    not null default 0,
  hands          int    not null default 0,
  win_count      int    not null default 0,     -- 胡牌數
  deal_in_count  int    not null default 0,     -- 放槍數
  riichi_count   int    not null default 0,     -- ⚠ 日麻專用指標:引進日麻時啟用;台麻不計
  call_count     int    not null default 0,     -- 吃碰槓數
  rank_sum       int    not null default 0,     -- 名次總和 → 平均順位
  win_points_sum bigint not null default 0,
  updated_at     timestamptz not null default now(),
  primary key (member_id, game_type, period)
);
-- 衍生指標(查詢時計算或物化):
--   胡牌率   = win_count / nullif(hands,0)
--   放槍率   = deal_in_count / nullif(hands,0)
--   平均順位 = rank_sum / nullif(games,0)
--   吃碰槓率   = call_count / nullif(hands,0)
```

## 3. 牌 / 動作編碼

**牌面(`tile`,文字碼):一律兩碼,固定長度(v0.4 修訂)**

> 舊版長度不一(數牌 2 碼 `1m`、字牌 1 碼 `E`、花牌 3 碼 `fl1`),解析與對齊皆不便。v0.4 起**全部統一為 2 碼**:第 1 碼為數字或字母,第 2 碼為類別/區分碼。

| 類別 | 編碼 | 說明 |
|---|---|---|
| 萬 | `1m`–`9m` | 一萬～九萬 |
| 筒 | `1p`–`9p` | 一筒～九筒 |
| **條** | `1t`–`9t` | 一條～九條(台麻稱「條」,不用日麻「索/s」) |
| 風牌 | `E0` `S0` `W0` `N0` | 東 / 南 / 西 / 北 |
| 三元牌 | `B0` `F0` `C0` | 白 / 發 / 中 |
| 花牌(台16) | `H1`–`H8` | 春夏秋冬(`H1`–`H4`)+ 梅蘭竹菊(`H5`–`H8`) |

- **字牌補 `0`**:風牌與三元牌以原字母 + `0` 補足兩碼,`0` 無數值意義,僅為對齊長度。
- **花牌用 `H`**(Hua):避免與三元牌「發 `F0`」的 F 字首混淆。
- **台麻無紅5**:紅五(舊版 `0m/0p/0s`)為日麻寶牌機制,台麻不存在,已自本表移除。若未來引進日麻規則集(`ruleset='jp13'`),另於日麻牌面字典定義(見 §11),不污染台麻牌組。
- **牌組張數**:台16 = 108 數牌(3 花色 × 9 種 × 4)+ 28 字牌(7 種 × 4)+ 8 花牌 = **144 張**;南部台無花則為 136 張。

**動作(`action`):** 以台16為現行規則:`flower`/`replace_flower`(補花)為台麻動作。`riichi`(立直)、`dora_reveal`(寶牌翻示)為**日麻專用動作**,僅保留於 schema,引進日麻規則集(`ruleset='jp13'`)時啟用,台麻現行不使用。「聽牌」可由事件序列推導,不必另存。

`meta` 範例(吃):`{"called_from":2,"meld":["3m","4m","5m"]}`

**摸切 / 手切旗標(v0.4):** 「摸到直接打」與「打手裡的牌」是 L2 牌效分析的重要訊號,雖可由 `draw`+`discard` 事件序列推導,建議在 `discard` 事件的 `meta` 直接標記 `{"from_draw":true}`(該打牌即剛摸進那張=摸到直接打)或 `false`(打的是手裡舊牌=手切),省去查詢時重算。用語一律台麻白話「摸到直接打 / 打手裡的牌」,不用日麻「摸切 / 手切」。

## 4. 來源與信心:資料品質與調和

| 層級 | 來源 | 信心 | 用途 |
|---|---|---|---|
| 局結果(誰胡/放槍/名次/點數) | `table_feed` 全自動桌數位資料、`operator` 記錄員 | 高 | **核心成績**:胡牌率、放槍率、平均順位 |
| 逐張細節(打哪張/吃碰槓/輪次) | `cv` 俯視鏡頭 AI | 中(帶 confidence) | **進階分析 + 回放**:台數效率、聽牌判斷、牌效 |

**調和規則:** 同一事件有多來源時,可信度 `operator > table_feed > cv > online`;保留全部,以最高可信來源為準(`is_corrected` 標記人工覆寫)。

**聚合門檻:** 核心成績只採計「局結果」可靠的局;CV-only 的進階指標需 `confidence >= 門檻`(例如 0.9)才計入官方數字,否則僅作參考或標「推測」。

## 5. 聚合邏輯(虛擬碼)

```text
function onGameFinalized(game):       # game.status -> 'finished' 且通過驗證
  if not game.is_ranked: return
  for p in game_players(game):
    for period in ['lifetime', monthOf(game.ended_at)]:
      upsert member_stats_agg (p.member_id, game.game_type, period):
        games          += 1
        hands          += handsCountIn(game)
        rank_sum       += p.final_rank
        win_count      += handsWonBy(p.seat, game)            # 來自 hands(可靠)
        deal_in_count  += handsDealtInBy(p.seat, game)        # 來自 hands(可靠)
        win_points_sum += pointsWonBy(p.seat, game)
        # 進階(需信心門檻):
        # riichi_count:日麻專用,引進日麻時啟用;台麻不計
        call_count     += confidentEvents(game, p.seat, in ['chi','pon','kan_*'])
  recomputeRating(game)               # 見下

function recomputeRating(game):       # 以名次調整評等(類線上麻將排位機制)
  for p in game_players(game):
    expected = expectedRankScore(member_rating[p.member_id], opponents)
    delta    = K * (rankReward(p.final_rank) - expected)
    member_rating[p.member_id].rating       += delta
    member_rating[p.member_id].games_played += 1
  # 同時把 avg_rank / win_rate / deal_in_rate 由 member_stats_agg 回填 member_rating
```

聚合建議以 Supabase Edge Function 在「對局結束並驗證」事件觸發,或定時批次跑。

## 6.5 段位對照(rating → 熊階梯;前端顯示依據)

> `member_rating.rating` 存的是連續 Elo 分數;**對外顯示的「段位」是把 rating 切成階梯**。切法由設定檔定義,前端與後台共用同一份,確保一致。

**段位階梯(對齊會員端 App 定案):6 階 × 4 級 + 賽季稱號**

| 階(由低到高) | 級 | 說明 |
|---|---|---|
| 銅牌熊 | I / II / III / IV | 入門 |
| 銀牌熊 | I / II / III / IV | |
| 金牌熊 | I / II / III / IV | |
| 白金熊 | I / II / III / IV | |
| 鑽石熊 | I / II / III / IV | |
| 大師熊 | I / II / III / IV | 頂階(段位天花板) |
| **雀神熊** | (無級數) | **賽季稱號**:每季全國/全店排名頂點者獲得,非 rating 階梯,賽季結算後授予 |

- **rating → 階級**:設定檔存每一階每一級的 rating 門檻(例如 銅牌熊 I = 0–99、銅牌熊 II = 100–199…),查詢時把 rating 映射到「金牌熊·II」這種顯示字串。門檻可調(後台設定),不寫死。
- **雀神熊是稱號不是段位**:它不由 rating 決定,而由賽季排名結算授予,存在稱號/成就系統(見會員端),與 `member_rating.rating` 分離。
- **純娛樂麻將也計段位**:只要有開桌消費即計順位 → Elo → 段位;段位看順位/勝負,與桌上是否計積分、輸贏多少無關(守賭博紅線)。

## 7. 賽事回放

回放不需另存資料:取某 `game_id` 的 `paipu_events`,`order by hand_id, turn_no, event_ts`,即可逐輪重播。賽事級(`is_official=true`)因經記錄員校正,回放最完整;一般場以 CV 資料回放,缺漏處以信心值標示。

## 8. 分層儲存與效能

- **熱層:** 近 N 個月的 `paipu_events` 月分區留在 Postgres。
- **冷層 / 資料湖:** 舊分區匯出為 Parquet 進物件儲存,接 ClickHouse / BigQuery 跑跨店分析與 AI 訓練。
- **讀取原則:** 會員儀表板、配桌一律讀 `member_stats_agg` / `member_rating`,**不掃原始事件**。
- 量未起來前(單店),只用 Postgres 分區 + 聚合表即可,先別上資料湖。Schema 先設到位,DB 之後再分層。

---

## 9. 隱私與權限

- 牌譜與成績綁定身分屬個人資料。**分析資料湖一律以假名 `member_key` 取代真實身分**,身分對照表獨立存放、嚴格權限。
- Supabase RLS:會員僅能讀自己的 `member_stats_agg` / `member_rating` / 個人牌譜;聚合運算以 service role 後端執行。
- 會員條款須載明蒐集範圍、用途、保存期限與刪除權。

## 10. 與配桌引擎的接縫

```text
paipu_events ──聚合──▶ member_stats_agg ──回算──▶ member_rating ──即時讀取──▶ 配桌引擎
                                          └──────▶ rankings(店內/全國)
```

`member_rating` 是兩個系統的唯一接點:資料中台負責「寫」(由牌譜回算),配桌引擎負責「讀」(即時媒合)。兩者解耦,各自獨立部署。

## 10. 牌譜完整度分級(v0.2 新增:目標 = 圍棋棋譜等級,每一手皆記錄)

> `paipu_events` 的 schema 本就支援逐手記錄;本節定義「資料怎麼來」的三個等級。
> 人工無法記錄每一手(四家輪轉、秒級牌速),L1 以上一律設備驅動。

| 級 | 內容 | 來源 | 部署 |
|---|---|---|---|
| **L0** | 局結果(誰胡/放槍/台數)+ 將結算 | 店員快速輸入 | 第一階段全桌 |
| **L1** | 牌河逐打 + 吃碰槓 + 攤牌手牌(= 棋譜主譜) | 俯視鏡頭 CV | 第二階段一般營業桌 |
| **L2** | **完整每一手**(含每家摸進的暗牌 + 起手牌) | 四選一(見下):側面鏡頭直拍 / 智慧牌山 / RFID 牌 / 攤牌反推 | 依路線而定,側面鏡頭路線即可用於一般營業桌 |

### L2 四條技術路線(v0.4 新增第 1 條為主路線)

1. **側面鏡頭直拍手牌(v0.4 新增,現階段主路線)**:每家一支側面鏡頭,直接拍該玩家立在面前的手牌,以**快照輪詢 + 前後比對**抓每一手的摸/打(詳見 §10.3 手牌象限)。
   - **不需特殊牌桌或晶片牌**,只需在 L1 俯視之外多四支鏡頭 → 一般營業桌即可部署,成本遠低於牌山序/RFID。
   - **可靠度高於攤牌反推**:反推只對胡牌者成立、且只得「摸過哪些牌」的集合;側面直拍得到「第幾輪摸什麼、打什麼」的時序,四家皆可。
   - **起手牌一併解決**:開局 16 張攤平最好拍,側面直接取得起手牌(見 §10.1)。
   - **殘留死角**:全程手搓、牌背朝外、且摸進後留手不打的牌,側面拍不到 → 由路線 4(攤牌反推)在局末**補該筆殘牌的集合**、標低 confidence(見 §10.3 三方對帳)。此為「主路線 + 局末校驗」而非單獨依賴反推。
2. **牌山序**:全自動桌砌牌時辨識並記錄整座牌山順序 → 配合起莊與摸牌規則,**每家摸進牌可數學推導**,不需「看」暗牌。牌山序 + L1 牌河 + 攤牌 = 完整閉環。**選桌關鍵規格:洗牌機構是否具牌張辨識、可否輸出牌山資料/API。** 旗艦/賽事桌適用。
3. **RFID 牌 + 感應桌面**:逐張即時識別,最精確、成本最高;賽事/直播桌適用。
4. **攤牌反推(零硬體,現作為路線 1 的局末校驗)**:L1 牌河 + 攤牌手牌反推各家摸進序列;多數可唯一確定,推不出者標低 confidence。單用時只對胡牌者成立、且僅得集合非時序,故現定位為**側面鏡頭的補洞校驗**,非獨立主路線。

### Schema 補充

-- 牌山序(每局一筆;來源:智慧桌輸出或 RFID)
create table wall_orders (
  hand_id    bigint primary key references hands(id) on delete cascade,
  tiles      jsonb  not null,        -- 144 張依砌牌順序之牌面陣列
  source     event_source not null,  -- table_feed / operator
  confidence numeric not null default 1.0
);
-- 推導出的摸牌事件寫入 paipu_events(action='draw'),
-- source 標 'table_feed'(牌山推導)或 'cv'(攤牌反推),confidence 隨之。

### 與分析/IP 的關係
- L1 已可支撐:逐輪回放、台數效率、吃碰槓傾向、AI 教練初版。
- L2 才能支撐:完整「上帝視角」回放(同圍棋復盤)、進攻/防守期望值分析、職業賽事轉播疊圖、頂級 AI 訓練資料 —— 此即旗艦店電視牆與牌譜資產的最終形態。

### 10.1 起手牌記錄(v0.2.1 補充)

- 起手牌事件已在 schema(`paipu_events.action='deal'`,每家一筆、tiles 於 meta);本節補「資料怎麼來」。
- **首選(v0.4):側面鏡頭直拍。** 開局每家把 16 張攤平理牌,是整場最容易辨識的一刻(牌面朝上、靜止、無遮擋);每家側面鏡頭直接拍下起手牌,四家皆得,**不需牌山序、不需骰子點數、不需感應桌**。這是側面鏡頭路線(§10 路線 1)的附帶產物。
- **備選:牌山序推導鏈**(旗艦/賽事桌用智慧桌時):牌山序 + 開門位置(骰子點數)+ 固定發牌程序 → 每家起手牌 100% 可推算。若走此路,`hands` 需記錄骰子/開門點——

```sql
alter table hands add column dice_roll smallint;   -- 骰子點數(決定開門位置;僅牌山序路線需要)
-- 來源:智慧桌感應 / 俯視 CV 辨識桌面骰子(高可辨)/ 店員或平板點選(降級)
```

- **末選:L1-only 反推**:攤牌手牌 + 打出的牌 + 吃碰槓可反推起手牌(部分情況有歧義,標低 confidence)。僅在無側面鏡頭時使用。

**解鎖的分析能力:**（v0.4 註:因起手牌改由側面鏡頭直拍取得,以下三項不再受 §10.2「L2 硬體暫不考慮」限制,五鏡頭系統就緒即可做)
1. **運氣/實力分離**:起手牌即算先天牌力(距聽牌張數、潛力值),評等改為「相對於起手牌的表現」——起手牌差守住名次加更多分;運氣評等化的解藥,段位公信力大幅提升。
2. **AI 教練質變**:可給出「起手牌不利但選擇正確」等真回饋。
3. **公正性稽核**:長期起手牌分布統計 → 驗證洗牌隨機性、偵測做牌;公正場認證的數據基礎。

### 10.2 範圍決策(v0.4 修訂)
- **現階段目標:L0 → L1 →(新增)L1+側面鏡頭。** 分三塊:
  - **L0**:店員局結果輸入。
  - **L1**:俯視鏡頭 CV(海底逐打牌序、吃碰槓、攤牌)。
  - **L1+側面(v0.4 新增中間層)**:四支側面鏡頭直拍手牌 → 逐輪摸打 + 起手牌。**用純鏡頭達成過去歸類為 L2 的多數能力,不需智慧牌山/RFID/感應桌。**
- **仍暫不考慮的重硬體**:骰子感應、RFID 牌、智慧牌山桌。相關 schema(`wall_orders`、`dice_roll`)保留,屬「掛起」非「刪除」,旗艦/賽事桌未來可隨時啟用,系統無需改動。
- **從掛起中救回(改由側面鏡頭達成)**:起手牌記錄、四家逐輪摸打、運氣/實力分離評等 → 不再等重硬體,五鏡頭就緒即可做。
- **側面鏡頭仍解不掉的殘留**:全程手搓且留手不打的暗牌時序 → 由攤牌反推在局末補集合、標低 confidence(§10.3)。
- **原型硬體(待《牌譜鏡頭安裝》定案)**:方案二 = 單台 Pi 5 + Hailo 加速棒 + 五支 USB 鏡頭(一俯視、四側面),集中式單主機,先驗證辨識與摸打邏輯;實測算力不足再拆多主機。
- 賽事桌備選(不靠感應):選手同意下之每席手牌鏡頭(M-League 模式),僅限賽事/直播情境。

### 10.3 兩種擷取象限:海底(俯視)vs 手牌(側面)(v0.4 改寫)

台麻的物理現實對「海底」和「手牌」剛好相反,兩者要用不同擷取策略,不可混為一談。

**象限 A:海底 / 棄牌(俯視鏡頭)→ 即時事件擷取**
- **鐵律:台麻打出的牌混丟中央,不排列。** 牌堆「事後」不可讀,故海底**不採快照讀取**,改採**即時事件擷取**:
  - 牌落地瞬間 = 最後一次完整可見 → 當下完成「哪家 + 哪張 + 第幾輪」記錄。哪家可由**逆時針固定輪轉**推定(開局定錨東家後,下一位一定是逆時針下家),不必靠牌落在誰的河判斷。
  - 動作偵測當閘門(有牌飛出才啟動辨識),平時低功耗待機。
  - 吃碰槓 = 取走「最新打出那張」(堆頂、剛記錄過)+ 亮牌落地,會**打斷逆時針輪轉**(跳位),需以吃碰槓事件校正輪轉鏈,避免錯位傳播。

**象限 B:手牌(側面鏡頭,每家一支)→ 快照輪詢 + 前後比對**
- **與海底相反:手牌立在玩家面前是穩定、可重複觀察的**,故手牌**採快照輪詢**(每 1~2 秒掃一張),不需即時事件觸發。
- 流程:輪詢快照 → 輕量畫面差異過濾靜態幀(手沒動就跳過,省算力)→ 有變動才跑 CV 讀全手牌 → 與上一張有效快照**逐張比對** → 分類成摸/打/摸打(摸到直接打 vs 打手裡的牌)→ 標時序上傳。
- **手搓死角**:全程牌背朝外、摸進留手不打的牌,側面讀不到 → 該筆缺口交三方對帳補(見下)。起手牌因攤平最好拍,不受此死角影響。

**三方對帳(v0.4;取代舊版兩方反推)**
局末以三個獨立來源交叉補漏與驗證:
1. **側面摸打流**(象限 B):四家逐輪摸打。
2. **俯視出牌流**(象限 A):海底逐打 + 吃碰槓,含逆時針時序。
3. **攤牌反推集合**:最終手牌 + 全部打出 + 吃碰槓用掉 − 起手牌 = 該家本局摸過的牌集合(僅集合、無時序)。
- **對帳規則**:側面與俯視對得上的打牌 → 互相印證、拉高 confidence;側面漏拍的打牌 → 用俯視補;側面與俯視都沒拍到的摸牌 → 必落在反推集合內,寫入但標低 confidence 且時序標「推測」。
- 官方核心成績仍只採局結果(店員/桌台);CV 事件流供回放與進階分析,矛盾處降信心/標人工抽查。

**硬體影響:** 俯視需連續影像推論(算力較高);側面為輪詢式、負載較輕。單主機集中式(方案二)需實測一台是否同時扛得住一路俯視 + 四路側面,不足則拆主機。列入鏡頭選型核心項。

賽事直播桌未來可另議賽規(轉播可讀性需求);一般營業桌一律以混堆 + 手搓為預設假設,不依賴客人改變打牌習慣。

### 10.4 規則集:南部台(無花)/ 北部台(有花)(v0.2.4)
- **鐵律:北部台有花(144 張)、南部台無花(136 張)。** 主場(高雄)= 南部台 / 無花。
- `games.ruleset` 細分:
  - `tw16_noflower`(南部台)= 136 張;**停用** `flower`/`replace_flower` 補花事件;無花牌計分。
  - `tw16_flower`(北部台)= 144 張(8 花);啟用補花事件;正花/花槓/八仙等花牌計台。

### 10.5 座位 ↔ 會員綁定(seat → member)(v0.4 新增)

> 鏡頭認得的是**座位**不是**人**:`paipu_events` 只記「seat 1 摸一條、打一餅」,不知道 seat 1 是哪位會員。把座位對到會員,**不是鏡頭的工作,是開桌流程的工作**。schema 已預留 `game_players`,本節補「綁定怎麼發生」。

**對齊鏈路**

```
paipu_events(seat)  ──┐
                       ├─ 用 game_id + seat 相接 ─▶  每一手 → member_id → 會員成績
game_players(seat→member_id) ──┘
```

- `paipu_events` 記 `seat`(1~4);`game_players` 記「本對局該 seat 是哪個 `member_id`」;兩者以 `game_id + seat` join,即把「東家的每一手」對應到具體會員。
- **鏡頭不認人**,只需認得「這是第幾家的牌」;人是誰由開桌流程綁定。

**綁定時機(來源:M2 桌台系統開桌 / 報到)**

> **前提:開局四人隨機入座,鏡頭無法自行辨識「哪個座位是哪個會員」。因此「座位 → 會員」的綁定是一個必要的人工步驟,無法自動化,也無法省略。** 以下區分兩件常被混為一談的事:

- **「座位 → 會員」(問題 A):必要人工。** 鏡頭認不出「東邊這人是哪個會員」,一定要有人(店員或客人自己)把四人對到四個座位。這步永遠要做。
- **「出牌起點 / 輪轉方向」(問題 B):可自動。** 擲骰定莊 → 東家座位確定 → 其餘照逆時針推。這步鏡頭可自理,不需認人。

**主力做法(執行問題 A 的人工綁定,擇一或並用):**
1. **店員平板派位**:開桌時店員把四位會員指定到東南西北 → 寫入 `game_players`。
2. **客人自助掃碼**:客人各自 LINE 掃「自己座位」的碼完成綁定 → 把人工從店員分攤到客人,**但判斷「這人=這會員」的動作仍由客人本人完成,不是鏡頭代勞**。

> 上述兩者都是人工,差別只在「誰來輸入」;鏡頭與 QR 只能**減輕輸入負擔**,取代不了「把人對到座位」這個判斷本身。

**輔助(只降低人工負擔,不取代綁定):**
- **開局定錨共用**:擲骰定莊確定的東家座位,同時給鏡頭當「輪轉起點」(問題 B)。此動作**與《牌譜鏡頭安裝規格》§6.1「開局定錨東家」為同一件事**,但它只解決問題 B,**不取代問題 A 的人工綁定**。
- **座位標記輔助**:桌角 QR / 座位牌供客人自助掃碼或俯視讀取,加速派位;有則更省事,無則靠店員派位,不影響運作。

**綁定粒度與邊角處理**

- **綁在「每一對局」,非整晚**:一將打完常換莊 / 換座,故 `game_players` 掛在 `game_id` 底下,每開新對局重新綁一次座位(現行 schema 已如此,無需改動)。
- **中途換人**:有人打一半離開、換人補上 → 開桌系統須記一筆換人事件並在新對局重綁,否則後續事件會算到錯的會員頭上。建議換人一律**結束當前對局、開新對局**處理,保持「一對局內座位對會員固定」的簡單假設。
- **匿名 / 訪客**:非會員入座時 `member_id` 允許為 null(`game_players.member_id` 本就可空),該座位牌譜仍記錄、僅不歸戶到會員成績。

**與成績聚合的關係**:§5 聚合邏輯以 `game_players` 的 `member_id` 為準累計;`member_id` 為 null 的座位不進 `member_stats_agg`(但事件仍存於 `paipu_events` 供回放與匿名分析)。

**未來選項:當日 Re-ID 自動座位(v0.4 增補;省去逐將輸入座位)**

> 原則:**不建人臉/生物特徵資料庫**。身分永遠由櫃檯掃碼確定;影像只做「櫃檯這位 = 座位上這位」的**當日臨時比對**(Re-ID),打烊即刪。

- 流程:
  1. 櫃檯掃碼報到 → 身分由掃碼 100% 確定(不靠臉)。
  2. 報到當下拍一張 → 轉成**臨時特徵向量**,僅掛在「今日這位客人」。
  3. 入座後,桌邊鏡頭偵測到座位上的人 → 與「今日報到名單」的臨時特徵比對(範圍僅當日在店者,比對集合小) → 自動寫入 `game_players` 座位;換將換位、中途換人可持續自動偵測更新。
  4. **當日打烊 → 臨時特徵全數刪除**,不留存。
- 模型組成:偵測用 YOLO(與認牌共用),比對用開源 Re-ID 嵌入模型(如人形 OSNet;拍得到正臉時可用 ArcFace 類)。**人形 Re-ID 可連當日衣著/體型一起比對**,角櫃鏡頭拍不到正臉亦可運作;通用模型即可,無需自行訓練。
- 落地形態:**先半自動**——系統推薦四人座位,POS 一鍵確認後才寫入;誤認率實測夠低再考慮全自動。
- 個資:縱使當日即刪,拍攝與處理仍屬生物特徵處理,**報到時須告知並取得同意**(「僅當日自動入座使用、打烊即刪」);拒絕者掃碼照常消費,座位改手動指定,功能不強制。
- 優先序:配桌體驗優化,**非主線**;於牌譜辨識(認牌)主線驗證後再實作。

### 11.3 鐵則

- **現在不做日麻**:所有日麻項目維持「保留但停用」,不投入開發。
- **台麻是主場**:現行所有成績、段位、統計、配桌一律以台麻為準;文件與介面用台麻用語(輪/吃碰槓/連莊/台/圈風),不用日麻用語(立直/振聽/巡目/副露/本場)。
- **未來引進日麻走「新增規則集」而非「改造台麻」**:兩套規則集並存,靠 `ruleset` 切換,互不干擾。
