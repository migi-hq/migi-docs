# MIGI 麻將連鎖 — 牌譜鏡頭安裝規格 v0.1

> **這是什麼／何時讀**:五鏡頭實體安裝規格(四角置物櫃、俯視吊點、走線供電、原型階段先錄影後上硬體)。要買鏡頭、跟裝潢/木工溝通、或決定要不要先買 Pi 5 時讀這份。

> 範圍:自動牌譜系統的**實體鏡頭配置、硬體方案、供電/網路、安裝位置、校正與健康監看**。
> 這份是《牌譜成績資料中台技術設計 v0.4》§10.2 / §10.3 所引用的「鏡頭安裝(待定案)」實體文件。
> 用語鐵則:台麻用語(輪 / 吃碰槓 / 連莊 / 台 / 圈風);不用日麻用語(立直 / 巡目 / 副露)。
> 摸打分類一律台麻白話:「摸到直接打」/「打手裡的牌」,不用日麻「摸切 / 手切」。
> 現況:規格與原型階段,實體尚未架設;硬體先不採購,待邏輯與算力實測後再選型下單。**現階段先走「錄影 → 事後判讀」驗證,連 Pi 5 / Hailo 都先不用碰(見 §4.4)。**

## 1. 系統總覽:五鏡頭分工

一桌 = 五支鏡頭,分兩種角色。**鏡頭數固定為五,主機數則視方案而定(見 §4)。**

| 鏡頭 | 數量 | 看什麼 | 產出 | 擷取策略 |
|---|---|---|---|---|
| 俯視 | 1 | 海底(棄牌)+ 吃碰槓亮牌 | 逐輪出牌序列(含時序) | 即時事件擷取 |
| 側面 | 4 | 每位玩家自己的手牌 | 每家逐輪摸打 + 起手牌 | 快照輪詢 + 前後比對 |

**兩種擷取策略為何不同(對齊技術設計 §10.3 兩象限):**
- **海底是「事後不可讀」**:台麻打出的牌混丟中央、不排列,所以俯視必須在牌落地瞬間即時擷取,錯過就讀不回來。
- **手牌是「隨時可讀」**:手牌立在玩家面前是穩定的,所以側面用固定頻率輪詢拍照、前後比對即可,不必搶瞬間。

## 2. 鏡頭職責細節

### 2.1 俯視鏡頭(1 支)

- **拍攝範圍**:整桌桌面(海底棄牌區 + 四家吃碰槓亮牌區)。
- **職責**:
  1. 偵測海底多一張牌 → 記錄「哪張牌被打出」。
  2. **歸屬靠逆時針輪轉**:開局定錨東家後,出牌一定照逆時針輪轉,系統靠「上一個出牌者的逆時針下家」推定這張是誰打的,不必真的看到那隻手。
  3. **吃碰槓偵測**:有人吃/碰/槓會亮牌落地,並**打斷逆時針輪轉(跳位)**;俯視要抓到這個事件,用來校正輪轉鏈,避免後面整串歸錯人(錯位傳播)。
- **運算特性**:需連續影像推論(動作偵測當閘門,有牌飛出才啟動辨識),算力負載最高的一支。

### 2.2 側面鏡頭(4 支,一人一支)

- **拍攝範圍**:該玩家立在面前的整副手牌(牌面朝該鏡頭)。
- **職責**:
  1. **起手牌直拍**:開局 16 張攤平理牌時,直接拍下完整起手牌(整場最好拍的一刻)。
  2. **逐輪摸打**:每 1~2 秒拍一張快照,與上一張有效快照逐張比對,算出「摸了什麼、打了什麼」:
     - 多一張 → 摸牌
     - 少一張 → 打牌
     - 多一張又少一張(張數不變)→ 摸打(摸進留手、換別張打)
     - 少 2~3 張且沒摸 → 疑似吃碰槓(牌亮出落地),交俯視確認
  3. **摸到直接打 vs 打手裡的牌**:比對摸進那張與打出那張是否同一張,分類後標 `from_draw` 旗標。
- **權限隔離(天然)**:每支側面鏡頭只看得到「自己這位玩家」的牌面,別家的牌背對著它拍不到 —— 剛好符合麻將資訊不對稱,一人一支、各看各的。

## 3. 實體安裝位置

### 3.1 俯視鏡頭

- **位置**:桌面正上方、垂直朝下(鳥瞰視角)。
- **要點**:高度要能吃到整張桌面;避免頂燈造成反光/陰影;鏡頭與主機用短排線相連時主機需一併吊裝(方案二改用 USB 線則主機可落地,見 §4)。

### 3.2 側面鏡頭(關鍵:牌面朝哪,由玩家決定,不是鏡頭)

搓牌的人手牌**立起、牌面朝自己胸口**,牌背朝桌外。因此「一目了然拍到牌面」的**唯一角度是與玩家同側**:

- **建議位置**:每位玩家的**頭頂偏後、朝下俯拍**,鏡頭視線與玩家自己看牌的視角接近 → 牌面對玩家、也就對這支鏡頭。
- **不可行位置**:玩家正對面(拍到牌背)、正側面(拍到牌的窄邊)——都讀不到牌面。
- **實體限制**:玩家背後常是椅背/牆/走道,支架要伸到頭頂後方朝下,需固定牢、不擋人、不被身體晃到遮住。這是**靜態、喬一次就穩定**的問題,比「搶拍瞬間」好解。

### 3.3 桌面配置示意

```
                   [俯視鏡頭] ← 桌面正上方朝下
                        │
        玩家3手牌 ─────┼───── 側3(玩家3頭頂偏後朝下)
              │      海底     │
   側4 ── 玩家4    (混堆棄牌)   玩家2 ── 側2
              │   吃碰槓亮牌   │
        側1 ─────────┼───────── 玩家1手牌
                        │
                  (四支側面各自對準一位玩家的牌面)
```

## 4. 硬體方案

### 4.1 現階段採用:方案二(單主機集中式)

**一台 Pi 5 + Hailo 加速棒 + 五支 USB 鏡頭。**

- **為何集中式**:原型階段的目標是先驗證「辨識準不準、摸打邏輯對不對」,單一主機**最好裝、最好除錯、最少東西出包**。把「多主機時鐘同步」「多節點 Wi-Fi 斷線」這兩個最容易出包的變數直接消掉,專心搞定核心。
- **鏡頭型式**:五支一律用 **USB 鏡頭**(不用樹莓派 CSI 排線相機)——USB 線才牽得夠遠,讓五支擺到各自位置又接回同一台主機。
- **每支鏡頭 vs 主機**:五支 USB 鏡頭全部連回這一台 Pi 5;資料在同一台機器內,**時序天生同步**,不需跨機對時。

### 4.2 供電與網路

| 項目 | 規格 | 說明 |
|---|---|---|
| 主機電源 | Pi 5 官方 27W USB-C 供電 | Pi 5 較耗電,不可用一般手機充電器,力道不足會不穩 |
| USB 供電 | **獨立供電 USB Hub(必備)** | 五支 USB 鏡頭同時接一台,主機 USB 埠帶不動,需外接有獨立電源的 Hub |
| 網路 | Wi-Fi | Pi 5 內建;牌桌位置訊號要夠強。只有「一台」要連網,不像五主機版要顧五個 |
| 插座需求 | 主機 1 + USB Hub 1 | 集中式只需 2 個插頭(對比五主機版的 5 個) |

### 4.3 算力風險(方案二最大未知數)

**一台 Pi 5 是否同時扛得住「一路俯視即時追蹤 + 四路側面輪詢」,必須實測,現在不能打包票。**

- 俯視是連續影像推論、最吃力;四路側面是輪詢式、負載較輕,但四路疊加仍是壓力。
- Hailo 加速棒分擔推論負載,理論上可行,但要跑過真實負載才算數。
- **若實測不足** → 走升級路線(§7)。

### 4.4 原型驗證階段:先錄影、事後跑(不做即時,先不碰 Pi 5 / Hailo)⭐

在方案二(即時系統)之前,**現階段先走「錄影 → 事後判讀」**。這是驗證期最省錢、最務實的做法。

**做法**
1. 用一般攝影機 / 手機(俯視一支、側面幾支)**真的錄下幾場牌**。
2. 影片丟進電腦,抽格成一張張圖。
3. 拿這些**真實畫面**測辨識準度、餵 `hand_tracker` 的摸打比對邏輯。
4. 邏輯與辨識都驗證通過,再決定要不要升級成即時系統(方案二)。

**錄影事後跑幫你省掉的**
- 不用即時運算 → **現階段連 Pi 5、Hailo、邊緣運算盒都不用買**,一般攝影機錄檔即可。
- 不用搶拍時機 → 影片連續,每一格都在,不會錯過摸牌瞬間。
- 可重複重跑 → 模型改好後,同一支影片可重算;即時系統錯過就沒了。

**錄影事後跑「不會」幫你省掉的(難度只是搬家,沒消失)**
- **辨識準度不變**:事後判讀不會讓 AI 更會認牌;且錄影常比即時更糊(固定幀率硬錄,手在動、牌在晃的幀一樣糊)。辨識準不準這個核心難題,錄影沒解決。
- **物理死角不變**:手搓、牌背朝外、被手擋住 → 錄影一樣拍不到牌面。攝影機位置(側面要在玩家頭頂偏後拍牌面)跟即時系統一模一樣。AI 再強也看不到畫面裡根本沒出現的牌背。
- **模型與邏輯照樣要做**:目前沒有現成 AI 能「吃一支麻將影片、吐一份牌譜」。該訓練的台麻辨識模型、該寫的摸打比對邏輯(即 `hand_tracker` 那套)一個都少不了,只是從「邊算邊餵」改成「餵錄好的影片」。
- **事後處理的新麻煩**:多支影片要對時間軸、影片檔大、跑一場要花時間。

**定位**:錄影事後跑是**原型驗證期的階段方案**,不是最終形態。驗證通過後,若要做成牌桌常駐、即時出牌譜,再評估升級為方案二(即時)或維持錄影批次處理。

**開發順序(對齊全案)**:假資料驗邏輯(`hand_tracker` 已做)→ **錄影真實畫面驗辨識 + 邏輯(本階段)** → 才談即時硬體(方案二 / §7)。

## 6. 部署與運行流程

### 6.1 開局定錨(每局必做)

逆時針輪轉鏈需要起點,每局開始要確定「東家是誰、從誰開始」:
- 首選:俯視辨識擲骰 / 開門。
- 降級:開局由店員或玩家按一顆鈕標記東家。

### 6.2 逐輪擷取

- 俯視:動作偵測閘門 → 牌落地瞬間記「哪家 + 哪張 + 第幾輪」。
- 側面:輪詢快照 → 輕量差異過濾靜態幀 → 有變動才跑辨識 → 前後比對算摸打。

### 6.3 局末三方對帳(對齊技術設計 §10.3)

局末以三個獨立來源交叉補漏:
1. 側面摸打流(四家逐輪摸打)
2. 俯視出牌流(海底逐打 + 吃碰槓 + 逆時針時序)
3. 攤牌反推集合(最終手牌 + 全部打出 + 吃碰槓用掉 − 起手牌 = 本局摸過的牌集合)

側面與俯視對得上 → 拉高信心;側面漏拍的打牌 → 俯視補;兩者都沒拍到的摸牌 → 必落在反推集合內,寫入並標低信心、時序標「推測」。

### 6.4 一致性檢查

- 每隔幾輪核對:**海底牌河總數 = 各家棄牌數加總**,抓輪轉錯位。
- 攤牌時以手牌 + 吃碰槓紀錄反向對帳,矛盾處降信心、標人工抽查。

### 6.5 健康監看(多節點系統的必要防呆)

即使方案二只有一台主機,五支鏡頭仍可能單支故障(鬆脫、遮擋、失焦)。系統需回報「五支鏡頭此刻是否都正常出圖」,某支掛掉要能告警,避免那一路資料默默漏掉還以為牌譜完整。

## 7. 升級路線(原型 → 產品化)

| 觸發條件 | 升級方向 |
|---|---|
| 一台 Pi 5 扛不住五路 | **方案三**:俯視獨立一台 Pi 5(+ 加速棒),四側面共用另一台 → 兩主機 |
| 兩台仍不足 / 要更強推論 | 中央主機改用 **NVIDIA Jetson Orin** 系列(AI 邊緣運算,GPU 較強) |
| 要做多桌 / 加盟量產 | **方案一**:一鏡頭一主機的分散式架構,擴充彈性最大 |
| 覺得視覺死角(手搓/遮擋)無法接受 | **感應桌 / RFID 晶片牌**(不靠視覺,準確率天生 100%);完全不同硬體類別與成本量級,屬旗艦/賽事桌選項 |

原型驗證成功前,不投入上述升級。

## 8. 已知限制與退化行為

- **手搓全程牌背 + 摸進留手不打**:側面讀不到該張,靠三方對帳補「集合」(知道摸過、不知第幾輪),牌譜該格標低信心 → **優雅退化,不整份崩壞**。該牌通常後續某輪會被打出(俯視看到)或胡牌/流局攤牌時現形。
- **摸到直接打且只拍到休息態(16→16 無變化)**:側面看不到 → 該張打牌由俯視海底補。
- **辨識出錯 / 牌數對不上**:標記異常、需人工複查,**但不丟資料**(append-only)。
- **官方成績不受影響**:核心成績(誰胡 / 放槍 / 名次 / 台數)仍以局結果(店員 / 桌台)為準;鏡頭 CV 事件流供回放與進階分析,低信心資料存而不污染官方數字。

## 9. 與資料中台的接縫

```
五鏡頭辨識 ──(即時 insert)──▶ paipu_events(source='cv', 帶 confidence)
                                        │
                          局末三方對帳、補漏、標信心
                                        │
                                ──聚合──▶ member_stats_agg / member_rating
```

- 側面與俯視事件一律寫入 `paipu_events`,`source='cv'`,各帶 `confidence`。
- 用同一個 `game_id` / `hand_id` / `turn_no` 串起四家側面 + 俯視,拼成一局完整牌譜。
- 欄位與編碼對齊《牌譜成績資料中台技術設計 v0.4》§2、§3(牌面碼、`from_draw` 旗標等),三邊(鏡頭 / Supabase / 前端 viewer)講同一套語言。
