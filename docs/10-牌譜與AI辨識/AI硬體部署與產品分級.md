## 0. ⚠ 與既有文件的三處差異(先讀這段)

### 0.1 🔴 側面鏡頭角度 —— 以既有文件為準,v1.0 那個角度會拍到牌背

v1.0 §10 寫「安裝於每位玩家的**左前方或右前方**,低角度斜向看牌面」。

**這在台麻是錯的。** 搓牌的人手牌**立起、牌面朝自己胸口**,牌背朝桌外 ——
從玩家左前方或右前方拍,看到的是牌背或牌的窄邊,不是牌面。

正解見《牌譜鏡頭安裝規格》§3.2:**玩家頭頂偏後、朝下俯拍**,
鏡頭視線與玩家自己看牌的視角接近,牌面對玩家也就對這支鏡頭。

> v1.0 有一句是對的:「不建議直接從正上方拍立起來的手牌,因為牌面可能被角度遮住」。
> 那與「頭頂偏後」不衝突 —— 正上方看到的是牌的上緣,**偏後**才吃得到牌面。

### 0.2 🟡 主機選型 —— 不是衝突,是不同規模

v1.0 假設「NVIDIA RTX GPU 的 Windows/Linux 主機」,既有文件寫 Pi 5 + Hailo。
兩者講的是不同東西:

- **Pi 5 + Hailo**:單桌原型(既有文件 §4.1)
- **RTX / Jetson 級主機**:多桌集中式(本文件 §3、§4)

⚠ **現階段兩者都不買。** 既有文件 §4.4 定案是「先錄影、事後判讀」,
連 Pi 5 都先不碰。v1.0 的 Phase 1(手機錄影測試)與那個決定一致。

### 0.3 ✅ 資料路徑改用 SQLite 緩衝 —— 採納 v1.0

既有文件 §9 寫的是「五鏡頭辨識 ──(即時 insert)──▶ `paipu_events`」。
v1.0 §3 主張中間加一層本地 SQLite,網路恢復後再同步。**採納。**

理由比 v1.0 講的更強:**牌譜是不可重建的資料。**
台麻打出的牌混丟中央、不排列,海底「事後不可讀」(既有文件 §1)——
斷網那幾分鐘漏掉的輪次,事後沒有任何方法補回來。

而且**沒有人會發現**:POS 結帳失敗店員當場就知道(收不到錢),
但牌譜少幾輪不會有任何症狀,直到有人回放牌局才發現缺一段。

```
Camera → YOLO → tracker → game_engine → event_writer
                                              ↓
                                          SQLite(本地,離線照寫)
                                              ↓
                                        Sync Service
                                              ↓
                                    Supabase paipu_events
```

⚠ 同步端要有**冪等鍵**,否則重送會寫出重複事件 ——
與 POS 的 `idempotency_key` 同一個道理(見硬規則與 `checkout_tx` 的作法)。

## 1. 產品三級

三級**共用同一套 AI Core**(YOLO / tracker / game_engine / event schema / SQLite / Supabase),
差別只在影像輸入與硬體配置。

| | MIGI AI Home | MIGI AI Club | MIGI AI Pro |
|---|---|---|---|
| 對象 | 家用、朋友局 | 固定私場、小型麻將館、加盟據點 | 正式麻將館、直營店 |
| 鏡頭 | 2~4 支 | 4~5 支 | **5 支/桌**(1 俯視 + 4 側面) |
| 連接 | USB + 快拆支架 | PoE Camera + PoE Switch | 集中式 PoE + CAT6 |
| 主機 | AI Box | AI Box(內建 PoE Switch) | AI Server(多桌共用) |
| 安裝 | 不施工,打完收起來 | 固定安裝 | 需施工、拉線 |

**Home / Club 的鏡頭數少於 5 支,代表牌譜完整度會降。**
少了俯視就沒有海底事件、少了某一家的側面就少那家的摸打流 ——
三方對帳(既有文件 §6.3)會退化成兩方甚至一方。
賣這兩級時要講清楚「能記到什麼程度」,不要讓客戶以為跟 Pro 一樣。

## 2. 私場加盟的限制

私場(客廳、社區活動室、簡易包廂)通常**不能施工、不能拉 CAT6、場地可能更換**,
所以不能要求天花板施工 + 弱電箱 + 機櫃。

**MIGI AI Kit** 的目標:

```
打開箱子 → 固定 Camera → 插線 → 開機 → App 自動校正 → 開始
```

目標 **5~10 分鐘完成安裝**。

固定方式用 Super Clamp / Magic Arm / 桌邊夾具 / 燈架,不鑽天花板。
未來可開發官方 Camera Mount,針對標準麻將桌設計固定位置與高度。

### 兩種連接方案

| | 方案 A:USB | 方案 B:AI Box + PoE |
|---|---|---|
| 接法 | Camera ×4 → 供電 USB Hub → AI Box | Camera → RJ45 → AI Box(內建 PoE Switch) |
| 優點 | 開發快,OpenCV 直接讀 | 線材乾淨、距離不受限、最適合產品化 |
| 缺點 | 線亂、Hub 穩定性待測、長線有距離限制 | 硬體成本較高 |
| 定位 | MVP / 研發原型 | 未來的加盟標準品 |

## 3. 正式門市網路架構(Pro)

每支鏡頭一條 **CAT6**,同一條線供電 + 傳影像(PoE)。

```
Main Camera ─┐
Camera N ────┤
Camera E ────┼── CAT6 ──▶ PoE Switch ──LAN──▶ AI Server
Camera S ────┤
Camera W ────┘
```

**正式門市不需要** HDMI 擷取卡、DeckLink、USB Hub —— 那些是原型階段的臨時作法。

---

## 4. 多桌擴充

4 張桌 = **20 支鏡頭**。

```
桌1(5) ┐
桌2(5) ├── PoE Switch ── AI Server ── SQLite ── Internet ── Supabase
桌3(5) │
桌4(5) ┘
```

⚠ **「一台 AI Server 帶幾張桌」現在不能定,必須實測。**
未來要決定的:GPU 型號、是否每 2~4 桌一組 Server、RAM/SSD 規格、網路頻寬。

### 推理頻率要分級,不要每支都跑滿

20 支鏡頭都跑 30 FPS 是純粹浪費 GPU。

| 鏡頭 | 用途 | 頻率 |
|---|---|---|
| 主(俯視) | 桌面事件、牌落地瞬間 | 較高 —— 錯過就讀不回來 |
| 玩家側面 ×4 | 手牌確認 | 中低 —— 手牌隨時可讀,不必搶瞬間 |

再加動態調節:**偵測到動作才提高頻率,靜止就降下來。**
這與既有文件 §6.2 的「動作偵測閘門 / 輕量差異過濾靜態幀」是同一件事的硬體側說法。

## 5. 研發順序(五階段)

**不要直接採購 20 支鏡頭。**

| 階段 | 做什麼 | 現況 |
|---|---|---|
| 1 | 手機錄影 → 桌機跑 YOLO,驗證台麻辨識模型 | **← 現在在這裡**(既有文件 §4.4) |
| 2 | 單鏡頭原型:驗牌大小、焦距、光線、安裝高度、辨識率 | |
| 3 | 單桌雙視角:驗摸牌、打牌、手牌前後變化、交叉驗證 | |
| 4 | 單桌完整系統(1 俯視 + 4 側面)接完整資料鏈 | |
| 5 | 門市壓力測試(4 桌 20 鏡頭):GPU/CPU/頻寬/SSD/長時穩定/斷線恢復 | |

壓力測試完成後才決定 AI Server 數量、GPU 型號、PoE Switch 規格。

---

## 6. 標準化比鏡頭數量重要

> AI 的成功關鍵不是用最多鏡頭,而是**讓鏡頭位置、視角、光線與麻將桌保持標準化**。

環境標準化之後,模型不必為了應付各種奇怪角度而變大 ——
比單純追求更大的 YOLO 模型更容易達到穩定辨識。

未來要建立的標準(**數值現在不能猜,要用真實麻將桌測**):

- Camera Mount / Position / Height Standard
- Lighting Standard
- AI Calibration Board

待測項目:桌面尺寸、天花板高度、玩家距離、麻將牌尺寸、鏡頭焦距、
Sensor Size、光線、遮擋情況。
