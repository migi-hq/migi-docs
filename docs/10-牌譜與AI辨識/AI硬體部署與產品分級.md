## 0. ⚠ 與既有文件的三處差異(先讀這段)

### 0.1 🔴 側面鏡頭角度 —— 以既有文件為準,v1.0 那個角度會拍到牌背

v1.0 §10 寫「安裝於每位玩家的**左前方或右前方**,低角度斜向看牌面」。

**這在台麻是錯的。** 搓牌的人手牌**立起、牌面朝自己胸口**,牌背朝桌外 ——
從玩家左前方或右前方拍,看到的是牌背或牌的窄邊,不是牌面。

正解見《牌譜鏡頭安裝規格》§3.2:**玩家頭頂偏後、朝下俯拍**,
鏡頭視線與玩家自己看牌的視角接近,牌面對玩家也就對這支鏡頭。

> v1.0 有一句是對的:「不建議直接從正上方拍立起來的手牌,因為牌面可能被角度遮住」。
> 那與「頭頂偏後」不衝突 —— 正上方看到的是牌的上緣,**偏後**才吃得到牌面。

### 0.2 🟡 主機選型 —— 不是衝突,是不同規模

v1.0 假設「NVIDIA RTX GPU 的 Windows/Linux 主機」,既有文件寫 Pi 5 + Hailo。
兩者講的是不同東西:

- **Pi 5 + Hailo**:單桌原型(既有文件 §4.1)
- **RTX / Jetson 級主機**:多桌集中式(本文件 §3、§4)

⚠ **現階段兩者都不買。** 既有文件 §4.4 定案是「先錄影、事後判讀」,
連 Pi 5 都先不碰。v1.0 的 Phase 1(手機錄影測試)與那個決定一致。

### 0.3 ✅ 資料路徑改用 SQLite 緩衝 —— 採納 v1.0

既有文件 §9 寫的是「五鏡頭辨識 ──(即時 insert)──▶ `paipu_events`」。
v1.0 §3 主張中間加一層本地 SQLite,網路恢復後再同步。**採納。**

理由比 v1.0 講的更強:**牌譜是不可重建的資料。**
台麻打出的牌混丟中央、不排列,海底「事後不可讀」(既有文件 §1)——
斷網那幾分鐘漏掉的輪次,事後沒有任何方法補回來。

而且**沒有人會發現**:POS 結帳失敗店員當場就知道(收不到錢),
但牌譜少幾輪不會有任何症狀,直到有人回放牌局才發現缺一段。

```
Camera → YOLO → tracker → game_engine → event_writer
                                              ↓
                                          SQLite(本地,離線照寫)
                                              ↓
                                        Sync Service
                                              ↓
                                    Supabase paipu_events
```

⚠ 同步端要有**冪等鍵**,否則重送會寫出重複事件 ——
與 POS 的 `idempotency_key` 同一個道理(見硬規則與 `checkout_tx` 的作法)。

### 0.4 🔴 v1.0 §14「方案 A 桌框整合、四角藏鏡頭」對手牌鏡頭不成立

這是 §0.1 的直接推論：桌框、桌角都在**玩家前方或側前方**，從那裡看手牌一樣只看得到牌背。
⇒ **手牌鏡頭不可能藏進桌子裡**，只能在玩家後上方（吊架、燈架、座椅後方的柱子、天花板吊點）。

能整合進桌子的只有兩樣：
- **俯視鏡頭**：可以跟桌子正上方的燈具一起設計（不是桌框，是燈）
- **計分板**：已經是每桌的固定設備，日後可以內建進桌面（與桌廠的簡報談的就是這個）

⚠ 《牌桌區裝潢預留需求清單》原本寫「側面鏡頭藏在四角置物櫃、高約 80–90cm」——
那個高度在玩家側前方，同樣會拍到牌背，**已同日更正**（見那份文件）。

## 1. 產品三級

三級**共用同一套 AI Core**(YOLO / tracker / game_engine / event schema / SQLite / Supabase),
差別只在影像輸入與硬體配置。

| | MIGI AI Home | MIGI AI Club | MIGI AI Pro |
|---|---|---|---|
| 對象 | 家用、朋友局 | 固定私場、小型麻將館、加盟據點 | 正式麻將館、直營店 |
| 鏡頭 | 2~4 支 | 🆕 **1 支起**（只裝俯視，見 §8），要逐手重播再加到 5 支 | **5 支/桌**(1 俯視 + 4 側面) |
| 連接 | USB + 快拆支架 | PoE Camera + PoE Switch | 集中式 PoE + CAT6 |
| 主機 | AI Box | AI Box(內建 PoE Switch) | AI Server(多桌共用) |
| 安裝 | 不施工,打完收起來 | 固定安裝 | 需施工、拉線 |

**Home / Club 的鏡頭數少於 5 支,代表牌譜完整度會降。**
少了俯視就沒有海底事件、少了某一家的側面就少那家的摸打流 ——
三方對帳(既有文件 §6.3)會退化成兩方甚至一方。
賣這兩級時要講清楚「能記到什麼程度」,不要讓客戶以為跟 Pro 一樣。

## 2. 私場加盟的限制

私場(客廳、社區活動室、簡易包廂)通常**不能施工、不能拉 CAT6、場地可能更換**,
所以不能要求天花板施工 + 弱電箱 + 機櫃。

**MIGI AI Kit** 的目標:

```
打開箱子 → 固定 Camera → 插線 → 開機 → App 自動校正 → 開始
```

目標 **5~10 分鐘完成安裝**。

固定方式用 Super Clamp / Magic Arm / 桌邊夾具 / 燈架,不鑽天花板。
未來可開發官方 Camera Mount,針對標準麻將桌設計固定位置與高度。

### 兩種連接方案

| | 方案 A:USB | 方案 B:AI Box + PoE |
|---|---|---|
| 接法 | Camera ×4 → 供電 USB Hub → AI Box | Camera → RJ45 → AI Box(內建 PoE Switch) |
| 優點 | 開發快,OpenCV 直接讀 | 線材乾淨、距離不受限、最適合產品化 |
| 缺點 | 線亂、Hub 穩定性待測、長線有距離限制 | 硬體成本較高 |
| 定位 | MVP / 研發原型 | 未來的加盟標準品 |

## 3. 正式門市網路架構(Pro)

每支鏡頭一條 **CAT6**,同一條線供電 + 傳影像(PoE)。

```
Main Camera ─┐
Camera N ────┤
Camera E ────┼── CAT6 ──▶ PoE Switch ──LAN──▶ AI Server
Camera S ────┤
Camera W ────┘
```

**正式門市不需要** HDMI 擷取卡、DeckLink、USB Hub —— 那些是原型階段的臨時作法。

## 4. 多桌擴充

4 張桌 = **20 支鏡頭**。

```
桌1(5) ┐
桌2(5) ├── PoE Switch ── AI Server ── SQLite ── Internet ── Supabase
桌3(5) │
桌4(5) ┘
```

⚠ **「一台 AI Server 帶幾張桌」現在不能定,必須實測。**
未來要決定的:GPU 型號、是否每 2~4 桌一組 Server、RAM/SSD 規格、網路頻寬。

### 推理頻率要分級,不要每支都跑滿

20 支鏡頭都跑 30 FPS 是純粹浪費 GPU。

| 鏡頭 | 用途 | 頻率 |
|---|---|---|
| 主(俯視) | 桌面事件、牌落地瞬間 | 較高 —— 錯過就讀不回來 |
| 玩家側面 ×4 | 手牌確認 | 中低 —— 手牌隨時可讀,不必搶瞬間 |

再加動態調節:**偵測到動作才提高頻率,靜止就降下來。**
這與既有文件 §6.2 的「動作偵測閘門 / 輕量差異過濾靜態幀」是同一件事的硬體側說法。

## 5. 研發順序(v1.1 調整)

**不要直接採購 20 支鏡頭。**

| 階段 | 做什麼 | 現況 |
|---|---|---|
| 🆕 0 | **先用計分板已經有的資料**：每一局的莊家、誰胡、誰放槍、台數、牌型（`hands`），不需要任何硬體 | ✅ **已經在累積**（2026-10-26：3,635 局、55 場） |
| 1 | 手機錄影 → 桌機跑 YOLO,驗證台麻辨識模型 | **← 現在在這裡**(既有文件 §4.4) |
| 2 | 🆕 **先驗玩家鏡頭的位置**：一支鏡頭裝在玩家頭頂偏後，實拍確認牌面拍得清楚（含焦距、光線、搓牌時手的遮擋） | |
| 3 | 單鏡頭俯視原型：驗牌落地瞬間的擷取、河牌與副露、反光 | |
| 4 | 單桌完整系統(1 俯視 + 4 側面)，接上計分板錨點與完整資料鏈 | |
| 5 | 門市壓力測試(4 桌 20 鏡頭):GPU/CPU/頻寬/SSD/長時穩定/斷線恢復 | |

🎯 **第 2 階段改成先測玩家鏡頭，不是先測主鏡頭**：整套方案最大的未知數是「從哪裡拍得到立起來的手牌」，
v1.0 原稿就在這一點寫錯（§0.1、§0.4）。主鏡頭從正上方拍平放的牌，風險小很多，排在後面。

壓力測試完成後才決定 AI Server 數量、GPU 型號、PoE Switch 規格。

## 6. 標準化比鏡頭數量重要

> AI 的成功關鍵不是用最多鏡頭,而是**讓鏡頭位置、視角、光線與麻將桌保持標準化**。

環境標準化之後,模型不必為了應付各種奇怪角度而變大 ——
比單純追求更大的 YOLO 模型更容易達到穩定辨識。

未來要建立的標準(**數值現在不能猜,要用真實麻將桌測**):

- Camera Mount / Position / Height Standard
- Lighting Standard
- AI Calibration Board

待測項目:桌面尺寸、天花板高度、玩家距離、麻將牌尺寸、鏡頭焦距、
Sensor Size、光線、遮擋情況。

🆕 **Lighting Standard 要寫具體**：麻將牌面是亮面，在正上方的點光源下會整片反白。
⇒ 用**柔光、面光源**，避免俯視鏡頭旁邊就是燈泡；反光仍然太強時，鏡頭加**偏光鏡**。
這一項跟裝潢一起定（吊燈與俯視鏡頭本來就在同一個位置）。

## 7. 🆕 計分板當錨點：AI 只補「中間每一手」，不從零猜

v1.0 的 `game_engine` 要自己判斷誰坐哪、誰是莊、第幾局、誰胡、誰放槍。
**這些智慧計分板現在都已經知道，而且是四家確認過的：**

| 計分板已經有的 | 在哪 |
|---|---|
| 座位 ↔ 會員 | `session_players`（計分板「我是誰」選人） |
| 這一將的座位順序、起莊 | `session_rounds.seat_ring`／`first_dealer_seat` |
| 每一局的莊家、連莊、圈風 | `hands.dealer_seat`／`renzhuang`／`wind` |
| 誰胡、自摸或放槍、台數、牌型 | `hands.result`／`winner_seat`／`deal_in_seat`／`tai_pattern`／`patterns` |
| 局的開始與結束時間 | `hands.created_at`／`confirmed_at` |

⇒ AI 的工作縮小成：**在計分板的兩個事件之間，補出每一手摸了什麼、打了什麼。**
- 局界由計分板給，AI 不用自己判斷「這一局結束了沒」
- 座位綁會員由計分板給，鏡頭只要綁座位（v1.0 §11 那一半是對的）
- 胡牌結果可以拿來**驗證** AI：計分板說東家自摸 4 台，AI 推出來的手牌湊不出 4 台，就知道那一局辨識有問題，標成低信心

🎯 這也是研發第 0 階段的意思：胡牌率、放槍率、自摸率、連莊、牌型分布 **今天就算得出來**，不必等鏡頭。

## 8. 🆕 鏡頭分階段加：Club 從 1 支開始

| 裝了什麼 | 拿得到 | 拿不到 |
|---|---|---|
| **只有俯視 1 支** | 打出的每一張牌、吃碰槓、補花、河牌順序 ⇒ 吃碰槓率、副露統計、放槍的那張牌 | 每個人手上有什麼、摸了什麼 |
| **俯視 ＋ 手牌 4 支** | 上面全部 ＋ 每一手摸打 ⇒ 逐手重播、AI 教練、牌效分析 | — |

⇒ **Club 等級可以每桌 1 支起步**，客人要逐手重播或店家要做 AI 教練時再加手牌鏡頭。
每桌從 5 支降到 1 支，硬體與施工成本是好幾倍的差距，而且俯視鏡頭沒有「拍到牌背」的風險。

⚠ 只有俯視時，海底事件（誰打了哪張）仍然要在**牌落地的瞬間**抓：
台麻的海底混在一起，事後回頭看分不出是誰打的（既有文件 §1）。這是主鏡頭推理頻率不能降的真正原因。

## 9. 🆕 🔴 防作弊與隱私：手牌畫面絕對不能即時給任何人看

手牌鏡頭拍到的是**每個人的底牌**。這一節 v1.0 完全沒有，但它是上線的前提：

| 規則 | 理由 |
|---|---|
| **不提供任何即時畫面**（包括店員、老闆、同桌的人） | 能即時看到別人底牌的系統，本身就是作弊工具 |
| 只保留辨識結果，**原始影片限時自動刪除**（例如當日打烊） | 留著就是外洩風險，而辨識結果已經足夠 |
| 逐手重播只在**這一局結束之後**才開放，而且只給同桌四人 | 打的當下看得到別人的牌，就不是重播是偷看 |
| 存取原始影片要有紀錄，誰在什麼時候看了哪一段 | 有爭議時才查得到 |
| 第一次入座前告知並取得同意（個資法第 8 條） | 拍攝顧客要告知目的與保存期限 |
| 鏡頭畫面盡量不入臉（取景只到手牌區） | 減少個資範圍；Re-ID 另有自己的同意流程（《當日 Re-ID 座位比對實作》） |

⚠ **賭博紅線也在這裡**：系統只記牌與台數，**永遠不顯示、不計算金錢**。

## 10. 🆕 成本與授權（v1.0 全文沒有金額）

- **先定每桌硬體預算上限，再回頭選型。** 沒有上限的話，沒辦法判斷一個方案能不能賺回來。
  直營店 14 桌 × 5 支 ＝ **70 支鏡頭**，而 Club 若從 1 支起步只要 14 支。
- 要估的項目：鏡頭 × 支數、PoE Switch、AI Box／Server、支架、施工拉線、燈具調整、每年的維護與更換。
- 🔴 **YOLO11 是 AGPL-3.0／Enterprise 雙授權**：閉源商用前要確認企業授權，或請律師確認 AGPL 義務
  （《台麻 AI 辨識實作指南》§2.1）。POC 不受影響，賣給加盟或私場之前必辦。

## 11. 🆕 更短的一條路：跟電動麻將桌廠商要資料

電動麻將桌的洗牌機本來就會碰到每一張牌。如果桌子能**輸出牌山順序**，
或在桌面**感應打出的牌**，就能跳過大部分鏡頭（《牌譜成績資料中台技術設計》的 `table_feed` 來源）。

跟桌廠談的時候，問題清單：
1. 洗牌機能不能記錄並輸出牌山順序？用什麼介面（USB、序列埠、網路、API）？
2. 桌面有沒有感應器能知道哪個位置放了牌？
3. 計分板能不能內建進桌面（電源、固定位置、平板尺寸）？
4. 桌上的燈具能不能預留俯視鏡頭的位置？
5. 開放資料介面的條件與費用

⚠ 不採用晶片牌（RFID）的理由仍然成立（作弊聯想、品牌定位，見《RFID-NFC 晶片牌可行性評估》）——
這裡問的是**桌子本身的機構**，不是在牌裡放晶片。
