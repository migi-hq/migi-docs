# MIGI 總部後台（HQ）架構藍圖 v1.1

> **這是什麼**：總部後台的模組架構與實作優先序。
> **什麼時候讀**：規劃或實作 HQ 新模組（券管理、會員、報表）時。


> 定位：**總部後台 = hq.migi.tw**，與門市 POS（pos.migi.tw）是**兩個獨立前端、共用同一 Supabase**。
> 用途：跨全集團的「建檔與策略」——商品、券、會員、報表、門市、加盟。
> 這是「POS 能接真實資料」的前提：HQ 在資料庫建了商品/發了券，POS 才撈得到。
> 本文件是規劃藍圖，非程式碼。確認方向後逐模組實作。

## 一、系統定位（兩個系統的邊界）

| | 總部後台 HQ | 門市 POS |
|---|---|---|
| 網址 | hq.migi.tw | pos.migi.tw |
| 誰用 | 總部管理者、行銷、老闆 | 單店店長、店員 |
| 管什麼 | 建檔與策略（商品/券/會員/報表/門市） | 當下營運（開桌/收桌/結帳/配桌） |

| 權限差異 | 總部角色（總部管理/行銷/唯讀…） | 店長 vs 店員（在 POS 內部） |
| repo | migi-hq（總部後台）| migi-pos |

★「店長 vs 店員權限」屬於門市 POS 內部，與 HQ 無關。

## 二、技術選型（與現有系統一致）

- **前端**：React + Vite（同 migi-web/migi-pos），部署 Cloudflare Pages
- **後端**：同一個 Supabase（ref roksgepxxmcewlkshtzn）
- **登入**：Supabase Auth（Email/密碼，總部員工帳號；非 LINE）
- **權限**：RLS + 角色。HQ 帳號有 org 級權限（看全集團），透過 org_id 存取所有 store
- **部署**：全走 Dashboard，不用 CLI（同既有慣例）
- **相容**：vite.config 加 target es2015（同 migi-web LIFF 教訓，雖 HQ 不走 LINE，但求一致保險）

## 三、模組地圖（依優先順序）

### 🟢 第一波（解鎖 POS 接真資料——最優先）

**M-商品管理**（POS 撈商品的來源）
- 列表：所有商品（檯費 service / 餐飲 fnb / 商品 merch），可篩分類、上下架狀態
- 建立/編輯：名稱、分類、價格、單位、庫存、上架狀態
- 操作表：`products`
- ★對照 order_items.kind 映射（service→fee / fnb→fnb / merch→goods）在 POS 端結帳時處理，HQ 只管 products.category
- 這個做完，POS 的 CATALOG 就能改撈真實 products

**M-優惠券管理**（會員 App + POS 用券的來源）

券管理其實有三塊，關係是「券種是本體，發放是把券種給誰」：

**(1) 券種管理**（coupons）— 建「有哪些券」〔第一波做〕
- 券種列表：所有券模板
- 建券：折扣類型（percent/fixed/free）、面額、適用範圍（applies_to: table_fee/fnb/ride/topup/null）、有效期、min_spend/max_discount/free_product_id
- 操作表：`coupons`

**(2) 發放**（member_coupons）— 「把某券種發給誰」〔第一波做「手動發」〕
- ★第一階段只做**手動發**：選券種 → 選會員（單發）或條件（批次，如「所有新會員」）→ 發出去
- 手動發已覆蓋約 90% 需求，簡單不出錯
- 操作表：`member_coupons`；後端 grant_coupon RPC 已備

**(3) 發放規則 / 自動化**（grant_rules）— 「什麼行為自動觸發發券」〔★第二階段才做，別急〕
- 這是連接**會員 App 獎勵頁**的地方：成就達成 / 完成任務 / 扭蛋抽中 → 自動發對應券或點
- ★複雜度警告：全自動規則引擎 = 小型行銷自動化系統（觸發條件/防重複/時間窗/上限…），不要一開始做
- 後端 grant_rules / grant_points/coupon/on_trigger_tx 接口已備，量大了再接

---

### 🔗 獎勵頁（會員 App）與發券的關係

會員 App 獎勵頁的「成就 / 任務 / 摸彩扭蛋」**不是新券種，是「發券的觸發器」**：

```
會員完成任務「連續簽到7天」→ 觸發 → 發一張「免費奶茶券」（券種來自券種管理）
會員扭蛋抽中「檯費9折券」    → 觸發 → 發一張「檯費9折券」
會員達成成就「首次配桌」      → 觸發 → 發 50 點 or 一張券
```

- 發出去的**券種**永遠來自「券種管理」建的那些
- 「哪個達成 → 發哪個券」由**發放規則(grant_rules)**定義
- 職責分工：會員 App 前端負責獎勵頁「呈現與互動」；達成後「實際發什麼」由 grant_rules 決定；規則由 HQ 設定

**★分階段落地：**
- **現在**：券種管理 + 手動發。獎勵頁達成後，先**手動/半自動**發券（扭蛋因為抽中即發，是唯一第一個需要自動發的）
- **之後**：手動發變負擔時（會員多、活動頻繁），把常見發放做成 grant_rules 自動觸發

**結論：獎勵頁達成「跟券管理有關」，但關係是「觸發發券」而非「等同」。第一版不必做複雜的自動規則引擎。**

### 🟡 第二波（會員經營）

**M-會員管理**
- 會員列表、搜尋（暱稱/手機）
- 會員 360：基本資料、點數餘額、消費紀錄、持有券、段位、牌風
- 手動調整：發點、發券、加註記（member_interactions）
- 操作表：`members`、`wallets`、`wallet_txns`、`member_coupons`

**M-報表 / BI**
- 營收、來客、客單價、開桌數、桌台使用率（後端 daily_report_tx 已有）
- 跨店比較（多店後）
- 操作：`daily_report_tx`、各報表視圖

### 🔵 第三波（連鎖化，M5+）

**M-門市管理**：建店、店長帳號、初始化 doc_counters（正式建店流程）
**M-加盟拆帳**：加盟主分潤、拆帳報表
**M-員工/權限管理**：總部帳號、角色指派
