## 1. 架構總則

### 1.1 一個核心、多個模組(不是三套系統)
CRM / POS / ERP 不是三套獨立軟體,而是**同一個資料庫上的不同模組介面**:

```
                ┌─────────────────────────────┐
   LIFF 會員端  │        共用核心 (Core)        │  員工後台 Web
  ─────────────►│  orgs / stores / members /   │◄─────────────
                │  wallet / tables / products  │
                └──────────────┬──────────────┘
        ┌─────────┬────────────┼────────────┬─────────────┐
      CRM 模組   POS 模組    配桌模組      成績模組       ERP 模組
     (會員經營) (交易結帳)  (媒合引擎)   (牌譜/段位)   (進銷存/報表)
      + 點餐 · 訂位 · 賽事 · 叫車 · 商城 —— 全部掛在同一個核心上
```

一筆「開桌扣點」= POS 交易 = CRM 消費紀錄 = ERP 營收,**同一筆資料,三種視角**。

### 1.2 多租戶從 Day 1
為了未來的系統授權 / 加盟,每張業務表都帶:
- `org_id` — 租戶(品牌;現在只有你自己)
- `store_id` — 分店

現在看似多餘,授權時就是命脈。RLS 全部以 `org_id` 為第一道隔離。

### 1.3 命名與既有文件的關係
《配桌引擎》的 members / tables / match_requests…、《資料中台》的 games / hands / paipu_events… 全部納入本骨架,**補上 org_id**(原文件單店視角未含)。

## 2. 共用核心(Core)— DDL

```sql
-- 租戶與分店
create table orgs (
  id    bigint generated always as identity primary key,
  name  text not null,
  plan  text not null default 'self'        -- self / franchise / licensed
);

create table stores (
  id       bigint generated always as identity primary key,
  org_id   bigint not null references orgs(id),
  name     text not null,
  address  text,
  is_active boolean not null default true
);

-- 會員(= CRM 主檔;LINE Login 綁定)
create table members (
  id            bigint generated always as identity primary key,
  org_id        bigint not null references orgs(id),
  line_user_id  text,
  display_name  text not null,
  phone         text,
  home_store_id bigint references stores(id),
  tier          text not null default 'basic',   -- basic / silver / gold / vip(珍奶/焦糖布丁/提拉米蘇對應)
  joined_at     timestamptz not null default now(),
  -- v0.4 會員360 人口屬性(性別/生日必填、其餘選填,漸進式收集)
  gender        text,                              -- 男女比是核心營運指標、婦女場資格
  birthday      date,                              -- 配桌年齡合拍 + 生日關懷
  occupation    text,                              -- 選填:推估可來時段
  district      text,                              -- 選填:商圈分析(只到區)
  acquisition_source text,                         -- 得知管道(行銷歸因)
  -- v0.4 RFM/生命週期(系統定期算出,非手填;欄位先建,功能分波)
  last_visit_at timestamptz,                        -- R 最近來店
  visit_count   int not null default 0,             -- F 來店次數
  lifecycle     text not null default 'new',        -- new/growing/regular/at_risk/churned
  primary_staff_id bigint,                           -- 業務型店員歸屬(我的客人)
  unique (org_id, line_user_id)
);

-- 點數錢包(法律核心:桌面不見現金)
create table wallets (
  member_id bigint primary key references members(id) on delete cascade,
  balance   bigint not null default 0 check (balance >= 0)  -- 點
);

create type txn_type as enum
  ('topup','table_fee','fnb','merch','refund','adjust','event_fee');

create table wallet_txns (
  id         bigint generated always as identity primary key,
  org_id     bigint not null,
  store_id   bigint,
  member_id  bigint not null references members(id),
  type       txn_type not null,
  amount     bigint not null,            -- 正=入點, 負=扣點
  ref_table  text,                       -- 'table_sessions' / 'orders' ...
  ref_id     bigint,
  staff_id   bigint,
  note       text,
  created_at timestamptz not null default now()
);
create index on wallet_txns (org_id, store_id, created_at);
create index on wallet_txns (member_id, created_at);
-- 規則:wallet 餘額只由 Edge Function(service role)以交易方式更新,
--       任何端不得直接 update wallets。每筆變動必有 wallet_txns。

-- 員工與角色
create table staff (
  id        bigint generated always as identity primary key,
  org_id    bigint not null references orgs(id),
  store_id  bigint references stores(id),
  auth_uid  uuid unique,                 -- Supabase Auth
  name      text not null,
  role      text not null default 'floor' -- floor / manager / hq / owner
);
-- v0.4 業務型店員「雙重歸因 + 雙重獎金」(兩店員可同時各拿,互不衝突):
--   ① 配桌獎金:店員人工配成一桌 → 50元 給 table_sessions.promoted_by_staff_id;
--      系統自動配(promoted_by_staff_id=null)→ 不發個人,計入全店獎金池(不勞不獲)。
--   ② 綁定客人獎金:名下客人(members.primary_staff_id)每次有效消費 → 10元/人 給主責店員。
--      防刷門檻:需「完成收桌結帳 + 該次消費 ≥ 下限(預設100點)」才算一次。
--   一桌上限 = 配桌50 + 4人×10 = 90元(視客人綁定狀況浮動;未綁店員的人不發那10)。
--   情境:阿美配桌(拿50)+小婷是阿珍的客人(阿珍拿10)→ 兩店員同桌各拿各的。
--   獎金不掛儲值。全店成桌率達標另有全店獎金(防搶客)。
-- 獎金規則表(同 pricing_tiers 資料驅動精神,數字後台可改,程式只查表):
create table bonus_rules (
  id        bigint generated always as identity primary key,
  org_id    bigint not null,
  store_id  bigint,                     -- null=org預設,有值=分店覆寫
  rule_key  text not null,              -- match_made(配桌) / visit_commission(綁定客人)
  amount    bigint not null,            -- 金額(元):match_made=50, visit_commission=10
  min_spend bigint,                     -- 綁定獎金的有效消費門檻(預設100)
  is_active boolean not null default true
);
-- 業績聚合由報表層(§3.5)對 promoted_by_staff_id / primary_staff_id + bonus_rules 計算。
```

## 3. 模組明細

### 3.1 POS 模組(交易 / 結帳)
```sql
-- 桌台(沿用配桌文件,補 org)
-- tables: + org_id

-- 開桌 session = 計時計費單位
create table table_sessions (
  id         bigint generated always as identity primary key,
  org_id     bigint not null,
  store_id   bigint not null,
  table_id   bigint not null references tables(id),
  game_id    bigint,                     -- 連到成績模組 games
  started_at timestamptz not null default now(),
  ended_at   timestamptz,
  mode       text not null default 'matched',  -- v0.4 matched(配桌) / private(包桌)
  fee_points bigint,                     -- 結算點數(成交價快照,後續改價不影響歷史)
  promoted_by_staff_id bigint references staff(id)  -- v0.4 促成店員(業務獎金歸因)
);

-- v0.4 每桌每人計費狀態(配桌按人頭,各人狀態不同 → 必須獨立記錄)
create table session_players (
  session_id bigint not null references table_sessions(id) on delete cascade,
  member_id  bigint not null references members(id),
  join_type  text not null default 'opener',  -- opener(開桌在場) / mid_join(中途加入)
  status     text not null default 'playing',  -- playing/completed/late/forfeit
  charged_points bigint not null default 0,     -- 實際扣款(快照)
  joined_at  timestamptz not null default now(),
  primary key (session_id, member_id)
);

-- v0.4 計費規則(資料驅動:級距結構、價格全進表,後台可改,程式只查表)
-- 帶 store_id → 總部設預設、分店可覆寫(中央定價+分店自訂);store_id null = org 預設
create table pricing_tiers (
  id         bigint generated always as identity primary key,
  org_id     bigint not null,
  store_id   bigint,                     -- null = 全 org 預設;有值 = 該店覆寫
  mode       text not null,              -- matched(配桌) / private(包桌)
  rule_key   text not null,              -- matched_full/matched_midjoin/private 等
  min_unit   int,                        -- 配桌:將數下限;包桌:分鐘下限
  max_unit   int,                        -- 上限(null=無上限)
  points     bigint not null,            -- 點數
  sort_order int not null default 0,
  is_active  boolean not null default true
);
create index on pricing_tiers (org_id, store_id, mode, is_active);

-- 計費規則初始值(本案實務拍板,後台可改):
-- 配桌(按人頭):
--   matched_full    打滿3將      → 150 點/人
--   matched_midjoin 中途加入     → 100 點/人(加入當下扣,不經150再退)
--   (遲到/棄賽未滿3將 → 照收 matched_full 150,由結算邏輯判定)
-- 包桌(按時間階梯,整桌計):
--   private 0-120分  → 400 / 120-300分 → 600 / 300-1440分 → 800(封頂)
-- 開桌即扣:配桌開桌扣在場者150;包桌先問打多久→扣對應階梯。
-- 超時:時段前10分提醒(店員+客人),續→補扣升階,不續→收桌,不自動偷扣(網咖式)。

-- 桌邊點餐(餐飲)
create table orders (
  id         bigint generated always as identity primary key,
  org_id     bigint not null,
  store_id   bigint not null,
  member_id  bigint references members(id),
  table_id   bigint references tables(id),
  status     text not null default 'open',  -- open/served/paid/void
  total_points bigint not null default 0,
  created_at timestamptz not null default now()
);

create table order_items (
  order_id   bigint not null references orders(id) on delete cascade,
  product_id bigint not null,
  qty        int not null default 1,
  unit_points bigint not null,
  primary key (order_id, product_id)
);
```
POS 流程(v0.4 細化):
1. 報到選模式(配桌/包桌)→ 2. 開桌:查 `pricing_tiers` 算價 → 開桌即扣(配桌扣在場者150/人寫 `session_players`;包桌先問時長扣對應階梯)→ 3.(點餐)→ 4. 中途加入:扣100、寫 `session_players(join_type=mid_join)` → 5. 超時前10分提醒 → 6. 收桌結算:配桌依各人 status 退補(遲到/棄賽不退)、包桌依最終階梯,寫 `table_sessions.fee_points`(快照)、產生 `wallet_txns(table_fee/fnb)`、扣 `wallets.balance`、觸發三項更新(消費累積分級 / 牌局成績段位 / 店員業績歸因)。
完整規則見《開桌結帳流程規格》。

### 3.4b MDM 多店主檔下發(v0.4,多店/加盟階段)
> 解決:多店後品牌一致性。總部一處改、全店同步,同時保留分店彈性。

**三層資料權限**(不是全統一或全自訂):
| 類型 | 誰能改 | 例子 |
|---|---|---|
| 總部鎖定(全店一致) | 只有總部 | 品牌 CIS、會員分級規則、段位算法、核心計費架構 |
| 總部預設+分店覆寫 | 總部設預設、分店可調 | 菜單、價格、pricing_tiers、bonus_rules、營業時間 |
| 分店自主 | 分店自決 | 該店活動、排班、在地促銷 |

**機制(已預留)**:`pricing_tiers`/`bonus_rules`/`products` 的 `store_id`:
- `store_id = null` → 總部預設(全店適用)
- `store_id = 某店` → 該店覆寫(只對該店生效)

MDM 要補的是**下發流程**:總部改預設 → 套用到所有「未自訂」的分店(已自訂的店保留其覆寫)。對標 7-ELEVEN「總部改一次全台同步」。
落地:單店用不到;多店/加盟才實作下發流程。結構(store_id 覆寫)Day 1 已在。

### 3.4c MA 行銷自動化(v0.4,有會員量後)
> 解決:會員關懷/召回自動化,店員只處理需人情味的部分。

**觸發式自動旅程**(條件→自動動作):
| 觸發 | 動作 | 目的 |
|---|---|---|
| 新會員入會 | 歡迎+新手禮 | 第一印象 |
| 入會7天未回訪 | 新手回訪優惠 | 養成習慣(關鍵留存節點) |
| 常客突然N天沒來 | 「想你了」+小誘因 | 流失挽回 |
| 生日 | 祝福+優惠 | 關係經營 |
| 點數快到期 | 提醒 | 促回流 |
| **牌咖上線/開局** ⭐ | 「你的牌咖在打牌,要來嗎」 | 用社交網絡召回(MIGI獨有) |
| **段位快升級** ⭐ | 「再贏X場升段」 | 用成就感召回(MIGI獨有) |

最後兩個(牌咖、段位)是 MIGI 獨有的召回鉤子,比折扣更黏。資料來源:mahjong_buddies、member_rating、member_availability。

**防騷擾原則**(呼應安心定位):頻率上限、行為觸發非無差別群發、可關閉。MA 是貼心提醒不是促銷轟炸。

**MA × 店員 CRM 同系統分工(關鍵架構)**:
兩者不是兩套系統,是**同一份會員資料的兩個出口**:
```
        同一份資料(members + RFM/lifecycle + member_interactions)
                   │
       ┌───────────┴───────────┐
   MA(系統自動)          店員 CRM(人工·我的客人)
   排程觸發→推播          讀資料→人工關懷
       └────→ 都寫回 member_interactions ←────┘
```
- **共用 member_interactions**:不管 MA 自動發或店員手動發,全寫進同一張互動紀錄 → 避免重複打擾(MA 發前先查最近有無被聯絡)、店員看得到系統已發過什麼、每客人有完整互動時間軸。
- **指派規則**:標準量大低個人化(生日/點數到期/7天喚回)→ MA 自動;高價值需人情味(VIP流失/大戶)→ 指派店員;**MA 發了沒反應 → 自動升級指派給 primary_staff_id 店員**(我的客人介面跳待辦)。
- **先 MA 自動試(省人力)、不行升級店員(用人情味)**。
- 全在 Supabase 一庫,天然同步、不存在串接(呼應 §8「A 自建」:MA 要跟核心會員資料即時黏,外部工具做不到無縫)。

**技術**:Supabase 排程(pg_cron/Edge Function 定時)掃描觸發條件→LINE Messaging API 推播→寫 member_interactions。
落地:會員量起來後做;初期會員少,店員手動(我的客人)就夠。結構(RFM/lifecycle/interactions/availability)Day 1 已在。

### 整合方式判準(取代舊「自建 vs SaaS」二分法)

> 實務鐵則:**「API 串來串去」是最大隱藏成本**(對方改版你就壞、出事互踢皮球、資料對不齊、省下的開發費全花在維護串接)。
> 所以判準不是「自建 vs 買」,而是「**這系統要不要跟我的核心資料即時黏在一起**」,分三類:

| 整合方式 | 適用 | 為什麼 | 要不要碰 API |
|---|---|---|---|
| **A 自建(長在自家 DB)** | POS、CRM、點數錢包、配桌、成績、ERP 輕量、MDM、忠誠度/段位 | 跟核心資料即時黏 → 同一個資料庫、同一筆會員,**根本不存在串接** | 否(同庫) |
| **B 檔案匯出/匯入** | 會計、薪資、報表給會計師、巡檢結果 | 不需即時同步 → 月底匯出 CSV/Excel 給對方,**不是串接是傳檔**,零技術風險 | 否(傳檔) |
| **C 只串大廠標準 API** | 金流收款、LINE 推播、電子發票(財政部加值中心) | 不得不即時互通 → 只挑被幾萬家串過、文件完整、不會說改就改的大廠 | 是(但限大廠) |

**關鍵結論:照此判準,真正需要「即時串 API」的只有金流 + LINE + 電子發票三處;其餘要嘛長在自家(A)、要嘛傳檔案(B)。** 你最痛的「跟一堆小 SaaS 互串」場景不該發生 —— 任何要靠脆弱 API 才能跟核心資料對齊的小眾 SaaS,優先改用 A 或 B,或乾脆不用。

**逐項標記**(取代前面各階段表的「SaaS」字樣,實際整合方式如下):
- POS / CRM / 錢包 / 配桌 / 成績 / ERP輕量 / MDM / MA簡版 / 加盟帳務 / 忠誠度 → **A 自建**
- 會計 / 薪資 / 巡檢 / EPM預算 / 報表外送 → **B 檔案交換**
- 金流 / LINE推播 / 電子發票 → **C 串大廠標準 API**
- 設備維護(EAM)/ 客服 / ITSM / LMS / 法遵 等純後勤工具 → 可用獨立 SaaS,**但以 B(匯出對帳)為主,不做即時串**;真要串再評估,且僅限該工具有成熟標準 API 時。
