# POS 硬體與採購規劃

> **這是什麼／何時讀**：第一家店的 POS 櫃台硬體選型、電子發票加值中心與金流的評估方向、
> 以及客人螢幕的產品定位。要買設備、跟供應商談、或規劃櫃台配置時讀這份。
>
> ⚠ **軟體架構請以 `CLAUDE.md` 與 `docs/01-資料庫/` 為準**，本檔只負責硬體與外部服務。
> 原始版本（2026-08-17 歸檔前）對後端架構的敘述與現況不符，已在第 2 節更正。

## 1. 核心目標

- MIGI 自建 POS，不依賴套裝 POS 廠商。
- 前端 React + Vite；資料庫與後端邏輯以 Supabase（Postgres + RLS + RPC）為核心。
- 需要串接電子發票加值中心 API、付款金流，以及現場硬體。
- 櫃檯流程保持簡潔：**POS 做交易，App 做體驗。**
- 系統要能支援多店／加盟與 AI 麻將辨識。

---

## 2. 系統架構

| 層級 | 技術／設備 | 責任 |
|---|---|---|
| POS 前端 | React 18 + Vite，Chrome Kiosk Mode | 桌況、開桌、點餐、結帳、會員識別、發票選項 |
| 部署 | Cloudflare Pages（GitHub push 自動 build）| 更新不必逐台安裝 |
| 雲端平台 | Supabase | PostgreSQL、RLS、Realtime、Storage |
| **資料庫內邏輯** | **Postgres RPC（SECURITY DEFINER）** | 開桌、收費、儲值、結帳 —— **主線在這裡** |
| 對外 HTTP | Supabase Edge Functions（Deno）| 只用於電子發票、金流、LINE 等第三方 API |
| 電子發票 | 加值中心 API | 開立、載具、統編、捐贈、作廢、折讓 |
| 付款 | 待選（TapPay／綠界／藍新等）| 信用卡與行動支付 |
| 本機硬體橋接 | 獨立 Local Print Service | 瀏覽器 ↔ ESC/POS 印表機、錢箱 |
| AI 辨識 | **獨立主機，與 POS 分離** | 見 `docs/10-牌譜與AI辨識/可跑YOLO的硬體選項比較.md` |

### 為什麼不需要 Node.js 伺服器

React 負責 UI，Supabase 負責資料庫、權限與即時資料，商業邏輯寫在 Postgres RPC 裡。
需要保護 API Key 或呼叫第三方時才用 Edge Function（Deno 執行）。

**「不用 Node.js」不等於「沒有後端程式」** —— 後端程式在資料庫裡。
印表機橋接程式仍需要，但它跑在店內電腦、技術可自選。

## 3. Chrome Kiosk 模式

- Chrome／Edge 的 Kiosk Mode 全螢幕執行，Windows 開機自動啟動並導向 POS 網址。
- POS 已內建**版本號顯示與開機看門狗**（側邊欄顯示 `vMMDD-HHmm`，
  開機比對 `version.json` 自動重載）—— 這是為了根治「分不清跑的是哪一版」。
- PWA 尚未做，目前是一般網頁 + Kiosk。

> ⚠ **離線是目前的缺口。** 所有查詢都走 Supabase RPC，斷網時 POS 完全不能用
> （只有錯誤提示，沒有離線模式）。店內網路備援與停電策略見第 12 節待確認事項。

## 4. 電子發票

```text
React POS → Edge Function → 電子發票加值中心 → 財政部
```

- **API Key 絕不放前端。**
- 核心流程不只開立，還有作廢、折讓、退貨重開、載具、統編、捐贈。
- 離線開票不是「斷線先印、之後補傳」那麼簡單，要依正式規範與加值中心方案實作。
- 正式合作前取得：API 文件、Sandbox、錯誤碼、測試帳號、技術支援窗口。

### ⚠ 開票時點尚未拍板

儲值制之下，同一筆錢有兩個可能的開票時點，兩邊都開就是**同一筆錢報兩次銷售額**。
A/B 兩案、給會計師的三個問題、以及「發票金額 = 非點數付款金額」這條共通規則，
見 **`docs/00-進度與索引/待辦與未定案.md` §發票開立時點**。

**這一題沒定案之前不要簽加值中心的約** —— 它會影響你需要的 API 面向
（是「儲值時開一張大額」還是「每次消費開小額」，量級差很多，費率談法也不同）。

## 5. 加值中心比較方向

| 對象 | 定位 | 正式決定前要確認 |
|---|---|---|
| 美麗科技／WiXtar | 優先洽談；重點是自建 POS 的 API 整合能力與載具支援 | 最新 API、Sandbox、費率、技術支援、合作資格 |
| 鯨躍科技 | 另一主要比較對象 | REST／SOAP、Sandbox、文件、費率、支援時段與 SLA |

**選擇原則：不看品牌，比 API 品質、文件、測試環境與技術窗口。**
實際索取文件並實測「開立 → 作廢 → 折讓 → 載具」四流程再決定。

> 本節是討論方向，**不是對任一業者現行條款、價格或資格的認證**。

## 6. 電子發票載具

載具屬於**電子發票流程**，不是金流商的功能。POS 應支援：

- 手機條碼載具　- 會員載具　- 公司統編　- 捐贈碼　- 紙本證明聯

- 手機載具用 USB 2D Barcode Scanner 掃客人手機上的條碼。
- 掃描器若走 **USB HID 鍵盤模式**，React 直接收字串即可，不必寫驅動。
- 會員完成設定並同意後，POS 可自動帶出會員載具，省掉重複掃描。

實際支援項目依加值中心確認。

---

## 7. 金流

- **TapPay 是金流 API 平台**，不是 POS，也不是發票加值中心。
- 採用金流商不影響發票 —— 發票仍由加值中心處理。
- 可採「金流一家 + 發票一家」，也可評估同一家供應商包多項。
- 選定前確認：實體門市／刷卡機支援、退款、對帳、Apple Pay／Google Pay／LINE Pay。

## 8. 客人螢幕的產品定位

> **POS 做交易，App 做體驗。**

| | 內容 |
|---|---|
| 店員螢幕 | 開桌、點餐、結帳、付款、發票 |
| 客人螢幕 | 消費明細、金額、付款方式、載具／統編、付款結果、導向 App 的 QR Code |

**客人端不塞排行榜、成就、AI 分析、完整會員中心** —— 那些放 App。
客人螢幕保留觸控能力，未來有明確需求再加互動。

## 9. 櫃台硬體配置

### 螢幕

- 建議 **店員 24 吋觸控 + 客人 21.5～24 吋觸控**。
- 雙 24 吋非必要；櫃檯空間、支架承重與成本有壓力時，客人端 21.5 吋較平衡。
- 最終依櫃台深度、觀看距離、支架承重與品牌視覺決定。

### VESA 與支架

- VESA 是螢幕背面的標準安裝孔位，常見 **75×75 mm** 與 **100×100 mm**。
- 採購螢幕時**優先確認支援 VESA**（雙螢幕支架、Mini PC 掛螢幕後方都要靠它）。

| 方案 | 特性 | 建議 |
|---|---|---|
| POS 專用整合式雙螢幕支架 | 結構整合、安裝簡單、外觀像傳統 POS | 追求快速部署可考慮 |
| **雙 VESA Arm** | 高度、角度、前後位置好調；換螢幕彈性大 | **較推薦**，選白／銀色符合 MIGI |

### 主機：Mini PC vs 一般 PC

兩者本質相同，React + Chrome + Supabase 都能跑。

| | 優勢 |
|---|---|
| Mini PC | 體積小、耗電低、安靜、可藏櫃台或掛螢幕背後 |
| 一般 PC | 擴充性高、維修換件容易；已有品質良好的商用桌機可直接用 |

**結論**：已有合適的 PC 就不必為了「POS」重買。
從零採購且重視櫃台整潔 → **Mini PC**。
POS 不需要高階 GPU；**AI 麻將辨識務必與 POS 分離**。

### 介面：不必為 COM Port 買貴機器

- COM Port（RS-232）是傳統序列介面，新採購優先選 **USB 或 LAN**。
- 錢箱常見做法是接在發票機的 **RJ11 錢箱埠**，由發票機觸發開箱，不必直接接電腦。

### 連接方式

```text
Mini PC（Windows）
│
├─ HDMI / DisplayPort → 店員 24 吋觸控螢幕
├─ HDMI / DisplayPort → 客人 21.5～24 吋觸控螢幕
├─ USB                → 2D QR / Barcode 掃描器
├─ USB 或 LAN         → 電子發票熱感印表機
└─ 發票機 RJ11        → 錢箱
```

## 11. 結帳 UX

| 階段 | 店員 POS | 客人螢幕 |
|---|---|---|
| 消費中 | 桌況、點餐、訂單 | 消費摘要／總額 |
| 結帳 | 確認訂單、選付款與發票方式 | 金額 + 付款方式提示 |
| 付款 | 等待付款結果 | 信用卡／行動支付提示 |
| 發票 | 載具／統編／捐贈／紙本 | 發票資訊或掃描提示 |
| 完成 | 完成交易 | 謝謝光臨 + QR Code 導向 App |
