# 電子發票與儲值點數

> **這是什麼／何時讀**：電子發票什麼時候開、開多少，以及儲值點數的本金與贈點怎麼分。
> 要動發票串接、錢包、儲值、退款、服務條款的點數章節之前讀這份。
>
> **2026-10-05 使用者拍板。** 在此之前這一題掛在《待辦與未定案》§發票開立時點，標「需會計師拍板」
> 從 08 月掛到 10 月。使用者決定由 Claude 直接判斷，**法規方向由 Claude 負責，
> 條號與函釋原文請記帳士核對一次**（第七節列了要核對的項目，約十分鐘的事）。

## 一、拍板結論

| | 定案 |
|---|---|
| **什麼時候開發票** | **B 案：儲值時不開，消費時才開**（儲值給「儲值證明」，不是統一發票） |
| **發票金額** | **現金 ＋ 本金點數**。贈點、優惠券、會員折扣都是折扣，不進發票金額 |
| **錢包** | **分成本金與贈點兩格**（照台灣「儲值金／贈送金」的主流做法） |
| **扣款順序** | **贈點先扣，扣完才扣本金**（服務條款草稿第四條早就這樣寫） |
| **效期** | **本金不設期限**（禮券規定不准）；**贈點可以設期限**（無償取得，不受那條限制） |
| **退款** | **只退本金餘額**；贈點不退；已用掉的贈點從退款裡扣回（服務條款草稿第六條「選項二」） |
| **履約保證** | **要做**，而且要在收第一筆真實儲值之前辦好 |
| **稅別** | 一律**應稅 5%**（麻將館是一般娛樂業，不是 15%／25% 的特種飲食業） |
| **點數跨法人使用** | 🔴 **未定，要問律師**。在那之前：**點數只能在儲值的那個法人旗下的店使用** |

## 二、為什麼是 B 案（消費時開）

### 🔴 先更正：文件原本的推論把規則講反了
《待辦與未定案》原本寫「傾向 A，因為台灣對**現金禮券**的處理是出售時開立」。
**方向是反的**。財政部對禮券分兩種：

| 禮券種類 | 什麼時候開發票 |
|---|---|
| **商品禮券**：寫明換「某樣東西」（一杯咖啡、一份套餐） | 賣出禮券時 |
| **現金禮券**：只寫金額，用多少扣多少 | **持券人拿來消費時** |

MIGI 的點數按金額扣，是後者 ⇒ **消費時開**。
📌 實例：星巴克隨行卡儲值只給收據，買東西時才開發票。

⚠ 那段原本還說「原設計者站 A 案，否則 `topup_orders` 不會有 `invoice_no` 欄位」
（《資料模型設計說明》也這樣推論）。欄位存在只代表當初**預留了可能性**，不是決定。
B 案之下 `topup_orders.invoice_no`／`invoice_at` **用不到**，不要拿它當證據。

### B 案對 MIGI 另外兩個實際的好處
- **退款簡單**：沒用完的本金還沒開過發票，直接退錢。A 案要開折讓單，跨期更麻煩
- **營業稅晚繳**：收到儲值時不用馬上繳，消費了才繳

### 代價
- **發票張數變多**：A 案是儲值時一張大額，B 案是每次消費一張小額。加值中心多半按張數計費，**報價要用 B 案的張數去談**
- 用點數付的消費也要開發票（只要那筆用到了本金點數）

## 三、本金與贈點分帳

### 台灣常見的四種做法
| | 做法 | 誰在用 | 評價 |
|---|---|---|---|
| 1 | **純贈點當折扣**：消費回饋的點數，折掉的部分不開發票 | 量販、超商的會員點數 | 沒有爭議，但那是「回饋點數」，跟儲值加贈不同 |
| 2 | **儲值金／贈送金兩個帳戶**：本金開發票，贈送金當折扣 | 美容美髮、健身房、連鎖餐飲的儲值方案 | ✅ **主流**，MIGI 採用這個 |
| 3 | **按比例攤**：1,000 元買 1,150 點，每點值 0.87 元 | 少數大企業的會計系統 | 最精確，但每次都要四捨五入，對帳痛苦 |
| 4 | **不分**：用掉多少點就照面額開 | 系統分不出來的小店 | 不違法，只是贈點那部分**多繳 5% 營業稅** |

### MIGI 的規則
```
儲值 1,000 送 150   →  本金 +1,000、贈點 +150
消費 300（全用點數） →  先扣贈點 150、再扣本金 150   →  發票 150
消費 300（點數 100 ＋ 現金 200，此時贈點已用完） →  本金 100 ＋ 現金 200  →  發票 300
```

### 為什麼贈點先扣
- 贈點會過期，先扣才不會讓客人眼看著它過期（客訴來源）
- 退款時要計算的東西變少

### 🔴 退款一定要扣回已用的贈點
不寫這條會被鑽：儲值 1,000 送 150 → 先把 150 用完 → 申請退 1,000 ⇒ 白拿 150。
```
可退金額 ＝ 本金餘額 −（已使用的贈點，如果本金已經被動過的話）
```
⚠ 「已使用的贈點」要能從流水查得出來 ⇒ 每一筆扣款都要記「扣了多少本金、多少贈點」。

## 四、履約保證與效期

依經濟部《零售業等商品（服務）禮券定型化契約應記載及不得記載事項》，
「圈存一定金額的晶片卡或其他類似憑證」也算禮券，App 內的儲值點數幾乎確定在範圍內。

| | 本金點數 | 贈點 |
|---|---|---|
| 能不能設期限 | ❌ 不能，寫了也無效 | ✅ 可以（無償取得） |
| 要不要履約保證 | ✅ 要 | ❌ 不用 |

**履約保證四選一**：金融機構足額保證、信託、同業連帶保證、公會聯合連帶保證。
小店最常見的是**跟往來銀行談足額保證或信託**，成本主要是手續費。
🔴 **收第一筆真實儲值之前要辦好**。自己人測試買的不算，但上線當天第一位客人儲值就算。

📌 贈點效期多長、要不要做「滑動效期」（最後一次使用起算），**是營運決定不是法規問題**，
  做的時候再定。服務條款草稿第四條的建議是滑動效期，對客人比較友善。

## 五、🔴 點數能不能跨法人使用（未定）

系統裡 7 間店分屬 5 個法人（總部直營 3 間，其餘各自一個法人）。

```
客人在直營店（總部法人）儲值
→ 拿到加盟店（另一個法人）消費
```
一張儲值點數如果能在「**發行人以外**」的店家使用，可能從「禮券」變成
《電子支付機構管理條例》管的東西，那要金管會的執照，一般公司拿不到。
**加盟體系算不算「發行人自己的店」，Claude 沒有把握**，這題要問律師，
而且要在**第一間加盟店開幕前**問。

### 在律師回覆之前
- **點數只能在儲值的那個法人旗下的店使用** ⇒ 直營三間互通，加盟店各自獨立
- 這同時讓發票單純：儲值收錢的法人 ＝ 消費開發票的法人，不需要法人之間對帳

📌 資料層已經預留了這件事：`wallet_txns` 有 `store_id` 與 `served_store_id` 兩欄，
  `topup_orders` 有 `held_by_entity`。做的時候先查它們目前怎麼被寫，不要另外發明一套。

### 🔴 草稿函式要修的地方
| | 問題 | 改法 |
|---|---|---|
| ① | 金額用 `orders.payable`（含點數） | 改成 **現金 ＋ 本金點數**。用 `payable` 的話，以線上 25 筆已付款訂單來算（應付 2,999，其中點數 1,847），**六成會被多開** |
| ② | 品項用原價 `line_total`，有折扣時明細加總 ≠ 發票總額 | 加一列負數的「折扣」明細（多數加值中心支援，**要在 sandbox 確認**）；不支援就按比例攤到各品項 |
| ③ | ~~沒有替儲值建草稿的函式~~ | **B 案之下不需要**，取消 |
| ④ | 沒有折讓 | 跨期退款只能開折讓單，做退款流程時一起做 |
| ⑤ | `set_invoice_pref_tx` 收 `p_member_id` | 會員自己設定時身分要用 `current_member_id()`（硬規則 2.7）。今天只有 service_role 叫得動所以沒有洞，**開給會員 App 那天要改** |

### 🔴 錢包要拆成兩格
```
現在   wallets.balance（一格）  wallet_txns.amount（一個數字）
要改   本金餘額 ＋ 贈點餘額（＋ 贈點到期日）
       每一筆流水記「本金變動多少、贈點變動多少」
```
會寫 `wallet_txns` 的函式有 7 支：`checkout_tx`／`topup_tx`／`topup_void_tx`／`reverse_txn_tx`／
`_charge_core`／`dev_reset_test_data_tx`／`dev_set_test_balance_tx`；
另外 `fix_wallet_balance_tx` 會重算餘額。**全部都要跟著改**，漏一支就會讓兩格對不起來而且不報錯。

🎯 **時機：現在**。資料庫裡全部是測試資料，今天改幾乎零成本。
等真實客人儲值後再拆，每一筆舊餘額都要回推是本金還是贈點，很可能推不回來（硬規則 5.6「不可回溯」那一類）。

### 結帳與開票的關係
```
結帳成功 → 同一筆交易內建 pending 草稿（不碰網路，不會失敗）
          ↓
Edge Function 撈 pending → 送加值中心 → mark_issued／mark_failed
          ↓
failed 進錯誤儀表；總部看得到、可以重送
```
理由：同步開票的話，加值中心逾時會讓**整筆結帳失敗、收不了錢**；
而發票失敗的原因（載具打錯、字軌用完）通常跟這筆消費無關。
這跟已經拍板的「消費紀錄結帳當下就有，不等發票」一致（CLAUDE.md 待辦 13）。

## 八、開工順序

```
① 錢包拆本金／贈點   ← 不依賴任何外部條件，現在就能做，而且越晚越貴
② 修草稿函式（金額、折扣明細）＋ 結帳時建 pending 草稿
③ 統編下來 → 選加值中心 → 申請 sandbox
④ Edge Function：送出、回寫、重試；failed 進錯誤儀表
⑤ POS 結帳畫面：載具／統編／捐贈；需要時印證明聯
⑥ 會員 App 的發票區：設定載具、查發票
⑦ 作廢與折讓（跟退款流程一起）
```
⚠ 第 ④ 步起會**真的上傳財政部**。測試一律用加值中心的 sandbox 帳號，
正式帳號的金鑰只設在正式站的 Edge Function secret。
