## 0. 核心營運模型

**全料理包 + 隔水加熱**

首店不設廚師、不現做熱食。所有主食品項採「連麵一起的整份」冷凍料理包，現場以 IH 爐深鍋隔水加熱後出餐。炸物、蛋塔、厚片走氣炸烤箱。甜點冷藏即取。飲料吧台現調。

這個模型的三個結果：

- **零廚藝門檻**：新人訓練約十分鐘，看 SOP 表操作即可
- **零生鮮報廢**：不進培根、燻雞、青菜、蔥等短效期食材
- **產能靠設備不靠人**：瓶頸是 IH 鍋數與烤箱容量，不是人手

**代價（需接受）**：口味被供應商鎖死、無法差異化、客人吃得出料理包。因此定價不宜過高，文案不得宣稱「主廚現做」。

## 4. 廚房規格與法規

### 4-1 施工原則：建好、先不裝滿

廚房硬體是最難事後補的——排煙管道、給排水、電力、防火建材一旦沒做，後續要停業施工並重新申報。

**裝修階段必須做足（不可事後補）**

- 排油煙管道與補風
- 給排水（含截油槽）
- **電力容量**：含 IH 專用迴路，預留 2–3 口容量
- 防火建材與消防設備
- 瓦斯管線拉至廚房但不接設備（成本增加有限，保留退路）
- 建照／使用執照的餐飲用途登記
- **預留爐台位置**：先空置或放層架，管線排煙拉到位。需主動向設計師提出，否則會依現有設備清單壓縮空間

**設備分階段購置**：開幕僅 IH ×2 + 微波 ×1 + 氣炸烤箱 ×1。未來要現做熱食時再添購爐具。

### 4-2 IH vs 瓦斯

採 IH 路線。優點：免瓦斯申請與定期檢查、無燃燒廢氣、溫控精準（與 SOP 邏輯一致）、無明火、檯面易清潔。

限制：鍋具須為磁性材質；無法爆炒（無鑊氣）；**電力需求大**，多台需專用迴路——此點必須在裝修階段納入電力容量計算。

### 4-3 法規盤點

**登記時建議直接以「有廚房、可現做熱食」的完整規格申請**，不因開幕期只用微波而登記較低類別——升級需重新申報，一開始做足較省事。

待確認項目：
- 公司／商業登記，營業項目含餐飲
- 食品業者登錄
- 食品類別申報
- 從業人員健康檢查
- 衛生管理人員（視規模是否達標）
- 油煙排放相關規範
- 消防設備審查
- 🔴 **電子發票**（見 12-5）—— 餐飲營業一定要開發票，而系統端整條未接

### 5-2 隔水加熱三項要點

**① 濾網籃是必需品**
直接把包丟進滾水，撈取危險且慢。用附把手的濾網籃，一籃放 3–4 包，時間到整籃提起。每鍋配 2 個交錯使用。

**② 多組計時器**
不同品項時間不同，同鍋可能同時跑兩三種。使用多組計時器或手機多計時，避免遺漏。

**③ 水位與水質**
長時間滾水會蒸發，水位低則加熱不均；包裝袋久泡水會變濁。**每四小時換水一次**，寫入日常檢查表。

### 5-3 冷凍白飯操作（若未來上飯類）

微波 700W 加熱 1–2 分鐘，**須覆蓋一張沾濕的廚房紙巾**，否則米飯表面乾硬，客人一吃即知是冷凍飯。

| 品項類別 | 容器 | 注意事項 |

| 義大利麵 | 淺盤 | 叉子好操作 |
| 中式乾麵 | 中碗 | |
| 水餃 | 中碗 + 醬碟 | |
| 炸物 | 紙襯籃或盤 | **不可用有蓋盒**，會悶軟 |
| 甜點（杯裝） | 直接給 + 小匙 | 不用洗盤 |
| 甜點（切片） | 小盤 + 叉 | |
| 綜合堅果 | 小陶碟 + 小夾／小勺 | |

### 6-1 兩個關鍵決定

**內用餐具：飲料用封口杯（拋棄式），餐點用可洗餐具。**
可洗質感好、長期成本低、符合品牌定位；封口杯避免潑灑風險。

**麻將桌專用餐具須特別選**：淺、穩、不易倒，最好有防滑底。深碗在麻將桌上極易被撞。

### 6-2 桌邊器具站（必設）

小碟、竹籤、夾子、餐具、紙巾、濕紙巾。須設在客人自己拿得到的位置，否則店員會被反覆呼叫。

### 6-3 未解決的硬體問題：餐點放置

麻將桌中央是牌、四邊是牌尺與籌碼，**客人沒有地方放碗盤**。此問題直接影響炸物與主食能否真的賣得動。

三個方向擇一：**邊桌／掛式托盤／桌角小平台**。此項須在空間規劃階段一併解決。

🔴 **而且它會污染首月數據**：如果沒地方放，炸物與主食的銷量會偏低，而 POS 上看起來會像「**客人不愛吃**」——實際是「**沒地方放**」。這兩個結論導向完全相反的行動（換菜色 vs 加平台）。
→ 首月檢視時要能分辨。見 12-6。

## 7. 庫存管理

### 7-1 三類分管

| 類別 | 內容 | 進貨頻率 | 管理強度 |
|---|---|---|---|
| **冷凍** | 主食料理包、炸物、蛋塔生胚、甜點 | 兩週一次 | 低（保存期長） |
| **冷藏** | 甜點成品、鮮奶、煮好的珍珠 | 三天一次 | **高（每日檢查）** |
| **常溫** | 茶葉、堅果、咖啡豆、餅乾盒 | 一個月一次 | 低 |

全料理包模型下，**冷藏區塊已大幅縮減**，是唯一需要每日盯效期的區域。建議製作效期表貼於冰箱門，每日晨間確認。

### 7-2 首月抓量原則

開幕前無法預估銷量，**一律進最小量**，寧可賣完掛「已售完」。前三週的 POS 數據會揭示真實需求，之後再調整。

⚠ **「已售完」用哪個欄位要先定義** —— `products` 有 **`is_active` 與 `is_available` 兩個**，用錯會把「今日售完」變成「永久下架」。見 12-3。

自建 POS 的紅利就在這裡——不用猜，看數據。

### 7-3 堅果保存

未開封冷藏，保存期約 8 個月；開封後密封冷藏。大包裝拆封後若一週內未售完會走油耗味。

**建議買 3 公斤級而非 30 公斤級**，寧可多訂幾次。

### 8-2 待詢價項目

1. 最低訂購量（單一品項最少幾公斤／幾包）

4. 是否接受小店家長期少量固定叫貨（每月 5–10 公斤）

1. 各品項單包規格與售價
2. 隔水加熱標示時間（填入 SOP 表）

**冷凍白飯（未來飯類用）**
1. 每包克數（170g 偏小，200g 較適合正餐）
2. 每箱包數與單價（目標每包成本 15 元以內）

| 風險 | 說明 | 對策 |
|---|---|---|
| **供應商單點依賴** | 整個餐飲營運壓在料理包供應商，斷貨／漲價／換配方／倒閉即直接停擺 | **主力品項至少準備一家備援供應商** |

## 10. 對 POS 系統的需求

菜單定案後，`products` 與 `order_items` 需要以下調整。

⚠ **本節的欄位建議寫於菜單定案時，其中數項在系統裡已經存在或已改名。**
**動手前務必先看第 12 節的修正**，不要照本節直接開欄位。

### 10-1 products 新增欄位

| 欄位 | 型別 | 用途 |
|---|---|---|
| `display_group` | text | 客人看到的分類：飲料／甜點／零嘴／炸物／主食。⚠ 見 12-2：`subcategory` 可能已可勝任 |
| `prep_station` | text | 出餐路由：`bar` / `kitchen` / `none`。**必須獨立於收入桶**，否則常溫即取品項會混進出餐佇列。⚠ 原文寫 `kind`，該欄位已於 2026-08-19 改名為 `revenue_type` |
| `min_tier` | text | 商品可見性控制。供未來「主廚特調」等隱藏品項使用。⚠ 見 12-4：**後端也要擋**，只靠前端過濾不算數 |
| `option_schema` | jsonb | 該商品支援哪些選項。茶飲、咖啡、厚片、炸物各不相同，前端讀此欄位決定渲染內容，新增品項不必改 code |
| `prep_time` | int | 分三級：隔水加熱 8–12 分、氣炸 6–8 分、吧台／即取 0–1 分 |

`option_schema` 範例：

```
茶飲：{"sweetness": 5段, "ice": 5段, "addons": true}
咖啡：{"temp": ["冰","熱"], "addons": false}
厚片：{"flavor": ["奶酥","花生","草莓","巧克力"]}
炸物：null
```

⚠ **選項（option）與規格（variant）要分清楚**：見 12-7。
甜度、冰塊、厚片口味**不影響價格** → 是 option。
「大杯 +15」**影響價格** → 那是 variant，不可塞進 `option_schema`。

### 10-2 addons 表（新建）

```
addons: id, name, price, is_active, sort_order
```

開幕期僅一筆（珍珠 10 元）。未來上椰果、茶凍只需後台新增一筆並設 `is_active = true`，**POS 前端自動長出選項，一行 code 都不用改**。

前端務必寫成「渲染 addons 清單」，**不可寫成「珍珠開關」**。

🔴 **但在建這張表之前先看 12-8** —— 加料當成一般商品可能更好，
價格／成本／庫存／收入分桶／「券不折加料」全部免費繼承，而且不用新表。

### 10-3 order_items.options（jsonb）

```json
{
  "sweetness": "半糖",
  "ice": "去冰",
  "addons": [
    { "id": "pearl", "name": "珍珠", "price": 10 }
  ]
}
```

**三個設計要點：**

1. **`addons` 必須是陣列**，即使今天只有一個元素。日後擴充不必改 schema 或 migrate 舊資料。
2. **選項須凍結在下單當下**。之後改價或改選項名稱，舊單不得跟著變——這是用 jsonb 而非關聯表的理由。
3. **加料價格須快照進 `options`**。`addons` 表的價格是「現在的定價」，訂單裡存的是「當時付了多少」。不可靠即時查表計算 `subtotal`。

🔴 **第 3 點有一個安全面向原文沒提到**：快照的**來源**必須是後端查表，不是前端送來的數字。見 12-1。

### 10-4 其他

- **吧台／廚房出餐單必須印出選項**，否則會做錯（半糖去冰不顯示 = 做成正常糖）
- **券綁 `free_product_id` 時須明訂加料是否計入**。建議：券只免商品本體，加料照付。⚠ 這條規則若採 12-8 的做法會**自動成立**，不用另外寫邏輯
- **出餐佇列建議顯示排序編號**。IH 鍋與烤箱是有限資源，同時進來六份時，店員需知道先動哪一個，而非全部標「準備中」
  🔴 **POS 目前沒有出餐佇列這個畫面**，但狀態機已經存在。見 12-9

## 12. 系統面補充（2026-08-27 對照現有 codebase 後加）

> 本節是把第 10 節的建議對照**實際的資料庫與函式**之後的修正。
> ⚠ 第 10 節寫於菜單定案時，其中數項在系統裡已經存在或已改名。
> **實作前以本節為準。**

### 12-1 🔴 加料價格必須後端查，不可信前端

2026-08-27 剛把 `checkout_tx` 改成「**單價／名稱／收入桶一律回查 `products` 主檔**」，
前端只送 `product_id` + `qty`（CLAUDE.md 待辦 2）。

⚠ 如果加料的金額由前端算好放進 `order_items.options`，
**那個剛堵掉的洞會從加料重新打開** —— 前端可以送 `{"addons":[{"price":0}]}`。

→ **前端只能送 `addon_id`（或加料的 `product_id`），金額後端查表填入。**
「快照」指的是**後端查到之後寫進去凍結**，不是「照抄前端送來的數字」。

### 12-2 `display_group`：先確認 `subcategory` 現在裝什麼

`products` 目前已有的分類欄位（2026-08-27 查證）：

| 欄位 | 現況 |
|---|---|
| `category` | text NOT NULL（service／fnb／merch） |
| `revenue_type` | text NOT NULL（venue_fee／fnb／retail／other）—— **錢算哪一桶** |
| `subcategory` | text —— **貨號第二段，毛利維度** |

而「飲料／甜點／零嘴／炸物／主食」**本身就是一個毛利維度**。
→ 開新欄位之前先看 `subcategory` 現在有沒有在用、裝什麼值。
⚠ 若兩者職責重疊，會重演 2026-08-16 那次：文件說「`products` 尚未有 `kind` 欄位」，
實際線上早就有了，於是建出**兩個職責重疊的欄位**（CLAUDE.md 踩坑第 29 條）。

**所以三個維度是**：
```
display_group   客人看到的分頁      → 可能用 subcategory
prep_station    後場走哪一站        → 需新增
revenue_type    錢算哪一桶、能不能折 → 已存在
```

### 12-3 ⚠ 「已售完」用 `is_available`，不是 `is_active`

`products` 有**兩個**布林欄位，第 7-2 節只提到 `is_active`：

| 欄位 | 推測語意 | 用錯的後果 |
|---|---|---|
| `is_active` | 這個商品還在賣（**下架**） | 🔴 今日售完 → 變成永久下架 |
| `is_available` | 今天有沒有貨（**售完**） | |

⚠ **兩者的實際語意要先查證再寫進 SOP**（硬規則 3：不要猜）。

📌 而且 2026-08-27 改 `checkout_tx` 時**刻意不過濾 `is_active`**，理由是：
「結帳是**已經發生的交易**，不是決定要不要賣。東西客人都吃了才在收錢那一刻擋下來，
比讓它成立更糟。」→ **擋銷售要在 `list_products_tx`（不列出來），不是在結帳。**

### 12-4 `min_tier` 只靠前端過濾不算數

「主廚特調限定品項」若只在前端依等級過濾，**前端仍可送出那個 `product_id`**。
同「前端只送意圖不送事實」——`checkout_tx` 必須也擋。

📌 對得上的地方：`member_tiers.chef_special` 的 `threshold_amount = null`（**邀請制**），
所以「主廚特調品項」正是 `min_tier` 的第一個使用者。設計方向是對的。

### 12-5 🔴 發票：法規清單漏了，而系統端整條未接

餐飲營業一定要開發票。而 CLAUDE.md 待辦 13 記著：

- `create_invoice_draft_tx` 寫好了，但 **`migi-pos/src` 裡 `invoice` 一次都沒出現**
- **沒有串任何電子發票加值中心**（綠界／ecPay／關貿）
- `invoices` 表 **0 筆**

資料骨架其實齊了（載具、捐贈碼、統編、內含稅拆分都有），但**要先想清楚**：
誰呼叫、什麼時機、失敗了誰重送、作廢與折讓、代付時開給誰、字軌配號。

→ **這是法規硬條件，不是營運不便。應與公司登記同批處理。**

### 12-6 餐點放置問題會污染首月數據

第 6-3 節的未解問題有一個數據面後果：
沒地方放 → 炸物與主食銷量偏低 → POS 上看起來像「**客人不愛吃**」。

🔴 「換菜色」與「加平台」是完全相反的行動，而數據本身分不出來。

→ 首月檢視時要能分辨。可用的訊號：
- 同一桌**只點飲料甜點**的比例（若很高，可能是空間問題不是口味問題）
- 內用 vs 外帶的差異
- 直接問：前兩週店員主動問「為什麼不點熱食」，把答案記進 `member_interactions`

### 12-7 選項（option）與規格（variant）不要混

| | 影響價格 | 放哪 |
|---|---|---|
| 甜度、冰塊、厚片口味、炸物調味 | ❌ | `option_schema` |
| 「大杯 +15」、「加大份量」 | ✅ | 🔴 **不可放 `option_schema`** |

影響價格的是 **variant**，Square／Shopify 都把兩者分開。
現在單一杯型所以碰不到，但**先講清楚，免得日後把 size 塞進 option**。

### 12-8 🎯 建議：加料就是商品，不建 addons 表

第 10-2 節建議新建 `addons` 表。另一個做法是**把加料當成 `products` 的一列**
（`revenue_type = 'fnb'`），`option_schema` 只記「哪些商品可以當這個商品的加料」。

| | 免費得到 |
|---|---|
| 價格 | 走 12-1 的主檔查詢，**不用另外防前端竄改** |
| 收入分桶 | 珍珠 10 元自動歸 fnb |
| 成本與庫存 | `unit_cost`／`stock_qty`／`tracks_stock` 全部繼承 |
| **「券不折加料」** | 🎯 `checkout_tx` 的免費券只算 `free_product_id` 那一項，**加料自然不在內** |
| 折扣控制 | `discountable` 已存在，要不要讓加料被折是一個旗標 |

⚠ 代價：`order_items` 會多一列，收據上分兩行。
POS 可以視覺上把它縮排在主商品下面。

⚠ 業界兩種都有（Square 的 Modifier List 是獨立概念，但有自己的價格與成本）。
判準是**這裡的加料有沒有成本與庫存** —— 珍珠有（要煮、冷藏、每日檢查），
所以當成商品比較划算。

### 12-9 🎯 出餐佇列的狀態機已經存在

`orders.status` 的允許值是：

```
open / preparing / served / paid / void
```

**`preparing` 與 `served` 從來沒被用過** —— `checkout_tx` 一律寫 `'paid'`。
所以出餐佇列的地基已經在了，缺的是畫面與推進狀態的動作。

🔴 **但有一個順序問題要先拍板**：**先付款還是先出餐？**

POS 現在是**結帳即 `paid`**，餐飲是加購（`pos_addon_checkout_tx`）。
所以出餐佇列要看的是「**已付款但未出餐**」的訂單 —— 那跟 `open → preparing → served → paid`
的直覺順序**相反**。

→ 選項：① 另開 `fulfilled_at` 時間欄位（不動 status）
② 讓餐飲品項走不同的 status 流程
**①比較不會動到金流。**

📌 出餐佇列會是 POS 側邊欄的新項目（CLAUDE.md 待辦 18 記著「快速結帳」「交班日結」要加回去，這是第三個）。

### 12-10 餐飲沒有會員折扣 —— 定價不用預留空間

2026-08-17 決定：**會員等級折扣只折檯費，不折餐飲**（`checkout_tx` 的基數是 `rem_fee`）。

理由記在 `docs/08-決策與踩坑/決策紀錄.md` 第二十節：
餐飲的會員權益是**生日招待與限定品購買權**，不是折扣。

→ **主食 90–130 的定價不用再預留 5–10% 的折扣空間。**
⚠ 但**券**可以折餐飲（`applies_to = 'fnb'`），所以促銷仍有工具。

### 12-11 開幕不要開 `tracks_stock`

`products` 已有 `stock_qty` 與 `tracks_stock`。
但開啟它代表**每一項都要有人盤點**——27 項每日盤點是一份實際工作。

⚠ 硬規則 5.5 的判準：「這個功能需要有人每週維護嗎？需要的話先確認那個人存在。」

→ **開幕建議只用「售完」旗標（12-3），不開 `tracks_stock`。**
待三個月數據出來、確定哪幾項值得管，再逐項開啟。
📌 例外：**抽獎的實體周邊必須開**（限量，發完要擋），見
`docs/03-會員App與社交/抽獎獎品池設計.md`。
