## 0. 核心營運模型

**全料理包 + 隔水加熱**

首店不設廚師、不現做熱食。所有主食品項採「連麵一起的整份」冷凍料理包，現場以 IH 爐深鍋隔水加熱後出餐。炸物、蛋塔、厚片走氣炸烤箱。甜點冷藏即取。飲料吧台現調。

這個模型的三個結果：

- **零廚藝門檻**：新人訓練約十分鐘，看 SOP 表操作即可
- **零生鮮報廢**：不進培根、燻雞、青菜、蔥等短效期食材
- **產能靠設備不靠人**：瓶頸是 IH 鍋數與烤箱容量，不是人手

**代價（需接受）**：口味被供應商鎖死、無法差異化、客人吃得出料理包。因此定價不宜過高，文案不得宣稱「主廚現做」。

## 2. 分類與出餐站對照

菜單分類（客人看到的）與出餐路由（後場走的）是**兩個獨立維度**，不可互相牽制。

> ⏳ **兩個欄位都還不存在**（`display_group` / `prep_station`）——
> 它們是第 10-1 節提議要新增的。本節描述的是**目標狀態**，不是現況。
>
> 📌 而這個「兩個維度不可互相牽制」的原則，系統裡**已經有一個成功前例**：
> 2026-08-19 把 `kind` 拆成 `category`（放哪一頁）＋ `revenue_type`（錢算哪一類），
> 理由一模一樣 —— 教室課程是 `category='service'` 但不該算檯費。
> ⇒ 出餐站是**第三個**維度，而不是把它塞進前兩個之一。

| display_group | 品項數 | prep_station 分佈 |
|---|---|---|
| 飲料 | 8 | bar × 8 |
| 甜點 | 7 | none × 5、kitchen × 2（蛋塔、厚片） |
| 零嘴 | 1 | none × 1 |
| 炸物 | 6 | kitchen × 6 |
| 主食 | 10 | kitchen × 10 |

**合計**：bar 8｜none 6｜kitchen 18 ＝ **32 項**

**兩層時機分類（供菜單設計與客人引導參考）**

- **牌局中**（可放、一口、涼了不難吃）：飲料、甜點、零嘴
- **休息／開局前**（趁熱、需坐好吃）：炸物、主食

## 4. 廚房規格與法規

### 4-1 施工原則：建好、先不裝滿

廚房硬體是最難事後補的——排煙管道、給排水、電力、防火建材一旦沒做，後續要停業施工並重新申報。

**裝修階段必須做足（不可事後補）**

- 排油煙管道與補風
- 給排水（含截油槽）
- **電力容量**：含 IH 專用迴路，預留 2–3 口容量
- 防火建材與消防設備
- 瓦斯管線拉至廚房但不接設備（成本增加有限，保留退路）
- 建照／使用執照的餐飲用途登記
- **預留爐台位置**：先空置或放層架，管線排煙拉到位。需主動向設計師提出，否則會依現有設備清單壓縮空間

**設備分階段購置**：開幕僅 IH ×2 + 微波 ×1 + 氣炸烤箱 ×1。未來要現做熱食時再添購爐具。

### 4-2 IH vs 瓦斯

採 IH 路線。優點：免瓦斯申請與定期檢查、無燃燒廢氣、溫控精準（與 SOP 邏輯一致）、無明火、檯面易清潔。

限制：鍋具須為磁性材質；無法爆炒（無鑊氣）；**電力需求大**，多台需專用迴路——此點必須在裝修階段納入電力容量計算。

### 4-3 法規盤點

**登記時建議直接以「有廚房、可現做熱食」的完整規格申請**，不因開幕期只用微波而登記較低類別——升級需重新申報，一開始做足較省事。

待確認項目：
- 公司／商業登記，營業項目含餐飲
- 食品業者登錄
- 食品類別申報
- 從業人員健康檢查
- 衛生管理人員（視規模是否達標）
- 油煙排放相關規範
- 消防設備審查

### 5-2 隔水加熱三項要點

**① 濾網籃是必需品**
直接把包丟進滾水，撈取危險且慢。用附把手的濾網籃，一籃放 3–4 包，時間到整籃提起。每鍋配 2 個交錯使用。

**② 多組計時器**
不同品項時間不同，同鍋可能同時跑兩三種。使用多組計時器或手機多計時，避免遺漏。

**③ 水位與水質**
長時間滾水會蒸發，水位低則加熱不均；包裝袋久泡水會變濁。**每四小時換水一次**，寫入日常檢查表。

### 5-3 冷凍白飯操作（若未來上飯類）

微波 700W 加熱 1–2 分鐘，**須覆蓋一張沾濕的廚房紙巾**，否則米飯表面乾硬，客人一吃即知是冷凍飯。

### 6-1 兩個關鍵決定

**內用餐具：飲料用封口杯（拋棄式），餐點用可洗餐具。**
可洗質感好、長期成本低、符合品牌定位；封口杯避免潑灑風險。

📌 **與周邊的交集**：MIGI 冷飲杯（350 元）自備杯折 10 元 ——
那是**手搖飲**的權益，跟這裡的封口杯是同一條產線上的決定。
見《首店周邊商品規劃》4-1。

**麻將桌專用餐具須特別選**：淺、穩、不易倒，最好有防滑底。深碗在麻將桌上極易被撞。

### 6-2 桌邊器具站（必設）

小碟、竹籤、夾子、餐具、紙巾、濕紙巾。須設在客人自己拿得到的位置，否則店員會被反覆呼叫。

### 6-3 未解決的硬體問題：餐點放置

麻將桌中央是牌、四邊是牌尺與籌碼，**客人沒有地方放碗盤**。此問題直接影響炸物與主食能否真的賣得動。

三個方向擇一：**邊桌／掛式托盤／桌角小平台**。此項須在空間規劃階段一併解決。

⚠ 與《首店周邊商品規劃》4-5 的「自助吧沖洗區」是**同一批待解硬體問題**，
應該一起進空間規劃，不要分兩次提。

## 7. 庫存管理

### 7-1 三類分管

| 類別 | 內容 | 進貨頻率 | 管理強度 |
|---|---|---|---|
| **冷凍** | 主食料理包、炸物、蛋塔生胚、甜點 | 兩週一次 | 低（保存期長） |
| **冷藏** | 甜點成品、鮮奶、煮好的珍珠 | 三天一次 | **高（每日檢查）** |
| **常溫** | 茶葉、堅果、咖啡豆、餅乾盒 | 一個月一次 | 低 |

全料理包模型下，**冷藏區塊已大幅縮減**，是唯一需要每日盯效期的區域。建議製作效期表貼於冰箱門，每日晨間確認。

### 7-2 首月抓量原則

開幕前無法預估銷量，**一律進最小量**，寧可賣完掛「已售完」。

✅ **POS 已經有這個開關**：`products.is_active`（後台商品管理頁右側那顆切換）。
⚠ 但它跟 **`is_available`** 是兩件事，別搞混：
```
is_active     這個商品還在賣嗎        （下架＝不再販售）
is_available  今天供應嗎              （售完＝暫時沒有）
```
🎯 **臨時售完應該用 `is_available`** —— `is_active=false` 是「這個品項退掉了」，
用它表達「今天賣完」會讓報表把它算成已停售商品。

前三週的 POS 數據會揭示真實需求，之後再調整。

自建 POS 的紅利就在這裡——不用猜，看數據。

### 7-3 堅果保存

未開封冷藏，保存期約 8 個月；開封後密封冷藏。大包裝拆封後若一週內未售完會走油耗味。

**建議買 3 公斤級而非 30 公斤級**，寧可多訂幾次。

## 10. 對 POS 系統的需求

菜單定案後，`products` 與 `order_items` 需要以下調整。

> ⚠ **這一節是提案，不是現況。** 下列五個欄位與 `addons` 表**今天都不存在**
> —— 撰寫時要記得，前面第 1、2 節已經先用它們描述菜單了。

### 10-1 products 新增欄位

| 欄位 | 型別 | 用途 |
|---|---|---|
| ~~`display_group`~~ | — | 🔴 **2026-09-10 決定不做，改用既有的 `subcategory`**。見本節末 |
| `prep_station` | text | 出餐路由：`bar` / `kitchen` / `none`。**必須獨立於 `category` 與 `revenue_type`**，否則常溫即取品項會混進出餐佇列 |
| `min_tier` | text | 商品可見性控制。供未來「主廚特調」等隱藏品項使用，POS 依當前客人等級過濾 |
| `option_schema` | jsonb | 該商品支援哪些選項。茶飲、咖啡、厚片、炸物各不相同，前端讀此欄位決定渲染內容，新增品項不必改 code |
| `prep_time` | int | 分三級：隔水加熱 8–12 分、氣炸 6–8 分、吧台／即取 0–1 分 |

> 🔴 **2026-09-08 修正**：原文寫「`prep_station` 必須獨立於 **`kind`**」——
> `kind` 這個欄位 2026-08-19～20 已從整個系統移除，取代它的是
> `category`（放哪一頁）＋ `revenue_type`（錢算哪一類）。
> 🎯 **那句話的意思完全正確，而且已經有前例**：那次拆分就是因為
> 「放哪一頁」與「錢算哪一桶」會分岔。**出餐站是第三個維度**，
> 同樣不可以塞進前兩個之一。
>
> ### 🔴 2026-09-10：`display_group` 不做了，那個問句的答案是「會」
>
> 上面那句「加欄位前先問一句：它與 `category` 會不會又是同一個東西
> 兩個地方？」**方向是對的，但問錯了對象** —— 該比的不是 `category`，
> 是 **`subcategory`**。
>
> ```
> 這份文件要的五類    飲料 · 甜點 · 零嘴 · 炸物 · 主食
> product_taxonomy    DRK  · DES  · SNK  · FRY  · MEAL     ← 一模一樣
> ```
> ⇒ **`subcategory` 本來就在回答這件事**，只是餐飲底下當時只登記了
> DRK 與 MEAL 兩個，看起來像撐不起五個分頁。補三筆主檔資料就夠了，
> 不需要新欄位。
>
> ⚠ 而它自己舉的例子正好證明這一點：「堅果的 `category='fnb'`
> 但客人心裡是零嘴」—— 那是 **`category`** 與分頁分岔，
> 而 `subcategory` 就是 `SNK 零嘴`。
>
> 🎯 **真正會分岔的只有 `prep_station`**（蛋塔歸甜點卻走廚房）——
> 那是**第三個維度**，跟分頁無關，日後要做出餐佇列時仍然要獨立一欄。
>
> ✅ POS 已於 2026-09-10 改成讀 `subcategory`（`migi-pos` 7cca580），
> 分頁順序由 `product_taxonomy.sort` 決定：
> **飲料 20 · 甜點 22 · 炸物 24 · 零嘴 26 · 主食 28**。
> 📌 順序對得上第 2 節的「兩層時機」：牌局中吃得到的排前面。
> 📌 `MEAL` 的中文同時從「餐點」改成「主食」——
> 餐飲底下有五類之後，「餐點」會跟上一層的「餐飲」撞名。

`option_schema` 範例：

```
茶飲：{"sweetness": 5段, "ice": 5段, "addons": true}
咖啡：{"temp": ["冰","熱"], "addons": false}
厚片：{"flavor": ["奶酥","花生","草莓","巧克力"]}
炸物：null
```

⚠ **`option_schema` 管不了庫存。** 要分尺碼／口味獨立算庫存就必須是不同 SKU
（同《首店周邊商品規劃》5-2 的 T恤尺碼問題）。

### 10-2 addons 表（新建）

```
addons: id, name, price, is_active, sort_order
```

開幕期僅一筆（珍珠 10 元）。未來上椰果、茶凍只需後台新增一筆並設 `is_active = true`，**POS 前端自動長出選項，一行 code 都不用改**。

前端務必寫成「渲染 addons 清單」，**不可寫成「珍珠開關」**。

### 10-3 order_items.options（jsonb）

⚠ `order_items` 今天的欄位是
`id, order_id, product_id, qty, created_at, org_id, name, unit_price, line_total, revenue_type`
—— **沒有 `options`**，這是要新增的。

```json
{
  "sweetness": "半糖",
  "ice": "去冰",
  "addons": [
    { "id": "pearl", "name": "珍珠", "price": 10 }
  ]
}
```

**三個設計要點：**

1. **`addons` 必須是陣列**，即使今天只有一個元素。日後擴充不必改 schema 或 migrate 舊資料。
2. **選項須凍結在下單當下**。之後改價或改選項名稱，舊單不得跟著變——這是用 jsonb 而非關聯表的理由。
3. **加料價格須快照進 `options`**。`addons` 表的價格是「現在的定價」，訂單裡存的是「當時付了多少」。不可靠即時查表計算 `subtotal`。

> 📌 **第 3 點與系統現有的原則衝突，要想清楚**：
> `checkout_tx` 2026-08-27 起**單價一律回查 `products` 主檔，不採信前端**
> （硬規則 5.8：前端只送意圖不送事實）。
> ⇒ 加料價格**也必須由後端從 `addons` 查**，前端只送 `addon_id`；
> 「快照」是**後端寫進 `order_items.options` 的動作**，
> 不是「前端送多少就記多少」。
> 🔴 寫成後者的話，改一個 JSON 就能把珍珠買成 0 元。

### 10-4 其他

- **吧台／廚房出餐單必須印出選項**，否則會做錯（半糖去冰不顯示 = 做成正常糖）
- **券綁 `free_product_id` 時須明訂加料是否計入**。建議：券只免商品本體，加料照付。此規則要寫進券的定義，避免現場爭議
  ✅ `coupons.free_product_id` **欄位已存在**（與 `discount_type='free'` 搭配）
- **出餐佇列建議顯示排序編號**。IH 鍋與烤箱是有限資源，同時進來六份時，店員需知道先動哪一個，而非全部標「準備中」
