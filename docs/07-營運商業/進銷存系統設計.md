# 進銷存系統設計

> 2026-09-10 建立。起點是「世界級進銷存需要哪些功能？進出庫？」
> 📌 相關：CLAUDE.md 待辦 44（品項規格）、待辦 18（庫存屬於後台）、
> `docs/07-營運商業/首店餐飲籌備.md`（品項型態的來源）

---

## 一、先回答那個問題：進出庫只是一層，而且不是最難的那一層

世界級進銷存大約七層，由下往上。**進出庫是第 ③ 層的一部分**。

| 層 | 內容 | MIGI 今天 |
|---|---|---|
| ① **料件與單位** | 採購單位／使用單位／銷售單位的**換算率**（一箱 24 瓶、一個蛋糕 8 片） | ❌ |
| ② **進** | 供應商、採購單、**收貨**、進貨成本、退供 | ❌ |
| ③ **存** | **異動流水**、多店庫存、調撥、**盤點**、報廢耗損、效期批次 | ❌ |
| ④ **銷** | 銷售扣帳、**配方 BOM**、退貨 | ❌ |
| ⑤ **成本評價** | 加權平均／FIFO／標準成本 | ❌ |
| ⑥ **補貨** | 安全庫存、再訂購點、低量警示 | ❌ |
| ⑦ **報表** | 周轉率、呆滯品、**損耗率** | ❌ |

### 🔴 實查現況（2026-09-10）

```
會扣 stock_qty 的函式        0 支
碰得到它的                   admin_list_products_tx（讀）
                            admin_upsert_product_tx（後台手打時整個覆寫）
進貨／異動／供應商的表        一張都沒有
products.unit_cost          九筆全部是 0        ← 成本會計也還沒開始
現在的庫存                   水餃 50 · 厚片 50   ← 賣掉 202 筆品項一次都沒動過
```

⇒ **那個 50 是有人在後台打上去的裝飾。** 進銷存不是「做了一半」，是**完全不存在**。

## 二、真正決定這套系統有沒有用的，只有三件事

其餘四層都是這三件事的延伸。

### 🎯 ① 庫存是一本流水帳，不是一個數字

`stock_qty` 是**結果**不是事實。沒有異動流水，就永遠答不出
「為什麼少了 30 個」——而那正是唯一有人會問的問題。

📌 這與 `wallet_txns` 是同一個形狀：**流水 append-only、餘額靠重算**。
CLAUDE.md 已經記過「能重算就不要相加」，庫存完全適用。

⚠ 每一筆異動要記：類型、數量、**前後結存**、來源單據、時間、誰。
少了「誰」與「來源單據」，盤虧的時候沒有任何線索。

### 🎯 ② 單位換算是最容易被低估、錯了全盤皆錯的一層

你**買一種單位、用另一種、賣第三種**。

```
買   一箱 24 瓶
用   一瓶
賣   一杯（一瓶倒 3 杯）
```

這三個數字對不起來，上面六層全部是垃圾 —— 而且**不會報錯**，
只會讓報表安靜地錯。

### 🎯 ③ 盤點是唯一的校正機制

帳面**一定**會偏離現實，因為耗損、試吃、打翻、報廢**都不會自己進系統**。

⚠ 沒有盤點，誤差會無限累積，然後所有人開始不看那個數字 ——
**一個永遠不準的數字會訓練人忽略它**，跟硬規則 3.5 那個
「永遠紅的檢查」是同一個病。

## 三、🔴 MIGI 需不需要配方 BOM：看品項型態，不是看規模

《首店餐飲籌備》寫得很清楚：**首店不設廚師、不現做熱食，
所有主食採「連麵一起的整份」冷凍料理包**，而**飲料吧台現調**。

那句話直接決定了答案：

| 型態 | 例子 | 需要什麼 |
|---|---|---|
| **整份料理包** | 主食 10 項、炸物、冷凍甜點 | 1 包 ＝ 1 份 ⇒ **只要進出庫**，連換算都不用 |
| **需分切** | 巴斯克乳酪、千層蛋糕 | **換算率**（1 個 ＝ 8 片） |
| **大包裝分裝** | 零食（大包裝進貨、店內分裝小陶碟） | **換算率** |
| 🔴 **現調** | **飲料吧台** | **這才是 BOM** |

### ⚠ 一個要更正的說法

2026-09-10 我先講「世界級的解法是配方 BOM」——**那是把答案講得比問題大**。

```
水餃 / 厚片 / 雞塊   叫貨進來直接賣   → ①單位換算（甚至 1:1）
珍奶                 自己調           → ④配方
```

一包 100 顆水餃拆成 10 份，那是**一個換算率不是配方**。
🎯 **配方要等飲料吧台真的開始營運才出現**，而那時它只涵蓋飲料那一類，
不是整套菜單。

## 四、最小版：依痛感排序，不是照七層做

| | 做什麼 | 為什麼是這個順序 |
|---|---|---|
| **1** | **異動流水表 ＋ 結帳扣帳** | 沒有這個，其他每一項都是空的 |
| **2** | **進貨**（跟誰買、幾個、多少錢） | 流水才有來源；順帶把 `unit_cost` 填起來，毛利才算得出來 |
| **3** | **盤點** | 帳面一定會偏，這是唯一的校正 |
| **4** | **損耗**（報廢、試吃、打翻） | 不記的話盤點永遠對不起來，**而人會怪系統不準** |
| **5** | **換算率** | 分切與分裝的品項才需要 |
| **6** | 配方 BOM | **飲料吧台上線那天**，不是現在 |

### 🎯 而它有一個今天就存在的商業驅動力

《首店餐飲籌備》自己寫了：

> **冷凍容量是最容易低估的硬體。** 32 項中約 21 項需冷凍……
> 開幕前務必試算：每項每日預估份數 × 進貨週期 = 所需包裝體積。

⇒ **「每項每天賣幾份」正是進銷存的第一個產出**，
而那個數字決定進貨週期與冷凍櫃要買幾台。
📌 這不是抽象的「管理需求」，是一筆會花錢的硬體決定。

## 五、永遠不要做（明列，不要每次重新討論）

- **效期批次追蹤（FIFO/FEFO）** —— 除非開始賣生鮮。冷凍料理包的效期以月計，
  用「進貨日 ＋ 目視」就夠，而批次追蹤要每一筆異動都帶批號
- **多倉調撥** —— 見下面那一節。🔴 **真正的理由不是「店太少」，
  是七間店裡只有三間是你的庫存。**
- **標準成本差異分析** —— 那是工廠的東西（料工費差異），
  MIGI 的成本就是進貨價
- **MRP 需求規劃** —— 為生產排程設計的，這裡沒有生產

⚠ 判準同硬規則 5.5：**這個功能需要有人每週維護嗎？需要的話先確認那個人存在。**

## 五之一、🔴 多倉調撥：七間店不是七個倉

### 我第一版寫錯了，而且錯得很有代表性

我原本寫「等真的有兩間店在互相調貨。**今天七間店裡只有一間在營運**」——
**兩處都是我沒查就寫的**（硬規則 3）。實查 `stores`：

| `store_type` | 幾間 | 哪些 |
|---|---|---|
| **直營** | 3 | MIGI 高雄自由 `S01`、前鎮 `S02`、台南東區 `S04` |
| **加盟** | 2 | MAYU 苓雅 `S03`、MAYU 西屯 `S06` |
| **系統授權** | 1 | 大雅雀藝館 `S07` |
| **自家場** | 1 | 永康雀友場 `S05` |

```
七間全部 is_test = true      ← 一間都還沒真的營運，不是「只有一間」
有桌位的只有兩間             MIGI 高雄自由 14 桌 · MIGI 前鎮 4 桌
其餘五間                     0 桌 0 場 0 訂單
```

### 🎯 而那張表給了一個比「店太少」強得多的理由

**調撥的前提不是「有兩間店」，是「兩間店屬於同一個庫存主體」。**

```
直營 3 間之間搬貨   → 是「移動」，同一個主體，調撥說得通
加盟 / 系統授權 / 自家場 4 間 → 🔴 那不是你的庫存
```

⚠ 把貨從直營店「調撥」到加盟店，**在帳務與稅務上是一筆銷售不是一次移動** ——
它要開發票、要認列收入、要算加盟商的進貨成本。
📌 那屬於 `docs/07-營運商業/加盟帳務設計.md` 的範圍，不是進銷存的調撥功能。

🔴 **所以「多倉調撥」這個功能名稱本身就會誤導人**：
做出來之後，第一個使用它的人很可能拿它把貨「調」給加盟店，
而那一筆**應該是訂單**。系統不會報錯，只會讓兩邊的帳都錯。

⇒ **真的要做的時候，第一個問題是「這兩間店是不是同一個法人」**，
不是「怎麼搬數字」。

## 六、放哪裡：`migi-admin`

📌 **待辦 18 早就拍板，不要重新討論**：

> 庫存與報表不回來：那是 `migi-admin` 的事。前場與後台是兩套 App
> （Square Register 上沒有進貨單），放進 POS 就是同一件事兩個地方維護。

### ⚠ 唯一的細節：盤點是在店裡拿著平板走動做的

那一頁**仍然屬於後台**，但版型要能在平板上用。
📌 同待辦 10 的判準：**一套版型站在滑鼠與手指的交集**，
不要為平板做第二套（斷點判斷的是寬度，而 1024px 的平板與
1024px 的筆電視窗寬度一模一樣）。

## 七、🔴 九成的成本不在程式，在每天的紀律

②③④ 每一項都需要**有人在店裡動手**：

```
收貨    要有人清點實到幾箱，而不是照單簽收
盤點    要有人固定週期數
損耗    打翻一杯要有人記一筆
```

⚠ **這三件事沒有人做，系統就會產出一個持續偏離現實的帳面庫存** ——
而那比沒有系統更糟，因為它看起來像有。

🎯 所以開工前要先回答的不是「用什麼架構」，是
**「誰收貨、誰盤點、多久盤一次」**。
