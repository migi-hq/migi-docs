## 0. 一句話

**60 枚 ＝ 60 個事件名，一對一。**
🔴 **不可以讓兩枚共用一個事件名** —— `fire_event_tx` 只比對 `trigger->>'event'`，
共用的話一次事件會把那一批**全開**（跟 meta 那個洞一模一樣）。
⚠ 唯一的例外是 `onboarding_29`（meta，帶 `count`），它走 `ach_meta_tx`。

## 4. ⚠ 兩個數字要一起看

```
新手畢業的門檻                      15 枚
A 區可解鎖的（active，不含它自己）   17 枚   ← 線上實測
```
🔴 **差距只有 2 枚。** 日後把 A 區任何一枚關掉之前先回來看這裡 ——
關掉 3 枚就變成一枚**永遠解不開**的成就，而那不會報錯。
✅ 匯入 SQL 的驗證段第 ⑦ 格就是在盯這件事。

### 🎯 而這個數字是驗證段抓出來的，不是我算對的
我在這裡與匯入 SQL 的註解裡都寫過「差距 3 枚」，因為我把
**`active 18` 直接當成「可解鎖 18」** —— 而那 18 枚裡有一枚
就是「新手畢業」自己，**它不能算進自己的門檻**。
⚠ 差一枚看起來無所謂，但它正好是「還剩幾枚可以關掉」的餘裕，
而那個餘裕被高估時，症狀是**某天關掉第 3 枚，成就從此永遠解不開**。
📌 同硬規則 3.56 的反面：那次是期望值錯、函式對；
  **這次是期望值錯、而驗證段寫對了，所以它把我抓出來。**
