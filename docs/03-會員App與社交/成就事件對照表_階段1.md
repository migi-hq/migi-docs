### 🎯 餐飲與儲值走觸發器，那是查證出來的不是偏好
```
orders 的 AFTER INSERT 看不到品項   checkout_tx:223 插 orders、:239 才插 items
checkout_tx 是 302 行 ＋ INVOKER     全系統的計價／券／等級引擎
⇒ 觸發器掛 order_items（statement 級 ＋ transition table）與 topup_orders
```
🔴 **判準是 `products.subcategory` 不是 `order_items.revenue_type`** ——
餐飲三類全是 `fnb`，用 revenue_type 的話**甜點會被算成餐點**。
✅ 行為測試第 ① 格就是那個負對照（只買甜點不可以解鎖），它過了。
🔴 **觸發器要自己吞例外** —— 它沒有呼叫端能包它，不吞的話
成就寫入失敗會**回滾整筆結帳**。（與 `settle_session_tx` 做法不同，
那裡是呼叫端包。）

### 🎯 第三批本來要改 8 支函式，查證之後換成 7 個觸發器
決定性的一筆：**寫 `team_members` 的函式有四支**
```
apply_team_tx · create_team_tx · invite_to_team_tx · respond_team_request_tx
```
而這張表原本只記了 `respond_team_request_tx` 一支
⇒ **改函式的話，另外三條入團路徑永遠不會發事件，而且不報錯。**
📌 同一個形狀也出現在 `member_registered`：觸發器掛 `AFTER INSERT`
⇒ `rebound`／`existing_line` 走的是 UPDATE，**天生排除，不用寫條件**。

🔴 **`team_joined` 的 WHEN 要排除 `role = 'leader'`：**
`create_team_tx` 會把團長自己也插一列 ⇒ 不排除的話建團的人同一秒
拿到 21 與 22 兩枚，而 22 的說明是「找到一起打牌的人了」——
**建自己的團不是那件事。**
✅ 行為測試 ⑧⑨ 是同一組正負對照：團長只有 21、入團的 B 只有 22。

🔴 **`buddy_added` 只對 `member_id` 發。** 牌咖是雙向關係，
`respond_buddy_invite_tx` 插的是 A→B 與 B→A **兩列**，逐列觸發剛好一人一次。
（多事一點對 `buddy_id` 也發，就變成每人兩次。）

🔴 **`like_given` 與 `like_received` 的兩個 perform 各包一層例外** ——
與其餘五支不同，因為 target 是**別人**：他那邊寫入失敗不該讓按讚的人也拿不到。

🔴 **「發在哪」這一欄 2026-09-20 整欄改過** —— 原本寫的是「應該改哪支函式」，
而實際落地的是觸發器。**照舊值去改函式的話，改完什麼都不會發生。**

| 事件 | 發在哪 | 成就 | 備註 |
|---|---|---|---|
| `member_registered` | `members` AFTER **INSERT** | 新手報到 | 🎯 `rebound`／`existing_line` 走 UPDATE ⇒ 天生排除 |
| `title_granted` | 同上（同一支觸發器函式） | 第一個稱號 | **稱號是註冊預設就有的** ⇒ 與註冊同一個時刻。條件 `title <> ''`：日後拿掉 DEFAULT 它會自己停 |
| `rank_placed` | `members` AFTER UPDATE OF rank | 取得正式段位 | WHEN `old.rank is null and new.rank is not null` ⇒ **升等不重發** |
| `session_finished` | `settle_session_tx` | 第一次開桌 | 🎯 最大的發射點，日後 B 區也掛這裡 |
| `session_won` | `settle_session_tx` | 第一次贏得牌局 | 判準是 `final_score > 0`（**不是名次**，見 CLAUDE.md） |
| `queue_session_done` | `settle_session_tx` | 第一次參與配桌 | 那一場的 `mode = 'matched'` |
| `booking_session_done` | `settle_session_tx` | 第一次預約包桌 | 那一場來自 `bookings` |
| `fnb_drink` | `order_items`（statement 級） | 第一杯飲料 | `products.subcategory = 'DRK'` |
| `fnb_meal` | 同上 | 第一份餐點 | `subcategory in ('MEAL','FRY','SNK')` |
| `topup` | `topup_orders` | 第一次儲值 | WHEN `status='paid' and member_id is not null` |
| `snack_granted` | `snack_grants` | 第一個點心 | `qty > 0` |
| `snack_consumed` | 同上（同一支） | 餵一次小熊 | `qty < 0`。**用正負號分，不綁 `reason`** —— 日後多一種扣減理由時綁 reason 會安靜地不算 |
| `team_created` | `teams` | 建立牌咖團 | `created_by` |
| `team_joined` | `team_members` | 加入牌咖團 | 🔴 WHEN 排除 `role='leader'`，涵蓋**全部四條**入團路徑 |
| `like_given` | `member_likes` | 送出第一個讚 | 🎯 一列發**兩個**事件 |
| `like_received` | 同上（同一支） | 收到第一個讚 | ⚠ 對象是 `target_id`，不是呼叫者 |
| `buddy_added` | `mahjong_buddies` | 第一個牌咖 | 🎯 只對 `member_id` 發 —— 雙向兩列，逐列觸發剛好一人一次 |
| — | — | 新手畢業 | **meta**，`ach_meta_tx` 自己處理，不用發事件 |

### 🔴 `title_granted`：稱號是**註冊預設就有**（2026-09-20 拍板）
```
members.title   NOT NULL DEFAULT '新手上路'   ← 註冊那一刻就戴上了
```
⇒ `register_member_tx` 的 `'created'` 那條路要發**兩個事件**：
`member_registered` ＋ `title_granted`（同一支函式兩個事件，
同 `like_player_tx` 發 `like_given` ＋ `like_received`）。

⚠ **同一天先選過「改成賺來的」又改回來**，而那個往返留下一個有用的分辨：
```
member_app_state.titles = []   ✅ 對的 —— 那是「解鎖清單」，預設稱號不在裡面
set_my_title_tx 放行新手上路    ✅ 對的 —— 它不是解鎖來的，所以不必在清單裡
```
🎯 **同樣這兩件事，在「賺來的」那個前提下是缺陷，在「預設就有」下是正確。**
📄 那份被推翻的設計留在 `sql/_設計稿未落地/2026-09-20_稱號改成賺來的.sql`
—— 裡面**步驟 ③④ 日後還要用**：`ach_unlock_tx` 今天**不會**把
`grants_title` 寫進 `members.title`（只回傳），而旗艦 MIGI 那枚就是
`grants_title = 'MIGI'`。

### ✅ 三個容易漏的，三個都有對應的驗證格
· **`like_received` 的對象是別人** —— 照抄 `like_given` 會把讚記在按的人身上。
  → 行為測試 ⑪ 是**交叉負對照**：A 不可以有「收到」、B 不可以有「送出」。
· **`buddy_added` 兩個人都要發** —— 牌咖是雙向關係。→ ⑫ 驗兩個人都拿到。
· **`member_registered` 只在真的新建時發** —— `rebound`（舊客人換 LINE）
  那條路發了的話，一個 2019 年的老客人會在換手機那天拿到「新手報到」。
  → **靠 `AFTER INSERT` 這個選擇本身擋掉**，不是靠條件式（改不壞）。

## 4. ⚠ 兩個數字要一起看

