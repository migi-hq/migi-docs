> 2026-08-30 建立、同日更新。動任何與「客人是誰」有關的東西之前先讀這份。
> 每一格都是查 `pg_proc` / `information_schema` / `pg_constraint` 查證過的，不是設計稿。

## 為什麼會有這份文件

MIGI 的會員身分由**兩條線索**組成：

| 線索 | 來源 | 誰保證它是真的 | 判定 |
|---|---|---|---|
| `members.line_user_id` | LIFF `id_token` → Edge Function 驗簽 | LINE | ✅ 可信 |
| `members.phone` | **客人自己填的** | **沒有人** | 🔴 不可信 |

🔴 **所有問題都源於第二行。** 手機在 MIGI 不只是聯絡方式，
它是**認回舊帳號的鑰匙** —— 而一把沒有人驗證過的鑰匙，就是一把公開的鑰匙。

### A 表改了什麼

| # | 改前 | 判定 | 改後 |
|---|---|---|---|
| A3 | `rebound` → **直接把 LINE 綁進他的帳號** | 🔴 帳號接管 | `phone_taken`，不寫入 |

🎯 **`line_conflict` 這個 action 消失了** —— 它跟 A3 對客人是同一件事
（「這支號碼屬於一個不是你的帳號」）。分兩個名字只會讓前端維護一份**一定會漏**的清單，

⚠ **A2 不能砍**：LIFF 在網路不穩時重送很常見，
砍掉會讓「已經綁好的人再按一次」變成「請洽櫃檯」。

⚠ **順序反過來才是這次改動的核心**：原版是**先寫再判斷**
（`update … where line_user_id is null` → 看 `FOUND`），
所以「不該綁」那一刻資料已經寫進去了。現在是先查、不是他就直接 return。

## 表 B · 六種客人，六條路

> 這一節用**櫃檯講得出口的說法**寫（2026-08-30 使用者確認過的六條），
> 而不是用資料表的欄位。左邊是客人的處境，右邊是系統實際會做什麼。

| # | 客人的處境 | 系統做什麼 | 狀態 |
|---|---|---|---|
| **B1** | **新客人** | 授權（無感）→ 暱稱 → 手機 → **驗證碼** → 生日 → 性別 → 完成 | ✅ 已上線 |
| **B2** | **老客人，沒登出** | 比對 `line_user_id` → 直接進 App | ✅ 已上線 |
| **B3** | **老客人，自己登出過** | 同上 —— **不重走註冊、不發簡訊** | ✅ 已上線 |
| **B4** | **換了 LINE**（門號沒變） | 應該：驗手機 → 認回舊帳號 | 🔴 **還沒做**，現在走櫃檯 |
| **B5** | **換了門號**（LINE 沒變） | 照樣直接進 App；到個人設定驗新號碼 | 🟡 **登入沒問題，改手機的工具還沒做** |
| **B6** | **兩個都換** | ① 找店員換綁　② 或重新註冊（舊資料留在原帳號） | ✅ 對，但有順序陷阱 ↓ |

### B1 · 沒有「註冊按鈕」

從圖文選單點進來**就是 LIFF 授權**，在 LINE 內是無感的（客人什麼都不用按）。
⚠ 所以流程圖上不要畫「點選註冊」那一步 —— 它不存在。

### B2／B3 · 其實是兩層

`localStorage` 先畫（不白屏）→ **背景用 `line_user_id` 校正**。
所以本機存的就算是舊的、甚至是別人的，也會被換成對的（C6 因此關閉）。
🔴 但**問不到時保持現狀，不登出** —— 店裡 wifi 一抖就把客人踢出去，比顯示舊名字糟得多。

### 🔴 B4 有一個前提，不做到就會出事

```
要用「驗過的手機」認回舊帳號
  → 前提是**舊帳號上的手機本來就驗證過**
```

否則：A 填錯號碼填成 B 的（未驗證）→ B 之後驗證成功
→ **B 拿到 A 的點數與消費紀錄**。那就是 C4。

🎯 **這反過來證明「註冊時就強制驗」是對的**：
只要每個帳號從第一天就驗過，這個模糊地帶根本不存在。
⚠ 現況：既有 5 個測試帳號的 `phone_verified_at` **都是 null**，
所以就算 B4 做出來，他們也認不回來 —— 只能走櫃檯。真實客人不會有這個問題。

### 🔴 B6 的順序陷阱 —— 話術要先講

```
❌ 先重新註冊 → 變成兩個帳號 → 只能靠合併工具 → **不存在**（待辦 15）
✅ 先找店員   → 換綁就好（rebind_line_user_tx，函式已存在）
```

⚠ 所以對外說法是「**先別自己註冊，先找我們**」。
註冊完再說就晚了：那時 `rebind_line_user_tx` 會回 `line_user_already_bound`。

### 📌 為什麼登入只比對 LINE 不比對手機

| | 用途 | 登入會用到嗎 |
|---|---|---|
| `line_user_id` | **身分** | ✅ 唯一的依據 |
| `phone` | 聯絡方式 ＋ 換 LINE 時的找回線索 | ❌ 完全不用 |

不用手機當登入依據的三個理由：
**① 門號會被回收** —— 你退租，幾個月後電信商發給別人，那個人就變成你。
**② 每次都要重驗** —— 手機沒有「持續登入」的狀態，用它登入等於每次都發簡訊。
**③ LINE 已經驗過了** —— LINE 帳號本身就要手機驗證才開得了。

🎯 所以 **B4 能不能自助，決定了手機這個欄位有沒有意義** ——
它是唯一能跨越「換了 LINE」的線索。

### C4 的形狀 —— 從「接管」變成「阻斷」

客人 A 把自己的手機改成 B 還沒註冊的號碼
→ B 之後註冊時拿到 `phone_taken` → **B 永遠註冊不了那支號碼**。
⚠ 不再是接管（A3 已堵），但仍然是阻斷。
→ 所以 `set_member_phone_tx`（D2）做出來時，**改已有值的手機一定要走店員**。

### C6 已經真的發生過（2026-08-29），2026-08-30 修掉

創辦人在 LIFF 走註冊，**進去變成測試01**。
資料庫可以證明 `register_member_tx` 一次都沒被呼叫到 ——
不是「繼承」，是那台裝置的 localStorage 裡存著別人，
所以**連 LINE 授權那一步都不會出現**。

```js
App.jsx:95   if (!member) return <Register …/>      // 修之前：member 來自 localStorage
```

🔴 **那時這個 App 的身分是 localStorage 說了算，不是 LINE 說了算。**

✅ **修法：本機當首屏，LINE 負責校正。**
開機仍然先用本機值畫（不白屏），同時背景 `whoAmI()`：

| 後端說 | 做什麼 |
|---|---|
| 是這個人 | 換成他 |
| **明確**沒有這個人 | 登出 |
| **問不到** | 🔴 **保持現狀，不可以登出** |

⚠ 最後一條最重要：**問不到 ≠ 沒有**。
店裡 wifi 一抖就把客人踢出去，比顯示一個舊名字糟得多。
⚠ 為什麼不「一律先問後端再畫」：那會讓每次開 App 白屏 1–2 秒，
而 LIFF 是 LINE 的內建瀏覽器、網路本來就不穩。
📌 這跟暱稱、頭像、餘額是同一套做法 —— 差別只在身分這一格以前沒有人做校正。

## 📌 兩個原則

### ① 驗證（你是誰）與聯絡（怎麼找到你）是兩件事

| 手機拿來做什麼 | 需要驗證嗎 | 業界對照 |
|---|---|---|
| 當身分 | ❌ LINE 已經驗過了 | — |
| 當聯絡方式（叫車、桌況、客訴） | ❌ 填錯頂多打不通 | foodpanda / Uber Eats：**那支手機不認回舊帳號** |
| 🔴 **當認回舊帳號的鑰匙** | ✅ **一定要** | 星巴克 / 全聯：手機當主鍵 → **一定發 OTP** |

**MIGI 修之前是第三種，卻沒有驗證。**

### ② `member_id` 是通行證，在待辦 14 完成之前

`get_wallet_tx(p_member_id)` / `get_my_orders_tx(p_member_id)` 都是 anon 叫得動的。
🔴 所以**任何會回傳別人 `member_id` 的路徑都是洞** ——
而那正是修之前 A4／A5 在做的事，且那段程式碼的註解還寫著
「不回傳對方的 `line_user_id` —— 那是別人的識別碼」。**防到了錯的東西。**
