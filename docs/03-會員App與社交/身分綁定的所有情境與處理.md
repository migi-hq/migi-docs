# 身分綁定：所有情境與處理流程

> 2026-08-30 建立。動任何與「客人是誰」有關的東西之前先讀這份。
> 每一格都是查 `pg_proc` / `information_schema` 查證過的，不是設計稿。

## 這份文件要回答的問題

MIGI 的會員身分由**兩條線索**組成：

| | 來源 | 誰保證它是真的 |
|---|---|---|
| `members.line_user_id` | LIFF 的 `id_token`，Edge Function 驗簽後取得 | ✅ LINE |
| `members.phone` | **客人自己填的** | 🔴 **沒有人** |

🔴 **所有問題都源於第二行。** 手機在 MIGI 不只是聯絡方式，
它是**認回舊帳號的鑰匙**（`register_member_tx` 用它找人並綁定）——
而一把沒有人驗證過的鑰匙，就是一把公開的鑰匙。

## 表 A · 註冊／登入當下的每一種組合

進入點：LIFF → `liff.getIDToken()` → Edge Function `line-login`（service_role）
→ 驗簽取得 `sub` → `register_member_tx(org, 暱稱, 手機, sub)`。

🔴 **前端從頭到尾沒有一個「可以自由填的身分參數」** —— 那是整套設計的核心。

### 判斷順序（三份都套用之後）

| # | 條件 | action | 給 member_id？ | 客人看到 |
|---|---|---|---|---|
| **A1** | `line_user_id` 查得到 | `existing_line` | ✅ **他自己的** | 直接進 App「歡迎回來」 |
| **A2** | 手機查得到，且那個帳號的 LINE **就是他** | `existing_line` | ✅ **他自己的** | 同上（重試／併發） |
| **A3** | 手機查得到，**其他任何情況** | **`phone_taken`** | ❌ | 「這支手機已經是 MIGI 會員了。請用原本的 LINE 帳號登入，或在櫃檯出示這個畫面由店員協助綁定。」 |
| **A4** | 沒送 `line_user_id` ＋ 手機查得到 | `existing_phone` | ❌ | 同上 |
| **A5** | 都查不到 | `created` | ✅ 新建的 | 「歡迎加入 MIGI」 |
| **A6** | 沒填手機 ＋ 沒 LINE | raise `need phone or line_user_id` | — | 錯誤訊息 |

### 改了什麼

| | 改前 | 改後 |
|---|---|---|
| 手機對得上、對方**沒綁** LINE | 🔴 `rebound` → **直接綁進他的帳號** | `phone_taken`，**一個字都不寫** |
| 手機對得上、對方**已綁別的** | `line_conflict`，但**交出 member_id** | 併進 `phone_taken`，不給 id |
| 沒送 LINE、手機對得上 | 🔴 `existing_phone` ＋ **交出 member_id** | `existing_phone`，不給 id |
| 誰能呼叫 | 🔴 **anon ＋ PUBLIC** | 只有 `service_role`（Edge Function） |

🎯 **`line_conflict` 這個 action 消失了** —— 它與 A3 對客人是同一件事
（「這支號碼屬於一個不是你的帳號」），分兩個名字只會讓前端要維護一份清單。

⚠ **A2 不能砍**：LIFF 在網路不穩時重送很常見，
砍掉會讓「已經綁好的人再按一次」變成「請洽櫃檯」。

⚠ **順序反過來才是這次改動的重點**：原版是**先寫再判斷**
（`update … where line_user_id is null` → 看 `FOUND`），
所以「不該綁」那一刻資料已經寫進去了。現在是先查、不是他就直接 return。

### 🔴 順帶的後果：POS 也叫不動 `register_member_tx` 了

它用 anon。今天 POS **沒有註冊功能**（三個 repo 掃過零呼叫），所以沒壞。
⏳ 但日後要做「櫃檯幫客人註冊」，需要一支 DEFINER 包裝或走 Edge Function。

### 🔴 A3：帳號接管

```sql
update members set line_user_id = p_line_user_id
 where id = v_existing and line_user_id is null;   -- v_existing = 手機對得上的那個人
```

填一個**還沒綁 LINE 的舊客人的手機** → 你的 LINE 綁進他的帳號
→ 錢包、消費紀錄、等級、優惠券全部到手。

⚠ 唯一的護欄是 `line_user_id is null`，所以**暴露的正是「櫃檯註冊過但還沒用 LINE 的舊客人」**
—— 而那群人正是**有餘額的人**。

### 🔴 A4／A5：不用綁定就能看到別人的錢包

`line_conflict` 那段的註解寫著「不回傳對方的 line_user_id —— 那是別人的識別碼」，
**但它回傳了 `member_id` 與 `display_name`** ——
而在待辦 14 完成之前，**`member_id` 才是會員端的通行證**：

```
register_member_tx(org, '隨便一個暱稱', 對方的手機)  → member_id
get_wallet_tx(member_id)      → 餘額、優惠券、點數流水
get_my_orders_tx(member_id)   → 完整消費明細
```

🔴 **防到了錯的東西。**
📌 已修：`sql/applied/2026-08-30_註冊路徑停止洩漏會員身分.sql`
（收回 anon ＋ A4／A5 不再交出 `member_id`）。

| # | 情境 | 登入還通嗎 | 現在會怎樣 | 該怎麼處理 |
|---|---|---|---|---|
| **B1** | 老客人再來（同 LINE、同手機） | ✅ | A1 | — |
| **B2** | 全新客人 | ✅ | A2 | — |


**「讓客人能改手機」不是小功能，它是唯一能預防 B5 的東西。**

### 🔴 C4 的形狀（唯一還開著的自助路徑）

客人 A 把自己的手機**改成 B 還沒註冊的號碼**
→ B 之後註冊時手機對得上 A 的帳號 → `phone_taken` → B 進不去。
⚠ 現在不會被接管了（A3 已堵），但會變成**阻斷**：B 永遠註冊不了那支號碼。
→ 所以 `set_member_phone_tx`（D2）做出來時，**改已有值的手機一定要走店員**。

### ⚠ C10 是這次改動的代價，要講清楚

堵掉 A3 之後，**換了 LINE 的舊客人自己救不回來**。
今天零影響（4 個測試帳號 ＋ 創辦人，而創辦人已綁好），
但**上線前必須把表 E 的 ① 或 ② 做出來**，否則會變成客訴。

### 🔴 C6 已經真的發生過

2026-08-29：創辦人在 LIFF 走註冊，**進去變成測試01**。
資料庫可以證明 `register_member_tx` 一次都沒被呼叫到 ——
不是「繼承」，是那台裝置的 localStorage 裡存著別人，
所以**連 LINE 授權那一步都不會出現**。

```js

```

⚠ 當下的解法是「個人設定 → 登出」，但那只是繞過。
**這個 App 的身分是 localStorage 說了算，不是 LINE 說了算。**

所以「店員換綁」不是「按一個鈕」，需要一個交換機制：

```

店員 POS  →  搜手機找到舊帳號 → 輸入那 6 碼
          →  rebind_line_user_tx(org, member, line_user_id, staff_id)
```

要做：`line_bind_codes` 表 ＋ 產碼／核碼兩支 RPC ＋ 兩端各一個畫面 ＋ 店員登入。
⚠ **唸 LINE 名稱給店員是不行的** —— `line_user_id` 不是名稱，而且名稱可以改。

## 📌 順帶記下來的兩個原則

**① 驗證（你是誰）與聯絡（怎麼找到你）是兩件事。**

| 手機拿來做什麼 | 需要驗證嗎 |
|---|---|
| 當身分 | ❌ 不用 —— LINE 已經驗過了 |
| 當聯絡方式（叫車、桌況、客訴） | ❌ 不用 OTP —— 填錯頂多打不通 |
| 🔴 **當認回舊帳號的鑰匙** | ✅ **一定要** |

📌 foodpanda／Uber Eats 台灣用 LINE 登入後也要填手機，但**那支手機不會認回舊帳號**
—— 所以他們不需要 OTP。星巴克、全聯是手機當主鍵 → 他們**一定**發 OTP。
**MIGI 現在是第三種，卻沒有驗證。**

**② 待辦 14（JWT）是根本解，但它不能單獨做。**
JWT 之後 `member_id` 不再是通行證，A4／A5／C3 自然消失。
⚠ 但待辦 21 的五項阻擋條件必須先完成，而其中一項（帳號合併）
**必須在 JWT 之前或同時做** —— JWT 上線那一刻就是
「LINE 帳號 ↔ member」正式綁定的時候，那時若已有重複帳號，綁定會固定下來。
