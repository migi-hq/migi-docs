# 抽獎獎品池設計

> 2026-08-27 建立。**維度與機制已定案，詳細品項待討論。**
> 對應：`CLAUDE.md` 待辦 33（會員 App 接線進度表）的「搓牌抽獎」那一格。
> 現況：`migi-web/src/pages/rewards.jsx` 的抽獎是**純前端**
> （`Math.random()`，不扣點、獎品不會發、點數顯示寫死 1,250）。

---

## 一、定價前提（所有數字的基礎）

儲值 1000 送 150 點 → **1 點的實付成本 ≈ 0.87 元**。

```
單抽 50 點  ≈ 客人實付 43.5 元
十連 450 點 ≈ 客人實付 391 元
```

→ **抽獎的獎品池設計，本質上是定價問題，不是遊戲設計問題。**
每一抽的獎品期望成本必須明顯低於 43.5 元。

⚠ 抽獎**不是營收**：客人用的是已經付過的錢（預收款）。
抽獎是**把負債轉成商品成本**。這一點會影響報表怎麼看它。

---

## 二、🔴 MIGI 與手遊的三個根本差異

不能照抄手遊的獎品池設計，因為：

| | 手遊 | MIGI |
|---|---|---|
| **獎品邊際成本** | SSR 角色 = 0 | T恤、提拉米蘇都有真實成本 |
| **貨幣性質** | 遊戲貨幣（憑空發行） | **點數 = 預收款 = 真錢負債** |
| **公平性風險** | 課金影響戰力（pay-to-win） | ✅ 不存在 —— 獎品不影響牌局，可以純粹是樂趣 |

🔴 **獎品池不要放點數** —— 拿負債換負債，會計上毫無意義，等於用抽獎印錢。

---

## 三、獎品的五個維度（決定主檔 schema）

| 維度 | 值 | 用途 |
|---|---|---|
| **履約方式** | `app_state` ／ `coupon` ／ `free_product` | 決定發獎程式怎麼寫 |
| **邊際成本** | 金額（0 = 零成本） | 🔴 **算期望值 —— 定價的核心** |
| **可否重複** | 是／否 | 永久品要有重複轉換規則 |
| **總量上限** | null ／ 數字 | 限量實體 |
| **是否啟用** | bool | 分批上架用 |

### 🎯 稀有度不是分類維度

**稀有度是機率的顯示結果**，主檔不用存它，抽獎動畫自己推導：

```
機率 < 0.5%  → 傳說
機率 < 2%    → 史詩
機率 < 5%    → 稀有
其餘         → 普通
```

⚠ `rewards.jsx` 的 `TIER_UI`（glow／sparkle／halo）已經寫好了，繼續用。

### 🎯 履約方式只有三種，而且都已經存在

| 方式 | 機制 | 現況 |
|---|---|---|
| `app_state` | 寫進養成熊狀態 | ✅ `save_app_state_tx` 已有 |
| `coupon` | 發一張折抵券 | ✅ `member_coupons` 整套已有 |
| `free_product` | 發一張**免費兌換指定商品**的券 | ✅ `coupons.discount_type='free'` ＋ `free_product_id` 已存在 |

🔴 **不需要建兌換子系統，也不需要 POS 新畫面。**
實體獎品（T恤、牌尺）就是一張指定商品的免費券，
客人來店裡結帳時照現有流程核銷，庫存從 `products.stock_qty` 扣
（`tracks_stock` 也已經有）。
⚠ 前提：那些周邊要在 `products` 裡有商品列 —— **那是設定不是開發**。

## 五、期望成本 ≈ 16.7 元／抽

```
⑦ 店內兌換券  6.05
⑧ 檯費優惠    4.27
⑨ 實體周邊    3.30
⑩ 特殊權益    3.05
①–⑥ 零成本    0
              ≈ 16.7 元
```

客人實付 43.5 元 → **毛利率約 62%**。

📌 **25% 的抽獎會拿到店裡真的能用的東西**（⑦⑧⑨⑩），其餘 75% 是小熊養成內容。
四抽有一抽有實感。⚠ 這個比例是刻意的 —— 票券占比太低（例如 12%）會讓人覺得
「都抽到沒用的」而停止抽獎。

## 六、保底（不是加分項，是核心）

| | 規則 |
|---|---|
| **十連保底** | 必出 ⑦⑧⑨⑩ 任一 —— **一定有能用的東西** |
| **累計保底** | 每 30 抽必出 ⑧ 檯費優惠以上 |
| **實體周邊** | 🔴 **不保底** |

🔴 沒有保底 = 有人會抽 200 次一無所獲。**那個人會退坑並且到處講。**
🔴 實體周邊不能保底，因為是限量的 —— **承諾一個可能發完的東西，比不承諾更糟**。

---

## 七、🔴 刻意不放進池子的

| | 為什麼 |
|---|---|
| **點數** | 拿負債換負債，等於用抽獎印錢 |
| **成就徽章** | **成就的價值來自「做到了」** —— 抽到的成就是假的，會讓整面成就牆貶值 |
| **段位／實力相關稱號** | 同上 |
| **暢打以外的檯費全免** | 會跟暢打的定價打架 |

---

## 八、實作的兩個必須做對

🔴 **機率必須在後端。**
現在 `pickTier()` 是前端 `Math.random()` —— **前端決定中獎**，
打開 devtools 就能中傳說。同「前端只送意圖不送事實」（待辦 2）。

🔴 **扣點必須冪等。**
網路斷線重試 → 扣兩次點、抽兩次。
`checkout_tx` 的 `idempotency_key` 是現成的模式，照抄。

## 九、⚠ 待決事項

| | 問題 |
|---|---|
| **美術成本** | ②③④ 共 38 項每一個都要畫，粗估幾週。**建議首發只上 30–40 個，其餘分批** —— 而這正好要求獎品池是**資料不是程式碼**，之後加獎品是新增一列 |
| **教練熊指導券** | 需要有人執行 —— 硬規則 5.5：做之前先確認那個人存在 |
| **限量品發完** | 建議「換等值商品」，且規則要講得出來，不是店員臨場發揮。⚠ 若改成「庫存 0 就從池子拿掉」，**實際機率會變**，「機率固定」就不成立 |
| **暢打券 ×3** | 暢打是「當日」→ 必須發成三張各自的當日券，不是一張三天的 |
| **券的有效期** | 建議 30 天（`member_coupons.expires_at` 已有欄位） |
| **法規** | ⚠ 台灣對「付費隨機獎品」有機率揭露規範（線上遊戲是明文要求）。點數是真錢換來的，形狀很接近。**機率一定要在 App 裡公開揭露**，而且做之前問一下律師或會計師 —— 同 CLAUDE.md 對派車代收款的處理方式 |
