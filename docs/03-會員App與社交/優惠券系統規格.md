# 優惠券系統規格

> 這是什麼:MIGI 券種定義、發放機制、使用時機與紅線。
> 什麼時候讀:做發券後台、會員端錢包、結帳折抵,或新增券種時。

## 券種

| kind | 中文 | 折抵對象 | 範例 |
|---|---|---|---|
| table_discount | 檯費折扣 | 檯費 | 檯費 9 折 / 檯費折 50 點 |
| unlimited_play | 暢打 | 檯費 | 平日暢打 3hr |
| ride | 派車 | 派車費 | 派車折抵 100 |
| fnb | 餐飲 | 餐飲 | 免費經典奶茶 / 餐飲 9 折 |
| topup_bonus | 儲值加碼 | 儲值 | 儲值加碼 10% |
| generic | 會員優惠 | 綜合 | 生日好禮(生日/新手/回歸皆歸此類) |

折抵方式 `discount_type`：`percent` / `fixed`（折抵金額） / `free`（免費）。

> ⚠ **`discount_value` 是折抵百分比，不是折數（2026-08-17 拍板）。9 折券填 `10`，不是 90。**
> 本檔舊版寫 `percent`(90=9折)，與 `checkout_tx` 的 `round(cap * discount_value / 100)`
> 差九倍 —— 同一個數字兩種解讀。採實作那側（對齊 Shopify / Square / Stripe，
> 它們一律存「折抵幅度」而非「保留比例」）。
> **但後台輸入框要讓店員填折數、由程式換算** —— 台灣人講 9 折不講 10%，
> 讓人做心算換算就是在製造這個矛盾。

## 鐵則

**券只折抵 MIGI 服務費(檯費/餐飲/派車/儲值),絕不折抵或碰觸桌上輸贏。**
贈點一律進「贈點」帳,不可換現。

## 資料結構

- `coupons` — 券種定義(後台可建)。欄位:name / kind / discount_type / discount_value / applies_to / valid_days / valid_until / is_active。
- `member_coupons` — 會員持有的券。發放即一筆,用掉改 status。欄位:member_id / coupon_id / status(active|used|expired) / granted_at / used_at / used_txn_id / expires_at。

## 會員端呈現

- **擁有**:錢包頁「我的優惠券」入口(點數卡下方),點開看可用券清單。
- **使用**:各結帳點自動帶出可用券 — 開桌結帳帶檯費券、點餐帶餐飲券、叫車帶派車券。

## 發放機制(總部後台)

**自動發放**(觸發式,走後端 `grant_on_trigger`),8 種觸發:
new_member(新會員入會) / birthday(生日當月) / tier_up(會員升級) / referral_referee(被推薦人) / referral_referrer(推薦人) / topup_threshold(儲值門檻) / survey(問卷回填) / online_claim(線上領券入會)。

每條規則可設「發券」或「贈點」,可開關,寫入 `grant_rules`。

**手動發券**:搜會員 → 選券或點 → 填事由 → 發放。走 `grant_coupon_tx` / `grant_points_tx`,含冪等與稽核,發放紀錄留存。

**適用範圍**:總部可將規則下發到「全加盟通用 / 直營 / 特定分店」,呼應 MDM 多店主檔下發。

## 扭蛋關聯

扭蛋為獨立畫面,**點數或扭蛋券二選一**(50 點/抽),保底 10 抽必中、機率公開。
文案守線:「多消費 · 克制不賭博」。

# 業界對照與缺口（2026-08-17 盤點）

> 對照 Shopify Discounts / Square / Stripe Coupons / Oracle Retail Price Management
> 的促銷資料結構，盤點 MIGI 現況缺什麼、哪些現在就該補、哪些永遠不必做。
> **依痛感排序，不是依完整度排序。**

## 成熟促銷系統的五層

| 層 | 回答什麼問題 | MIGI 現況 |
|---|---|---|
| ① 促銷定義 | 折什麼、折多少 | `coupons` ✅ |
| ② 適用範圍 | 能折哪些品項 | `applies_to` enum ⚠️ 太窄，見《資料模型設計說明》三之二 |
| ③ 資格條件 | 誰能用、什麼時候能用 | **只有 `min_spend`** ❌ |
| ④ 發放 | 誰拿到了、怎麼拿到的 | `member_coupons` ✅（但 `grant_rules` / `grant_log` **不存在**）|
| ⑤ 核銷 | 實際折了多少、折在哪幾行 | 只有單頭金額 ⚠️ |

**MIGI 強在 ①④，弱在 ②③⑤。** 這很典型 —— 券系統通常從「發得出去」開始做，
「折得精準、算得回來」是後來才痛。

---

## 缺口一：折扣沒有攤回品項（最痛，而且現在做最便宜）

`order_items` 沒有折扣欄位，`orders` 只有單頭的 `coupon_discount` / `tier_discount`。

**後果**：算不出「餐飲扣掉折扣之後的實際營收」。
而毛利分析正是 `subcategory`（飲料 vs 餐點毛利結構不同）存在的理由 ——
分類做得再細，折扣攤不回去就還是算不出真實毛利。

**第二個後果**：部分退貨無解。客人退一份水餃，該退多少折扣？
折扣攤在哪幾行沒記錄，只能事後重算 —— 而重算規則若日後改過，歷史就對不上。

業界一律做 **line-level allocation**：
Shopify 的 `discount_allocations`、Square 的 `applied_discounts`、
SAP 的 condition records，都把折扣攤到行並存下來。

> **務實版**：`order_items` 加 `discount_amount bigint not null default 0`，
> `checkout_tx` 在分桶排乾時順手按行比例攤下去。
> **現在做最便宜** —— `order_items` 還沒有真實資料，不必回填。

---

## 缺口二：沒有疊加規則（同樣兩張券，順序不同金額不同）

`checkout_tx` 對 `p_coupon_ids` 陣列**逐張套用，順序由前端傳入決定**。
而分桶排乾（fee → fnb → goods）會改變後一張券的 `cap`。

具體：一張「全品項折 100」+ 一張「檯費 9 折」，
先套哪張，檯費剩多少不同，第二張折出來的金額就不同。
**前端送出的陣列順序決定客人付多少錢**，而那個順序是使用者點選的先後。

業界做法：`stackable` 旗標 + `priority` 排序 + 互斥群組（exclusion group）。
Shopify 直接規定同類折扣不可疊加，Square 有明確的 apply order。

> **務實版**：`coupons` 加 `stackable boolean default false` 與 `priority int default 100`。
> `checkout_tx` 依 `priority` 排序後套用；`stackable = false` 的券一次只准用一張。
> 這樣「順序」就由資料決定，不由使用者點選順序決定。

---

## 缺口三：資格條件只有 `min_spend`

缺的（都是行銷一定會要的）：

| 條件 | 用來做什麼 |
|---|---|
| 每人可用次數 | 「每人限用一次」 |
| 發行總量上限 | 「限量 100 張」 |
| 限定門市 | 加盟店不吃總部的券 |
| 限定星期／時段 | 「週二飲料券」「離峰時段」 |
| 限定會員等級 | 「提拉米蘇專屬」 |
| 新客限定 | 拉新 |

每加一種就要改 `checkout_tx`，**跟 `applies_to` 是同一個病** ——
行銷一個活動企劃 = 一次金流函式改版。

> **務實版**：`coupon_rules(coupon_id, rule_type, rule_value)`，
> 與 `coupon_scope` 同一批做（`CLAUDE.md` 待辦 0.8）。
> `checkout_tx` 只實作「讀規則、逐條檢查」一次，之後新增規則類型不必再改它。

---

## 缺口四：已發出的券是負債，但沒有帳

未核銷的券等同於承諾未來要打的折 —— 跟儲值一樣是**負債**，不是行銷費用。
目前沒有任何地方算得出「已發出未使用的券，潛在金額多少」。

發 1000 張「檯費折 50」，帳上什麼都看不到，直到客人集中來用。

> **務實版**：先不必建表。一個 view 就夠：
> `未核銷券潛在金額 = sum(依 discount_type 估算的最大折抵)`，
> 百分比券用 `max_discount` 估，沒設上限的視為風險項目單獨列出。
> **這個 view 本身就會逼你去給每張百分比券設上限。**

---

## 缺口五：沒有「生效起始」

`coupons` 有 `valid_days` / `valid_until`，`member_coupons` 有 `expires_at`，
但**沒有 `valid_from`**。做不了「下個月才能用」的券。

這不只是行銷需求 —— 若「贈點次月生效」那類設計成立（`CLAUDE.md` 待辦 11），
同一個機制會用同一個欄位。

> **務實版**：`member_coupons` 加 `valid_from timestamptz`，
> `checkout_tx` 的可用性檢查加一條。三行的事。

---

## 缺口六：一個欄位裝兩種單位

`discount_value` 同時裝「百分比」與「金額」，靠 `discount_type` 區分。
**這正是 9 折 / 90 那個矛盾的溫床** ——
一欄兩用時，欄位名沒辦法把單位講清楚。

業界拆兩欄（Shopify：`percentage` 與 `fixed_amount` 是不同的 discount value 型別）。

> **務實版**：這個可以不改。單店規模下，拆欄位的收益不如把
> **後台輸入框做對**（選了「百分比」就顯示 `%` 後綴、選了「金額」就顯示 `$` 前綴，
> 並且百分比欄位讓店員填折數由程式換算）。
> 但 `discount_value` 的語意**必須先拍板**（見《資料模型設計說明》`coupons` 節）。

---

## 明確建議：不要做的

| 功能 | 為什麼不做 |
|---|---|
| BOGO（買一送一）、第二件半價 | 麻將館的餐飲品項少、單價低，用「免費品項券」就能覆蓋 |
| 跨品項組合折（套餐邏輯） | 菜單只有個位數品項，直接建一個套餐商品比寫規則引擎便宜 |
| 規則引擎（Talon.One 那種 DSL）| 那是給有專職行銷團隊、每週上檔活動的規模。單店用不到 |
| 動態定價 / 個人化折扣 | 需要的資料量與人力都不在這個階段 |

**判準：這個功能需要有人每週維護嗎？需要的話，先確認那個人存在。**

---

## 動手順序

| 時機 | 做什麼 | 為什麼是這個時機 |
|---|---|---|
| **現在** | `discount_value` 語意拍板 | 還沒發出任何一張券，改了零成本 |
| **現在** | `order_items.discount_amount` + `checkout_tx` 分攤 | `order_items` 還沒有真實資料，不必回填 |
| **發券後台開工前** | `coupon_scope` + `coupon_rules` + `stackable`/`priority` | 還沒有已發出的券要遷移 |
| **發券後台開工前** | `member_coupons.valid_from` | 與上面同一批 |
| **有真實發券量之後** | 負債 view | 沒有券的時候這個 view 是空的 |
