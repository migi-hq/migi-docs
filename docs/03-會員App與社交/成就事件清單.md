## 0. 一句話

而其中 `session_finished` 一個就推進幾十枚。

## 1. 🔴 三類成就的行為完全不同，不可以用同一套處理

```
① 純事件驅動   251 枚（84%）   事件一發就推進，不用額外判斷
② 條件型        22 枚          事件發生時還要「查關係」才知道算不算
③ meta          27 枚          「解鎖 N 個 X 類成就」
```

### ① 純事件驅動（251 枚）—— 引擎今天就支援

```
完成一場牌局 → fire_event_tx(member, 'session_finished', 1, …)
              → 引擎自己找出所有 trigger.event = 'session_finished' 的成就
              → 依 struct 分流：specific 解鎖／cumulative 累加／streak 推進
```
✅ **呼叫端只要發事件，不用知道有哪些成就。**

### ② 條件型（22 枚）—— 判定留在呼叫端，但要集中一處

例子：
```
同桌其他三人都是你的牌咖
與 10 位不同牌咖各完成至少 1 場
同桌四人段位階級相同
四個時段各完成至少 1 場
五個餐飲子分類各點過一次
```
這些**不是計數，是查關係**。

🔴 **不要在 `settle_session_tx` 裡寫 22 個 if** ——
那會讓收桌函式必須知道成就系統的存在，而它是動不得的金流函式。

✅ **正解：一支專門的判定函式**
```sql
_ach_check_session(p_member uuid, p_session uuid)
  -- 在這裡查關係，條件成立才 fire_event_tx 發專屬事件
  -- settle_session_tx 只要呼叫它一次
```
🎯 **耦合只有一行**：收桌函式不知道 22 個條件，只知道「收桌了，去檢查一下」。

### ③ meta（27 枚）—— 🔴 **引擎今天處理不了**

```
解鎖 15 個新手成就 ／ 解鎖 10 個牌局類成就 ／ 解鎖 5 個段位類成就 …
```

`fire_event_tx` 只比對 `trigger->>'event'`，**它不會數「已經解鎖幾個」**。

✅ **要補一支 `ach_meta_tx`**，由「成就解鎖」這件事自己觸發：
```
任何成就解鎖 → 引擎發 'achievement_unlocked'
             → ach_meta_tx 數該分類已解鎖幾枚 → 夠了就解鎖 meta
```

🔴 **而它會遞迴**：解鎖 meta → 又發一次解鎖事件 → 可能再解鎖另一個 meta。
```
❌ 深度限制         要傳參數、要記層數，而且「限幾層」沒有人答得出來
✅ **只有非 meta 解鎖時才發事件**   一層就夠，而且不需要任何計數器
```
⚠ 判準：`trigger ? 'count'` 為真的就是 meta（見 §3 的 trigger 格式）。

## 3. `trigger` 的格式

```jsonc
// ① 純事件驅動
{ "event": "session_finished" }

// ② 條件型 —— 事件名就是那個條件（由 _ach_check_session 判斷後發）
{ "event": "session_all_buddies" }

// ③ meta —— 🔴 有 count 就是 meta
{ "event": "achievement_unlocked", "scope": "ui_category", "value": "game", "count": 10 }
{ "event": "achievement_unlocked", "scope": "group_key",   "value": "牌型收藏", "count": 5 }
```

🎯 **`trigger ? 'count'` 就是「這是不是 meta」的判準** ——
不用另外加欄位，也不用維護一份 meta 清單。

⚠ `scope` 只有兩個值（`ui_category` / `group_key`），**不要再加第三個** ——
那會開始變成規則引擎（硬規則 5.7）。

## 4. ⏳ 三個還沒決定的

### 4.1 `fnb_order` 一張單發幾次？

```
甲   一張單發一次，delta = 品項數
乙   每個品項各發一次
```
⚠ 差別在**「嘗遍 5 種」那一族**：它要數**不同品項**，而 delta 加總數不出「不同」。
⇒ 那幾枚其實是 ② 條件型（要查 distinct），不是純累積。
📌 **建議甲 ＋ 把「嘗遍 N 種」歸到條件型**，在 `_ach_check_order()` 裡查。

### 4.2 `session_finished` 要不要帶 payload？

那 22 枚條件型要知道「哪一場」才查得了關係。
```
✅ _ach_check_session(member, session_id)  ← 判定函式自己去查那一場
   fire_event_tx 維持不帶 payload
```
🎯 這樣 `fire_event_tx` 的簽名不用動，而它已經上線了。

### 4.3 事件要不要留紀錄？

今天**不留** —— `member_achievements.last_idem` 只記最後一把鑰匙。
⚠ 代價：查不到「這枚成就是哪一場解鎖的」。
📌 真的需要時再加一張表，**不要現在建**（第 N 個「建了沒人讀」）。

## 5. 工作量

```
要改的既有函式   約 12 支
其中一半的工作   集中在 settle_session_tx（最大的發射點 ＋ 條件型的觸發時機）
要新寫的         ach_meta_tx ＋ _ach_check_session ＋ _ach_check_order
```

### 建議順序

```
① ach_meta_tx              meta 27 枚，而且它不依賴任何既有函式
② 匯入 300 枚（含 trigger） 有了 trigger 才知道要發什麼事件
③ settle_session_tx 發事件  一支就解開最多枚
④ checkout_tx 發事件        餐飲與消費
⑤ 其餘社交類逐支加
⑥ 等記分板 → hand_finished
```

🔴 **不要反過來先改函式** —— 沒有成就資料的話，
`fire_event_tx` 每次都掃出 0 筆，**看起來完全正常而且什麼都不會發生**。
