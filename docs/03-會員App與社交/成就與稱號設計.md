> 2026-09-19 拍板。這份是**成就與稱號的唯一權威**，動手前先讀完這一份。

> 這份的工作是把那兩份**對起來**、補上缺的條件、並把稱號那條斷掉的線接回去。

## 1. 三個結構決定（2026-09-19 拍板，不要重新討論）

### 1.1 分類只留前端那套六類

```
新手 · 牌局 · 社交 · 餐飲 · 探索 · 特殊
```

🔴 **文件 §11 那套 `consume` / `social` / `skill` 作廢。**
它從來沒有人用過，而前端這套**已經畫在成就牆的分類 tab 上，客人天天看得到**。

⚠ 保留兩套的話就是**同一個事實兩個名字**（這個專案記過七次的病）。
文件那三類其實是在問「這枚靠什麼資料判定」——**而那個答案在條件 SQL 裡本來就有**，
不需要多一個欄位來重講一次。

**⚠ 順手要修的分類錯誤**：`早鳥達人` / `夜貓王` 現在掛在「新手」，
但它們要 10 場早場／夜場 —— 那是「牌局」不是新手。

### 1.2 `tier` 是**稀有度**，不是牌型

```
普通 norm  ·  稀有 rare  ·  傳說 legend
```

🔴 現在程式把稀有度跟牌型綁在一起，**兩處要改**：

```js
// rewards.jsx:74
label: '傳說 · MIGI 牌型'        →  '傳說 · 極稀有'

// rewards.jsx:85（還有 :140 與 :1504 兩處同樣的字串）
const desc = a.tier === 'legend' ? '在 MIGI 門市胡出 MIGI 牌型' : ...
   → 這句要**還給「首次／十次／百次 MIGI」那三枚自己**，不可以綁在 tier 上
```

⚠ 不改的話，**日後任何一枚升到傳說，說明都會自動變成「胡出 MIGI 牌型」** ——
而那是一句錯的話，且不會有任何錯誤訊息。

### 1.3 獎勵分工照 §8.5 的鐵則，不要動

| | 給什麼 |
|---|---|
| **小熊養成** | 裝扮、賽季限定（穿在熊身上） |
| **成就** | 徽章／稱號／限定購買權（掛在名字旁邊） |

🔴 **同一樣獎品不可以兩邊都送。** 觸發可以共用（打 10 場同時餵養成與成就），
**獎品不可以共用**。

## 2. 25 枚清單

> 進度形狀沿用前端：`on`（已解鎖）或 `cur / req`（進行中）。
> 「今天算得出來嗎」= 現在的資料庫有沒有那個事實，不是「做了沒」。

### 2.1 今天就能接的 10 枚

| 枚 | 稀有度 | 分類 | 條件 | 資料來源 |
|---|---|---|---|---|
| 新手報到 | 普通 | 新手 | 註冊完成 | `members.created_at` |
| 首次開桌 | 普通 | 新手 | **第一次坐上桌**（不分配桌／包桌） | `session_players` 第 1 列 |
| 點一杯飲料 | 普通 | 新手 | 買過 1 杯飲料 | `order_items` → `products.subcategory = 'DRK'` |
| 第一份餐點 | 普通 | 新手 | 買過 1 份非飲料的餐飲 | `subcategory in ('DES','FRY','SNK','MEAL')` |
| 第一次贏得牌局 | 普通 | 新手 | 桌上積分 > 0 | `session_players.final_score`（2026-09-06 起才有） |
| 第一次配桌 | 普通 | 社交 | 第一次**透過配桌**成桌 | `table_sessions.mode = 'matched'` |
| 打滿 10 場 | 普通 | 牌局 | 10 場 | `session_players` 列數 |
| 早鳥達人 | 普通 | **牌局** | 10 場早場 | `migi_slot_of(activated_at) = 'morning'` |
| 夜貓王 | 普通 | **牌局** | 10 場夜場 | `migi_slot_of(...) = 'evening'` 或 `'late'` |
| 交到 5 個牌咖 | 普通 | 社交 | 5 個 | `mahjong_buddies` |
| 升上金牌熊 | 稀有 | 牌局 | `rating` 達 `gold` 的下限 | `rank_tiers`（bronze→master 六階） |

⚠ **「升上金牌熊」不可以比對 `members.rank` 的字串**（存的是「金牌熊 II」這種顯示字串）——
門檻改了字串也會跟著變，但**歷史達成紀錄不該跟著變**。一律比 `rating` 對 `rank_tiers` 的下限。

⚠ 上表 11 列而不是 10 列，因為「第一次配桌」是這次從「第一次同桌」改出來的（見 §3.3）。

### 2.2 等 M4 電子計分的 9 枚

```
首次胡牌 · 首次自摸 · 首次特殊牌型 · 第一次連莊 · 連莊 5 次 · 清一色
首次 MIGI · 十次 MIGI · 百次 MIGI
```

🔴 **`hands` / `games` / `game_players` / `paipu_events` 今天一張表都沒有**（2026-09-19 實查）。
所以這 9 枚**不是「還沒做」是「做不了」** —— 條件寫得出來，判定沒有輸入。

✅ 它們**照樣要建進主檔**，只是 `is_active = false`。
理由：主檔是清單，成就牆已經在畫它們（灰色未解鎖），
**拿掉會讓客人看到的成就總數縮水**，而那是倒退。

### 2.3 等賽季結算的 1 枚

**當季雀神** —— `season_champions` 表在，但本季到 **2027-01-01** 才結束。
⚠ 所以它**必然空到明年**，那是規則不是 bug。

### 2.4 造訪 3 家店 —— 條件不用改

今天有桌的只有**高雄自由（14 桌）與前鎮（4 桌）**兩間 ⇒ 今天不可能達成。
✅ **條件照寫不動** —— 第三間店開了它自然就活了。**這不是資料問題是開店進度。**

## 3. 六個「從來沒有定義過」的東西

> 🔴 這一節才是這份文件真正的產出。
> 前五個是條件沒寫，**第六個更嚴重：它撐著整個傳說層**。

### 3.1 🔴 「MIGI 牌型」整份 docs 一次都沒出現過

```
grep 'MIGI 牌型'  →  只有 rewards.jsx 的 4 處字串，docs 零筆
```

而**傳說級那三枚（首次／十次／百次 MIGI）全部靠它**。

⚠ 更麻煩的是「牌型」這個詞在這個專案裡**已經有另一個意思**：
`牌搭戰略落地設計.md:73` 的「牌型一致（台16 / 三人）」指的是**玩法**，
而成就要的是**役**（大三元、清一色那種）。同一個詞兩件事。

**⏳ 待拍板（本文件不替它決定）**，但要決定的問題已經明確：
1. MIGI 牌型是**一個自創役**（例如某個湊出「咪吉」形狀的牌型），還是**一組既有役的集合**？
2. 它由誰認定？—— 靠牌譜辨識（M4）還是**店員現場按一顆鈕**？

📌 **建議在 M4 動工前拍板**，因為它會決定 `hands` 要不要多一個欄位。
⚠ 在那之前，前端那句「在 MIGI 門市胡出 MIGI 牌型」**不要拿去別的地方複製**。

### 3.2 第一次打卡 → **新增「到店留影」**（見 §5）

🔴 **「打卡」這個詞在 App 裡已經被用掉了**：
`rewards.jsx:1450` 的「抽屜的日記 · 每日報到」→ `CheckinPage`。
而徽章圖 `badge08` 被畫成了**相機** —— 同一個詞兩件事，第八次。

✅ **決定：做「到店拍照」這個新功能，但成就與功能都不准叫「打卡」。**
名稱定為 **「到店留影」**。徽章圖（相機）終於對得上它的名字。

### 3.3 首次開桌 = 第一次坐上桌 → 連帶改掉「第一次同桌」

`首次開桌` 定為「第一次坐上桌，不分配桌或包桌」。
🔴 但這樣就跟同一組的 `第一次同桌` **完全重疊**。

✅ **`第一次同桌` 改成 `第一次配桌`**（第一次透過配桌成桌）。
🎯 兩枚從此不重複，而且**配桌是 MIGI 的護城河**，值得專屬一枚。

### 3.4 餐飲組合 → 改名 **「嘗遍 5 種」**

原本叫「餐飲組合」而 `req: 5`，**名字跟數字對不上**，沒有人說得出 5 是什麼。

✅ 條件：**吃過 5 種不同的餐飲品項**
（`count(distinct product_id)` where `revenue_type = 'fnb'` ≥ 5）。

🎯 改名字不改數字：`cur: 2 / req: 5` 的進度條已經畫在畫面上了，
而首店有 **32 個餐飲品項**，5 種是一個會讓人回訪去湊的門檻。

### 3.5 隱藏成就 → **「不打烊」：同一天打了 2 場以上**

✅ 今天就算得出來（`session_players` join `table_sessions`，同一個台北日曆日 ≥ 2 場）。

📌 曾評估另外兩個並推翻：
- **「連續 3 週同一個星期幾來店」** —— 要等三週才知道有沒有中，
  而隱藏成就的價值正在於「**咦我什麼時候解開的**」，延遲三週就沒有那個瞬間了。
- **「整桌四人都是同一個牌咖團」** —— 太漂亮了，**那應該是稱號不是隱藏成就**。

### 3.6 造訪 3 家店 —— 不用補，見 §2.4

## 4. 稱號：那條線現在是斷的

### 4.1 文件說「頂級成就給稱號」，而 25 枚沒有一枚接到

§3.3 的原文：

| 成就類型 | 給什麼 |
|---|---|
| 頂級成就 | **稱號** + 限量編號品 + 包廂 |

而 §11 的 schema 裡 `reward_type` / `reward_ref` **正是為這件事留的欄位，從來沒有填過值**。

### 4.2 🔴 現在的稱號清單是假的，而且有兩個撞名

`rewards.jsx:862` 的 `TITLE_LIST`：

| 稱號 | 問題 |
|---|---|
| 新手上路 | ✅ **一定要保留** —— 後端 `set_my_title_tx` 硬性放行它，而全部會員現在戴的就是它 |
| 三屆雀神 | ⏳ 「三屆」要記錄歷屆冠軍次數，`season_champions` 撐得住 |
| 自由店店霸 | ⏳ 月冠，今天沒有任何成就對應 |
| **早鳥達人** | 🔴 **同時是徽章又是稱號**（`ACH` 裡有同名的一枚）—— 違反 §8.5 鐵則「同一樣獎品不可兩邊送」 |
| **夜貓王** | 🔴 同上 |
| 揪團達人 | ⏳ 沒有對應的成就，條件未定義 |

⚠ **而抽獎池 §⑤ 已經有六個稱號**：
早起的鳥／夜貓子／常勝軍／一發入魂／四暗刻／手氣爆棚（**全店限量 20 個**）。
🔴 `早鳥達人` ↔ `早起的鳥`、`夜貓王` ↔ `夜貓子` —— **同一件事，一個用抽的一個用練的**。
客人會覺得被耍。**時段類的稱號歸抽獎，成就這邊要讓開。**

### 4.3 稱號的三個來源（分工，不要混）

| | 來源 | 會不會收回 |
|---|---|---|
| ① | **頂級成就的獎勵** | ❌ 永久 |
| ② | **賽季榮譽**（雀神） | ✅ **會** —— 卸任者退回 |
| ③ | **抽獎**（6 個，含限量 20 個的「手氣爆棚」） | ❌ 永久 |

🔴 **②「會收回」跟現在對客人講的話衝突**：
`stats.jsx:1070` 寫著「小熊頭像和稱號解鎖後就留著，掉段位或換季都不會消失」——
**那句話要改**，否則雀神卸任那天就是一次客訴。

### 4.4 ⏳ 稱號清單待拍板

判準已經定了（使用者 2026-09-19）：**累積很多 · 條件特殊 · 難度很高**，
而三者共同的意思是**稀缺** —— 稱號掛在名字旁邊人人看得到，
給太多就變成噪音，而且會讓早拿到的人覺得不值錢。

候選（**尚未拍板**，等成就引擎做完再定，因為那時才知道哪些條件真的算得出來）：

| 屬性 | 候選 | 今天算得出來？ |
|---|---|---|
| 累積很多 | 百戰（100 場）／常駐（來店 100 天）／牌搭之王（配桌認識 20 個牌咖） | ✅ |
| 條件特殊 | **全員到齊**（整桌四人同一個牌咖團）／滿堂彩（同一場四人都給你讚）／三巡（同一天早中晚各一場） | ✅ |
| 難度很高 | 店霸（當月該店勝場第一）／雀神（賽季冠軍） | 🟡 等賽季 |

🔴 **門檻現在全是猜的**：真實客人 0 個，100 場／100 天／20 人都沒有分布可以參考。
→ **門檻寫成資料不要寫成程式碼**，開幕三個月後拿真實分布回來校一次，目標是最上面約 5%。
⚠ 「暫定」兩個字會讓它看起來像還沒定，於是**沒有人回來對過**
（`member_tiers` 的門檻就這樣錯了三週）。所以門檻要有**一個負責回頭看的時間點**，寫進上線清單。

## 5. 到店留影（新功能）

### 5.1 什麼時候能拍 —— 當下有進行中的牌局

```
session_players 有你這一列  ＋  left_at is null  ＋  table_sessions.status = 'open'
```

🎯 零新硬體，不用 GPS 也不用掃 QR，而且照片**自動綁到那一場**
（之後在牌局詳情裡看得到「那天拍的」）。
🔴 不綁的話，在家拍一張也算 —— 這枚徽章就沒有意義了。

### 5.2 ⏳ 照片給誰看 —— **這一格還沒拍板**

🔴 **查證到一個會決定架構的事實**（2026-09-19）：

```
storage.buckets    store-photos public=true / member-avatars public=true / team-crests public=true
```

**現有三個 bucket 全是公開的** —— 拿到網址就看得到。
頭像與團徽本來就要給人看，所以那是對的；
**但打卡照片如果在畫面上寫「只有你看得到」而存在 public bucket，那就是說謊。**

| | 甲 · 自己的紀念冊（**建議**） | 乙 · 公開留影牆 |
|---|---|---|
| bucket | **private** ＋ 後端發簽名網址 | public（同頭像） |
| 誰看得到 | 只有自己 | 所有人 |
| 審核 | **不用** | 🔴 要有人每天看佇列 |
| 炫耀 | 徽章公開、照片不公開 | 照片本身 |

**建議甲，理由不在程式在人**：硬規則 5.5 ——
「這個功能需要有人每週維護嗎？需要的話先確認那個人存在」，
而看審核佇列的那個人**今天不存在**。
⚠ 照片裡有客人的臉，**漏審一張的代價比團徽高得多**。

✅ 甲仍然要保留 `blocked` 旗標與總部下架 RPC（照抄 `admin_remove_avatar_tx` 那一套）——
日後要開公開版時它是現成的，而**事後補稽核補不回來**（硬規則 5.6）。

### 5.3 一場一張，可重拍覆蓋

不做相簿。「今天的紀念」一張就夠 ——
不限張數就要處理容量、排序、刪除、封面，**每一項都是一個新畫面**。

### 5.4 成就條件

拍過第 1 張就解鎖。

## 6. 資料表

### 6.1 沿用文件 §11 的形狀，但欄位要改

```sql
create table achievements (
  code          text primary key,       -- 'first_seat' 這種，不可改（歷史紀錄靠它）
  name          text not null,          -- 中文名，**可以改**
  cat           text not null,          -- 新手/牌局/社交/餐飲/探索/特殊
  tier          text not null,          -- norm / rare / legend（稀有度）
  req           int,                    -- null = 一次性；有值 = 進度型
  hidden        boolean not null default false,
  title_code    text,                   -- 🎯 **只有頂級那幾列填它**，這就是稱號那條線
  is_active     boolean not null default true,   -- 等 M4 的 9 枚先 false
  sort          int
);

create table member_achievements (
  member_id     uuid,
  code          text,
  achieved_at   timestamptz not null default now(),
  primary key (member_id, code)
);
```

🔴 **`code` 與 `name` 一定要分家**（同 `member_tiers` 的教訓）：
中文名日後會改，而**歷史達成紀錄不可以跟著變**。

⚠ **`category` 那一欄不要建**（§1.1 的決定）。

### 6.2 條件寫成資料還是程式碼？

⚠ **不要做規則引擎**（硬規則 5.7 明列永遠不做）。
25 枚的條件差異太大（有的看訂單、有的看場次、有的看時段），
硬要塞進一張 `condition jsonb` 就是在為七間店蓋 SAP。

✅ **每一枚一段 SQL，集中在一支 `recalc_achievements_tx(member)` 裡**，
`achievements` 主檔只管「有哪些、叫什麼、屬於哪一類、給不給稱號」。

🎯 判準：**主檔管「清單與展示」，判定邏輯管「怎麼算」** ——
前者會被後台改，後者不會。

### 6.3 什麼時候判定

⏳ 待定，但三個候選已經清楚：
① 結帳／收桌後觸發　② 開 App 時算一次　③ pg_cron 定時掃

📌 **建議 ①＋②**：③ 要有人看告警而那個人不存在（同硬規則 5.5）。

```
① 成就引擎（主檔 ＋ member_achievements ＋ recalc）   ← 做完當天就有 11 枚會亮
② 成就牆接真資料（現在 on / cur 全是寫死的）
③ 稱號（title_code 接出來，set_my_title_tx 改查真表）
④ 到店留影
⑤ 等 M4：9 枚牌技成就 ＋ MIGI 牌型拍板
```

🔴 **④ 排在後面是刻意的**：它做完只多 **1 枚**，
而且**還是要等引擎才發得出徽章** —— 先做它就是先做一個發不出獎的功能。

### 7.1 做之前要知道的三件事

1. **成就牆現在整面是假的**：`on: 1` 是逐一寫死的 ⇒ **每個會員看到的已解鎖徽章一模一樣**。
2. **稱號現在是前端說了算**：`save_app_state_tx` 的 `titles` 是「兩邊聯集、只增不減」，
   手打一次 RPC 就能拿到「三屆雀神」（待辦 40）。
   ✅ 引擎做完之後 **`titles` 要變成唯讀的計算結果**，`p_titles` 參數拿掉。
3. **那行註解寫「原本 18 個 + 新手系列 10 個」= 28，實際是 25** —— 文件會漂，數字當場數。
