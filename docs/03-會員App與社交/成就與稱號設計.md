## 2. 架構：事件驅動（照抄，這是好設計）

後端動作發生時丟一個事件，系統自己比對 `achievements.trigger->>'event'`
找出所有該推進的成就：

```sql
首次到店 → fire_event_tx(member, 'visit_completed', 1, null, visit_id::text)
點一筆餐飲 → fire_event_tx(member, 'fnb_order',     1, null, order_id::text)
每日到店 → fire_event_tx(member, 'daily_visit', 1, to_char(now(),'YYYY-MM-DD'), visit_id::text)
做出咪幾 → fire_event_tx(member, 'migi_win',        1, null, hand_id::text)
```

### 四種結構（`struct`），判定邏輯只有三套

| `struct` | 意思 | 走哪支 |
|---|---|---|
| `specific` / `prestige` | 一次達成即解鎖 | `ach_unlock_tx` |
| `cumulative` | 累積計數，跨門檻自動解級 | `ach_progress_tx` |
| `streak` | 連續（帶 `period_key` 去重） | `ach_streak_tx` |

分級門檻在 `achievement_tiers`（tier_level／threshold／reward_points）。

### 🎯 為什麼這不違反「永遠不要做規則引擎」（硬規則 5.7）

規則引擎的定義是**讓非工程師自己寫規則**（要 DSL、編輯器、測試環境、除錯工具）。
這套不是：**判定條件留在呼叫端**（誰發事件誰負責判定），
`achievements` 只存「事件名 → 哪些成就要推進」的對照。

⇒ 新增一個成就**不用改程式碼**，但新增一個**事件**要改（那是對的分工）。

### 已經內建、不要重做的四件事

```
冪等鍵      每個成就各自一把（'evt:<event>:<code>'），同一來源事件不會重複計
requires_code  前置依賴 —— 沒解鎖前置就跳過，系列成就不會跳級
valid_from/to  限時檔期，null = 永久
pinned         釘到個人展示櫃（🔴 現成的是 3 枚，要改成 1 枚，見 §3⑨）
```

### ✅ 兩個欄位直接回答了本來以為斷掉的線

```
grants_title   掛在名字旁的稱號  ← 成就 → 稱號那條線，它有
is_signature   品牌旗艦成就（＝咪幾）
```

## 3. 🔴 四份 SQL 不能直接跑：八個問題與修法

> 每一項都查證過。**架構照抄，這八處必須改**。

### ① `grant_points_tx` 不存在

```
實查 2026-09-19：pg_proc 裡沒有任何 grant_points% 的函式
```
而 `ach_unlock_tx` 有 `if a.reward_points > 0 then perform grant_points_tx(...)`，
seed 的 `reward_points` 是 50／80 ⇒ **第一次解鎖就在 runtime 炸**。
⚠ `CREATE FUNCTION` 不檢查函式體（硬規則 7）——建立時完全不會報錯。

**修法（二選一）**：
- **A（建議）**：第一批 `reward_points` 一律 0，成就只給徽章與稱號。
  這正好是 §8.5 的鐵則——**成就給榮譽，點數是最克制的那一層**。
- B：包一支 `grant_points_tx` 走現有的 `wallets` ＋ `wallet_txns`
  （⚠ `wallet_txns` 是 append-only，要插流水再 `fix_wallet_balance_tx`）。

### ② 沒有任何 `grant` / `revoke` —— 最嚴重的一個

這個專案設了 default privileges ⇒ **在 `public` 新建的函式一建立就是
`anon` 明確可執行**（硬規則 2.6b）。

🔴 ⇒ `fire_event_tx(任意 member, 'migi_win', ...)` **任何人叫得動**
⇒ 偽造任何事件解鎖任何人的任何成就。
而它是 `SECURITY DEFINER`，**RLS 擋不住它**。

**修法**：每一支都要收，而且**兩個方向都要收**（硬規則 2.6b）：
```sql
revoke execute on function public.f(...) from public;
revoke execute on function public.f(...) from anon, authenticated;
grant  execute on function public.f(...) to service_role;
```
⚠ 只有「客人自己按的」那幾支（例如 `ach_pin_tx`）才給 anon，
而且**身分必須從 JWT 取，不收 `p_member`**（見 ④）。

### ③ 四支核心 RPC 沒有 `security definer`

`ach_unlock_tx` / `ach_progress_tx` / `ach_streak_tx` / `ach_pin_tx`
全是 `language plpgsql as $$`（＝ INVOKER），
而 `fire_event_tx` 與 `assert_ach_admin` **有** DEFINER。**不一致。**

三張表都有 RLS 且**只有 SELECT policy**（insert／update 0 條 ＝ 全擋）
⇒ INVOKER 下前端直接叫會寫不進去。

🎯 而經由 `fire_event_tx`（DEFINER）呼叫時**會通** ——
**這正是硬規則 2.5 記的形狀：「函式在包裝裡跑得動 ≠ 前端叫得動」**
（`topup_tx` 那次，櫃檯儲值從上線起沒成功過一次）。

**修法**：四支都加 `security definer set search_path = public`。

### ④ 會員 id 由呼叫端指定

`ach_unlock_tx(p_member uuid, ...)` 等四支都收 `p_member`。
2026-09-11 才剛把最後一支「anon 叫得動又信前端 member_id」的函式收掉
（`log_app_event_tx`），現在全庫是 **0 支** —— 這套會讓它變回 4 支。

**修法**：客人自己按的那幾支改 `coalesce(current_member_id(), p_member)`，
並確認 `member_id_src` 埋點的 `jwt_override` 仍然是 0。

### ⑤ `assert_ach_admin(p_staff_id)` 收前端指定的 staff_id，而且自己寫了第三份權限定義

```sql
select role into v_role from staff where id = p_staff_id;
if v_role not in ('hq','owner') then raise ...
```
🔴 兩個問題：**填別人的 id 就是假造稽核**（2026-09-04 的通則），
而 `role in ('hq','owner')` 是**第三份**「誰是最高權限」的定義
—— `has_store_access()` 犯過一模一樣的錯，2026-09-04 已改成呼叫 `can()`。

**修法**：整支刪掉，改 `can('ach.write')`（權限碼用動詞，待辦 29 ④）。

### ⑥ `motivation` CHECK 只有 6 種，企劃是 10 種

建表那份是 v2.0，企劃是 v2.3 起就十種。
⇒ **執行順序有依賴**：必須先跑「十種動機軸增補」才匯得進企劃的清單。
⚠ 索引沒寫這個順序，而症狀是匯入時整批 CHECK 失敗。

新增的四種：`habit` / `expression` / `story` / `consumption`。
📌 其中 `habit` 有一條覆蓋規則：**凡 `struct=streak` 一律歸 `habit`**。

### ⑦ RLS 是 org 級，而 `member_achievements` 是個資

三條 policy 都是 `org_id = current_org_id()`。
待辦 21 已經把 17 條讀取 policy 收緊到總部（`can('member.read')` 那批），
而「誰解鎖了什麼」是同一類的東西。

**修法**：`achievements` / `achievement_tiers` 維持 org 級（那是主檔，人人可讀），
`member_achievements` 的**別人的資料**要擋 —— 客人只能讀自己的。

### ⑧ 🆕 稀有度四級，而 schema 與前端都只有三級

企劃 v3.0 把稀有度定成 **普通／稀有／史詩／傳說**，但：

```
achievements 表     🔴 根本沒有稀有度欄位
rewards.jsx 的 tier  只有三值：norm / rare / legend
```

**修法**：
1. `achievements` 加一欄（`rarity text check (rarity in ('norm','rare','epic','legend'))`）。
   ⚠ **不要沿用 `rarity_cached`** —— 那一欄是「實際解鎖率」，是**養出來的結果**；
   稀有度是**設計時指定的**。兩者都要，但**不可以共用一欄**
   （這個專案記過七次的「一個名字兩個意思」）。
2. 前端加 `epic` 的視覺（現在只有灰底／粉底／墨底金框三種）。
3. 🔴 **三處把稀有度跟「MIGI 牌型」綁在一起的字串要拆**：
   `rewards.jsx:74` 的 group label、`:85`／`:140`／`:1504` 的 desc。
   不拆的話，**日後任何一枚升到傳說，說明都會自動變成「胡出 MIGI 牌型」**。

### ⑨ 🆕 展示櫃只能放 1 枚，而 `ach_pin_tx` 寫死 3 枚

```sql
-- 現成的
select count(*) into v_cnt from member_achievements where member_id=p_member and pinned;
if v_cnt >= 3 and not r.pinned then raise exception '展示櫃最多 3 枚'; end if;
```
2026-09-20 拍板**只能放 1 枚**（個人檔案上一個位置，放最想代表自己的那枚）。

**修法**：不是把 3 改成 1 就好 —— 那樣客人要先取下舊的才能釘新的，
**多一步沒有意義的操作**。應該改成**切換語意**：
```sql
-- 釘新的之前，先把舊的取消
update member_achievements set pinned = false
 where member_id = p_member and pinned and id <> r.id;
```
⚠ 連帶：企劃 R 區的「三格展示櫃」已刪除，「展示櫃第一格」改名**「我的招牌」**
（原本的名字暗示有多格）。

### ⚠ 另外兩個不是問題但要知道

- **seed 63 筆是舊版**（v2.0 兩軸分類，檔頭寫「65 個」實際 63 筆），
  而且全是 `自摸女王`／`大三元` 這種 **M4 才算得出來的**。**不要跑那段**，
  改用企劃的 300 枚。
- **`is_hidden` 與 `visibility` 兩個欄位並存**：範本說 visibility 取代 is_hidden
  且「底層自動同步」，但**沒有看到做同步的觸發器**。兩個都留會漂，
  建表時就該只留 `visibility`。

## 5. 分類：畫面維持前端現有的 6 類，一個字都不用改

```
資料層   group_key  23 區（企劃的 A~W）＋ series      ← 完整存著
畫面層   新手 · 牌局 · 社交 · 餐飲 · 探索 · 特殊      ← 現在畫在成就牆的 tab 上
```

### 🔴 「6 類撐不住 300 枚」是錯的判斷，2026-09-19 當天推翻

找到企劃之後，第一反應是「它有 10 大頁籤，所以 6 類不夠」，
並一度提議改成 `新手/牌桌/牌友/吃喝/到店/彩蛋` ——
**那六個跟現有的六類逐一對得上**，繞了一圈回到原點。

🎯 **真正的問題不是類數不夠，是枚數太少**：25 枚分 6 類，
「探索」與「特殊」各只有 1 枚，看起來像分類壞掉，其實是清單還沒填進去。

📌 **教訓：一份更完整的文件，不代表它每個決定都比較好。**
看到企劃有 10 大頁籤就假設「企劃想得比較周到」，
而沒有問「這 10 個有沒有必要」—— 那是把完整度當成了正確性。

### 🔴 畫面分類不能從 `group_key` 推導

`第一杯飲料`／`第一份餐點` 在企劃的 **A 區「新手引導」**，
但客人點「餐飲」tab 時本來就該看到它們。

⇒ 企劃的 23 區是按「**什麼時候發生**」分，畫面六類是按「**關於什麼**」分。
**兩者不是多對一，A 區會散到多個 tab。**

**所以 `achievements` 要兩個欄位**：`group_key`（企劃 23 區，對照用）
＋ **畫面分類逐枚指定**。

### ⚠ 前端現有的分類有錯，要順手修

`早鳥達人` / `夜貓王` 現在掛在「新手」，而它們要 10 場早場／夜場 ——
那是「牌局」不是新手。

### tab 跟著資料長，不要寫死六個

階段 1 的 29 枚落在 **新手多數 · 牌局少數 · 餐飲 2 · 社交 4**
⇒ 開幕時只畫有東西的 tab。
🔴 寫死六個的話，「探索」「特殊」會空著。

## 6. 稱號

### 6.1 三個來源，分工不要混

| | 來源 | 會不會收回 |
|---|---|---|
| ① | **成就的 `grants_title`** | ❌ 永久 |
| ② | **賽季榮譽**（雀神） | ❌ 永久 —— **每季一個專屬稱號**，例：「2026 秋季雀神熊」 |
| ③ | **抽獎**（6 個，含全店限量 20 個的「手氣爆棚」） | ❌ 永久 |

✅ **三個來源全部永久，沒有任何稱號會被收回**（2026-09-22 使用者更正）。
🔴 這裡原本寫「雀神會收回，卸任者退回」—— **錯的**。
  正解是稱號**帶著季別**：每一季的冠軍拿到的是**那一季自己的**稱號，
  下一季的冠軍拿的是另一個，所以兩者不會互搶，也就沒有「卸任」這件事。
🎯 `stats.jsx:1070` 那句「小熊頭像和稱號解鎖後就留著，掉段位或換季都不會消失」
  **本來就是對的**，不用改（原本這裡說它要改，那是被錯的前提帶歪的）。
⚠ 稱號格式照使用者給的例子：`<年> <季>季雀神熊`。季的叫法要跟賽季名稱同一份
  （「2026 段位秋季賽」→「2026 秋季雀神熊」），不要另外寫一份季別對照。

### 6.2 現在的稱號清單是假的，而且撞名兩個

`rewards.jsx:862` 的 `TITLE_LIST` 六個裡：
- `新手上路` ✅ **一定要保留**（後端 `set_my_title_tx` 硬性放行，全部會員現在戴的就是它）
- `早鳥達人` / `夜貓王` 🔴 **同時是徽章又是稱號**，而且跟抽獎池的
  「早起的鳥」「夜貓子」撞名 —— 違反 §8.5 鐵則「同一樣獎品不可兩邊送」。
  **時段類歸抽獎，成就這邊讓開。**

### 6.3 🎯 稱號連鎖：第一次開桌 → 新手上路 → 第一個稱號

```
成就「第一次開桌」  ＋  稱號「新手上路」  ＋  成就「第一個稱號」
```
🔴 **現況是註冊就送「新手上路」**，那樣「第一個稱號」在註冊當下就解開，
跟「新手報到」同時亮。改成**第一次開桌才給**，那枚成就才有意義。

⚠ 代價：新註冊還沒打牌的人**名字旁邊沒有稱號**。
`set_my_title_tx` 對「新手上路」是硬性放行的，改了要一起處理。

### 6.4 旗艦稱號「MIGI」

```
migi_02  十次咪幾  →  grants_title = 'MIGI'
```

判準：**累積很多 · 條件特殊 · 難度很高**，三者共同的意思是**稀缺**。
稱號掛在名字旁邊人人看得到，給太多就變成噪音。

⚠ 「暫定」兩個字會讓它看起來像還沒定，於是沒有人回來對過
（`member_tiers` 的門檻就這樣錯了三週）。
**所以要有一個負責回頭看的時間點，寫進上線清單。**

## 7. 到店留影（階段 4 的新功能，S 區 9 枚靠它）

### 7.1 什麼時候能拍 —— 當下有進行中的牌局

```
session_players 有你這一列 ＋ left_at is null ＋ table_sessions.status = 'open'
```
🎯 零新硬體，不用 GPS 也不用掃 QR，照片**自動綁到那一場**。
🔴 不綁的話在家拍一張也算，那 9 枚就全部沒有意義。

### 7.2 🔴 「打卡」這個詞不能用

`rewards.jsx:1450` 的「抽屜的日記 · 每日報到」已經佔用了它，
而徽章圖 `badge08` 被畫成**相機**。同一個詞兩件事。
✅ 功能與成就都叫 **「到店留影」**。

### 7.3 ⏳ 照片給誰看 —— 還沒拍板

🔴 **查證到一個會決定架構的事實**：
```
storage.buckets   store-photos public=true / member-avatars public=true / team-crests public=true
```
**現有三個 bucket 全是公開的** —— 拿到網址就看得到。
頭像與團徽本來就要給人看，所以那是對的；
**但打卡照片若在畫面上寫「只有你看得到」而存在 public bucket，那就是說謊。**

| | 甲 · 自己的紀念冊（建議） | 乙 · 公開留影牆 |
|---|---|---|
| bucket | **private** ＋ 後端發簽名網址 | public |
| 審核 | **不用** | 🔴 要有人每天看佇列 |

**建議甲，理由不在程式在人**（硬規則 5.5：那個看佇列的人今天不存在）。
⚠ 照片裡有客人的臉，漏審一張的代價比團徽高得多。
✅ 但 `blocked` 旗標與總部下架 RPC 仍要做（照抄 `admin_remove_avatar_tx`）——
**事後補稽核補不回來**（硬規則 5.6）。

### 7.4 一場一張，可重拍覆蓋

不做相簿。不限張數就要處理容量、排序、刪除、封面，每一項都是新畫面。

### 8.1 動手前要知道的三件事

1. **成就牆現在整面是假的**：`on: 1` 是逐一寫死的
   ⇒ **每個會員看到的已解鎖徽章一模一樣**。
2. **稱號現在是前端說了算**：`save_app_state_tx` 的 `titles` 是
   「兩邊聯集、只增不減」，手打一次 RPC 就能拿到「三屆雀神」（待辦 40）。
   ✅ 引擎做完之後 **`titles` 要變成唯讀的計算結果**，`p_titles` 參數拿掉。
3. **`repeat_cycle`（once／monthly／quarterly）目前沒有任何 RPC 在讀** ——
   建表有這一欄，但 `ach_unlock_tx` 只看 `status='unlocked'` 就回 `already`。
   ⇒ 要做每月可重複的成就時，那支要一起改。**現在不要填 monthly。**
