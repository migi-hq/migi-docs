# 通知系統規格 v1.0

> **這是什麼／何時讀**：通知的狀態模型、每一種通知的完整生命週期、已讀時機、
> 紅點語意、合併與清理。要改通知中心、加新的通知類型、或處理「按了接受通知還在」
> 這類問題時讀這份。
>
> 對照世界級做法（GitHub / Slack / LINE / Facebook / LinkedIn）整理，
> 並套用到 MIGI 現有的六種通知類型。

---

## 0. 最重要的一件事：三個狀態軸是獨立的

**絕大多數通知系統的 bug 都源自把這三件事塞進同一個欄位。**

| 軸 | 問的問題 | 誰改變它 |
|---|---|---|
| **送達** delivered | 這則通知產生了嗎、推播送出了嗎 | 系統 |
| **已讀** read | 使用者看過這一則了嗎 | 使用者「看」 |
| **已處理** actioned | 這則要求的動作做了嗎 | 使用者「做」 |

一則牌咖邀請可以是「**已讀但未處理**」——他看到了，還在考慮。
一則結算通知**永遠不需要處理**——它只是告知。

> **GitHub 的通知有明確三態：unread / read / done。**
> 「Done」是獨立的一鍵，跟已讀無關 —— 你可以讀了但沒完成，也可以直接標完成。
> LinkedIn 的邀請也一樣：接受／忽略是動作，跟「你有沒有看過通知」是兩回事。

🔴 **MIGI 現在只有 `unread` 一個欄位。**「已處理」沒有地方放 ——
所以接受完牌咖邀請之後，那則通知刷新回來還是一顆「接受」按鈕。
（`buddy_invites` 其實有 `pending/accepted/rejected`，但通知列沒有讀它。）

## 1. 通知分兩大類，行為完全不同

| | **可動作** actionable | **純告知** informational |
|---|---|---|
| MIGI 類型 | `buddy_req`、`table_req` | `settle`、`buddy_ok`、`table_ok`、`table_expired`、`system` |
| 有按鈕 | 接受／拒絕 | 查看（或沒有） |
| 有「已處理」狀態 | ✅ 必須有 | ❌ 不需要 |
| 會過期／失效 | ✅ 對方取消、房間解散、逾時 | ❌ |
| 批次已讀 | 可以已讀，**但不等於處理** | 可以 |
| 排序 | 未處理的優先 | 依時間 |

**兩類混在同一份清單沒問題**（LINE、FB 都是），但**狀態模型必須分開**。

## 2. MIGI 六種通知的完整狀態矩陣

| type | 類別 | 動作 | 未處理時 | 處理後顯示 | 會失效嗎 |
|---|---|---|---|---|---|
| `buddy_req` 牌咖邀請 | 可動作 | 接受／拒絕 | 兩顆按鈕 | 「已接受」／「已拒絕」灰字 | ✅ 對方取消、對方已封鎖你 |
| `table_req` 揪桌邀請 | 可動作 | 接受／拒絕 | 兩顆按鈕 | 「已加入」／「已拒絕」灰字 | ✅ **房滿了、房解散、開打時間已過** |
| `buddy_ok` 成為牌咖 | 告知 | 查看 | 查看鈕 | — | ❌ |
| `table_ok` 已加入牌桌 | 告知 | 查看 | 查看鈕 | — | ❌ |
| `table_expired` 房間過期 | 告知 | 查看 | 查看鈕 | — | ❌（它本身就是失效通知） |
| `settle` 結算完成 | 告知 | 查看 | 查看鈕 | — | ❌ |

### 🔴 失效是最容易漏掉的狀態

**揪桌邀請最危險**：客人晚三十分鐘打開通知，那桌可能已經滿了或解散了。

- ❌ **錯誤做法**：按下「接受」才發現失敗，跳一個錯誤訊息。
- ✅ **正確做法**：**列表載入時就顯示「已滿」「已解散」並停用按鈕。**

理由：讓人按一顆註定失敗的按鈕，比一開始就告訴他不能按更糟 ——
他會以為是系統壞了，而不是機會沒了。

## 3. 已讀的觸發時機：三種模式

| 模式 | 做法 | 代表 | 優點 | 缺點 |
|---|---|---|---|---|
| **A 開啟即全讀** | 進頁面就 `markAllRead()` | 早期的簡易實作 | 最簡單 | **你永遠看不到哪則是新的** |
| **B 開啟清紅點、離開才標已讀** | 進頁面只清 badge，離開時才寫已讀 | LINE、Facebook | 這一輪看得出新舊，紅點照樣清 | 需要在卸載時呼叫 |
| **C 逐則標記** | 每則點過才已讀，另有「全部已讀」 | GitHub、Slack | 最精確 | 要多點一次；通知量少時是多餘的 |

### MIGI 採 **B**

> 🔴 **現況是 A**（`notifications.jsx` 進頁面就 `markAllRead()`），
> 所以 `unread` 欄位雖然有從後端回來，畫面卻**永遠不可能顯示未讀狀態** ——
> 在你看到之前就被消掉了。

改成 B 只要移動一行，**後端零改動**：

```js
// A（現況）：進頁面就全部已讀
useEffect(() => { load(); markAllRead(); return onSocial(load) }, [])

// B（建議）：離開頁面時才標已讀
useEffect(() => { load(); return () => markAllRead() }, [])
```

為什麼不選 C：MIGI 的通知量小（一天幾則），沒有 GitHub 那種「稍後處理」的需求。
C 的精確度換不到對應的價值，還多一次點擊。

### ⚠ 已讀不等於已處理

即使整頁標成已讀，`buddy_req` 的「接受／拒絕」按鈕**仍然要留著**。
把已讀當成處理過，是本文件 §0 那個錯誤的最常見表現形式。

## 4. 未讀的視覺

| 狀態 | 樣式 |
|---|---|
| 未讀 | 淺粉底（`--brand-light`）+ 左側小圓點 + 文字粗體 |
| 已讀 | 白底、一般字重 |
| 已處理 | 白底 + 按鈕換成灰字結果（「已接受」） |

**未讀不要用紅色。** 紅色在這個 App 裡是錯誤（`--danger`），
拿來標「有新東西」會讓人以為出事了。用品牌粉。

---

## 5. 紅點語意：dot 還是數字

| 型式 | 語意 | 適合 |
|---|---|---|
| **Dot**（純圓點） | 有新東西 | **通知** |
| **Count**（數字） | 精確幾則未讀 | 訊息、待辦 |

**MIGI 用 dot。** 理由：

- 通知的數字**會讓人焦慮**，而且數字大了就失去意義（「37」跟「38」對使用者沒差別）
- 數字要精確才有用，而通知的「未讀」定義本身就模糊（滑過算不算看過？）
- Slack 的分法就是這樣：**mentions 用數字**（每一則都要回應），**其他活動用 dot**

例外：**未處理的可動作通知可以用數字** —— 「你有 2 則邀請待回覆」是精確且可行動的。

## 6. 合併與分組

### 6.1 合併（aggregation）

同類型、同對象的多則要合併成一列：

> 阿明、小琳 和其他 3 人 想加你為牌咖

Facebook / Instagram 都這樣做。**MIGI 現在量小，可以先不做**，
但 type 設計要預留：合併鍵 = `type + ref 類型`。

⚠ **可動作的通知不要合併** —— 合併之後就沒辦法一則一則接受／拒絕了。
FB 也只合併純告知類。

### 6.2 時間分組

`今天` / `本週` / `更早`。超過三十則時才有意義，現在可以先不做。

## 7. 點擊行為：深層連結

點通知要跳到**帶上下文的頁面**，不是只跳首頁。

| type | 點擊後 |
|---|---|
| `settle` | 該場牌局的結算詳情 |
| `buddy_ok` | 那個人的個人檔案 |
| `table_ok` | 該配桌房的等待畫面 |
| `table_expired` | 配桌列表（順便讓他重新找一桌） |

**`table_expired` 那個是留存設計**：房間過期是負面事件，
把他導到「還有這些桌可以加」比導到空白頁好。

## 8. 推播 vs 站內

| 通道 | 現況 | 說明 |
|---|---|---|
| 站內通知中心 | ✅ 有 | `app_notifications` + 輪詢 |
| 即時推送 | ❌ | Supabase Realtime，卡在 CLAUDE.md 待辦 14（LIFF 換 JWT） |
| LINE 推播 | ❌ | LINE Developers 帳號未申請（CLAUDE.md PENDING） |

**重要的通知不能只靠推播。** 推播會被關掉、會被系統吞掉、會漏。
站內通知中心是**唯一可靠的那一份**，推播只是加速。

→ 反過來說：**站內通知寫入失敗時使用者不會知道**。
所以關鍵訊息要有第二個出口 —— 例如揪桌邀請在配桌頁本身也看得到，
不能只存在於通知列。

## 9. 通知設定（上線前要有）

分類開關，至少三類：

- 牌咖與揪桌邀請
- 牌局結算
- **行銷與活動** ← **法規要求可關閉**

⚠ 台灣個資法與各平台的推播規範都要求商業訊息可退訂。
把行銷跟交易通知混在同一個開關，等於逼使用者為了關廣告連結算通知一起關掉。

## 10. 保留與清理

| 項目 | 建議 |
|---|---|
| 保留期限 | 90 天，之後歸檔或刪除 |
| 已處理的邀請 | **不刪、不隱藏** —— 通知是紀錄 |
| 未處理但已失效 | 顯示為失效，30 天後隱藏 |

**已處理的邀請不要讓它消失。** 按完就不見會讓人懷疑自己誤觸，
或想回頭確認「我剛剛按的是接受還是拒絕」。LINE 的好友邀請也是留著變狀態文字。
