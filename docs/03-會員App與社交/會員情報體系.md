# 會員情報體系（作息 / 耐心 / 人格 / 路程）

**【這是什麼】** 從行為自動推斷會員輪廓的四個維度，含資料來源與應用場景。
**【何時讀】** 做 M3（CRM / 推播 / 撮合優化）之前必讀；設計新表時確認別把原料欄位砍掉。

---

## 為什麼這是這門生意的核心

麻將館賣的不是桌子，是**「湊齊四個人的時刻」**。湊人的前提是知道誰什麼時候有空、能不能到、願意等多久。
M0 已有 `member_availability` 表（星期 × 時段 × often/sometimes/never，且分 `stated` 自填 / `inferred` 推斷），但那是空表——**關鍵是原料從哪來**。

---

## 四個維度

### 1. 作息（何時有空）

| 訊號層 | 來源 | 強度 |
|---|---|---|
| 真實到店 | `session_players.joined_at`（M2 上線後自動累積） | 最強 |
| 配桌意圖 | `match_queue_players.joined_at` | 強 |
| App 活躍 | `app_events` 的 `app_open` 時間分佈 | 輔助 |

視圖：`v_member_join_hours`（每人 × 星期 × 小時的加入次數）

**冷啟動補充**：App 個人檔案提供「我的空檔時段」讓會員自填（寫入 `source='stated'`），
行為資料還沒累積時可用；有行為後以 `inferred` 為準（人會亂填，行為不會說謊）。

### 2. 耐心（願意等多久）

視圖：`v_member_wait_stats`
- `max_patience_min` = 歷次 **quit 前**等待時長的最大值 → 「這位客人最多願意等 18 分鐘」
- `avg_wait_to_match_min` = 成桌前平均等待

**必須用 `leave_reason='quit'` 過濾**：`left_at` 有值可能是四種情況——
自己放棄(quit)／房被解散(cancelled)／等到過期(expired)／跳去別桌(switched)。
只有 quit 反映耐心；混算會被解散事件污染到不能用。

### 3. 行為人格（主動 vs 被動）

`match_queue_players.join_source`：
- `opened` = 自己開房 → **揪團核心客**，行銷話術用「開一桌吧」
- `browse` = 瀏覽列表加入
- `invited` = 受邀 → **跟隨者**，話術用「XX 開桌了要不要加入」

### 4. 路程（多快能到哪家店）

**推斷方式**：`play_at` / `matched_at` vs M2 的實際報到時間之差，同一家店累積取中位數
→ 「這位會員到自由店的慣性反應時間是 25 分鐘」

**殺手級應用**：三缺一、半小時後開打要推給誰？
推給「這時段通常有空（作息）**且** 30 分鐘內到得了（路程）」的人——Uber 派單邏輯。
推給要一小時車程的人是打擾，推給到得了的人是服務。

**不問地址、純行為推斷，會員無感。**

---

## 行銷黃金訊號

**`match_queues.status = 'expired'` 的房 = 「某人在某時段想打，但沒湊到人」**

這是全系統最精準的行銷觸點：隔週同時段主動推播「今晚要不要開一桌？已有 N 位牌咖有空」。
大多數系統只記錄成功的配桌——**成功的配桌是營收，失敗的配桌是情報**。

---

## 分析時的注意事項

- 被店員人工介入（喬時間、強制成桌、代打）的桌，計算「自然成桌速度」時要排除，
  否則店員越勤勞，數據看起來越漂亮，反而看不出哪個時段其實湊桌困難。
- 所有統計 `from v_real_members`，排除測試帳號。
- 推斷引擎（行為 → 回填 `member_availability.inferred`）規劃在 **M3**，屆時原料已累積數月。
