# 台麻側面鏡頭「前後比對算摸打」— 邏輯驗證原型

> **這是什麼／何時讀**：用假資料驗證「拿到前後兩份手牌，能不能算出摸了什麼、打了什麼」的
> Python 沙盤。要動手做側面鏡頭那條路線之前，先跑這個確認核心邏輯成立。
>
> **它不碰鏡頭、不碰 AI 模型、不碰硬體。** 假設牌已經被辨識成一串牌名，只驗證最核心的那層邏輯。
>
> 對應設計文件：[`docs/10-牌譜與AI辨識/牌譜成績資料中台技術設計.md`](../../10-牌譜與AI辨識/牌譜成績資料中台技術設計.md) §10（側面鏡頭 L2 路線）。

---

## 怎麼跑

```
python3 demo.py
```

依序跑 6 種情況、印出每一步偵測到的事件，最後輸出 `事件流範例.jsonl`
（一動作一行，就是即時寫入的格式）。

## 驗證了什麼（6 種情況都跑對）

| 情況 | 結果 |
|---|---|
| 1. 摸到直接打（有拍到摸完的 17 張）| 正確判成「摸中、打中、摸到直接打」|
| 2. 打手裡的牌（有拍到 17 張）| 正確判成「摸九筒、留手、改打九條」|
| 3. **漏拍了 17 張**，只看到前後兩個 16 張 | 仍能從淨變化算出「摸九筒、打九條」|
| 4. 摸到直接打、但**只拍到休息的 16 張** | 側面看不到（無變化），標記「要靠俯視補」|
| 5. **碰牌**（手牌一次少兩張）| 標記「疑似吃碰槓，需俯視確認」，不硬猜 |
| 6. 辨識出錯（牌數對不上）| 標記「異常、需人工複查」，但**不丟資料** |

**結論：前後比對算摸打的核心邏輯成立**，而且連「漏拍中間狀態」都能靠淨變化補回來（情況 3）。

真正算不出來的只有情況 4（摸切且只拍到休息態）—— 那本來就該交給俯視鏡頭，
符合《牌譜成績資料中台技術設計》§10.3 定的兩象限分工。

## 還沒做的部分

1. **真的牌辨識** —— 目前是手打的假字串，實際要換成鏡頭 + 訓練好的台麻 YOLO 模型
   （見 [`台麻AI辨識實作指南.md`](../../10-牌譜與AI辨識/台麻AI辨識實作指南.md)）
2. **俯視鏡頭邏輯** —— 海底出牌順序、逆時針歸屬、吃碰槓判定，另一支程式，還沒寫
3. **吃碰槓的完整處理** —— 情況 5 目前只「標記疑似」，是誰的牌、哪一種要靠俯視補
4. **多鏡頭彙整 + 局次 ID 串接** —— 四支側面 + 一支俯視要用同一個局次 ID 拼成一局
5. **對齊 `paipu_events` 欄位** —— 牌面編碼已對齊（兩碼制），但事件欄位名仍是暫用中文
   （「事件／玩家／牌」）。之後要換成 `game_id` / `hand_id` / `seat` / `turn_no` /
   `action` / `tile` / `meta` / `confidence`，才能直接 insert 進 Supabase。
   欄位定義見 [`sql/_設計稿未落地/牌譜資料庫schema.sql`](../../../sql/_設計稿未落地/牌譜資料庫schema.sql)（尚未執行）

## 牌面編碼

內部**一律存兩碼**（對齊 `paipu_events.tile`），顯示時才轉中文。
完整 42 類對照表與可複製的 Python 字典見
**[`牌面編碼對照表.md`](../../10-牌譜與AI辨識/牌面編碼對照表.md)** —— 那份是唯一來源，
本原型的 `tiles.py` 是它的實作。

三個容易踩到的台麻特性：**無紅5**、條用 `t`（不是日麻的 `s`／索）、
花用 `H1`–`H8`（避開「發 `F0`」的 F）。

## 術語

程式裡「摸到直接打／打手裡的牌」對應日麻的摸切／手切，
這裡刻意用台麻白話 —— 全系列文件的用語鐵則是台麻用語，日麻概念一律排除。
正式欄位命名待與 `paipu_events` 一起敲定。
