它們的共同形狀是：**不設也不會壞，只會安靜地錯。**

| | 不設會怎樣 |
|---|---|
| `orgs.live_from` | 報表**全部是空的**（不是「不準」是「空的」） |
| 創辦人的 `is_test` | 他的消費**永遠不算營收** |
| 賽季 | 第一季就是短的（可接受，見下） |

📌 沒有任何一項會拋錯、會變紅、會有人通知你。

## ① `orgs.live_from` —— 🔴 必做

```sql
update orgs set live_from = '2026-XX-XX 00:00+08' where id = '…';
```

**現在是 `null`。** 而 12 支 `v_real_*` 檢視表全部長這樣：

```sql
x.created_at >= coalesce(o.live_from, 'infinity'::timestamptz)   -- null ⇒ 永遠 false
```

⇒ **今天每一支 `v_real_*` 都回 0 列。** 那是設計上的空不是 bug ——
資料庫裡 `orders` 153 筆、`app_events` 3375 筆**全部是測試**，
因為真實客人到現在還沒出現。

🎯 **設下去的那一刻，今天這批全部永久消失在報表外。**

⚠ 設**當天 00:00**，不要設「現在幾點」—— 開店第一天早上的單也是真的。

## ②.5 常設測試帳號的隔離 —— 🔴 必做，而且今天還沒有

**測試01～04 上線後留著**（使用者 2026-09-05 決定）——
常設測試帳號是每個正式系統都有的東西，
2026-09-05 已給它們合成的 `line_user_id`（`TEST-01`…）與可登入的
auth user，走的是跟真客人**一模一樣**的身分路徑。

🔴 **但「後端分不出它們」正是問題所在**：它們的資料會混進真客人的畫面。

| 出口 | 現況 | 上線前 |
|---|---|---|
| 排行榜 `get_season_leaderboard_tx` | ✅ 已濾 `is_test` | — |
| **配桌房間** `list_match_queues_tx` | 🔴 沒濾 | 要濾 |
| **最近同桌** `list_recent_players_tx` | 🔴 沒濾 | 要濾 |
| **牌咖清單** `list_buddies_tx` | 🔴 沒濾 | 要濾 |
| **門市清單** `list_stores_tx` | 🔴 沒濾 | 要濾 |

🔴 **最痛的不是「看到假房間」，是真的桌子被佔走。**
`_try_auto_seat_tx` / `sweep_auto_seat_tx` / `_finalize_queue_full_tx`
**三支都不看 `is_test`**，而 pg_cron 每 5 分鐘在跑：

```
四個測試帳號湊滿一房 → 自動配桌 → 佔走一張真桌
```

`uq_sessions_open_table` 會把那張桌鎖住，店員在 POS 看到「預留中」
而沒有人會來。次痛的才是真客人報名進一個永遠湊不滿的房 ——
**那看起來完全像是系統壞了**。

## ✅ SQL 已經寫好：`sql/pending/2026-09-05_測試世界與正式世界分開.sql`

🎯 **規則不是「濾掉測試帳號」，是「兩個世界互不相見」**：

```
🔴 濾掉    →  測試帳號也看不到彼此  →  多人測試從此做不了
✅ 對稱    →  對方的 is_test = 我的 is_test
```

那正是 **Stripe test mode** 的規則（測試物件只跟測試物件互動），
而 MIGI 早就選了這個做法（`is_test` ＋ `v_real_*`）——
那份 SQL 只是把它補完，**不是引進 staging**（硬規則 5.7 明列不做）。

內容：`migi_test_world()`（「我在哪個世界」唯一的定義）＋
四支清單函式各加一個述詞 ＋ `match_queues` 的 BEFORE INSERT 觸發器。

⚠ **auto-seat 那三支不用改** —— 房間只能開在同世界的門市（觸發器擋住），
而 auto-seat 是從**該房間的門市**挑桌 ⇒ 測試房只配得到測試門市的桌。
**根因擋掉，症狀自己消失。**

🔴 **店員一律看得到兩個世界**（`current_staff()` 有身分就回 null）——
少了這道例外，POS 登入後會看不到測試門市，
而症狀是「桌況少了幾間店」，沒有人會聯想到過濾規則。

⚠ **那份 SQL 現在跑不動，而且那是刻意的**：第 ⓪ 段檢查
「有沒有至少一間正式門市」，沒有就整份拒絕執行。
→ **順序是：先標好哪幾間是真門市（②），才跑它。**

## 事後驗算（設完當天跑一次）

```sql
-- 全部應該有值、且數字要說得通
select
  (select live_from from orgs limit 1)                        as 營運起始,
  (select count(*) from members where is_test)                as 還是測試的會員,
  (select count(*) from stores  where is_test)                as 還是測試的門市,
  (select count(*) from v_real_orders)                        as 真實訂單,
  (select count(*) from v_real_app_events)                    as 真實事件,
  (select label from rank_seasons
    where now() >= starts_at and now() < ends_at limit 1)     as 現在這一季;
```

🔴 **`真實訂單 = 0` 在上線當天是對的**（還沒有人消費）——
所以這一句的用途是**隔天再跑一次**，看它有沒有從 0 變成正數。
⚠ 只跑當天那一次，會把「設對了」與「設錯了」看成同一件事
（同硬規則 3.55：驗「應該是空的」一定要有正對照）。
