## 0. 為什麼是「客人記分」不是「店員輸入」

決策紀錄第二十四節那張表，這份文件的一切都建立在它上面：

| | 店員輸入（原規格） | **客人電子計分** |
|---|---|---|
| 動機 | 🔴 多做一件事（硬規則 5.5：那個人存在嗎） | ✅ **他本來就要算分** |
| 完整度 | 忘記就沒有 | ✅ **不用就沒得算錢** |
| 誰受惠 | 系統 | ✅ **客人自己**（省去數籌碼、找零） |

🎯 **電子計分不是「記錄結果」，是「取代籌碼」。籌碼每把動，所以計分必須每把。**

而它解決了段位系統最根本的問題：MIGI 是檯費制不抽水，
**系統裡本來沒有任何時刻需要知道誰贏了** —— 日本雀莊有那個副產品（客人要算點結帳），
MIGI 沒有。**電子計分把那個副產品造出來了。**

## 1. 硬體與裝置

### 1.1 ✅ 平板**綁桌，不綁座位**（2026-09-20 定案）

```
綁     這台永遠是「自由店 A3」的            ← 一開始設定一次，之後不動
不綁   四個人誰拿哪一台都行                 ← 座位靠開局那三次點擊決定（見 §2）
```

🎯 **這讓客人零動作**：不用掃 QR、不用選桌號、不用看桌角貼紙。
坐下來拿起平板，**上面已經是 A3 的那四個人**。

📌 曾評估過的兩個方案都被推翻，理由記在這裡免得有人再提：
```
❌ 四台固定裝在桌邊、順時針物理決定    裝反了會「安靜地算錯一整晚」
❌ 領取式 ＋ 桌角貼紙填座位號          客人要低頭看貼紙，而且多四次互動
```
✅ 現在的方案兩個問題都沒有 —— **順序靠「誰是莊家的下家」問出來**，
而那是抬頭一眼就看到的事（§2.2）。

### 1.2 數量與成本（睜著眼睛付）

平板綁桌 ⇒ 數量按**桌數**算，不是按「同時在打」：

```
高雄自由 14 桌 × 4 = 56 台
前鎮      4 桌 × 4 = 16 台
                    ───
全部                72 台
```

⚠ 這不只是採購：**充電**（桌邊插座還是每天收回）、會遺失、會摔壞、系統要更新。
硬規則 5.5 的判準在這裡是「**每天管這 56 台的那個人存在嗎**」。

📌 **曾評估「客人用自己的手機」**（LIFF 已經在了，而且今天入座的人一定是會員），
**2026-09-20 決定不採用**。平板贏在三件事：
```
螢幕大不易誤觸 ／ 不耗客人的電 ／ **訪客也能用**
```
最後一項日後會變重要（見 §5.3 的 `member_id` 不一致）。

### 1.3 `table_devices`（新表）

```sql
table_devices
  id · org_id · store_id · table_id   ← 🎯 綁死，一開始設定一次
  label         'A3-1'（給人看的編號，**不代表座位**）
  device_token  長隨機字串，存平板的 localStorage
  is_active     遺失或故障時在後台撤銷
  last_seen_at  🎯 哪台沒電了／掉線了
```

🔴 **`label` 裡的數字不是座位** —— 它只是「A3 的第幾台」，
方便店員說「A3-2 壞了」。**座位是每一場重新決定的**（§2.2）。
⚠ 這一點要寫在後台的欄位說明上，否則下一個人會以為它是座位
（這個專案記過七次的「一個名字兩個意思」）。

📌 **`last_seen_at` 不是裝飾** —— 56 台裡有一台沒電，
**你要在客人喊之前就知道**。它應該進錯誤儀表（硬規則 12）。

## 2. 開局流程

```
① POS 帶客人到 A3     → table_sessions 建立、四筆 session_players
② A3 那四台平板自動顯示這四個人   ← 平板本來就知道自己是 A3
③ 四個人各拿一台，點「我是誰」
④ 任何一台點三次：莊家 → 莊家的下家 → 莊家的對家
⑤ 開打
```

### 2.1 ③「我是誰」不能省 —— 確認機制靠它

```
A 按胡 → 選被胡對象 B → 選牌型 → 🔔 **B 的平板**跳確認
                                    ↑ 系統要知道哪一台是 B 的
```
平板不知道自己是誰的話，只能四台都跳確認 ⇒ **確認就失去意義了**。

⚠ 並發問題：**四台不能選到同一個人**。前端擋不住（兩台同時按只差幾毫秒）
✅ **讓資料庫擋**：`session_players.device_id` 加 `unique (session_id, device_id)`
  ＋ 綁定時檢查那個人還沒被綁。

### 2.2 🎯 ④ 三次點擊定出全部順序，而且三次是必要且充分的

```
選莊家 A           → A
選 A 的下家 B      → A→B
選 A 的對家 C      → 剩下的 D 自動是 A 的上家
⇒ 下家鏈 A→B→C→D 完全確定
```
**少一次就不夠** —— 只知道 A、B 的話，C 與 D 誰是對家誰是上家分不出來。

🎯 **為什麼問「誰是莊家的下家」而不是「你坐第幾號位」**：
```
座位號   要低頭看桌角貼紙，而且貼紙可能貼反
下家     **抬頭一眼就看到**（莊家隔壁那個人）
```
**現場的人用現場的語言。**

⚠ **任何人都可以點這三次** —— 不需要指定某台平板來做。
四個人圍著桌子，誰先反應過來誰點。

### 2.3 座位在資料裡存什麼

`session_players.seat` 今天是 **`text` 且沒有任何約束**（58 列全是 null，從來沒用過）。

🎯 **建議存「下家鏈的序號」`1–4`，而且明確定義 1 的下家是 2**：
```
1 → 2 → 3 → 4 → 1      ← 開局那三次點擊填出來的
```
⚠ **不要存風位（E/S/W/N）** —— 風位跟著莊家輪動，
**莊家一換那一欄就過期了**，而它看起來完全正常。
✅ 風位是算出來的：`hands.dealer_seat` ＋ 下家鏈 ⇒ 任何一局的四個風位都推得出來。

⚠ 加約束：`unique (session_id, seat)`。

## 3. 每一局的流程

> 📌 **2026-09-23／24 在預覽上拍板的更新**（`docs/_資產/桌邊記分板_四台同步.html`、`_主畫面三案.html`）：
> · 用詞是「**局**」不是「把」（系統術語對照表：單把牌 ＝ 局 ＝ `hands`）
> · **付錢的人各自結算、不等別人**：確認 ＝ 這一家那份當場扣給胡的人；取消 ＝ 這一家不扣、不影響其他人。
>   所以 3.2 那個「B 已確認 · 等待 D」的中間狀態**不再畫**，畫面上也不出現「等某某確認」。
> · 一局什麼時候結束：最後一家回應完。至少一家確認就照常換莊／連莊；全部取消 ＝ 這一局沒發生。
> · 上一局還有人沒回應時，只擋「送出／流局／包牌」，不點名是誰。
> · 卡片上只有「取消」與「確認」兩種按鈕，確認兩倍寬；按了就回主頁。
> · **流局改成要一張確認框**（按的人自己確認；它不用別人確認，按錯沒人擋得住）。
>   另外三台**不跳任何結果卡**，畫面直接進下一局（2026-09-24 使用者指定：「流局其他人不用確認」）。
> · **哪些會推進牌局（局數＋1）**：胡牌、自摸、包牌、流局 **都會**；**咔啦碰不會**（局數、莊家、連莊都不動）。
>   2026-09-24 使用者重申，並在 `_A案互動.html` 上五種各跑一次確認過。
> · 送出的人**不用**自己再確認一次（3.5 包牌是例外，見下）。
> · **主畫面版型 ＝ A 案**（`_A案互動.html`）：頂條＋座位圖＋底部 HERO，卡片內容置中。
>   2026-09-24 試過 Cosy POS 風格（左側欄、卡片靠左、圓形圖示，`_Cosy風格.html`）**不採用** ——
>   使用者判斷原版比較好。側欄會吃掉 200px，六格從 320 縮到 252 寬。

### 3.1 胡牌（放槍）

```
A 按「胡」 → 選誰放的（B）→ 選牌型 → 🔔 **B 的平板跳確認**
                                      ├─ B 按確認 → 生效，四台同步
                                      └─ B 按駁回 → 回到 A 的輸入畫面重填
```

🎯 **只要被胡的人確認，不是三家都確認** ——
B 是唯一有動機檢查的人（他要付錢），一次互動就夠，不會拖慢節奏。

### 3.2 自摸

```
A 按「胡」 → 選「自摸」 → 選牌型 → 🔔 **B、C、D 三台都要確認**
```
⚠ 會出現中間狀態「**B 已確認 · C 已確認 · 等待 D**」——
**那個狀態一定要畫出來**，不然 A 會以為系統卡住。

### 3.3 流局

**任何人都可以按，不需要確認。**
🎯 理由：流局沒有人付錢（除非 ruleset 有罰符）⇒ **沒有得失分就沒有爭議**。
📌 流局時不存在「胡牌的人」，所以「誰按」在這裡沒有意義 —— 誰先按都一樣。

### 3.4 🔴 不設超時

B 賭氣不按就等著。**不要自動生效** ——
```
自動生效 ＝ 把確認變成裝飾
```
⚠ 卡住是現場問題，現場解決（四個人面對面坐著）。
✅ 但**所有人都要有「撤銷上一把」** —— 那才是真正的後路。

### 3.5 包牌（2026-09-23 拍板）

```
A 在自己的平板按「我包牌」 → 「確定要給這三家 ○○○？」取消／確認
  → 🔔 B、C、D 各自跳「收下這些積分，對嗎？」→ 誰確認，誰那一份才加進去（各自結算）
```
· **按的人就是付錢的人**，付給另外三家；沒有胡牌的人，所以**不選牌型**。
· 每家 1 底 3 台；牽涉莊家的那一份再加莊家台（1 ＋ 2×連莊）。A 自己是莊的話三份都加。
· 🔴 **2026-09-24 更正兩件事**（推翻 09-23 的「立刻生效、不用別人確認、一律下莊」）：
  1. **收的三家要按確認**，確認了數字才加 —— 跟胡牌一樣是各自結算。
  2. **莊家包牌才下莊；閒家包牌，莊家繼續連莊。**
· 按的人自己那一張確認框保留（他是付錢的人，先核對總數）。

### 3.6 咔啦碰（2026-09-24 拍板）

```
A 按「咔啦碰」 → 指定捨牌的那一家（B）→ 🔔 B 的平板跳確認 → B 確認才生效
```
| | |
|---|---|
| 誰付給誰 | **按的人（A）付給捨牌的人（B）** |
| 金額 | **固定 1 台，不算底**（100/20 的桌就是 20 分） |
| 莊家台 | **不加**，誰是莊都一樣 |
| 牌型 | 不進牌型選擇 |
| 確認 | **給的人不用確認，收的人要確認**（跟包牌相反：包牌是給的人確認、收的人不用） |
| 莊家／連莊 | 不動 |

⚠ 「收的人要確認、給的人不用」跟其他動作的邏輯不同，實作時不要套 3.1 那條「要付錢的人才確認」——
  這裡付錢的是按的人，確認的卻是收錢的人。理由是使用者定的，不是推出來的。
📌 主畫面上它跟「我包牌」共用右上那一格，切成上下兩顆（`_主畫面三案.html` A 案）。

## 4. 牌型與台數

### ✅ 預設選牌型，系統換算台數；也可以直接輸台數

```
預設   點「碰碰胡」「門清」「自摸」→ 系統按 ruleset 算出 6 台
備用   直接輸入「6 台」
```

🎯 **選牌型的價值不只是成就，是消除爭議** ——
「這副牌到底幾台」正是麻將桌上最常見的吵架，而選牌型讓**系統當那個算術的裁判**。
客人不用心算，也不會有人少報或多報。

⚠ **直接輸台數那一把不會有牌型資料** ⇒ 不觸發牌型成就。
🔴 所以「直接輸台數」要**藏一層**，不可以跟選牌型一樣順手 ——
否則大家都走捷徑，**牌型資料會永遠是空的**，而 C 區 31 枚成就等於白做。

### 🔴 這個決定直接決定 31 枚成就做不做得到

成就企劃寫得很明白：
```
① 只記台數   ⇒ B 區台數成就成立、**C 區 31 枚與 MIGI 全部不成立**（MIGI 是牌型，2026-09-24）
② 記到牌型   ⇒ C 區成立
```
✅ 選了 ②。所以 `hands` 要有一個**牌型陣列欄位**把它存下來，
🔴 **事後補不回來**（歷史牌局沒記就是沒記）。

### ✅ MIGI ruleset（2026-09-20 拍板，決策紀錄第二十四節那四個問題全部有答案了）

```
單把積分 ＝ 底 ＋ 台 × 台數          （底與台來自 stake_levels）

① 自摸     三家各付，胡牌者得三家之和
② 放槍     放槍者一家付全額，另外兩家 0
③ 莊家     **+1 台，雙向**（胡也加、被胡也加）
④ 連莊     連 N 拉 N，**+N 台**
```

### 🎯 而 ③④ 有一條統一的表述：**莊家的加台掛在莊家身上**

```
莊家附加台 ＝ 1 ＋ 連莊數 N

胡牌者是莊家   → 三家付款人都付「牌型台數 ＋ 莊家附加台」
胡牌者是閒家   → 閒家付款人付「牌型台數」
                 莊家付款人付「牌型台數 ＋ 莊家附加台」
```

🔴 **連莊是莊家的事，所以拉莊台由莊家承擔**，不是全桌一起加。
⚠ **後果：同一把裡每個付款人的台數可能不一樣** ——
計分不能只算一個數字，要**逐個付款關係算**。
✅ `hands.score_delta` 本來就是 jsonb 逐座位，撐得住。

### 驗算（級距 100/20，牌型 5 台）

| 情境 | 閒家付 | 莊家付 | 胡牌者得 |
|---|---|---|---|
| 閒家胡，閒家放槍 | 5 台＝200 | — | 200 |
| 閒家胡，**莊家放槍** | — | 5＋1＝6 台＝220 | 220 |
| 閒家自摸 | 5 台＝200 ×2 | 6 台＝220 | **620** |
| **莊家**胡，被放槍 | 6 台＝220 | — | 220 |
| **莊家**自摸 | 6 台＝220 ×3 | — | **660** |
| 連莊 2，**閒家**自摸 | **5 台＝200 ×2** | **8 台＝260** | **660** |
| 連莊 2，**莊家**自摸 | 8 台＝260 ×3 | — | **780** |

### ✅ MIGI 是**一個牌型，8 台**（2026-09-24 使用者更正）

🔴 在此之前這一節寫的是「咪幾 ＝ 牌型台數 ≥ 8」，**那個定義作廢了**。
MIGI 跟清一色、大三元一樣是牌型表裡的一格，選了就是 8 台，可以跟別的牌型一起算。
⇒ 咪幾成就（`migi_01`／`migi_02`）看的是**牌型陣列裡有沒有 MIGI**，不看台數。
⏳ **還沒定：哪一副牌算 MIGI**（牌型的組成）—— 要寫進 ruleset 並讓店員知道。
📌 預覽：`docs/_資產/桌邊記分板_A案互動.html` 牌型頁最後一格，一圈 `--gold` 金邊 ——
  跟成就「傳說」的金邊同一個 token，**是平板上唯一用金色的地方**（CLAUDE.md 硬規則 13.9 的例外）。

### 🔴 「大牌」看**牌型台數**，不看總台數

```
❌ 總台數 ≥ 8      連莊 2 次、牌型只有 5 台也會被算成大牌
✅ **牌型台數 ≥ 8**  「這副牌真的漂亮」才算
```
⇒ B 區的 `深夜大牌`／`連場大牌`／`梅開二度` 一律看**牌型台數**。
🎯 如果它們可以靠「剛好連莊很多次」拿到，那些成就就不值錢了。

### ⇒ `hands` 存什麼

```
tai_pattern   牌型台數     🎯 台數成就（大牌）看這個
patterns      牌型陣列     🎯 C 區 31 枚與 MIGI 看這個
renzhuang     連莊數       （設計稿已有）
dealer_seat   莊家座位     （設計稿已有）

📌 莊家附加台 ＝ 1 ＋ renzhuang ⇒ **實際計分推得出來，不用另外存**
```

### 其餘已定的規則

📌 **規則全台統一，只有有花／無花兩套**（2026-09-19 拍板）。
⚠ 風牌採 MIGI 自訂規則：**任何風刻 ＝ 1 台**，不分圈風門風
（跟標準台麻不同，**要讓店員知道** —— 老手會問「我東風圈當東家怎麼只有 1 台」）。
⏳ 大四喜／小四喜的台數要不要含那幾個風各自的 1 台，**還沒定**。

### 純娛樂局用 30/10 算分（2026-09-20 拍板）

`stake_levels` 的純娛樂原本是 `base=0, tai=0` ⇒ 每把算出來都是 0
⇒ 排不出名次 ⇒ 記分板對那一桌**沒有任何東西可以顯示**。
✅ **把那一列改成 `base=30, tai=10`，`is_hygiene` 維持 `true`。**
📄 `sql/pending/2026-09-20_純娛樂用30-10算分.sql`

🎯 **兩個欄位回答兩個不同的問題，不要混：**
```
base / tai    這桌**怎麼算**分
is_hygiene    這桌的分數**算不算數**
```
純娛樂要的正是「照 30/10 算分，但不算數」—— 而 `0/0` 表達不出那件事，
它是**把「沒有」寫成了一個值**（同「0 是斷言」那一族）。

🔴 **不加 `score_base` / `score_tai` 兩欄。**
這一節原本寫「那兩欄今天不存在，要加」——**那是沒查就寫的**。
撈 `information_schema` 才知道 **`base`／`tai` 早就存在而且可為 null**。
📌 同踩坑第 29 條的反向版：**先查再說「沒有」。**

🔴 **也不可以在記分板寫死 `if 純娛樂 then 30/10`** ——
30/10 本來就是另一列，寫死就是「一個事實兩個名字」第八次。

### ✅ 改這一列今天**零行為影響**（查出來的，不是猜的）
```
全庫讀 sl.base 的   1 支   placeholder_ranks_tx
                           而它是 case when sl.is_hygiene then null else … end
                           ⇒ 純娛樂在碰到 base 之前就被短路了
全庫讀 sl.tai 的    0 支   ⇒ 那一欄今天還沒有任何讀者，記分板是第一個
```

### 🔴 真正的分岔點在「記分板上線那天」
記分板會產生真的分數 ⇒ 那時要決定**寫不寫進 `session_players.final_score`**。
**寫的話，`get_my_stats_tx` 必須在同一批改**：
```
:76 / :104   and sp.final_score is not null      ← 🔴 它是靠 null 排除純娛樂的
:133 / :144  coalesce(sl.is_hygiene, false)      ← 各級距那一段才是看旗標
```
⇒ 純娛樂一旦有分數，**勝率／最長連勝／單場最多積分會靜默把它算進去**，
而 `:62` 那句「純娛樂與舊資料都不該進來」的註解會變成一句謊話 ——
**程式照跑、數字照樣看起來合理**。
✅ 正解：那一批把總計那兩行的 `final_score is not null` 換成 `not hygiene`。

## 6. 權限與安全

### 🔴 平板只能下單，不能付款

`device_token` 存在平板的 localStorage 裡 —— 那個憑證**物理上會被四個陌生人碰一整晚**。

```
✅ 記分              出錯可以撤銷
✅ 點餐「下單」       送出訂單，掛在這一桌
🔴 點餐「付款」       ← **不要**。扣點數 ＝ 花客人的錢
```
⇒ **收桌時在 POS 結帳**（現在本來就是這樣）。
🎯 這樣 token 外流的最壞後果是「有人幫別桌點了一份雞塊」，**不是「有人把餘額花光」**。

### 這是系統裡的第三種身分

```
POS      anon key ＋ 店員 LINE 登入
會員 App  LIFF ＋ JWT（2026-09-20 收尾完成，身分只認 JWT）
平板      🆕 device_token ＋ 綁定的 table_id
```
⚠ 設計時要照硬規則 2.6b **兩個方向都收授權**，
而且記分的 RPC **不可以收 `p_member_id`** —— 身分從 token 與座位解析出來
（同待辦 14 的通則：身分不可以由呼叫端宣告）。
