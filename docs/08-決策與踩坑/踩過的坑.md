## 一、部署與白屏

### 1. LIFF 白屏：build hash 含底線

**症狀**：網頁版正常、LIFF 白屏；清快取無效、網址加 `?v=N` 也無效。
**根因**：某次 Vite build 產生 `index-57-_FGWz.js` —— hash 含底線，LINE WebView 載入這種檔名失敗。
純機率事件，所以會「密集開發一個月都沒事，突然炸」。
**解法**：`vite.config.js` 設 `hashCharacters: 'hex'`，強制 hash 只用 0-9a-f。

**診斷法**：比對「網頁版原始碼的 JS 檔名」vs「LIFF 報的載入失敗檔名」——
檔名**一樣** = 檔案本身在 WebView 載不動；檔名**不一樣** = 才是快取問題。

> ⚠ **現況**：`migi-web` 已設定；**`migi-pos` 沒有設**（見第八節）。

### 2. LIFF 白屏：ES2020 語法

**根因**：LINE 舊版 WebView 不支援 `?.` / `??`，整個 module SyntaxError 靜默死掉，
**不觸發 `window.onerror`、Console 沒紅字**。網頁版正常是因為現代瀏覽器支援。
**解法**：`vite.config.js` 加 `build: { target: 'es2015' }`。**此設定不可移除。**
`migi-web` 與 `migi-pos` 都已設定（2026-08-14 確認）。

**診斷法**：`index.html` 加 inline 除錯器（錯誤 overlay + 版本標記 + 10 秒檢查 root 是否為空）。
「看得到標記但 root 是空的」= module 根本沒跑 = 語法或載入問題。

### 3. Cloudflare Pages build 失敗會靜默保留舊版

**症狀**：push 了好幾次，線上完全沒變。
**根因**：build 失敗時 Pages **保留上一次成功的版本**，不會有任何提示。
曾因 `src/assets/` 圖片沒進 repo，build 報 `Could not resolve "../assets/bear-lv1.webp"`。
**SOP**：**push 完瞄一眼 Deployments 是綠色 Success 還是紅色 Failed。**
這一步能省下大量「為什麼沒更新」的鬼打牆。

### 3b. build 成功 ≠ 已上線：Production 沒跟上最新 build（2026-08-15）

**症狀**：push 之後 Deployments 列表出現綠勾，但線上行為完全沒變。
清快取、無痕視窗、`Ctrl+Shift+R` 全部無效。

**根因**：Cloudflare Pages 頁面最上方的 **Production 區塊**顯示的是「目前正式環境服務的那個 deployment」，
它**不一定是列表最上面那筆**。當時的狀況是：

```
Production：       main ca4c1d3   an hour ago      ← pos.migi.tw 實際跑的
All deployments：  main 34ebe4d   6 minutes ago  ✓  ← build 成功但沒推上去
                   main a7e5eec  12 minutes ago  ✓  ← 同上
                   main ca4c1d3   an hour ago    ✓
```

兩個新 commit 都 build 成功，但正式網域還服務著一小時前的版本 ——
所以不管怎麼清瀏覽器快取都沒用，**線上根本還沒換版**。

**跟第 3 條的差別**：第 3 條是 build **失敗**、靜默保留舊版；
這條是 build **成功**、但正式環境沒推進。兩者的 Deployments 列表看起來都有綠勾，
差別只在最上方 Production 區塊顯示哪個 commit。

**診斷法（關鍵）**：**看 Production 區塊的 commit hash，不要只看列表有沒有綠勾。**
兩者對不上就是這個問題。

**確認程式碼有沒有問題**：每個 build 都有自己的預覽網址
（`https://<hash>.migi-pos.pages.dev`），直接開那個測。
若預覽網址行為正確 → 程式碼沒問題，純粹是正式環境沒換版。
這一步能立刻分辨「我寫錯了」還是「沒部署到」，省掉大量瞎猜。

**處置（依序）**：

1. **先重整 Cloudflare 頁面、等幾分鐘再看** —— 2026-08-15 這次就是如此：
   Production 一度落後兩個 commit（顯示一小時前的版本），約十幾分鐘後自己追上最新的。
   Deployments 列表更新得比上方 Production 區塊快，兩者短時間內不同步是正常的
2. 等了仍不對，才在該筆的 `⋯` 選單手動 Promote to production
3. 若反覆發生，檢查 Settings 的 Production branch 是不是 `main`

**別急著手動 promote** —— 多數情況只是延遲。真正的價值在第一步的診斷：
知道要看 Production 區塊的 hash，就不會浪費時間在清瀏覽器快取上。

### 3c. 批次替換腳本不懂 JSX 與物件屬性的差別（2026-08-15）

**症狀**：連續四次 build 失敗，Production 靜默停在四個 commit 之前，
使用者反覆回報「改了但畫面沒變」，而程式碼看起來都正確。

**根因**：用 PowerShell 腳本把寫死色碼批次換成 token 時，腳本只認「帶引號的色碼」：

```jsx
color: "#fff"   →  color: C.white     ✅ 物件屬性，正確
color="#fff"    →  color=C.white      ❌ JSX 屬性，缺大括號 → 語法錯誤
```

兩者長得幾乎一樣，但語法規則不同。JSX 屬性接變數必須寫 `color={C.white}`。

**Cloudflare build log 直接指出位置**：

```
Expected "{" but found "C"
223|  <Pill bg={C.accent} color=C.white>待成桌 3 桌</Pill>
```

**教訓有兩層**：

1. **批次替換之後一定要掃一次語法**，特別是 JSX。掃描條件：
   `\s\w+=[A-Za-z_$]` —— 屬性等號後直接接識別字而非 `{`、`"`、`'`。
   當時其實有跑這支掃描，第一項就列出了那一行，但沒把它當回事 ——
   **掃出來的東西要當成問題，不是當成雜訊**。
2. **push 完沒確認 build 成功，就等於沒交付**（同第 3 條）。
   四輪來回全都可以省掉，只要第一次回報「沒改」時就先看 Deployments。

**本機沒有 Node 的專案要特別小心**：無法在推之前跑 build 驗證語法，
Cloudflare 的 build log 是唯一的守門員 —— 那就更該每次都看。

### 4. `_headers` 快取設定：可以用，但只能指名個別路徑

**歷史**：
- v1 對根路徑用**萬用 `/*`** → JS 模組請求被回傳 HTML → MIME 錯誤 → 整站白畫面
- 因為這次事故，一度立下「絕對不要用 `_headers`」的規則
- v2 只擋 `/index.html`，漏了 `/` —— 但 LINE 載入的是根網址 → 根文件被快取住舊版 → 指向已刪除的舊 JS hash → 白屏
- **v3（現行）**：明確指名 `/`、`/index.html`、`/version.json`，不用萬用

**現行規則**：可以用 `_headers`，但**只能逐條指名檔案路徑，絕對不要用 `/*`**。
現行內容見 `migi-web/public/_headers`，動它之前先讀那個檔頭的註解。

### 5. 圖片換了不更新（固定檔名快取）

**根因**：`public/` 的檔案原樣複製、**檔名固定**，內容改了檔名沒變 → 瀏覽器用快取。
**根治**：圖片全部移到 `src/assets/`，用 `import` 引用（集中在 `src/lib/images.js`），
Vite 會加 content hash（`snack-cookie.a3f9c2.webp`），內容一改檔名自動變。
**規矩**：新圖放 `src/assets/` 並在 `images.js` 註冊，**不要放 `public/`**。
（例外：`public/default-avatar.svg` 仍是舊做法，要換它記得比照搬遷。）

### 6. 白屏排查 SOP

1. 先分辨純白 vs 🐻卡＋看版本號
2. 三 URL 交叉定位：`migi-web.pages.dev` ／ 電腦 Chrome `app.migi.tw` F12 ／ LINE 開 `version.json`
3. 查 `app_events` 有無 `app_error`

**電腦好、LINE 壞 = 快取層問題；兩邊都白 = 檔案沒進 repo 或語法問題。**

## 二、Supabase RLS 與權限

### 7. anon key 查詢「成功但回空陣列」

前端用 anon key 沒有 auth session → `current_org_id()` 回 null →
直接 `supabase.from('表').select()` **不報錯、回空陣列**，是最難察覺的失敗模式。

**鐵則：POS 與 App 所有查詢一律走 SECURITY DEFINER RPC。**（CLAUDE.md 硬規則 4）

### 8. `stack depth limit exceeded`（讀取 500）

**根因**：RLS policy 用了 helper 函式 `current_org_id()`，該函式查 staff/members 找 org，
但沒有 SECURITY DEFINER → 查表受 RLS 限制 → 觸發 policy → policy 又呼叫該函式 → 無限遞迴。

```sql
CREATE OR REPLACE FUNCTION public.current_org_id() RETURNS uuid
LANGUAGE sql STABLE
SECURITY DEFINER              -- 繞過 RLS，斷開遞迴
SET search_path = public      -- 配套安全設定，防注入
AS $$ ... $$;
```

**通則：所有被 RLS policy 引用的 helper 函式，一律 SECURITY DEFINER + SET search_path。**

### 9. `new row violates row-level security policy`（寫入 403）

兩個原因常同時存在：
- **policy 只有讀取**：`for select` 的 USING 不管寫入，INSERT/UPDATE 要有 WITH CHECK
- **登入帳號不在 staff/members**：`current_org_id()` 回 null，org_id 對不上

```sql
insert into staff (org_id, auth_uid, name, role)
values ('<org>', '<auth user id>', 'MIGI 總部管理員', 'hq');

create policy products_org_write on products
  for all
  using (org_id = current_org_id())
  with check (org_id = current_org_id());
```

**通則**：每個要用系統的登入帳號（HQ 管理員、每個 POS 店員）都必須在 `staff` 表有對應資料。

### 10. `REVOKE` 沒效果 —— PUBLIC 的預設權限

**根因**：建立函式時 PostgreSQL **預設把 EXECUTE 授予 PUBLIC**，anon / authenticated 從 PUBLIC 繼承。
只收回它們的明確授權，仍能透過 PUBLIC 呼叫。
**怎麼看出來**：查 `proacl`，開頭的 `=X/postgres`（等號前空白 = PUBLIC）就是。
**修法**：`REVOKE EXECUTE ON FUNCTION ... FROM PUBLIC, anon, authenticated;`

## 三、PostgreSQL 函式與遷移

### 11. 改函式簽名時 `CREATE OR REPLACE` 不會覆蓋舊版

PostgreSQL 把不同參數數量視為不同函式，會變成新舊並存，呼叫端可能打到舊的。
同一份 SQL 必須附 `DROP FUNCTION IF EXISTS public.函式名(舊參數型別清單);`（CLAUDE.md 硬規則 2）

已在 `register_member_tx`、`calc_session_fee_tx`、`join_session_tx` 各踩過一次。
2026-08-14 又在 `leave_match_queue_tx` 發現一組殘留的多載孤兒版。

**驗證方式**：
```sql
SELECT count(*), string_agg(pronargs::text, ',')
  FROM pg_proc WHERE proname = '函式名';
-- 應回 1；多於 1 代表新舊並存
```

### 12. `42P13: cannot remove parameter defaults from existing function`

**根因**：`CREATE OR REPLACE` 改既有函式，但新版沒帶原本的參數預設值。
**修法**：照 HINT 先 `DROP FUNCTION IF EXISTS xxx(參數型別列表);` 再 CREATE。

### 13. `CREATE FUNCTION` 不檢查函式體裡的欄位是否存在

**這是 2026-08-14 學到最貴的一課。** SQL 跑完沒報錯 ≠ 函式能用。
`dev_reset_test_data_tx` 有六處欄位對不上實際 schema（`closed_at`、`match_queue_members`、
`buddy_invites.from_member`、`wallet_txns.kind/points`、`members.points_balance`、`tables.status`），
第一個 UPDATE 就會拋 42703 —— **它從建立以來一次都沒成功執行過，卻被當成已完成三週。**

**鐵則：RPC 寫完必須實際執行並看到回傳，才算完成。**（CLAUDE.md 硬規則 7）

### 13b. 從未執行過的函式，每一行都是未驗證的（2026-08-15 又踩一次）

修好上面那六處欄位名之後，同一支函式再度失敗：

```
ERROR 23503: update or delete on table "orders" violates foreign key
constraint "order_items_order_id_fkey" on table "order_items"
CONTEXT: SQL statement "delete from orders where member_id = any(v_members)"
```

**根因**：原版註解寫「訂單（含明細、付款、發票草稿**由外鍵連動**）」，暗示是 CASCADE。
實際查證：

```
order_items    → orders   on delete RESTRICT
order_payments → orders   on delete RESTRICT
order_payments 另有觸發器 trg_payments_no_delete 禁止刪除
member_coupons → orders   on delete NO ACTION
```

**收過錢的訂單在設計上就不可刪**（與 `wallet_txns` 的 append-only 同一套財務原則）。
那行 `delete from orders` 存在三週、從未被執行過一次，因為函式在更前面就炸了。

**教訓**：修「從未成功執行過」的函式時，前面的錯誤只是擋住了後面的錯誤。
心態要是**逐行重新審視**，不是「修錯字」——
每一個對 schema 或約束的假設都要當場查證，不能因為原作者寫了註解就採信。

**順帶一提，這件事證明了一個好設計**：`trg_payments_no_delete` 加上 `RESTRICT` 外鍵，
讓「刪掉收過錢的訂單」在資料庫層就不可能。就算函式寫錯，帳也不會被清掉 ——
錯誤被擋在最外層，而不是靠寫程式的人記得別做。

### 14. 停用舊函式不要用 `CREATE OR REPLACE` 覆寫

覆寫會**抹掉原始碼**（無法稽核），而且可能觸發 42P13。
正確做法：`REVOKE` 撤銷執行權限 + `COMMENT` 標註停用原因，函式本體完整保留。

### 15. `array_agg is an aggregate function`

**根因**：用 `pg_get_functiondef()` 掃描函式時，碰到聚合函式就報錯。
**修法**：改讀 `prosrc` 欄位，並加 `prokind = 'f'` 排除聚合函式。

### 16. 改欄位名前，先查誰在引用它

`products.unit_points` 更名時，查到 `checkout_tx` 內含 `unit_points` 字樣一度以為會壞。
實際查證：那是 `order_items` 的欄位，不是 `products` 的，而且 `checkout_tx` 的價格全部來自
前端傳入的 JSON，根本不讀 `products` 表。
**通則**：看到函式裡有同名字串，先確認它指的是哪張表的欄位，不要直接假設。

### 17. 刪欄位的正確順序

要刪 `order_items.unit_points`（not null 舊主欄）時：
1. **先**改 `checkout_tx`，讓它不再寫入該欄
2. **再**補齊資料、把新欄設 not null、DROP 舊欄

順序反了，中間會有一段「函式寫入不存在的欄位」的空窗，結帳全部失敗。

### 18. append-only 帳本刪不掉

`wallet_txns` 與 `app_events` 都有觸發器禁止 UPDATE/DELETE：

```
ERROR: wallet_txns 為 append-only 帳本，不可 UPDATE/DELETE；退款請新增 reversal 分錄
```

**帳本只進不出。** 錯誤交易用沖正（`reverse_txn_tx`）抵銷，測試資料用 `is_test` 標記隔離。
另外 `wallet_txns` 沒有任何觸發器會自動同步 `wallets.balance` ——
插完流水要自己呼叫 `fix_wallet_balance_tx` 重算（2026-08-14 查證）。

## 四、Supabase SQL Editor 操作

### 19. 一次跑多個 SELECT 只顯示最後一個結果

**這是 SQL Editor 的行為，不是出錯。** 三段 SELECT 都執行了，只是結果區只顯示最後一段。

**鐵則**：診斷用 SQL **一份只放一個 SELECT**。要查多樣就用 `UNION ALL` 併成單一結果表
（欄位數要一致），或拆成多個檔。DDL（alter / create policy 等無回傳的）可以多段一起。

### 20. `jsonb_pretty` 的結果在網格裡看不到

回傳的是一整坨多行字串，塞在一格裡只看得到開頭幾個字元。
要看陣列內容改用 `jsonb_array_elements` 展開成多列：

```sql
select e->>'label' as 桌號, e->>'status' as 狀態, (e->>'players')::int as 人數
from jsonb_array_elements(list_tables_tx('<org>'::uuid, '<store>'::uuid)) e
order by 1;
```

## 五、前端 React

### 21. 元件沒 import 就使用 → build 過但點了就 crash

**根因**：JSX 用了未 import 的元件/函式，**打包器不會擋未定義的執行期識別字**，
只有真正執行到才炸。
**發生過兩次**：`App.jsx` 用 `SettleSheet` 但沒 import；清 import 時把還在用的 `track` 一起刪掉。
**預防**：刪 import 前全檔搜尋該識別字；改完關鍵路徑實際點一次。

### 22. 拆檔造成白畫面：漏帶依賴

拆 React 大檔時的連環坑，都是「漏帶東西」：
- 用了 `createPortal` / `useState` 但沒 import
- 元件依賴的子元件還留在原檔沒一起搬
- **最隱蔽的：漏抽 module 級常數**（`MJ_INK` 這類常數留在原檔，執行到才爆 not defined）

**驗證方法**：`esbuild` bundle **抓不到**這類執行期錯誤。
唯一可靠的是用 jsdom 真 DOM 環境實際 mount 渲染測試。

### 23. 元件參數漏傳

元件內用 `zIndex: z` 但函式簽名漏了 `z` → undefined → 一渲染就白畫面。

同類問題 2026-08-14 又出現一次，形式不同但根因一樣：
`TablePage` 傳給 `OpenCheckoutPage` 的 props 名稱是舊的（`back` / `mode2` / `players`），
新版解構的是 `{sessionId, table, mode, ...}` —— **多傳的被忽略、該有的是 undefined，不報錯**，
導致 `sessionId` 為 undefined 打進三支 RPC。
**通則**：改元件 props 介面時，全專案搜尋該元件的所有使用點，不能只改一處。

### 24. 用正則刪函式時範圍過寬會誤刪

`[\s\S]*?\n\}\n` 遇巢狀括號會多吃，已誤刪 `renderMid` 與 `closeTopup` 各一次。
**改用明確指定完整內容來取代，不要用正則批次刪。**

| 多行字串接合寫成 `+'` 而非 `'+` → 整段 JS `Invalid or unexpected token` | 每行固定收尾 `'+`，下一行固定開頭 `'`，改完必驗 |
| 眼睛看不出語法錯 | 交付前用 `node -e "new Function(script)"` 驗，要行號就抽成 .js 跑 `node --check` |
| 大型互動原型即時渲染會卡死 | 一律產出 HTML 檔交付下載，不在對話內即時渲染 |
| 中文檔名造成下載失效（「咖」字） | 檔名用英文小寫加連字號，中文放文件標題 |
| 對齊簡報時抄了深褐黑底 | 那是投影片舞台色，App/後台一律白底。要對齊的是白卡內部的設計語言 |

POS HTML 原型期的計價/版面坑：

| 症狀 | 根因 |
|---|---|
| 檯費顯示 0／「免收」 | `CATALOG.檯費` 改空陣列後 `catalogItem()` 查不到，回傳預設 `price: 0` |
| 舊檯費品項刪不掉 | `indexOf('檯費')===0` 判斷失敗（品名是「配桌檯費」）→ 改用 `>= 0` |
| 小計虛胖 | 誤含儲值金額 → 改用 `discountable(p)` |
| 按鈕文字不置中 | 兩條 `.payfor-btn` CSS 並存，舊的 `display:flex` 讓 `text-align:center` 失效 |
| 代付面板延續到別人身上 | `payForOpen` 是全域狀態，切換座位時未重置 |
| 步進鈕一高一低 | 全形 `＋` 與半形 `−` 基線不同 → 統一半形 + `line-height:1` |
| 名稱截斷失效 | flex 子元素預設不縮，需同時加 `min-width: 0` |
| 展開時把內容往上推 | 區塊在 `flex-direction:column` 容器底部，變高只能往上長 |

### 其他

- **貨號不回收**：刪除是軟刪除，回收號碼會撞號，且違反「一個貨號永遠對應同一商品」。
  `nextSku` 取現有最大值 +1，刪掉 002 後新增拿到 004。這是業界標準做法。

## 八、尚未發生但已可預見的坑（2026-08-14 推演）

這一節不是經驗，是**從現有程式碼推導出來的風險**。每條都附證據與觸發條件。
排在前面的是「條件成立就一定會發生」，後面是「動到那塊才會遇到」。

### P1. POS 與 admin 沒有 ErrorBoundary —— 渲染錯誤 = 全白且無自救

> ✅ **已處理（2026-08-14，`ca4c1d3` / `a872c89`）**：POS 與 admin 各加了一份。
> 不共用 migi-web 那份，因為它依賴 `analytics.js` 的 `track()` 與 App 端 CSS 變數，
> 照抄會在錯誤處理裡再炸一次。兩份都把錯誤訊息顯示在畫面上供截圖回報。
> 以下保留原始分析。

**證據**：`ErrorBoundary` 只存在於 `migi-web/src/lib/`，由 `migi-web/src/main.jsx:64` 包住整個 App。
`migi-pos` 與 `migi-admin` 兩個 repo 完全沒有這個檔案。

**為什麼危險**：`埋點事件字典.md` 寫著「ErrorBoundary 捕捉 React 渲染錯誤並顯示友善畫面
（不再白屏）」—— **那句話只對 migi-web 成立**，讀的人很容易以為三端都有。
而 POS 是店員營業中、客人站在櫃台前用的，白屏的代價比會員端高。

**觸發條件**：任何一次 render 階段的例外（讀 undefined 的屬性、元件回傳非法值…）。
本文第 21、22、23 條記的那幾類錯誤，在 migi-web 會被接住，在 POS 就是整頁白。

**建議**：把 `ErrorBoundary.jsx` 複製到 POS 與 admin，在 `main.jsx` 包住 App。成本很低。

### P2. ErrorBoundary 接不到非同步與事件處理器的錯誤

> ✅ **POS 已處理（2026-08-14，`ca4c1d3`）**：`migi-pos/src/lib/api.js` 新增 `rpc()`
> 統一包 try/catch，網路層失敗回 `{ message: '網路連線失敗…', network: true }`。
> **`migi-web` 與 `migi-admin` 尚未比照辦理** —— 兩者的資料層仍只解構 `{ data, error }`。
> 以下保留原始分析。

**這是 React 的邊界，不是實作缺陷**，但很容易誤以為「有 ErrorBoundary 就安全了」。
它只接 render / lifecycle 階段的錯誤，**接不到**：事件處理器內的例外、`await` 後的例外、
`setTimeout` 內的例外。

**具體風險點**：`lib/api.js` 的每支函式都是
`const { data, error } = await supabase.rpc(...)`，只處理 `error` 物件。
但**網路層失敗（離線、CORS、DNS）時 supabase-js 是直接 throw，不是回 error 物件**。
今天新增的 `enterTable` 是 `async` 事件處理器，真的 throw 的話會變成
unhandled rejection —— 畫面不會白，而是**點了完全沒反應、沒有任何提示**。

**觸發條件**：店裡 Wi-Fi 不穩。這在實體店是常態，不是邊緣情況。

**建議**：`api.js` 每支包 try/catch，網路失敗時回 `{ ok:false, reason:'網路連線失敗' }`，
讓呼叫端能 `flash()` 出來。比起加 ErrorBoundary 更根本 —— 使用者至少知道發生了什麼事。

### P3. POS 沒有版本看門狗，快取白屏無法自救

**證據**：`migi-web/vite.config.js` 有 `versionJson()` plugin，build 時產出 `version.json`，
App 開機比對版本，發現自己是舊版就自動強制重載一次。
`migi-pos/vite.config.js` 只有 9 行，沒有這個機制，`main.jsx` 也只有 0.2KB。

**觸發條件**：CDN 或瀏覽器快取住舊的 `index.html`，而它指向的 JS hash 已被新部署刪除
（本文第 4 條 v2 事故的成因）。migi-web 會自己重載復原，**POS 只能靠店員手動清快取**。

### P4. 換正式 org 時，三端寫死的 `MIGI_ORG_ID` 會一起變成隱形炸彈

**證據**：三個 repo 各自寫死同一個測試 org：

```
migi-pos/src/lib/supabase.js:18     MIGI_ORG_ID = '11111111-1111-1111-1111-111111111111'
migi-web/src/lib/supabase.js:10     （同上）
migi-admin/src/lib/supabase.js:8    （同上）
```

而「上線前必做」第 2 條要**砍掉測試 org、走正式建店流程生出新的 org**。

**為什麼特別危險**：改漏任何一端，那端傳的 `p_org_id` 就對不上，
RPC 回空陣列或空物件 —— **不會報錯**（本文第 7 條那個最難察覺的失敗模式）。
畫面看起來是「沒有資料」而不是「壞了」，很容易被當成資料還沒建。

**建議**：換 org 之前先把它改成環境變數（`VITE_MIGI_ORG_ID`），
讓三端從同一個來源取值，並在取不到時**明確拋錯**而不是靜默用預設值。

### P5. 加 `kind` / `flower` 欄位時會製造多載函式

`table_sessions` 缺這兩欄（見第八節），補上時勢必要改 `open_session_tx` 的簽名。
**依硬規則 2 必須先 `DROP FUNCTION`**，否則新舊並存。

**這次的靜默失敗特別陰險**：PostgREST 依具名參數解析，前端若還在傳舊的參數組合，
會打到舊版 → **開桌成功、不報錯，但 kind/flower 沒被寫進去**。
等於花力氣加了欄位卻永遠是 null，而且要很久才會發現。

同樣的道理適用於 `settle_session_tx` 改成 `SECURITY DEFINER` 的時候。

### P6. 配桌列表接真資料時，可能拿到空清單而不是錯誤

`list_match_queues_tx(p_org_id, p_member, p_store)` 的 `p_member` 是為會員端設計的
（查「我能加入的房」）。POS 要的是「本店所有進行中的房」。

**若 `p_member` 傳 null 時函式內部有 `where ... = p_member` 之類的條件，結果會是空陣列**，
畫面顯示「目前沒有這類配桌」—— 看起來像正常的空狀態，不像壞掉。
接之前先單獨呼叫該函式確認回傳，不要直接接上去看畫面。

### P7. `Receipt` 在還原座位時拿不到明細

今天新增的座位還原刻意把 `receipt` 設為 null（明細不在本次工作階段），
並在 `Receipt` 元件加了對應分支。**若日後有人改 `Receipt` 忘了這個分支，
還原進來的已結帳座位就會讀 `r.items` 而炸** —— 而 POS 沒有 ErrorBoundary（見 P1）。

## 九之二、UI 算得出來 ≠ 後端收得到（2026-08-15）

### 26. 前端自己算總額，但那些品項根本沒送給後端

**現象**：POS 開桌收費時加了「會員儲值 3300 點 $3000」，畫面「尚需支付 $3300」
算得好好的，按下確認結帳卻失敗。

**表面錯誤**是 `payfor_already_joined`（重複代付，後端正確擋下），
但那只是先撞到的那道牆。**就算沒有它，這筆也結不掉**：

- 首次結帳走 `join_session_tx`，而它**沒有 items 參數** ——
  只收它自己用 `calc_session_fee_tx` 算出來的檯費。
- 所以前端購物車裡的餐飲／商品／儲值**一項都沒送出去**。
- 後端算出應付 $300（檯費），前端卻送 `payments` 總額 $3300，
  `checkout_tx` 第 6 步「收款驗證：payments 總和必須剛好等於應付減點數」
  必然拋例外。

**更嚴重的是儲值**：POS 全專案**沒有任何儲值 RPC 呼叫**。
`doPay` 的 `topupCredit()` 只改 React state
（`balance: (s.balance||0) - ptUse + credit`），畫面餘額會跳，
但 `wallets.balance` 一動也沒動 —— 重新整理就變回去。
**儲值按鈕、彈窗、金額計算全部存在且看起來正常，但從來沒有真的生效過。**

**為什麼加購那條路沒事**：已入座再結帳走 `pos_addon_checkout_tx`，
那支**有**送 items，前端也會擋下 `kind='topup'` 並提示「儲值請走儲值流程」。
洞只在「首次結帳」—— 而那是最常用的路徑。

**教訓**：

- **UI 能把數字算出來，不代表那些資料有送到後端。**
  前端的合計是純顯示，它不知道後端會不會收。
- 這與硬規則 7（RPC 要實際執行看到回傳）是同一件事的另一面：
  那條講「後端沒被驗證」，這條講「**前後端的資料契約沒被驗證**」。
  兩邊各自都能跑，接起來才發現對不上。
- **檢查方式**：對每一個會改變金額的前端動作，問一句
  「這個值最後從哪支 RPC 的哪個參數進去？」答不出來就是洞。
  `topupCredit` 答不出來，因為根本沒有那支 RPC。

### 27. ★ 平行的東西不對稱 —— 2026-08-16 一天出現三次

**這不是一個 bug，是一類 bug。** 只要有兩個「本來該做同一件事」的東西
（兩支函式、兩張表、兩條路徑），而它們的能力或處理方式不一致，
那個差異就是一個等著被觸發的洞。

當天三個實例：

| # | 平行的兩者 | 不對稱在哪 | 後果 |
|---|---|---|---|
| 1 | `join_session_tx` ／ `pos_addon_checkout_tx` | 一支收 `p_items`、一支不收 | 開桌時加的餐飲商品**不會進 `orders`**，而前端 payments 含了那些金額，`checkout_tx` 收款驗證必然失敗 |
| 2 | `topup_tx` ／ `checkout_tx` | 找不到 `wallets` 時，一支自己建、一支拋例外 | **新會員完全無法結帳**，連純付現金都不行（`member <uuid> 沒有錢包`）|
| 3 | `order_payments` ／ `topup_orders` | 一張有 `cash_received`／`change_given`、一張沒有 | 消費全用點數付時，現金全歸儲值那張單，**實收與找零整個消失** |

**共同性質：都需要特定狀態才會浮現，所以躲得很久。**

- ① 要有人在開桌當下就加點餐飲 —— 測試時通常先結檯費再加購
- ② 要有「已註冊但從未儲值」的會員 —— 測試帳號通常都先儲過值
- ③ 要消費剛好被點數折光 —— 平常多少會收一點現金

②③ 尤其惡劣：**②在真實開幕當天，每一個新客人都是那個狀態。**
③則是「時有時無」——使用者會以為自己記錯了，根本不會回報。

---

#### 各自的修法與取捨

**① 加 `p_items`**（改簽名，先 `DROP FUNCTION`）。
拒收 `kind='fee'`（檯費由函式自算，重複送會重複收費）與 `kind='topup'`
（儲值寫 `topup_orders` 不是 `orders`）。

**② 用觸發器補齊，不改 `checkout_tx`**：
`members` 的 after insert → `create_wallet_for_member()`，加一次性回填。

> 為什麼不改 `checkout_tx`：「**會員一定有錢包**」該是**資料層的保證**，
> 不該由每個呼叫端各自判斷 —— 用觸發器一次涵蓋所有建立管道
> （`register_member_tx`、後台、將來的 LINE 註冊）。
> 而且 `checkout_tx` 是所有收款的唯一入口，為了補一個 null 檢查去動它，
> 風險與收益不成比例。

**③ 補欄位並定規則**：`topup_orders` 加 `cash_received`／`change_given`。
規則是「**實收找零只記在一張單上**」——實體收款是一次事件，
重複記錄會讓對帳金額翻倍：

```
orderCash > 0 → 記 order_payments
orderCash = 0 → 現金全歸儲值，記 topup_orders
```

---

#### 檢查方法

> **把平行的東西列成表對照，不一致處就是洞。**
>
> 動任何碰錢的東西之前，先問：
> 「還有誰在做同一件事？它們對相同的前置條件（有沒有錢包、有沒有入座、
> 場次開著沒、收了多少現金）反應一樣嗎？」
>
> 不一樣的話，**先確認那是刻意的設計，還是沒人發現的漂移**。
> 今天三次全部是後者。

這與硬規則 7（RPC 要實際執行看到回傳）互補：
那條防的是「**單一函式沒被驗證**」，這條防的是
「**每支各自都對，湊起來對不上**」。

### 28. 規則只遵守了一半：不直接改快取，卻拿快取當基準（2026-08-16）

**現象**：測試帳號 `測試04` 的餘額累積到 **19000 點**，
流水裡有 19 筆 `測試資料重置` 各 `+1000`。

**原本的算法**看起來完全合規：

```sql
-- 補一筆 adjust 讓餘額回到起點，不直接 UPDATE wallets.balance
p_reset_balance - coalesce(w.balance, 0) as delta
```

它確實**沒有**直接寫 `wallets.balance`（鐵則的字面要求做到了），
但它**拿 `wallets.balance` 當計算差額的基準**。

而 `測試04` 一直沒有 `wallets` 記錄（見第 27 條），
於是 `coalesce(null, 0)` → 0 → delta 永遠是 `1000 - 0 = 1000`。
跑一次加一千。

**最糟的是它看不出來**：`fix_wallet_balance_tx` 因為沒有 `wallets` 列所以什麼都沒做，
畫面顯示 0、流水卻在後面默默累積。直到錢包被建出來，
下一次重置時才終於重算 —— 19 筆一次全部浮現。

**修法**：基準改用流水加總。

```sql
p_reset_balance - coalesce((
  select sum(tx.amount) from wallet_txns tx
   where tx.member_id = m.id and tx.status = 'completed'), 0)
```

這樣即使快取失準、甚至 `wallets` 列不存在，delta 仍然算得對。

**教訓**：

> M1 碰錢鐵則第 1 條是「**餘額一律由 `wallet_txns` 流水推導，絕不直接設**」。
> 我只做到後半句（不直接設），前半句（一律由流水推導）沒做到 ——
> **而規則沒遵守的那一半，正是出事的那一半。**
>
> 「不直接改快取」和「不拿快取當真相」是兩件事。
> 只要有任何計算把快取當成輸入，那個快取就成了單一失效點。

**防線**：`sql/tools/重置測試資料.sql` 的最後一欄是健康檢查 ——
逐一比對每個測試帳號的 `wallets.balance` 是否等於流水加總，
有一個對不上就是 `false`。**每次重置都看那一欄。**
早兩天有它，就不會累積到 19 筆。

### 29. 「文件說還沒做」也不是證據 —— `applied/` 與 `docs/` 都不是線上鏡像（2026-08-16）

**現象**：我依據 `docs/01-資料庫/資料模型設計說明.md` 的
「⏳ `products` 尚未有 `kind` 欄位」直接寫了 `ALTER TABLE ... ADD COLUMN revenue_type`，
執行後才發現線上 `products.kind` 早就存在 —— **建出了兩個職責重疊的欄位。**

**查證後，那三支「pending」SQL 的真實狀態**：

| 檔案 | 檔案放在 | 文件說 | 線上實際 |
|---|---|---|---|
| `drop_leave_match_queue_overload` | `applied/` | 未跑 | **跑過了**（函式版本數 1）|
| `fix_members_tier_constraint` | `applied/` | 未跑 | **沒跑**（tier CHECK 仍 2 條打架）|
| `products加kind欄位` | `applied/` | 未跑 | **跑了一半**（欄位建了，`list_products_tx` 沒改，還在 `case category` 推導）|

三支都躺在 `applied/`，實際上兩支跑過、一支沒跑，而跑過的那支只做了一半。

**原因**：硬規則 3 原本寫的是「`sql/applied/` 不是線上現況的鏡像」。
我遵守了字面 —— 沒去翻 `applied/` 的檔案 —— 卻改成**相信 `docs/`**。
而 `docs/` 是人手維護的，漂得比 `applied/` 更兇：`applied/` 至少代表「某個版本曾經交付」，
文件裡的一句「尚未」只代表「寫這句話那天的印象」。

**推論**：判斷「線上有沒有這個東西」，只有一種證據算數 ——
**對 `information_schema` / `pg_proc` / `pg_constraint` 的查詢。**
檔案位置、文件敘述、待辦清單的勾選狀態，全部是二手傳聞。

**而且「跑過了」不等於「做完了」。**
`products加kind欄位` 建了欄位卻沒改函式，欄位躺著沒人讀 ——
DDL 成功與功能可用是兩回事（同第 7 條）。要驗的是**行為**，不是有沒有這個欄位。

**規矩**（三行查詢，成本遠低於建出重複欄位）：

```sql
-- 加欄位前
select count(*) from information_schema.columns
 where table_schema='public' and table_name='X' and column_name='Y';
-- 改函式前
select pg_get_functiondef(p.oid) from pg_proc p
  join pg_namespace n on n.oid=p.pronamespace
 where n.nspname='public' and p.proname='X' and p.prokind='f';
-- 改約束前
select conname, pg_get_constraintdef(c.oid) from pg_constraint c
  join pg_class t on t.oid=c.conrelid where t.relname='X';
```

> `pg_get_functiondef` 碰到彙總函式會拋 42809，掃全庫時要先用
> `prokind='f'` 過濾，並把過濾放在 `with ... as materialized` 裡強制先執行。

### 25. PowerShell 5.1 的 `Get-Content` 用 ANSI 讀檔，會把 UTF-8 中文讀成亂碼（2026-08-15）

**現象**：用 `Get-Content` 讀 `docs/` 下任何 .md，中文全變成
`# MIGI 暻餃???? ??鞈??嗆??箇閬?` 這種亂碼。

**原因**：專案所有 .md 都是 **UTF-8 無 BOM**，
而 Windows PowerShell 5.1 的 `Get-Content` 預設用系統 ANSI 碼頁（繁中機器上是 Big5）讀。
沒有 BOM 就偵測不到，直接照 Big5 解 → 全毀。

**代價**：2026-08-15 我用 `Get-Content` 寫了一支「掃描全 docs 有無亂碼」的腳本，
結論是「**70 個檔案全部受損**」，還一度準備請使用者回原始對話重新撈檔。
實際上一個字都沒壞 —— 壞的是我的讀法。

**關鍵區別**（實測）：

| 寫法 | 讀 UTF-8 無 BOM | 備註 |
|---|---|---|
| `Get-Content $f` | ❌ 亂碼 | 預設 ANSI |
| `Get-Content $f -Encoding UTF8` | ✅ 正確 | |
| `Select-String -Path $f -Pattern ...` | ✅ 正確 | 會自行偵測，可直接用 |
| `Get-Content $f \| Select-String ...` | ❌ 亂碼 | **管線進去就已經壞了**，Select-String 救不回來 |

**規矩**：

- 搜尋內容一律用 **`Select-String -Path`**（直接吃檔案路徑，不要用管線餵）。
- 真的需要 `Get-Content` 時**一定要加 `-Encoding UTF8`**。
- 寫檔同理：`Set-Content` / `Add-Content` 預設也是 ANSI，要寫檔請用 Write 工具，
  或明確加 `-Encoding utf8`。

**自我檢查**：任何「全部檔案都出問題」的掃描結果，先懷疑儀器再懷疑資料。
真實的損壞不會剛好 100% 命中，包括那些你剛剛才親手產生、確認正常的檔案。
