## 三、金流與計價（2026-07-12 改版）

### 現行決策

1. 所有商品售價單位為**元**（新台幣），顯示 `$100`
2. 付款方式：**純點數 / 純現金 / 點數+現金混合**
3. 1 點 = 1 元。點數從「計價單位」變成**付款方式（tender）之一**
4. **檯費 = 場地使用費，可以直接收現金**

### 為什麼改

牌桌上不能見的是**賭資現金**（輸贏籌碼），而場地使用費是正常的服務收費，收現金天經地義。
這釐清了紅線的真正邊界：**紅線是「牌桌賭資不見現金 + 點數不可兌現」，不是「店裡所有收費都不能碰現金」。**

### ⚠ 已作廢的舊規則（不要走回頭路）

- ❌「桌面不見現金，一律走點數」（cash→points first）
- ❌「所有付款先轉點數，無一例外」
- ❌「現金不足 → 提示先儲值」

### 現行金流鐵則

1. **一律會員，無例外** —— 純現金客也要建會員。
   舊鐵則真正想守的其實就是這件事（消費累積進 CRM、牌咖關係、店員業績歸因、段位掛人），
   現在直接守它，不繞點數這條路。
2. **一律入帳，現金也不例外** —— 每筆收款都要記 `order_payments`，沒有私下收現金的路徑。
3. **賭資不上桌** —— MIGI 只收場地費與商品費，不經手、不記錄、不抽成牌桌輸贏。

### 對系統的影響

`checkout_tx` 本來就是 tender 模型（應付金額 → 點數折抵 → 現金補足），**天生支援新模式**，
後端幾乎不用改。主要工作在 POS UI（付款方式選擇、實收找零）與開桌流程。

### 貨號採三段式（2026-08-07）

`類別-子類-品項`，例如 `SVC-TBL-M3`、`FNB-MEAL-DUMP`、`FNB-DRK-MILKTEA`。

真正的價值在**子類那一層** —— 同類別內需要分開看的維度（飲料 vs 餐點的毛利結構完全不同）。
有了它，`sku LIKE 'FNB-DRK-%'` 就能算飲料營收，不必另建分類對照表。

**演變過程**（避免走回頭路）：
1. 最早：貨號隨手取（`FEE-100`、純數字 `123`），與 category 對不上
2. 一度定：兩段式 `SER-001` 流水號 → **對檯費是錯的選擇**，流水號會把
   「配桌/包桌 × 將數/時段」的結構丟掉，`SER-002` 看不出是什麼
3. 定案：三段式，檯費用語意化第三段（M2/M3/MID/P02…），餐飲零售也用語意縮寫

**`SVC-TBL-MID` 為什麼獨立，不共用 `SVC-TBL-M2`**：兩者同價 100 但性質不同
（預定 2 將 vs 半路入場的低消）。共用的後果是：日後 2 將調價，中途加入被迫跟著改；
報表分不出「多少人是中途加入」—— 而那是評估配桌成桌品質的關鍵指標。

**已知代價**：字串比對會靜靜漏資料（打成 `FNB-DRINK-` 就從報表消失且不報錯）；
改貨號會改變歷史報表（`order_items` 不存 sku）。
日後若子類報表變關鍵，加 `products.subcategory` 欄位，貨號純當標籤。
頂層分類**不需要**用 LIKE —— `order_items.kind` 結帳時就存了 fee/fnb/goods，直接用更快。

### `unit_points` → `unit_price`（2026-07-12）

改元計價後欄位叫 points 名不符實，會長期誤導。趁測試階段、無真實訂單資料時一次改對。
`order_items` 原本 `unit_points`（not null 主欄）與 `unit_price`（相容欄）雙欄重複存同值，
已淘汰前者、後者轉正為 not null，`checkout_tx` 同步只寫 `unit_price`。

## 五、開桌與收費流程（2026-08-07）

| 決策 | 理由 |
|---|---|
| **收費一律委派 `checkout_tx`** | 券折抵、等級折扣、混合付款、冪等、五表寫入都已實作完整。自己重寫等於兩套邏輯並存，一旦不一致帳就出問題（草稿版重寫時完全漏掉「券」） |
| **兩步制**：開桌不收費，每來一人才收 | 對應櫃台實務 —— 麻將要等人到齊，客人是陸續報到的 |
| **收費時機：開桌即收**，不等收桌 | 佔位就付，保護成桌率 |
| **場次不設 `playing` 狀態** | 用 `activated_at` 是否有值區分「收費報到中／已開打」。不必擴充 status 約束，而 `activated_at` 本來就要記（日後接電控用） |
| **`org_id` 由桌位反查，不接受呼叫端傳入** | 函式是 SECURITY DEFINER（繞過 RLS），若信任呼叫端傳來的 org_id，任何登入者都能操作別的租戶 |
| **冪等鍵用正式欄位 + 唯一索引** | 草稿版借用 note 欄位（無約束、無索引），並發下兩個請求可能同時查不到而開出兩張桌 |
| **冪等鍵帶入座序號** | 同一人退出後再加入是新的收費事件，不能被當成重複請求 |
| **互黑檢查只警示不阻擋** | 系統處理標準，人處理例外 —— 店員保有最終裁量權 |
| **不用 `exception when others`** | 會連程式 bug 一起吞掉，除錯極痛苦 |

**開桌方式**：櫃台報到 + 雙軌開桌（滿四自動／店員手動例外）。
身分雙軌：LIFF 掃會員碼／報手機／店員代開（`line_user_id` 留空）。
識別用 **LIFF 掃會員碼**，不做實體卡、不做人臉。
員工後台採**購物車式開桌**：選空桌 → 連續掃會員進明細 → 選積分級距 → 合計 → 一鍵開桌結帳；
餘額不足擋下。

**收桌觸發三項更新**：消費累積 / 段位 Elo / 店員業績。（`settle_session_tx` 尚未實作）

**代付**：檯費份數 = 自己 1 份 + 代付人數。被代付者仍建立 `session_players` 記錄，
但 `charged_points = 0`、`paid_by = 付款人`。消費金額與發票都歸付款人 —— 誰出錢，帳就是誰的。

## 六、配桌、牌咖、黑名單（MA1-C）

### 配桌

- **成桌時間錨點 = `play_at`**（開房者指定的預定開打時間），不是「開房後 N 小時過期」
  - waiting 到 `play_at` 仍未滿員 → `expired`
  - **已成桌永不自動解散**；沒到的人由店員手動標 `no_show`
  - 理由：每個會員到店路程不同，用固定倒數對住遠的人不公平；「兩點半開打」是所有人共同的錨
- **房主退房 → 轉移給次早加入者**，不解散（對其他等待者公平）。房內剩 0 人才 `cancelled`
- **併發控制**：`join_match_queue_tx` 用 `SELECT ... FOR UPDATE` 鎖房，處理「兩人搶最後一位」
- **即時更新過渡方案**：先用 5 秒輪詢；等 LINE 真登入（authenticated）後再換 Supabase Realtime。
  理由：Realtime 走 RLS，而現階段 anon 被全擋
- **配桌等待層與計費桌分離**：App 的 `match_queues`（還沒入座）
  vs POS 的 `table_sessions`（已入座計費），用 `matched_session_id` 銜接

### 牌咖

- **邀請制**：單向發起 → 對方確認才成立（不是「互相加碰巧配對」）
- **拒絕無痕**：拒絕方跳 toast，發起方**完全收不到任何通知**
- **接受後**寫 `mahjong_buddies` 兩筆互指，並回通知給邀請方
- **不加防騷擾冷卻期**（被拒後可再邀）—— 已拍板不做
- **解除牌咖**：靜默雙向軟刪，對方不通知

### 黑名單

- **單向紀錄、雙向生效**：A 黑 B → 兩人互相看不到對方的房、互相進不去。
  只擋單向會讓 B 照樣加入 A 的房，形同虛設
- **訊息模糊化**：被擋一律顯示「此桌已無法加入」「無法邀請此牌咖」，與桌滿／解散同語氣，
  **永不洩漏黑名單存在**。理由：MIGI 是實體店，客人見得到面，資訊洩漏會在店裡引爆衝突
- **黑掉牌咖 → 自動解除牌咖關係** + 作廢未回覆邀請 + 清理相關通知

### 八之一、為什麼總部走 Email 而不是全部收斂到 LINE
（2026-08-29 補記。使用者提出「總部員工也用 LINE 會員登入，
用 SQL 設定第一個管理員，再由他升級其他人」，這一節記錄那次討論。）

#### 現況（查證過，不是推測）
```
staff       role=hq   auth_uid=2485579b-…   member_id=null
auth.users  1 個帳號：admin@migi.tw（2026-07-12 建立並登入過）
current_staff()  LEFT JOIN + 兩條 OR：
                 s.auth_uid = auth.uid()                  ← 總部 Email
              or m.line_user_id = (auth.jwt() ->> 'sub')  ← 店員／會員 LINE
```
✅ **兩條路都是通的**，`member_id = null` 是 Email 路徑應有的狀態，不是 bug。

#### 🔴 更正：原本寫的第一個理由是錯的
本節原本的理由之一是「**總部員工不是會員**」。**那個理由不成立**：

- 麻將館的店員**本來就很可能是常客** —— 他懂規則、認識人，那是優點不是問題
- 系統早就假設了這件事：`session_players.fee_waived_reason` 的已知值包含
  `'staff'`（店員身分，內部使用不進營收）—— 那個值的存在，
  就是在說「**店員會坐上牌桌，而且他是個會員**」
- 「客人 → 員工」的正式路徑就是 `grant_staff_tx(p_member_id, …)`，
  而它吃的是 **`member_id`**，本來就是為 LINE 路徑設計的

⚠ 一度以為的副作用（總部員工會出現在配桌名單、牌咖搜尋）也是錯的：
  配桌名單是**有報名的人**，不報名不會出現；被搜尋到則本來就正常。
  **唯一真的影響是「會員數統計」會含自己人** —— 那是報表層的小問題，
  不是身分層的理由。

#### ✅ 真正的理由只有兩個，而且都跟「員工是不是會員」無關
**① 🔴 LINE 掛了要有後路。**
全部收斂到 LINE 之後，LINE 服務中斷／Provider 出狀況／帳號被停，
就**沒有任何路徑能進後台查資料、對帳、處理問題**。
Email 那條是備援，而備援的價值就在它跟主路徑不共用故障點。

**② 🔴 消費者帳號的安全模型撐不起管理者權限。**
| | Email | LINE |
|---|---|---|
| 密碼 | 可設專用強密碼 | 是本人日常在用的 |
| 第二因素 | 可開 | **我們刻意關掉了**（客人多半沒設過 LINE 密碼，開了會卡死註冊） |
| 借用風險 | 低 | 換手機沒登出、家人共用都可能 |

客人用 LINE 沒問題（他最多看到自己的錢包）；
**`owner` 用 LINE 就不一樣 —— 那個帳號看得到全部會員的手機、消費、餘額。**

#### 📌 世界級對照：員工身分不走消費者帳號
| 公司 | 客人 | 員工／後台 |
|---|---|---|
| Shopify | Shop account / Email | Shopify ID（獨立，SSO ＋強制 2FA） |
| Square | 不需要帳號 | Square 帳號 ＋ **店員 PIN** |
| Starbucks | Rewards 帳號 | 內部 SSO |
| 全家／麥當勞 | App 帳號 | 工號 ＋ 排班系統 |

🎯 **所以現行架構（總部 Email ＋ 會員/店員 LINE）本來就是世界級的形狀**，
只是原本寫的理由是錯的。正確的理由是上面那兩條。

#### ⏳ 一個還沒做、但世界級都這樣做的東西：店員 PIN 切換
Square / Toast / Lightspeed 一律是「**裝置登入一次 → 個別店員用 PIN 快速切換**」。
理由很實際：一個班會交班、會有人代班，**要求每次都走完整登入是不可行的**。

→ 所以「店員用 LINE 登入」**可能不是最終形態** ——
  LINE 登入用來綁定裝置與確認身分**一次**，日常操作靠 PIN。
⚠ 但依硬規則 5.5：現在只有 1 個 staff、0 個店員登入，**做 PIN 是為不存在的問題蓋東西**。
  等真的有兩個以上店員在交班再說。

#### 結論：混合，不是二選一
| 身分 | 認證 |
|---|---|
| 會員 | LINE |
| 店員（POS） | LINE（`grant_staff_tx` 本來就這樣設計） |
| **總部／owner** | **Email**（備援 ＋ 專用強密碼與 2FA） |

⚠ **不要把總部那筆 staff 的 `member_id` 綁到創辦人的會員上。**
  要讓創辦人也能用 LINE 登入 POS 的話，正解是**另開一列 staff**
  （`member_id = 他的會員`、`auth_uid = null`、`role = 'owner'`），
  兩個唯一索引都不會衝突（Postgres 視多個 NULL 為相異）。
  🔴 那是授予最高權限的動作，等真的要用 POS 時再做。

## 十八、高雄自由店的性質（2026-08-15 裁決）

**背景**：兩份文件互相矛盾。

- `sql/applied/門市真實資料.sql` 寫著高雄自由店是「**第一家真門市**」，
  id 維持 seed 的 `22222222-…` 不換隨機 UUID —— 理由是已有 9 張表以
  `on delete restrict` 綁著它，換 id 要做搬遷手術、風險高
- 本文第十六節「上線前必做」#2 寫著要**砍掉測試 org（`11111111-…`）**、

**裁決：採用「砍掉測試 org」那條。**

→ `門市真實資料.sql` 的「第一家真門市」說法**作廢**，該檔僅保留為歷史紀錄。

**但它繼續當測試店用，資料照常累積**：
`list_stores_tx` 不看 `is_test`（2026-08-15 以 `pg_get_functiondef` 查證），
所以標成測試之後門市選單照常出現、14 張桌照常可用，

修正 SQL：`sql/pending/2026-08-15_高雄自由店標記為測試.sql`

**這件事的教訓**：`is_test` 由觸發器依**門市**帶入，不是依會員。

## 十九、當日暢打的規則（2026-08-17 拍板）

`SVC-TBL-DAY` 300 元，賣的是「今天在這間店打牌不再收場地費」。

| 項目 | 決定 |
|---|---|
| 有效期間 | **當天 23:59:59 前免費，隔天 00:00:00 開始收費** |
| 涵蓋範圍 | **配桌與包桌都免** |
| 販售位置 | 結帳頁的「**檯費**」分頁 |

### 為什麼包桌也免

原本 `calc_session_fee_tx` 的註解寫「暢打不影響包桌（那是場地費）」——
但 2026-08-17 包桌改成單人計價之後，兩者都是按人頭收的場地費，
那個理由不再成立。暢打買的就是「今天的場地費」，不該因為模式不同而分裂。

→ 實作上要把暢打判斷**移到模式分支之前**，目前它寫在配桌那個 else 裡。

### 時區是這條規則的風險點

「當天」必須是**台灣時間**。若 `has_daypass_tx` 用 UTC，
台灣時間 00:00–08:00 會被算成前一天 ——
客人早上七點來，會發現昨天買的暢打還有效、或今天買的還沒生效。
**這種錯每天只發生 8 小時，最難抓**，實作前必須先確認現行判準。

### 為什麼不是「不限將數」而是「當日」

兩種寫法在單一場次裡結果一樣，但跨場次不同：
「不限將數」聽起來像綁在一桌，客人打完換桌就會來問還算不算。
「當日」是時間邊界，說得清楚也查得明白（只要看今天有沒有那筆訂單）。

## 二十、會員等級折扣只折檯費（2026-08-17 拍板並上線）

《會員分級制度規格》寫的是「**桌時費** 95 折 / **桌時費** 9 折」，
但 `checkout_tx` 從一開始就拿 `(v_sub - v_coupon_cut)` 當基數，整張單都折了。
實測：測試01（提拉米蘇 9 折）檯費 150 + 水餃 80 → 折 −$23，照規格應為 −$15。

**規格是對的，實作走偏了。**

### 為什麼規格是對的

| 類型 | 邊際成本 | 打折的實質 |
|---|---|---|
| 檯費（場地／時段）| 趨近於零 | 空著也是空著，折扣換來使用率幾乎純賺 |
| 餐飲、商品 | 食材／進貨成本 30–40% | 每折一次都是真的少賺 |

毛利 40% 的餐飲品項打 9 折，**毛利直接掉四分之一**；檯費打 9 折幾乎不痛。
業界（星巴克回饋是兌換免費品項、超商會員只折特定品項、旅館 elite 折房價不折餐飲）
一律是「**折扣給產能，不給存貨**」。

### 已知後果：會員加購餐飲從此零折扣

改之前，提拉米蘇會員單買 $80 水餃會折 $8；改之後折 $0。
加購是每桌都會發生的動作，不是偶發，**客人感受得到**。

**仍決定照規格**，理由：

- 規格對餐飲的權益本來就不是折扣，而是「生日招待飲品」「商城限定品購買權」——
  一年一次的招待成本可控，感受卻比長年 98 折強
- 現在還沒有真客人習慣舊的折法，**這是改動代價最低的時刻**
- 要補償餐飲感受，用非價格權益補，不要把折扣攤回存貨

### 實作

`checkout_tx` 裡已經有現成的 `rem_fee`（券折抵後剩下的檯費，券的分桶邏輯一路維護著它），
基數換成它即可，不需另外重算。沒有券時 `rem_fee = v_fee`。
`v_tier_cut <= rem_fee`，比舊版更不可能算出負的應付。

## 二十一、店員登入與 PIN（2026-08-29 討論，結論：先不做 PIN）

### 🔴 世界級的 PIN，安全性不來自 PIN

```
裝置授權（一次，要用完整帳號登入）
   ↓
PIN 只在「已授權的那台裝置」上有效
```

**PIN 回答的是「現在站在這台機器前面的是誰」，
不是「這個人有沒有權限存取系統」。**

所以 4 位數字就夠 —— 攻擊者**必須實體站在店裡那台平板前**，
同一組 PIN 在網路上其他任何地方都沒有用。

🔴 **反過來說：沒有裝置綁定的 PIN 就只是一組 4 位數密碼**
（一萬種組合，暴力破解幾秒鐘）。那是這個機制最常見的誤用。

### 驗證機制（Square / Toast 的必備項，日後真要做時照這張表）
| | |
|---|---|
| PIN 存 hash 不存明文 | `pgcrypto` 的 `crypt()` + bcrypt（✅ pgcrypto 1.3 已安裝） |
| 連續錯 N 次鎖定 | 否則四位數幾秒就試完 |
| 同門市內不可重複 | 兩人同碼，系統就分不出誰是誰 |
| 每個操作寫 `staff_id` | 稽核 |
| 🔴 **後台不能用 PIN** | Square 後台一定要完整帳號 ＋ 2FA |

### 現況（2026-08-29 查證）
```
PIN／密碼／裝置相關欄位   🔴 完全沒有
裝置／終端機的表          🔴 完全沒有
staff 表                 沒有預留 pin 欄位
pgcrypto                 ✅ 1.3 已安裝
🔴 updated_by            table_sessions 0/99　orders 0/153 —— 全部是 null
```

### 🎯 結論：先做 LINE 登入 ＋ 裝置記住，不做 PIN
🔴 **真正痛的不是「切換太慢」，是「根本不知道是誰做的」**
（`updated_by` 全 null）。而依硬規則 5.6，**稽核欄位是不可回溯的** ——
今天不填，這段歷史就永遠沒有。

⚠ 但 PIN 是為「**一小時切換十次**」的餐飲業設計的。
麻將館一天 2 班的話，**LINE 登入兩次完全可以接受**。

✅ **而且先做 LINE 登入完全不會浪費** ——
世界級的 PIN 方案裡，「裝置授權」那一層本來就要用完整帳號登入，
**LINE 登入就是那一層**。PIN 是加在它上面的加速器，不是替代品。
→ 等「交班摩擦真的痛了」再加 PIN，那時地基已經在了。

### 「總部直接生成店員帳號」現在就做得到
```
店員先用 LINE 註冊成會員
  → 總部按一個按鈕：grant_staff_tx(member_id, store_id, role)
  → 他就能用 LINE 登入 POS
```
✅ 後端已存在，只差後台畫面。
⚠ 但**沒辦法憑空生成一個「沒有 LINE 的店員」走 LINE 路徑** ——
  身分要靠 `line_user_id`。那種帳號只能走 Email 路徑（就像總部那個）。

## 二十二、頭像照片：只保留一張，不做相簿（2026-08-29）

### 現況（查證，不是推測）
```
storage.buckets
  member-avatars   private   3MB   jpeg/png/webp
  store-photos     public    5MB   jpeg/png/webp

storage.objects   只有 1 個檔案
  member-avatars／d73fdac2-…/1785777818508.webp   274KB   08-03 17:23

members.avatar_photo_path  **單一 text 欄位** → 一個會員只能有一張
```
⚠ 那個檔案**不是孤兒檔**（`avatar_photo_path` 指向它），
  但 `avatar_source = 'bear'` —— **上傳了卻沒有套用**。

### 🔴 刪除的順序不能反
**先清資料庫的指標 → 再刪 Storage 的檔案。**
反了的話會留下「指向不存在檔案」的路徑，
畫面顯示破圖或空白**而且不會報錯** —— 同硬規則 3.85 那一類。

### 為什麼不做「我的照片庫」
| App | 做法 |
|---|---|
| LINE／Instagram／Discord | **只有一張當前頭像**，換了舊的就沒了 |
| Facebook | 有「大頭貼相簿」🔴 **但那是社交功能**（可按讚、留言），不是頭像管理 |

🎯 **「照片庫」不是頭像功能，是相簿功能。**

而多張的真正成本**不是儲存，是審核**。系統裡已經有一整套 moderation：
```
avatar_blocked / avatar_removed_count / admin_remove_avatar_tx(member, reason, block)
```
🔴 允許多張 ＝ 要審的東西變多倍，而依硬規則 5.5，**那個審的人現在不存在**。

### 結論
做「**移除我的照片**」一個動作，不做相簿：
1. **後端** `remove_my_avatar_photo_tx`：清 `avatar_photo_path`、
   若 `avatar_source = 'photo'` 就切回 `'bear'`、**再刪 Storage 的檔案**
2. **前端** `AvatarPickerSheet` 的「我的照片」那張卡加一個叉叉

⏳ **尚未實作**，也尚未拍板兩件事：
   ① 真的只要「移除當前」還是仍想要多張可切換
   ② 那張 08-03 的既有照片要不要現在就清掉

#### 🔴 為什麼推翻「包桌不計」
原規格只有一句「包桌不計」，**整個專案裡沒有寫任何理由**，
而且與《整合系統開發藍圖》:250「收桌觸發三項更新（…牌局成績段位…）」矛盾。

**而包桌佔麻將館生意的五成。**
→ 排除它等於**一半的客人段位永遠不動**，而且他們**看得到**那個系統
  （App 裡就有）→ 他們會以為壞掉，或覺得被排除。
⚠ 更嚴重的是：包桌客人很可能是**最好的客人**（買斷整桌、消費高、揪團穩定）。

**當初排除的合理猜測是「防熟人互刷」，但那個風險被高估：**
| | 評估 |
|---|---|
| 惡意作弊 | 三個朋友陪打幾十場故意輸，換一隻小熊頭像 —— **成本極高、報酬極低** |
| 🔴 取樣偏誤 | 四個實力差很多的朋友固定一起打 → 最強的永遠第一 → 段位虛高。**一定會發生，不是任何人的錯** |

→ 取樣偏誤留給 **M5 影像辨識與日後的 Elo** 解決（原規格本來就寫了「之後進化 Elo」）。
→ 而「大師的對手多樣性門檻」剛好把界線畫在對的地方：
  **固定四人包桌可以爬到鑽石 IV（第 20/24 階），大師才要求面對過不特定對手。**
  那句話很好講：「**大師熊要跟很多不同的人打過。**」

```

**兩件事一起改：起點從 1000 變 0，而且第一場一定會升級。**

| | 舊 | 新 |
|---|---|---|
| 起始分數 | 1000（銅牌熊 II） | **0（銅牌熊 IV）** |
| 銅牌熊第一小階 | 45 分 | **10 分** |
| 其餘小階 | 45 | 45（不變） |
| 順位點（低中高） | +30/+15/0/−20 等 | **完全不變** |
| 第一場 | 沒有特例 | 🎓 **定位賽 +30/+15/+10/+5** |

```
銅牌熊    0 ·  10 ·  55 · 100      ← 間距 10 / 45 / 45，大階寬 145
銀牌熊  145 · 190 · 235 · 280
金牌熊  325 · 370 · 415 · 460
白金熊  505 · 550 · 595 · 640
鑽石熊  685 · 730 · 775 · 820
大師熊  865 以上（另有對手多樣性條件）
```

#### 🎯 為什麼

- **0 分比 1000 分好懂** —— 沒有人需要解釋「為什麼我一開始有 1000 分」。
- **定位賽第 4 名也 +5**，最少 2 將 ⇒ **剛好 10 分 ⇒ 一定升到銅牌熊 III**。
  第一次玩的人拿到的不是一個數字，是**一個看得見的升級**。

#### 🔴 10 分是踩線，零餘裕

```
定位賽第 4 名 +5  ×  最少 2 將（未滿 2 將不計）  =  剛好 10 分
```
⚠ **這個門檻改成 11 就失效，而且不會有任何錯誤** ——
只是新客人第一場打完什麼都沒發生。
→ 驗證段因此**真的跑一次最少的 2 將**，不是只比對數字。

#### ⚠ 定位賽只有一次，不是保護傘

第二場開始回到低段 `+30/+15/0/−20`，**第 4 名會扣 20**。
判準是「**有沒有結算過的場次**」，**不是 `rating_games = 0`** ——
後者每季歸零（會變成每季送一次），而且逐將遞增
（2 將制下第 2 將就不算了，承諾只兌現一半）。

#### 期望值與天數（平均實力 · 一週一次）

| | 每將 | 說明 |
|---|---|---|
| 🎓 定位賽 | **+15** | 只有第一場 |
| 銅 · 銀 · 金 | **+6.25** | 正和，來就會上 |
| 白金 · 鑽石 | **0** | 零和，要贏才會上 |
| 大師 | **−6.25** | 負和 |

| 到這裡 | 分數 | 2 將/場 | 3 將/場 |
|---|---|---|---|
| 銅牌熊 III | 10 | **第 1 場** 🎓 | **第 1 場** 🎓 |
| 銀牌熊 IV | 145 | 11 週 | 7 週 |
| 金牌熊 IV | 325 | 25 週 ≈ 6 個月 | 16 週 ≈ 4 個月 |
| 白金熊 IV | 505 | 39 週 ≈ 9 個月 | 26 週 ≈ 6 個月 |

一季（26 場）結束時：2 將/場 → **金牌熊 IV**；3 將/場 → **白金熊 IV**。
降 2 大階後分別落在 銅牌熊 III 與 銀牌熊 IV。

🔴 **白金 → 大師要 360 分，而中段是零和 ⇒ 平均實力的人永遠到不了。**
| 第 1 名的比例 | 每將 | 場數（2 將） |
|---|---|---|
| 平均 25% | 0 | 🔴 永遠不會 |
| **明顯強 35%** | +7 | **26 場 ＝ 剛好一季** |
| 很強 40% | +10 | 18 場 |

🎯 **「明顯強的人剛好一季能拿到大師」—— 難度卡在對的地方。**

#### 🔴 這一改連帶動到三個原本「算出來」的東西

1. **小階門檻不能再用「區間平均切四段」** —— 銅牌 145÷4=36，
   會算成 0/36/72/108。→ 新增 `rank_sub_levels`，門檻變成**資料**。
   ⚠ 存**位移**不存絕對值 ⇒ `rank_tiers.min_rating` 仍是唯一真相。
   🎯 **收益當天就兌現**：銅牌 III 從 5 調成 10 時，**一支函式都不用動**。
2. **`rank_tiers.sub_count` 從此沒人讀** → 移除（留著還會誤導）。
3. **「降 2 大階」不能寫死 360** —— 那能成立是因為六個大階以前都 180 寬，
   現在銅牌是 145。→ 改成「目前大階的 min − 往下 N 階的 min」。

#### ⚠ 現在改是零成本，之後不是

```
會員 5 人 · 有段位的 0 人 · 有名次的 session_players 0 列
```
**一場計分的牌局都還沒發生過**，所以全部重設為 0 不需要換算任何歷史。
🔴 電子計分上線後就沒有這個機會了。

## 二十四、電子計分：把 L0 從「店員記錄」改成「客人的工具」（2026-08-29）

⚠ **先讀《牌譜成績資料中台技術設計》** —— 這一節是對它的**修正**，不是新發明。
🔴 我一開始沒讀就開始設計資料表與規則，那份文件早就把 schema 與多數規則定好了。

### 文件裡早就有的（不要重新設計）
```sql
games          一將（含 ruleset）
game_players   game_id, seat, member_id, final_rank, final_score
hands          🎯 這就是「每一把」
  round_wind E/S/W/N ｜ hand_no ｜ renzhuang 連莊數 ｜ dealer_seat
  result ∈ tsumo(自摸)/ron(放槍)/draw(流局)/abort(中止)
  winner_seat ｜ deal_in_seat(自摸與流局為 null) ｜ score_delta jsonb
```
⚠ 在 `sql/_設計稿未落地/牌譜資料庫schema.sql`，**沒跑過**。

| 規則 | 文件的答案 |
|---|---|
| 連莊 | ✅ **連 N 拉 N**（`hands.renzhuang` 的註解） |
| 花牌 | ✅ **主場（高雄）＝ 南部台／無花／136 張** → 花不計台 |
| 底／台／各牌型台數／花牌 | ✅ **參數化存 ruleset 設定檔，不寫死**（為了南店無花、北店有花、加盟可自訂） |
| L0 的定義 | 局結果（誰胡／放槍／台數）+ 將結算，**第一階段全桌** |

### 🔴 這一節修正的：L0 的執行者
```
文件：L0 =「店員快速輸入」
改成：🎯 客人用電子計分**取代籌碼**
```

| | 店員輸入（原規格） | 客人電子計分（本次） |
|---|---|---|
| 動機 | 🔴 **多做一件事** —— 硬規則 5.5 的「那個人存在嗎」 | ✅ **他本來就要算分** |
| 完整度 | 忘記就沒有 | ✅ **不用就沒得算錢** |
| 誰受惠 | 系統 | ✅ **客人自己**（省去數籌碼、找零） |

🎯 **這解決了段位系統最根本的問題**（見第二十三節）：
> MIGI 是檯費制不抽水，所以系統裡**沒有任何時刻會因為營運需要而必須知道誰贏了**。
> 日本雀莊記得成，是因為客人本來就要算點結帳 —— **MIGI 沒有那個副產品**。

**電子計分把那個副產品造出來了。** 原規格把 L0 當成「為了拿資料而叫店員做的事」，
本次把它變成「客人本來就需要的工具，順便產生資料」。

### 🔴 為什麼一定是「每把」，不能是「一將記一次」
我一度提「一將結束記四家總分」以降低輸入負擔（3 次 vs 48 次）。**那從根本上不成立**：

**籌碼是每一把移動的。** 打完一將，籌碼堆在那裡，**沒有人會把它結算成一個總分** ——
要記「一將的四家總分」，客人得**數籌碼**，那比每把點三下還麻煩。

✅ **電子計分不是「記錄結果」，是「取代籌碼」。籌碼每把動，所以計分必須每把。**

⚠ 我也一度說「每把輸入會拖慢節奏」——**那也講反了**：
| | 現在 | 電子 |
|---|---|---|
| 胡牌後 | 算台 → 三家各付籌碼 → 有時找零 | **點三下** |

### 每把的輸入（三下）
```
① 胡牌 / 流局
② 誰胡
③ 幾台 ＋ 自摸 or 誰放槍
```
**莊家與連莊由系統自己追蹤** —— 客人不用輸入。

### 純娛樂局：用 **30/10** 算分
🔴 `stake_levels` 的「純娛樂」是 `base=0, tai=0` → 每把算出來都是 0
  → 四家分數都是 0 → **排不出名次 → 沒有段位**。

**✅ 決定：純娛樂在計分時套用 30/10。** 只為了排名次，不涉及任何金錢。

⚠ 一度考慮「用胡牌次數排名」，**較差**：
  胡三個小牌 vs 胡一個大牌 → 次數排名會判錯，而底台算分正確反映台數。

📌 **底台確實會影響名次**（不是等比例縮放）：
```
底 30 台 10 ：胡 3 台 = 60 ｜ 胡 5 台 = 80   → 3:4
底 100 台 20：胡 3 台 = 160｜ 胡 5 台 = 200  → 4:5
```
底大台小 → 小牌相對划算。30/10 是**台重底輕**的一組，較獎勵大牌，對純娛樂局合理。

**實作不要寫死**：`stake_levels` 加 `score_base` / `score_tai`（可為 null，
null 就用 `base`/`tai`），純娛樂那筆填 30/10。
🎯 那樣「純娛樂用哪組底台算」是**資料不是程式碼**，日後要改只改一列。

### ⏳ 還要拍板的：ruleset 設定檔的內容
南部台 16 張無花，剩下這幾個數字要問店裡實際怎麼打：
- 自摸：三家各付多少？
- 放槍：放槍者一家付全部？
- 莊家胡／被胡：要不要加倍？
- 連莊加台：連 N 拉 N 是「每連一把加 N 台」還是「加 1 台 × N」？

🔴 **這幾個寫錯，客人第一天就會發現。**

### ⚠ 這是一個真的功能，不是小改動
| | |
|---|---|
| 後端 | `games` / `game_players` / `hands` 三張表 ＋ 算錢函式 ＋ 莊家狀態機 ＋ 將結算 |
| 前端 | 一整頁計分介面（**單手好按、不能誤觸**） |
| 前置 | ruleset 設定檔的內容 |

🔴 **而它必須在開店前上線** —— 否則那段時間的牌局沒有資料，
  段位系統就要一直等到 M5。

## 二十五、名詞：段位的分數叫「段位分」，牌桌的叫「積分」（2026-09-03 拍板）

### 問題：同一個詞在客人眼前有兩個意思

```
牌桌的      50/20、10/10 · 「想打多少積分」·「積分：50/20」·「本局積分」
段位的      「本季積分 180 分」·「總積分 48,200」·「積分到了就會升新段位」
```

客人分不出「本季積分 180」跟「積分 50/20」是不是同一件事 ——
而它們**完全無關**：一個是 `members.rating`，一個是 `stake_levels`。

### 決定

| 概念 | 中文 | 資料層 |
|---|---|---|
| **牌桌的分數／級距** | **積分**（不動） | `stake_levels` · `table_sessions.stake_level_id` |
| **決定段位的分數** | **段位分** | `members.rating` · `session_players.rating_after` |
| 錢包 | **點數**（本來就分得開） | `wallets.balance` |

🎯 **為什麼選「段位分」而不是「熊分」「戰力」「評分」**：
**它不需要被解釋**。畫面上到處都是「段位」，四個字自己就說完了
「這是決定段位的那個分數」。其他候選都要先學一次對應關係。
· ❌ 點數 —— 撞錢包
· ❌ 評分 —— 像在評價店家
· ❌ RP —— 客群有長輩
· 🟡 熊分 —— 品牌一致、好記，但第一次看到要猜
· 🟡 戰力 —— 一看就懂「多強」，但聽起來像固定值，而這個分數會掉

⚠ **後面不加「分」**：「本季段位分 180 分」是同一個字講兩次。

### 🔴 順帶修掉一個講反的標籤
排行榜與名人堂原本寫「**總積分**」—— 它排的是 `members.rating`，
而 rating **每季歸零、會上下**。「總」字說的是累積，**語意完全相反**。
→ 改成「段位分」。

### 只改中文，不改資料層
`rating` / `rating_after` / `rank_points` 這些名字**是對的** ——
英文沒有這個歧義。歧義只發生在中文，所以只改客人看得到的字。

⚠ **唯一該改的資料層名字是 `session_players.score_points`** ——
它叫 score 但裝的是段位分（`apply_session_rounds_tx` 把 `rank_points`
累加寫進去）。**那是資料層版本的同一個病**，M4 做電子計分時一起處理：
真正的桌上分數另開欄位，或把這一欄正名成 `rating_delta`。
🔴 **在那之前不要讓任何新功能讀它** —— 2026-09-03 就是讀了它才建出
一個「其實是連對率」的勝率。

### 改了哪些地方（2026-09-03 全部完成）
`migi-web/src/pages/stats.jsx`：Hero「本季段位分」、段位怎麼算的大標
「段位與分數」、怎麼算分的四張小卡、排行榜與名人堂的「段位分」×3、
「段位分到了就會升新段位」。
📌 **`各積分級距勝率` 維持不動** —— 那個「積分」指的是牌桌的級距，是對的。
