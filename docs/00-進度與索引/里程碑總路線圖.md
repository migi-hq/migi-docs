## M1 — 錢包金流核心 ✅ LIVE（24 項測試通過）

- `wallets` / `wallet_txns`（append-only，觸發器擋改擋刪）。
  **餘額只由流水推導**，`wallets.balance` 是快取。
- RPC（`00d_M1_錢包金流RPC.sql`）：`_charge_core` / `wallet_topup_tx` /
  `charge_fnb_tx` / `reverse_txn_tx` / `settle_session_tx` /
  ~~`charge_matched_tx`~~ / ~~`charge_private_tx`~~（後兩者**已封存**，見下）。
- 讀取用 `00e_M1_錢包讀取函式.sql`。
- **已驗證**：配桌 150／中途加入 100、包桌階梯、餘額一致性、冪等防重複、
  餘額不足擋下、雙重獎金、沖正不改舊帳。

### 碰錢五條鐵則

1. **餘額一律從流水來** —— 絕不 `update wallets set balance=...`，一定透過 RPC。
   （手動插流水後要呼叫 `fix_wallet_balance_tx` 重算。）
2. **改錢只走 RPC**（`SECURITY DEFINER`），前端不直接寫 `wallets` / `wallet_txns`。
3. **退款用 `reverse_txn_tx`** —— 不改不刪原交易，新增反向分錄。
4. **每筆帶 `idempotency_key`** —— 網路重試不重複扣。
5. ~~**金額查 `pricing_tiers`**~~ → **已作廢**。該表現為空表且無函式引用；
   檯費改由 `products` 的 `SVC-TBL-*` 貨號管理，`calc_session_fee_tx` 負責推算。

### 已封存的舊收費函式

`charge_matched_tx` / `charge_private_tx` —— v1.0 純點數扣款，
不支援現金與混合付款，且查空的 `pricing_tiers` 必報錯。
封存方式：`REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated`（本體保留供稽核）。
改用 `join_session_tx`。

# 階段 2：自動化（M2 + M4）

## M2 — 桌台 + 配桌引擎 🔨 開發中（最高優先）

**這是護城河核心。**

### 已完成

- **開桌核心 RPC**（2026-08-07）：`open_session_tx` / `calc_session_fee_tx` /
  `join_session_tx`（委派 `checkout_tx`）/ `activate_session_tx` /
  `get_session_tx` / `check_session_blocks_tx`。
- **POS 開收桌全流程**（2026-08-15，實機驗證通過）：開桌設定、座位還原、
  桌帳流水、加購（`pos_addon_checkout_tx`）、帶桌、牌規落地、
  代付、空桌自動回收、`ErrorBoundary` 與版本看門狗。
- **收費方式**：**元計價 + 混合付款**（純點數／純現金／點數+現金），
  **非**舊版的「開桌即扣點數」。詳見《開桌結帳流程規格 v2.0》。

### 未完成

- **`settle_session_tx` 仍是空殼** —— 收桌結算整條不存在：尾款、包桌超時補收、
  發票、消費累積、店員業績歸因全無。**目前最大的洞**（`CLAUDE.md` 待辦 3）。
- **配桌撮合引擎**：
  - 硬約束：黑名單雙向迴避、四人時間窗交集 ≥ 預估時長、有空桌。
    （「點數足夠」已不適用 —— 現在可用現金付款。）
  - 軟評分：段位接近、固定咖優先、等越久優先、時間窗快關加權、回流會員加權。
  - 替補機制：有人到點離開即時候補補位，牌局不中斷
    （**桌的壽命 vs 個人打多久解耦**）。
  - 第一階段先做「店員手動配桌看板」，引擎自動化緊接其後（表先建、流程先跑）。
- **Realtime 即時推播**：湊滿即時跳成桌卡（Supabase Realtime ~1s）；
  app 關閉時走 LINE Messaging API 背景推播。**需先完成 LINE 登入與權限收斂**。
- **超時提醒**：包桌結束前 10 分鐘通知店員。
- 子網域：`pos.migi.tw`（店員）、`table.migi.tw`（平板）。

### M2 需一併處理的 App 端配合需求

1. 開桌選人時，名單含**互黑會員跳警示**並建議分桌。
2. 店員可對**未滿房強制成桌 + 代打補位**；`play_at` 可由店員／房主修改並通知全員。
3. **代打局的店員成績，M4 結算時排除。**
4. **被人工介入的桌，M3 分析「自然成桌速度」時排除。**

## M3 — CRM + 行銷自動化 + 店員獎金 ⏳（需 M2）

- **CRM 經營**：`member_tags`（分群）、`member_interactions`（關懷紀錄）、
  RFM／生命週期自動計算、流失預警。
  > `member_tags` 表目前**不存在**（2026-08-15 查證）。
- **行銷自動化 MA**：觸發式旅程（入會歡迎／7 天未回訪／常客流失／生日／點數到期），
  加 MIGI 獨有召回鉤子「**牌咖上線／開局**」「**段位快升級**」（比折扣更黏）。
  MA × 店員 CRM 同系統分工：共用 `member_interactions`，
  MA 發了沒反應自動升級指派給主責店員。技術 = Supabase 排程 + LINE Messaging API。
- **店員業務獎金**（欄位 M0 已預埋：`promoted_by_staff_id` /
  `members.primary_staff_id` / `bonus_rules`）：
  - **雙重歸因、雙重獎金，兩店員可同時各拿**：
    配桌獎金 **50 元/桌**（歸促成店員；**店員人工配才發**，系統自動配 → 進全店池）；
    綁定客人獎金 **10 元/人/次**（歸主責店員；名下客人每次有效消費 ≥100 才抽）。
    一桌上限 = 50 + 4×10 = **90 元**。
  - **刻意不掛儲值金額** 🚫 —— 避免「再儲一萬啦」的推銷現場，守住安心定位。
  - 理念「系統是雷達、店員是飛彈」：底薪 6–7 成 + 獎金 3–4 成；
    最強店員 = 加盟主人才水庫（接 M5）。
  - 全店成桌率達標另有全店獎金（防搶客／藏客）。
- **店員後台「我的客人」CRM**：名下會員、誰多久沒來、誰生日快到、
  今天哪桌缺人、本月促成桌數 + 獎金即時數字（業務動力來自看到數字在跳）。
- **MDM 多店主檔下發**也在此階段。

### M3 的原料已經在收了

| 情報 | 來源欄位 |
|---|---|
| 作息 | `session_players.joined_at`、`match_queue_players.joined_at`、`app_events` 的 `app_open` |
| 耐心 | `leave_reason='quit'` 前的等待時長 → 每人耐心上限 |
| 行為人格 | `join_source`（opened 揪團核心客／invited 跟隨者）|
| 路程 | `play_at` vs 實際報到時間之差 → 每人到每店的慣性時間 |
| 行銷黃金訊號 | `match_queues.status='expired'` = 某人某時段想打但沒湊到人 |

> **耐心值只能用 `quit` 的資料算** —— 被解散的人不是沒耐心，混算會污染分析。

M3 的推斷引擎負責把上述行為回填 `member_availability`（`source='inferred'`）。

## M6 — 平台化授權（B2B 授權 + B2C 私場）📋　前置：M5 + 法務

## 整合方式鐵則

> 「API 串來串去」是最大隱藏成本。判準 =「要不要跟核心資料即時黏」。

- **A 自建（長在自家 DB）**：POS／CRM／錢包／配桌／成績／ERP 輕量／MDM／段位忠誠度
  → 同庫，**根本沒有串接**。
- **B 檔案匯出入**：會計／薪資／巡檢／報表給會計師 → 傳檔，零技術風險。
- **C 只串大廠標準 API**：**金流 + LINE 推播 + 電子發票**（財政部加值中心）
  —— 只有這三處真的需要即時串。

**原則：核心營運全部自建**（A 那一整排）；其中**護城河（配桌／牌譜段位／會員核心／點數錢包）是重中之重**。
只有 B + C 不自建。規模化後的周邊系統（SCM／WMS／EAM／加盟管理／BPM…）那一層才買成熟 SaaS，
靠多租戶 `org_id` / `store_id` 好串。

> ⚠️ 舊措辭「只自建護城河，其餘買 SaaS」是**錯的** —— 會誤讀成 POS／CRM／ERP 也買 SaaS。
> 正解：核心營運全自建，護城河是其中最關鍵一塊，不是唯一自建的。
