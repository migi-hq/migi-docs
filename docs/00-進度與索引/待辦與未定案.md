→ 這是「認證架構升級」與「會員條碼」的前置條件。

### 認證架構升級（接金流前必做）

目前 anon key + 信任前端傳來的 `p_member_id`，**沒有真實 Supabase auth session**。
M2 有金流之後這是實質風險。改動約 1–2 天，需 LINE Channel 建立後才能做。
上線前 RPC 要從 anon 收斂成 authenticated，並加 rate limit。

### staging 環境（接金流與發票前必須）

`is_test` 旗標隔離擋不住這幾件事 —— 它們不看資料庫欄位：
GA4／Meta 照樣記、發票會真的上傳財政部、金流會真的扣款、推播會真的發出去。

建議：Cloudflare Pages 分支部署（`main` → 正式、`staging` → 測試），
各吃不同環境變數，staging 不裝 GA4／Meta 追蹤 ID。

### 發票開立時點（未解，需會計師拍板）

**問題**：儲值制之下，同一筆錢有兩個可能的開票時點。兩個都開就是**同一筆錢報兩次銷售額**，
會多繳營業稅並虛增營收。所以只能擇一。

| | 儲值時 | 用點數消費時 | 現金消費時 |
|   |   |   |   |
| **A（推測為台灣標準）** | **開發票** | 不開 | 開發票 |
| **B** | 不開 | 開發票 | 開發票 |

**傾向 A。** 錢在儲值那一刻就進帳，收款行為已完成；台灣對現金禮券的處理是
出售時開立、兌換時不再開立。營業稅法第 32 條處理的正是「預收款延後開票」這件事 ——
B 會讓客人儲值後放三個月不用的那筆收入，三個月都沒進發票系統。

#### 不論 A 或 B，這條規則都成立

> **發票金額 = 該筆交易的「非點數」付款金額**

| 情境 | 發票金額 |
|   |   |
| 儲值 1000（含贈 150 點）| **1000** —— 贈點不是收到的錢，帳上是促銷費用／折讓 |
| 用點數買水餃 80 | **不開** |
| 現金買水餃 80 | **80** |
| 點數 50 + 現金 30 | **30** |

`order_payments` 已經分得出現金與點數，金額**直接算得出來，不需要改資料結構**。
這條可以先寫進 `settle_session_tx` / `create_invoice_draft_tx` 的設計，不會因為 A/B 而白做。

#### 要問會計師的三個問題

1. **開票時點**：A 還是 B？
2. **儲值發票的品名與稅別**：「儲值金」／「預收貨款」／其他？
3. **履約保證**（比前兩題更重要）——
   預付儲值可能適用「商品（服務）禮券」規範，見
   [`開店前主體與帳務Checklist.md`](../07 營運商業/開店前主體與帳務Checklist.md) §點數/儲值的法遵。
   若「**不得設使用期限**」適用，點數就**不能過期** ——
   那是產品設計層級的限制，不是技術問題，會回頭改動會員制度與財務假設。

> ⚠ 這三題會計師沒回覆前，`settle_session_tx` 的開票段不要動工。
> 其餘部分（包桌超時補收、場次收尾）不受影響，可以先做。

### 會員條碼掃描（防冒用）

待 LINE Login 後評估。需 App 端 LIFF 條碼 + POS 端掃描器，兩邊都要開發。

## 四、刻意延後（不是遺漏）

**規模化前補、現在補浪費：**

1. **React Query / TanStack Query** —— 目前每頁各自 `useEffect + fetch`，無快取共享。
   **這是目前離世界級最遠的一塊**，上線有流量後第一個補。
2. **樂觀更新** —— 按讚等操作即時回饋、失敗回滾。
3. **資料層失敗接上 `app_error` 埋點** —— 目前只 `console.warn`。
   （註：POS 已於 2026 08 15 補 `ErrorBoundary` 與 `rpc()` try/catch，
   但 **migi web 與 migi admin 的資料層還沒比照辦理**。）
4. **loading / empty / error 三態骨架屏** —— 目前只有「有資料」和「預設值」兩態。
5. **多裝置寫入衝突的系統性版本控制** —— 目前只有點狀補丁（稱號聯集只增不減）。

**等結構穩定：**

  **TypeScript** —— 等後端資料結構穩定後遷移。
  **自動化測試** —— 等功能穩定，上線前補關鍵路徑。
