## 一、跨階段前置阻礙

**這幾項卡的不只一件事，而且前置時間長，要早點動。**

### LINE Developers 帳號（尚未申請）

Provider、LIFF Channel、LINE Login Channel 全部未建立。
建議用公司 email 註冊 Business ID（帳號歸屬較清楚），之後再連動 LINE。
注意：**一個 LINE 帳號只能連一個 Business ID**，官方帳號申請需手機驗證。

→ 這是「認證架構升級」與「會員條碼」的前置條件。

### 認證架構升級（接金流前必做）

目前 anon key + 信任前端傳來的 `p_member_id`，**沒有真實 Supabase auth session**。
M2 有金流之後這是實質風險。改動約 1–2 天，需 LINE Channel 建立後才能做。
上線前 RPC 要從 anon 收斂成 authenticated，並加 rate limit。

### staging 環境（接金流與發票前必須）

`is_test` 旗標隔離擋不住這幾件事 —— 它們不看資料庫欄位：
GA4／Meta 照樣記、發票會真的上傳財政部、金流會真的扣款、推播會真的發出去。

建議：Cloudflare Pages 分支部署（`main` → 正式、`staging` → 測試），
各吃不同環境變數，staging 不裝 GA4／Meta 追蹤 ID。

### 發票法規疑慮（未解）

財政部規定預收款原則上**收款時就該開發票**（營業稅法第 32 條），
與「儲值不開票、消費時才開」的設計衝突。**需會計師確認。**

### 會員條碼掃描（防冒用）

待 LINE Login 後評估。需 App 端 LIFF 條碼 + POS 端掃描器，兩邊都要開發。

## 四、刻意延後（不是遺漏）

**規模化前補、現在補浪費：**

1. **React Query / TanStack Query** —— 目前每頁各自 `useEffect + fetch`，無快取共享。
   **這是目前離世界級最遠的一塊**，上線有流量後第一個補。
2. **樂觀更新** —— 按讚等操作即時回饋、失敗回滾。
3. **資料層失敗接上 `app_error` 埋點** —— 目前只 `console.warn`。
   （註：POS 已於 2026-08-15 補 `ErrorBoundary` 與 `rpc()` try/catch，
   但 **migi-web 與 migi-admin 的資料層還沒比照辦理**。）
4. **loading / empty / error 三態骨架屏** —— 目前只有「有資料」和「預設值」兩態。
5. **多裝置寫入衝突的系統性版本控制** —— 目前只有點狀補丁（稱號聯集只增不減）。

**等結構穩定：**

- **TypeScript** —— 等後端資料結構穩定後遷移。
- **自動化測試** —— 等功能穩定，上線前補關鍵路徑。
