## 基石 ①:主鍵用 UUID(不用 bigint 自增)

**決策:所有表主鍵用 UUID(`uuid` 型態,預設 `gen_random_uuid()`)。**

```sql
id uuid primary key default gen_random_uuid()
```

**為什麼(對應 MIGI 多租戶+加盟+碰錢):**
- **跨店/加盟不撞號**:bigint 各店從 1 開始會撞;UUID 各店隨機,永不撞,多店聚合/跨店會員無痛
- **不可猜**:bigint 的 id=5 可被遍歷試別人資料;UUID 猜不到,保護會員個資與金流
- **可分散式產生**:前端/各店裝置可先產生 id 不必等資料庫(離線、多店同步靈活)

**代價**:id 較長、肉眼難讀 → 機器不在乎,可接受。
**注意**:外鍵也全用 uuid;join 效能在你的規模無感。

## 基石 ②:時間存原始 UTC;「營業日」只是報表觀點(切點 00:00)

**決策:**
- 所有時間欄位用 `timestamptz`,儲存一律 **UTC 原始值**,顯示時才轉 +08(台灣)
- **資料只存「事件發生的原始時間」,絕不在資料裡寫死「這屬於哪個營業日」**
- **營業日切點 = 00:00(自然日)**;這是「算報表時才套用的規則」,不是存進每筆資料的欄位

```sql
created_at timestamptz not null default now()   -- 存 UTC 原始值
-- 營業日 = 報表查詢時,把原始時間轉 +08 後取日期(切點 00:00)
```

**核心觀念:原始時間是「事實」,營業日是「觀點」。**
- 配「開桌即扣」:每筆扣點算「扣點當下」的營業日(開桌扣的算開桌那天),不是收桌時間
- 改切點(萬一日後想改)只動報表查詢規則,**不動任何一筆歷史資料**

**兩種統計性質不同,切點只影響其一:**
| | 營收 / 開桌數 | 牌譜統計(勝率/放槍率/段位) |
|---|---|---|
| 本質 | 按「天」彙總 | 按「人」累積 |
| 需要營業日切點? | **要**(定義一天範圍) | **不用**(哪天打的都算進那個人) |

- **營收/開桌數**:要按營業日彙總 → 用切點(00:00)歸日
- **牌譜統計**:跟著人累積,不按天結算 → 直接用原始時間,**不受切點影響**
- 牌譜的「時段分析」(早場/晚場誰強):用原始時間的「時段」(幾點打的),仍與營業日切點無關

⚠️ 工程師注意:**不要把「營業日」寫死進任何資料表**,只存原始 UTC;營業日在報表/物化視圖查詢時才套。

## 基石 ③:軟刪除(碰錢/個資的資料絕不真刪)

**決策:會員、交易、牌局、桌次等核心資料一律軟刪除,加 `deleted_at`,不用 DELETE。**

```sql
deleted_at timestamptz   -- null=有效;有值=已刪(但保留)
```

**為什麼:**
- 法律、稽核、加盟拆帳糾紛都要查得到歷史 → 真刪 = 證據消失
- 查詢預設過濾 `deleted_at is null`
- 例外:純暫存/快取資料可硬刪

---

## 基石 ④:金額/點數用整數(bigint),絕不用浮點數

**決策:點數用 `bigint`(整數)。涉及現金小數用 `numeric`,永不用 `float/double`。**

**為什麼:**
- 浮點數有精度問題(0.1+0.2≠0.3)→ 碰錢是災難,帳會對不平
- 點數本來就是整數(150點/100點),bigint 最適合
- 若未來有小數(匯率、分潤比例)→ 用 numeric(精確十進位),不用 float

---

## 基石 ⑤:每張表審計欄(誰、何時、做了什麼)

**決策:所有業務表標配審計欄。**

```sql
created_at timestamptz not null default now()
updated_at timestamptz not null default now()   -- 觸發器自動更新
created_by uuid    -- 操作者(staff/member/system)
updated_by uuid
```

**為什麼:**
- 碰錢操作要有完整「誰、何時、做了什麼」→ 加盟拆帳糾紛、客訴、稽核的證據
- 漏了日後補 = 改全部表 + 歷史資料無從追溯

## 基石 ⑥:RLS Day 1 就開(多租戶隔離)

**決策:每張業務表帶 `org_id`,Row Level Security 第一天就開,不留「日後再開」。**

**為什麼:**
- 一旦有資料進來才補 RLS → 要回頭檢查所有歷史資料歸屬,風險高
- 加盟主 A 絕不能看到加盟主 B 的資料 → RLS 在資料庫層強制隔離
- 每張表 policy 以 org_id 為第一道隔離(沿用藍圖 §5 權限矩陣)

**★實戰教訓(2026-07-12,部署總部後台踩到):**
- **policy 用的 helper 函式必須 `SECURITY DEFINER + SET search_path = public`。** `current_org_id()` 查 staff/members 找 org,若無 SECURITY DEFINER,查表時受 RLS 限制 → 觸發那些表的 policy → 又呼叫 current_org_id() → 無限遞迴 → `stack depth limit exceeded`(讀取 500)。這是 Supabase RLS 教科書級陷阱,Supabase 官方推薦寫法就是 SECURITY DEFINER。
- **policy 要讀寫分開想。** 只建 `for select`(USING)的 policy,INSERT/UPDATE 會被 `new row violates row-level security policy` 擋。寫入要有 WITH CHECK(如 `create policy xxx_write for all using/with check (org_id = current_org_id())`)。
- **登入帳號要在 staff/members 表有對應資料**,否則 current_org_id() 回 null、讀寫全擋。~~HQ 管理員(Supabase Auth 帳號)要 insert 進 staff(role='hq', auth_uid=該帳號的 auth id)。未來每個 POS 店員帳號同理。~~

  🔴 **上面那句已過時（2026-08-23 更正）。** 線上的 `current_staff()` 判準是：

  ```sql
  from staff s join members m on m.id = s.member_id
  where m.line_user_id = (auth.jwt() ->> 'sub')
  ```

  也就是 **店員身分 = 一個有 LINE 綁定的會員 + `staff` 表一列**，不是 Supabase Auth 帳號。
  `staff.auth_uid` 這個欄位還在，但 **`current_staff()` 完全沒讀它** —— 那是舊設計的殘留。

  ⚠ 實務後果：`staff.member_id` 是 null 的那一列**永遠 join 不到**（INNER JOIN）。
  2026-08-23 查到現有唯一那筆「MIGI 總部管理員」正是這種情況，LINE 接上也登不進去。
  → 建立店員一律走 `grant_staff_tx(p_member_id, p_store_id, p_role)`，
  它吃的是 **member_id**；角色只能是 `floor` / `manager` / `hq` / `owner`。
  詳見 CLAUDE.md 待辦 20。

## 基石 ⑦:錢包並發控制(同時扣點不出錯)

**決策:錢包扣點一律在資料庫交易內、對該錢包列加鎖(`SELECT ... FOR UPDATE`),確保並發安全。**

**為什麼:**
- 兩個請求同時扣同一錢包 → 不加鎖會 race condition(扣兩次/餘額錯亂)
- 碰錢的經典坑,必須架構層面先解,不是日後補
- 做法:扣點 Edge Function 內 → begin → 鎖錢包列 → 檢查餘額 → 寫 wallet_txns → 更新 wallets.balance → commit(對應「做法三」明細為真相+快取餘額)

## 基石 ⑧:冪等性(網路重試不重複扣)

**決策:所有碰錢操作(儲值、扣點)帶冪等鍵(idempotency key),同一操作重送只生效一次。**

```sql
-- wallet_txns 加唯一冪等鍵
idempotency_key text unique
```

**為什麼:**
- 客人儲值/扣點,網路卡了重送 → 不做冪等會扣兩次錢 → 客訴且難補
- 前端產生唯一 key 隨請求帶上,後端發現 key 重複 → 直接回前一次結果,不重複執行

## 基石 ⑨~⑬:碰錢/帳務(大廠標準)

### ⑨ 雙邊追蹤錢流(簡化版複式記帳)
- 每筆錢的移動記「從哪來、到哪去」,不只單邊記某會員 +/−。
- 例:小婷扣150打牌 → 記「小婷錢包 −150」+「該店待結算營收 +150」。
- 接加盟拆帳:會員儲值的錢 ↔ 哪店待服務負債 ↔ 服務後轉營收(collected/served store)。
- **務實取捨**:第一版做「可追蹤錢流」(每筆記對方帳戶),不必嚴格借貸平衡;加盟金額大了再強化為完整複式記帳。避免過度設計。

### ⑩ 交易狀態機
- wallet_txns 加 `status`:pending / completed / failed / refunded。
- 純內部扣點可即時 completed;**儲值涉外部金流(綠界)必有 pending**(等金流商回覆)→ 成功/失敗。

### ⑪ 外部金流對帳欄位
- wallet_txns 留 `external_ref`(綠界/藍新的交易編號)。
- 對帳功能(系統帳 vs 金流商帳核對)日後做,但欄位現在留好。

### ⑫ 退款/沖正(ledger 不改舊帳)
- 扣錯/退費**不刪原紀錄、不改原紀錄**,而是再記一筆「反向沖正分錄」(相反金額,註明沖正哪筆)。
- 呼應 append-only:帳本只進不改,退款也是「再記一筆」。

### ⑬ 金額正負號方向約定
- 統一寫死:**+ 入點 / − 扣點**,用 check 約束強制,避免有人記反。

## 基石 ⑭~⑯:資料完整性

### ⑭ 外鍵與級聯規則(碰錢的不級聯刪)
- 明確定義每個關聯的 on delete:**碰錢/個資的一律 restrict(不可刪)**,靠軟刪除(③)。
- 刪會員 ≠ 刪他的交易紀錄(紀錄永久保留)。

### ⑮ 列舉值用 enum / check 約束
- 狀態、類型(txn_type、status、join_type…)用資料庫 enum 或 check 限制合法值,擋髒資料(打錯字進不來)。
- 實例:products.category check (service/fnb/merch)、staff.role check (floor/manager/hq/owner)、order_items.kind check (fee/fnb/goods)。

### ⑯ 唯一性約束在資料庫層
- 不能重複的在 DB 層擋,不只靠程式:如同一 org 內 line_user_id 唯一、同一 session 同一 member 不重複(session_players 複合主鍵已做)。

## 基石 ⑰~⑲:多租戶/安全

### ⑰ org_id 不可竄改
- 一筆資料的 org_id 建立後不可改(trigger/RLS 鎖),避免資料被搬租戶。

### ⑱ service_role 與 RLS 邊界
- 明確:**改錢(扣點/儲值/分潤)只能後端 service role 經 Edge Function**;前端只能讀自己的、永不直接改錢(沿用藍圖 §5)。

### ⑲ 個資加密與日誌遮罩
- 手機、生日等個資:評估加密儲存;**日誌/log 一律遮罩**(不可把會員手機、完整個資印進 log)。

---

## 基石 ⑳~㉒:維運/可靠

### ⑳ 備份與還原(PITR)
- 確認 Supabase 開啟 Point-in-Time Recovery(可還原到任一時間點)。碰錢資料毀損是災難,備份不可省。

### ㉑ Migration 版本控管
- 每次改 schema 留 SQL 檔、有版本、可回溯(藍圖已提,正式化)。一律 Dashboard 部署 + SQL 檔留存。

### ㉒ 軟刪除與唯一約束的衝突(經典坑)
- 軟刪一個會員後,他的手機號能否給新會員用?
- 唯一約束要含 deleted_at 條件(例:`unique(org_id, phone) where deleted_at is null`),否則軟刪的舊資料會擋住新註冊。
