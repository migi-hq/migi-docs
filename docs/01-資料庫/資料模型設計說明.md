# 資料模型設計說明

> **這是什麼**：資料表為什麼長這樣 —— 欄位語意、約束理由、設計取捨。
> **什麼時候讀**：設計新功能要接哪張表、或看到某個欄位不確定它是什麼意思時。
>
> ⚠ **這份講「為什麼」，不講「現在有什麼」。**
> 實際欄位、CHECK 允許值、RPC 簽名一律以 [`db-現況快照.md`](db-現況快照.md) 為準
> —— 那份是從線上資料庫直接盤出來的。本檔若與快照衝突，以快照為準。
>
> 合併自 `資料表結構速查` / `資料表總覽` / `資料模型與RPC` 三份（2026-08-15）。

## 一、分層概念（最重要的一張圖）

```
會員 App 端                          POS / 營運端
─────────────────                    ─────────────────
match_queues        ← 等待撮合房      table_sessions   ← 已入座計費桌
match_queue_players                   session_players
        │                                     ▲
        └──── matched_session_id ─────────────┘
              （線上湊齊 → 到店入座 → 店員開計費桌）
```

**「房」和「桌」是兩件事。** 房是線上約，還沒收錢；桌是實體入座，開始計費。
兩者用 `matched_session_id` 串起來。

**鐵則：POS 與 App 所有查詢一律走 SECURITY DEFINER RPC。**
前端用 anon key 沒有 auth session，`current_org_id()` 回 null →
直接 `supabase.from('表').select()` 會**查詢成功但回空陣列且不報錯**，
是最難察覺的失敗模式。（`CLAUDE.md` 硬規則 4）

## 三、關鍵欄位語意與約束理由

### `products`

`category` 限 **service / fnb / merch**（`products_category_check`）。
`unit_price` 是**售價（元）** —— 原名 `unit_price` 之前叫 `unit_points`，
2026-07-12 元計價遷移時更名。**單位從點變元，1 點 = 1 元**，型別仍是 bigint（基石④：金額不用浮點數）。

其餘約束：`stock_qty >= 0`、`unit_price >= 0`。
`is_active`（上不上架）與 `is_available`（現在有沒有貨）是**兩件事**，不要混用。

> ⏳ `products` 尚未有 `kind` 欄位，見 `sql/pending/2026-08-15_products加kind欄位.sql`。
> 目前 `list_products_tx` 是即時算出 `kind` 的。

### `order_items`

**此表不存 sku**，只存 `product_id` 與 `name` 快照。

好處：改商品 SKU 不影響歷史訂單。
代價：**用 SKU 做報表時，歷史資料會跟著商品當下的 SKU 走** —— 想要當時的 SKU 就查不到。

`kind` 限 fee / fnb / goods（允許 null）。外鍵對 `orders` 與 `products` 都是 **ON DELETE RESTRICT**
（基石⑭：碰錢的不級聯刪）—— 這就是為什麼收過錢的訂單刪不掉。

### `staff`

`role` 限 floor / manager / hq / owner。總部人員 `store_id` 留 null。

> **HQ 管理員必須在此表有一筆資料**（`role='hq'`、`auth_uid` = 該 Supabase Auth 帳號）。
> 否則 `current_org_id()` 回 null，讀寫全被 RLS 擋 —— 這踩過。

`members` 是會員（客人），`staff` 是員工。
`current_org_id()` 先查 `staff.auth_uid`，再查 `members.line_user_id`。

### `table_sessions`

`mode` 是 **`matched`**（配桌）/ `private`（包桌）—— **不是 `match`**。
`status` 是 open / completed / **`voided`** —— **沒有 `playing`**，
而且 voided 這個拼法**只有這張表**（其餘表一律 `void`，見快照開頭那張表）。

**狀態設計：場次沒有獨立的「進行中」狀態，用 `activated_at` 是否有值區分。**

| `activated_at` | 意思 |
|---|---|
| null | 收費報到中（人陸續來、陸續收錢）|
| 有值 | 已開打 |

這樣不必擴充 status 約束，而 `activated_at` 本來就要記（日後接電控桌用）。

**唯一索引**（防重複開桌的關鍵，快照沒列）：
- `uq_sessions_idem` ON (idempotency_key) WHERE idempotency_key IS NOT NULL
- `uq_sessions_open_table` ON (table_id) WHERE status='open' AND deleted_at IS NULL
  → **同一張桌不可能同時有兩個 open 場次**，靠資料庫層擋（基石⑯）。

計畫欄位：`planned_rounds`（配桌預定將數 2/3，包桌為 null）、
`planned_minutes`（包桌預估時長 120/300/1440，配桌為 null）。

### `session_players`

`join_type` 限 opener / mid_join / **sub**（sub = 代打，2026-08-07 擴充，
**M4 算段位時需排除代打**）。
`status` 限 playing / completed / late / forfeit。

| 欄位 | 語意陷阱 |
|---|---|
| `charged_points` | **此人實付金額（元）**。欄名沿用點數時代，語意早就改了 |
| `order_id` | 有值 = 已結帳 |
| `paid_by` | 有值 = 被代付（此時 `charged_points = 0`）|

### `orders`

金額有強制恆等式約束 `orders_amount_balance`，寫入前必須自己算對 —— 公式見快照。

## 三之二、分類維度：三套詞彙的來龍去脈

**同一個「檯費」概念，資料庫裡有三種拼法。** 寫 SQL 前先看這張表，不要猜：

| 欄位 | 允許值 | 這是什麼維度 |
|---|---|---|
| `products.category` | `service` / `fnb` / `merch` | **管理分類** —— 後台商品頁怎麼分頁、採購怎麼歸類 |
| `order_items.kind` | `fee` / `fnb` / `goods`（允許 null）| **財務分類** —— 結帳時錢落進哪個桶，決定券能不能折 |
| `coupons.applies_to` | `table_fee` / `fnb` / `ride` / `topup` / null | **促銷適用範圍** |

對應關係：`service ↔ fee ↔ table_fee`、`merch ↔ goods`、`fnb` 三者同名。

### 分成兩個維度是對的，命名不是

`category` 與 `kind` 今天剛好一對一，`list_products_tx` 用
`case category when 'fnb' then 'fnb' when 'merch' then 'goods' else 'fee' end` 即時推導。
看起來多餘，但**它們遲早分家**，而且已經有證據：

`applies_to` 有 `ride`（派車）與 `topup`（儲值）兩個財務桶，
**`category` 根本沒有對應值**。等 M8 教室課程上線，
那會是 `category='service'` 卻不該吃檯費折價券 —— 用 category 推導 kind 當場就錯。

→ `sql/pending/2026-08-15_products加kind欄位.sql` 就是要把 `kind` 存進商品主檔、
不再由 category 推導。**那支 SQL 的判斷是對的。**

至於三種拼法，那是不同時期各自取名的漂移。
**但不要為了統一命名去改** —— 這些值寫死在 `checkout_tx` 的折扣分桶邏輯裡
（`if cp.applies_to = 'table_fee' then …`），是碰錢的程式碼，風險遠大於收益。
記在這裡，讓下次寫 SQL 的人一眼看到就好。

### `order_items` 存快照是正確的做法

`order_items` 存的是 `name` 與 `kind` 的**快照**，不是外鍵指向 `products`。
這樣商品日後重新分類，**去年的營收報表不會被改寫**。
SAP / NetSuite / Oracle Retail 都是這個做法，這點不用改。

### ⚠️ `coupons.applies_to` 做成 enum 是撐不久的

**促銷適用範圍不該是型別欄位，應該是規則。**

行銷會不停發明新範圍 ——「聯名商品專用」「週二飲料」「新品嘗鮮」
「段位解鎖限定品」。每一個都要改 CHECK 約束、跑 migration、改 `checkout_tx`。
等於**行銷一個活動企劃 = 一次金流函式改版**。

業界（Shopify、Square、Oracle Retail Price Management）的做法是
「一組條件或明確清單」。最小可行版本是一張範圍表：

```
coupon_scope(coupon_id, scope_type, scope_value)
  scope_type ∈ kind | category | product_id
```

一張券可以有多列。`ride` / `topup` 那兩個尷尬的值也自然消失 ——
它們本來就不是商品分類，是硬塞進 enum 的。

**動手時機：發券後台開工前。** `grant_rules` / `grant_log` 目前完全不存在
（2026-08-15 查證），所以現在改成本最低 —— 還沒有任何已發出的券要遷移。
晚一步就得帶著一堆券做 migration。

### 還缺一個維度：稅務分類

目前**沒有任何稅務相關欄位**。台灣統一發票對餐飲、商品、服務的處理不見得相同，
而 `settle_session_tx` 要開發票時會需要。
→ **做發票前補**，不要等開票當天才發現。
