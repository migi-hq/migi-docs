# 資料模型設計說明

> **這是什麼**：資料表為什麼長這樣 —— 欄位語意、約束理由、設計取捨。
> **什麼時候讀**：設計新功能要接哪張表、或看到某個欄位不確定它是什麼意思時。
>
> ⚠ **這份講「為什麼」，不講「現在有什麼」。**
> 實際欄位、CHECK 允許值、RPC 簽名一律以 [`db-現況快照.md`](db-現況快照.md) 為準
> —— 那份是從線上資料庫直接盤出來的。本檔若與快照衝突，以快照為準。
>
> 合併自 `資料表結構速查` / `資料表總覽` / `資料模型與RPC` 三份（2026-08-15）。

## 一、分層概念（最重要的一張圖）

```
會員 App 端                          POS / 營運端
─────────────────                    ─────────────────
match_queues        ← 等待撮合房      table_sessions   ← 已入座計費桌
match_queue_players                   session_players
        │                                     ▲
        └──── matched_session_id ─────────────┘
              （線上湊齊 → 到店入座 → 店員開計費桌）
```

**「房」和「桌」是兩件事。** 房是線上約，還沒收錢；桌是實體入座，開始計費。
兩者用 `matched_session_id` 串起來。

**鐵則：POS 與 App 所有查詢一律走 SECURITY DEFINER RPC。**
前端用 anon key 沒有 auth session，`current_org_id()` 回 null →
直接 `supabase.from('表').select()` 會**查詢成功但回空陣列且不報錯**，
是最難察覺的失敗模式。（`CLAUDE.md` 硬規則 4）

## 三、關鍵欄位語意與約束理由

### `products`

`category` 限 **service / fnb / merch**（`products_category_check`）。
`unit_price` 是**售價（元）** —— 原名 `unit_price` 之前叫 `unit_points`，
2026-07-12 元計價遷移時更名。**單位從點變元，1 點 = 1 元**，型別仍是 bigint（基石④：金額不用浮點數）。

其餘約束：`stock_qty >= 0`、`unit_price >= 0`。
`is_active`（上不上架）與 `is_available`（現在有沒有貨）是**兩件事**，不要混用。

**2026-08-16 新增三個欄位**，讓「放哪一頁／錢算哪個桶／要不要盤點」三個問題各自有答案，
不再互相推導（推導會壞的具體案例見第三之二節）：

| 欄位 | 值 | 職責 |
|---|---|---|
| `revenue_type` | venue_fee / fnb / retail / other | **財務**：收入桶、折扣範圍、營收報表 |
| `subcategory` | TBL / MEAL / DRK / GOOD… | **毛利維度**：三段式貨號第二段，原本只存在 sku 字串裡 |
| `tracks_stock` | boolean | **庫存**：要不要盤點 |

`revenue_type` 與 `subcategory` **刻意暫時可為 null** ——
`migi-admin` 的 `saveProduct()` 直接 insert `products` 且不送這兩欄，
立刻加 NOT NULL 會讓後台新增商品當場失敗。等後台表單改好再補約束。

> ⚠ `products.kind` **也存在**（`2026-08-15_products加kind欄位.sql` 已執行），
> 但它是**孤兒欄位** —— 那支 SQL 只建了欄位沒改函式，`list_products_tx` 至今仍用
> `case category` 即時推導，沒有任何函式讀它。
> 保留原因：等 `kind` → `revenue_type` 的全面替換（前端 84 處）完成後，
> **最後一步再 drop**。現在 drop 只會冒 42703 的風險而買不到東西。

### `order_items`

**此表不存 sku**，只存 `product_id` 與 `name` 快照。

好處：改商品 SKU 不影響歷史訂單。
代價：**用 SKU 做報表時，歷史資料會跟著商品當下的 SKU 走** —— 想要當時的 SKU 就查不到。

`kind` 限 fee / fnb / goods（允許 null）。外鍵對 `orders` 與 `products` 都是 **ON DELETE RESTRICT**
（基石⑭：碰錢的不級聯刪）—— 這就是為什麼收過錢的訂單刪不掉。

### `coupons`

**⚠ `discount_value` 是「折抵百分比」，不是「折數」。**

`checkout_tx` 的算法是：

```sql
when 'percent' then round(cap * cp.discount_value / 100.0)
```

所以中文的「**9 折券**」（客人付九成）要填 **`discount_value = 10`**，不是 90。
填 90 會變成**折掉九成、客人只付一成**。

這不是假設性風險 —— `migi-web/src/pages/wallet.jsx` 的假券 fallback 就寫著
`{ name: '檯費 9 折券', discount_type: 'percent', discount_value: 90, max_discount: 45 }`。
那份是假資料（`CLAUDE.md` 待辦 7 要刪），但**照那個格式去後台建真券就會發出九折變一折的券**。
→ 發券後台開工時，欄位標籤必須寫「折抵 %」而不是「折扣」，或乾脆改成輸入折數再由程式換算。

`max_discount` 是**這張券最多折多少錢**（元）。
百分比券沒有上限會失控：同一張「檯費 9 折券」用在 $150 配桌折 $15，
用在 $800 包桌就折 $80。後端一律套用上限：

```sql
if cp.max_discount is not null and cut > cp.max_discount then cut := cp.max_discount; end if;
```

`min_spend` 比對的是**該券適用範圍內的金額**（`cap`），不是整張單的小計。

> 券的分桶與折抵順序見第三之二節；`applies_to` 做成 enum 撐不久的理由也在那裡。

### `staff`

`role` 限 floor / manager / hq / owner。總部人員 `store_id` 留 null。

> **HQ 管理員必須在此表有一筆資料**（`role='hq'`、`auth_uid` = 該 Supabase Auth 帳號）。
> 否則 `current_org_id()` 回 null，讀寫全被 RLS 擋 —— 這踩過。

`members` 是會員（客人），`staff` 是員工。
`current_org_id()` 先查 `staff.auth_uid`，再查 `members.line_user_id`。

### `table_sessions`

`mode` 是 **`matched`**（配桌）/ `private`（包桌）—— **不是 `match`**。
`status` 是 open / completed / **`voided`** —— **沒有 `playing`**，
而且 voided 這個拼法**只有這張表**（其餘表一律 `void`，見快照開頭那張表）。

**狀態設計：場次沒有獨立的「進行中」狀態，用 `activated_at` 是否有值區分。**

| `activated_at` | 意思 |
|---|---|
| null | 收費報到中（人陸續來、陸續收錢）|
| 有值 | 已開打 |

這樣不必擴充 status 約束，而 `activated_at` 本來就要記（日後接電控桌用）。

**唯一索引**（防重複開桌的關鍵，快照沒列）：
- `uq_sessions_idem` ON (idempotency_key) WHERE idempotency_key IS NOT NULL
- `uq_sessions_open_table` ON (table_id) WHERE status='open' AND deleted_at IS NULL
  → **同一張桌不可能同時有兩個 open 場次**，靠資料庫層擋（基石⑯）。

計畫欄位：`planned_rounds`（配桌預定將數 2/3，包桌為 null）、
`planned_minutes`（包桌預估時長 120/300/1440，配桌為 null）。

### `session_players`

`join_type` 限 opener / mid_join / **sub**（sub = 代打，2026-08-07 擴充，
**M4 算段位時需排除代打**）。
`status` 限 playing / completed / late / forfeit。

| 欄位 | 語意陷阱 |
|---|---|
| `charged_points` | **此人實付金額（元）**。欄名沿用點數時代，語意早就改了 |
| `order_id` | 有值 = 已結帳 |
| `paid_by` | 有值 = 被代付（此時 `charged_points = 0`）|

### `orders`

金額有強制恆等式約束 `orders_amount_balance`，寫入前必須自己算對 —— 公式見快照。

## 三之二、分類維度：四套詞彙的來龍去脈，與 2026-08-16 的收斂

**同一個「檯費」概念，系統裡有四種拼法。** 寫 SQL 前先看這張表，不要猜：

| 位置 | 允許值 | 這是什麼維度 | 狀態 |
|---|---|---|---|
| `products.category` | `service` / `fnb` / `merch` | **陳列與管理** —— 後台分頁、採購歸類、貨號前綴 | 保留 |
| `products.revenue_type` | `venue_fee` / `fnb` / `retail` / `other` | **財務** —— 收入桶、折扣範圍、報表 | ★ 2026-08-16 新增 |
| `order_items.kind` | `fee` / `fnb` / `goods`（允許 null）| 同上，但這是**成交當下的快照** | 待替換成 `revenue_type` |
| `coupons.applies_to` | `table_fee` / `fnb` / `ride` / `topup` / null | **促銷適用範圍** | 待刪，改 `coupon_scope` 表 |
| SKU 第一段 | `SVC` / `FNB` / `MCH` | **人讀的標籤**（見《商品與貨號規範》）| 保留 |

### 收斂方向：刪一套，不是併四套

四套裡只有**兩個是真的維度**：陳列（category）與財務（revenue_type）。

- `applies_to` 是**假的維度** —— 它就是財務桶換個拼法，
  另外硬塞了 `ride` / `topup` 兩個根本不是商品分類的值。改 `coupon_scope` 表之後整欄消失。
- SKU 第一段是**人讀的標籤**，規範明訂「貨號是給人和報表看的標籤，category 才是系統欄位」。
  全世界的 SKU 都是大寫縮寫，這是慣例不是漂移，可以留 —— 但**產生方式必須自動化**
  （前綴來自 `product_taxonomy`，不得寫在前端 JS）。

**`category` 與 `revenue_type` 不可合併，即使今天 1:1。**
兩個欄位如果永遠一樣，遲早有人會刪掉其中一個；用不同的值恰恰是在文件化「這是兩個維度」。
而且兩者的成長方向相反：`category` 會一直加（course / rental / event…），
`revenue_type` 應該永遠只有四個桶 —— 加一個就要改 `checkout_tx` 的分桶邏輯。

推導必壞的具體案例：

| 商品 | `category` | 正確 `revenue_type` | 用 category 推導的結果 |
|---|---|---|---|
| 配桌檯費 | service | venue_fee | venue_fee ✅ |
| 教室課程（M8）| service | lesson | **venue_fee ❌** 會吃到檯費折扣、灌水檯費收入 |
| 器材租借 | service | other | venue_fee ❌ |

### 為什麼識別碼是 `venue_fee`，中文卻顯示「檯費」

賣的是**場地與服務**，桌只是計價單位 —— 會員權益已承諾「專屬包廂」，包廂是房間不是桌；
且此 schema 裡 `tables` / `table_sessions` / `table_id` 已經滿場，再多一個 `table_fee` 讀起來會頓。

**中文一律「檯費」，不分層** —— 店員與客人看的是同一個畫面，不可能一個叫檯費一個叫場地費。
識別碼與中文不對應是常態：`fnb` / `retail` / `other` 本來就沒有一個是字面翻譯。
對照表在 `product_taxonomy.label`，程式直接讀，人不用背。

> 發票品名是**唯一可以不同**的地方 —— 那是法律文件，作業畫面不是。
> 若會計師建議印「場地服務費」，那是開票時的品名對照，`revenue_type` 仍是 `venue_fee`。

### `other` 是候車室，不是家

任何項目一旦有量，就給它自己的桶。
**M8 教室上線時直接開 `lesson`，不要先放 `other` 再搬** ——
`order_items` 是快照不回頭改，搬家會在報表留下一道永久接縫。

`other` 存在的意義是「先不要歸錯」：塞進既有的桶會污染歷史比較，放 `other` 只是暫時看不清楚。

> ⚠ 派車若是**代收代付**給司機，會計上根本不是收入而是代收款（與儲值同類），
> 不該有 `revenue_type`。做派車功能前先問會計師，不要直接開 `ride` 桶。

### 顯示名的唯一來源：`product_taxonomy`

2026-08-16 之前，分類顯示名有三套、SKU 前綴有兩套：

| | service | merch | 服務類前綴 |
|---|---|---|---|
| 規範文件 | 服務 | 周邊 | `SVC-` |
| `migi-admin` JS | **檯費** | **商品** | **`SER-`** |
| `migi-pos` JS | 服務 | 周邊 | — |

後果已經發生：後台新增服務類商品會產出 `SER-025`，與現有七筆 `SVC-TBL-*` 完全不同體系。

**根因不是有人打錯，是顯示用的常數寫在前端** —— 資料庫改了前端不會知道，而且不報錯。
→ `product_taxonomy` 表（11 列）+ `list_product_taxonomy_tx()`，三端都讀它，JS 不得寫死。

### `order_items` 存快照是正確的做法

`order_items` 存的是 `name` 與 `kind` 的**快照**，不是外鍵指向 `products`。
這樣商品日後重新分類，**去年的營收報表不會被改寫**。
SAP / NetSuite / Oracle Retail 都是這個做法，這點不用改。

### ⚠️ `coupons.applies_to` 做成 enum 是撐不久的

**促銷適用範圍不該是型別欄位，應該是規則。**

行銷會不停發明新範圍 ——「聯名商品專用」「週二飲料」「新品嘗鮮」
「段位解鎖限定品」。每一個都要改 CHECK 約束、跑 migration、改 `checkout_tx`。
等於**行銷一個活動企劃 = 一次金流函式改版**。

業界（Shopify、Square、Oracle Retail Price Management）的做法是
「一組條件或明確清單」。最小可行版本是一張範圍表：

```
coupon_scope(coupon_id, scope_type, scope_value)
  scope_type ∈ kind | category | product_id
```

一張券可以有多列。`ride` / `topup` 那兩個尷尬的值也自然消失 ——
它們本來就不是商品分類，是硬塞進 enum 的。

**動手時機：發券後台開工前。** `grant_rules` / `grant_log` 目前完全不存在
（2026-08-15 查證），所以現在改成本最低 —— 還沒有任何已發出的券要遷移。
晚一步就得帶著一堆券做 migration。

### 還缺一個維度：稅務分類

目前**沒有任何稅務相關欄位**。台灣統一發票對餐飲、商品、服務的處理不見得相同，
而 `settle_session_tx` 要開發票時會需要。
→ **做發票前補**，不要等開票當天才發現。

## 五、閒置與未建立的表

### `pricing_tiers`（閒置）

原設計：`matched` 用「將數」級距、`private` 用「分鐘」級距，可用 `store_id` 做分店覆寫。

**現況：此表為空，且已無函式引用**（舊的 `charge_matched_tx` / `charge_private_tx` 已封存）。
檯費改以 `products` 管理（`SVC-TBL-*` 貨號）。
