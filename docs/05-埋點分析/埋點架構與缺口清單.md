# 埋點架構與缺口清單

> 這是什麼：MIGI 行為分析的架構決策、已埋事件、以及還沒埋的完整缺口清單。
> 什麼時候讀：要新增埋點、要接 GA4／Meta、或要寫分析查詢時。

---

## 一、架構：一個埋點、多處輸出

```
使用者行為
    ↓
track()（src/lib/analytics.js）
    ↓
    ├──→ app_events（自己的庫）      全部事件，精確可關聯
    ├──→ GA4                        只送關鍵事件（尚未開啟）
    └──→ Meta Conversions API       只送轉換（尚未開啟）
```

**不要在頁面裡分別呼叫三套 SDK**，那會導致三邊資料對不起來。

### 自建與外部工具的分工

| 工具 | 送什麼 | 回答什麼問題 |
|---|---|---|
| `app_events` | 全部 + 狀態快照 | 產品決策、營運分析、客戶洞察 |
| GA4 | 頁面瀏覽 + 關鍵轉換 | 流量來源、跨裝置 |
| Meta CAPI | 只有轉換 | 廣告優化 |

**為何不能只有 GA4**：看不到會員身分與實際消費金額、資料被抽樣、不擁有原始資料、台灣環境下 Pixel 會漏 20–40%（ATT、cookie 封鎖、廣告攔截）。
**為何不能只有自建**：投廣告需要 Meta 收到轉換才能優化、跨站歸因看不到、現成報表要自己寫很久。

**Meta 建議走後端 Conversions API 而非前端 Pixel** —— LIFF WebView 內前端成功率更低。

## 二、已完成的基礎建設

每個事件自動帶上（`analytics.js` 處理）：

| 欄位 | 作用 |
|---|---|
| `_sid` | session id，30 分鐘閒置換一次。算得出「一次使用看了幾局才報名」 |
| `_seq` | 這次使用的第幾個動作 |
| `_sms` | 進入本次使用後幾秒 |
| `_eid` | event id，網路重試可去重，營收不會虛胖 |
| `_schema_v` | 事件格式版本，之後改格式歷史仍可讀 |
| `app_version` | build 時注入，可分版本比較 |

**離線佇列**：送失敗存 localStorage（上限 200 筆），開 App 或回到前景時補送。LINE WebView 網路不穩，這是必要的。

**測試閘門**：四個測試帳號 UUID 直接比對（不依賴 localStorage 的 `is_test`，因為切帳號路徑有好幾條，漏寫一次資料就洗不掉了）。測試帳號只寫自己的庫，**永不送 GA4／Meta**。

**狀態快照 helper**：`snapQueue()`、`snapWallet()`。

## 四、尚未埋的缺口

### A. 消費漏斗

**優惠券**
`coupon_list_view`、`coupon_detail_open`、`coupon_use_attempt`、`coupon_used`、`coupon_expired_unused`

**商品購買**（若 App 端要賣周邊）
`product_list_view`、`product_detail_open`、`add_to_cart`、`remove_from_cart`、`checkout_start`、`checkout_success`

### B. 配桌瀏覽行為

`match_page_view`、`store_filter_change`、`stake_filter_change`（知道客人想打多大）、`game_detail_open`、`queue_abandon`（看了局但沒報名）、`recurring_view` vs `recurring_join`（固定局 vs 即時局的轉換率）

### C. 留存與回訪

`session_duration`、`page_dwell`、`push_received`／`push_open`、`notif_click`、`deep_link_open`

### D. 小熊養成（差異化功能，完全沒埋）

`bear_page_view`、`bear_stage_up`、`title_unlock`、`bear_share`

**為何重要**：若數據顯示「常看小熊的人消費更高」就值得加碼；反之該砍。現在無法判斷。

### E. 摩擦點偵測

`search_no_result`（帶 keyword）、`error_shown`、`retry_click`、`back_immediately`（進頁面 3 秒內退出）、`permission_denied`、`rage_click`、`scroll_depth`、`time_to_first_action`

### F. POS 端（完全沒有埋點系統）

`checkout_duration`（店員效率）、`payfor_used`（代付使用率）、`coupon_applied_at_pos`、`member_search_fail`（可能要建檔）、`topup_at_pos` vs App 儲值比例、`session_settle_duration`

### G. 實驗基礎建設（有流量後再做）

`experiment_id` / `variant` 跟著每個事件走，進入實驗時記錄 `experiment_exposure`。現在不做但事件結構已留位置。

## 五、隱私治理

- **PII 不進事件** —— 別把手機號碼、姓名寫進 props，只放 `member_id`
- **保留期限** —— 超過 N 個月的原始事件應聚合後刪除
- **可刪除** —— 會員要求刪除資料時 `app_events` 也要能清（目前 append-only，需另想辦法）
