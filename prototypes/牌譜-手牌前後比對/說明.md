# 台麻側面鏡頭「前後比對算摸打」— 邏輯驗證原型

這是**原型階段的邏輯測試沙盤**，跑在你自己的電腦上，用假資料驗證
「拿到前後兩份手牌，能不能正確算出摸了什麼、打了什麼」。

**它不碰鏡頭、不碰 AI 模型、不碰硬體。** 它假設牌已經被辨識成一串牌名了，
專門驗證最核心的那層邏輯對不對。

---

## 怎麼跑

```
python3 demo.py
```

會依序跑 6 種情況，把每一步偵測到的事件印出來，最後輸出一份
`事件流範例.jsonl`（一動作一行的事件流，就是之前討論的即時寫入格式）。

---

## 這份原型驗證了什麼（6 種情況都跑對了）

| 情況 | 結果 |
|---|---|
| 1. 摸到直接打（有拍到摸完的 17 張） | 正確判成「摸中、打中、摸到直接打」 |
| 2. 打手裡的牌（有拍到 17 張） | 正確判成「摸九筒、留手、改打九條」 |
| 3. **漏拍了 17 張**，只看到前後兩個 16 張 | 仍能從淨變化算出「摸九筒、打九條」 |
| 4. 摸到直接打、但**只拍到休息的 16 張** | 側面看不到（無變化），標記「要靠俯視補」 |
| 5. **碰牌**（手牌一次少兩張） | 標記「疑似吃碰槓，需俯視確認」，不硬猜 |
| 6. 辨識出錯（牌數對不上） | 標記「異常、需人工複查」，但**不丟資料** |

重點結論：**你講的「前後比對算摸打」核心邏輯是成立的**，而且連
「漏拍中間狀態」也能靠淨變化補回來（情況 3）。真正算不出來的只有
情況 4（摸切且只拍到休息態）—— 這本來就該交給俯視鏡頭，符合我們之前定的分工。

---

## 這份原型「還沒做」的部分（之後才接）

1. **真的牌辨識**：現在的牌是手打的假字串，實際要換成鏡頭 + 訓練好的台麻 YOLO 模型。
2. **俯視鏡頭邏輯**：海底出牌順序、逆時針歸屬、吃碰槓判定 —— 另一支程式，還沒寫。
3. **吃碰槓的完整處理**：情況 5 目前只「標記疑似」，實際碰/槓/吃是誰的牌、哪一種，要靠俯視補。
4. **多鏡頭彙整 + 局次 ID 串接**：四支側面 + 一支俯視的資料要用同一個局次 ID 拼成一局。
5. **對齊 `paipu_events` 欄位**：牌面編碼已對齊（兩碼制），但事件欄位名仍是暫用中文
   （「事件/玩家/牌」）。之後要換成 `game_id` / `hand_id` / `seat` / `turn_no` /
   `action` / `tile` / `meta` / `confidence`，才能直接 insert 進 Supabase、
   餵進現成的 `migi_admin_paipu_viewer`。

## 牌面編碼（v1.0，兩碼制）

內部**一律存兩碼**（對齊 `paipu_events.tile`），**顯示時才轉中文**。

- 萬 `1m`–`9m` / 筒 `1p`–`9p` / 條 `1t`–`9t`
- 風 `E0` `S0` `W0` `N0` / 三元 `B0`(白) `F0`(發) `C0`(中)
- 花 `H1`–`H8`（春夏秋冬梅蘭竹菊）
- **台麻無紅5**；條用 `t`（非日麻 `s`/索）；花用 `H`（避開「發 `F0`」的 F）

台16 有花 144 張；南部台無花 136 張。詳見《牌面編碼對照表 v1.0》。

## 術語備註

程式裡「摸到直接打 / 打手裡的牌」對應的是日麻的摸切 / 手切，
這裡刻意用台麻白話，避免日麻用語。之後正式欄位命名再一起跟你敲定。
